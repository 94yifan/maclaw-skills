## D. 知识串联（核心）

### 缝合1（主·商业/客户管理）提醒的价值由接收方的决策节律决定，不由执行方的工作节律决定

**证据（今日一手）：** 逸凡原话「因为周三要开周会，所以在周会前要检查，周会后有一个及时的反馈，会让客户体感比较好」。落地结果：5 条策略项从「每日」改为「周一 10:00 检查 / 周四 10:00 反馈」；每日提醒只剩余额检查一条——而余额是唯一真正需要每日看的动作，因为断量是小时级风险，其余都是天级或周级。

**串联：** 10-21 缝合4 把动作分成可控（内部排期，催办有效）与不可控（平台竞价，催办无效）。今天补上第二半——**对不可控或策略执行类动作，正解不是催办，是把它从日常流移到决策节点。** 日常流是执行者视角（我今天做了什么），决策节点是客户视角（我明天要决定什么）。同一句话放在日常流里是噪声，放在决策前 24 小时是输入，放在决策后 24 小时是闭环。

**新认知：** 一条提醒的价值 = 它是否落在接收方即将做决定的那一刻。判据：写这条提醒时先写接收方的下一步动作；写不出（「他会拿去干嘛」答不上来），这条就是噪声，删掉或改挂点。

**曼拾用法：** 客户周报不改频率，改挂点。周三周会型客户固定两版——周一周二出「决策输入版」（数据 + 待定项 + 需要他拍板的三件事），周四周五出「落地确认版」（会上定的谁做什么、什么时候、下周怎么验证）。日常只保留两类：会断量的（余额/预算）、会超成本的（成本超区间）。其余全部移到节点。这一条可以直接进提案的「服务节奏」页，也是差异化的地方——同行还在按天发日报。

### 缝合2（主·系统层）修复落点由改动成本决定，不由病灶位置决定

**证据（第 10 次同型）：** tea-daily 今日 639,283ms / error / not-delivered。前 9 次修复分别落在：删探索性命令、命令加 `|| true`、改判定口径只看 lastDeliveryStatus、改 payload 文本、timeout 300→900。全部在交付通路与配置层。今日真因在脚本末尾两行：`connectOverCDP` 的 websocket 一直挂住 Node 事件循环，业务写完（raw + 台账都完成）而进程永不退出，只能被 exec 层 terminate，terminate 在 runner 眼里就是 Process failed。SC 今天读到脚本尾，加 `process.exit(0)`；我独立验证（tail 有该行、`node --check` 通过）。

**为什么是第 10 次而不是第 2 次：** 故障横跨两层，而两层的改动成本差一个量级。配置层一次 edit 就完成，脚本层要理解 CDP 生命周期、要判断能不能 `browser.close()`（会关掉用户浏览器）。只要存在这种不对称，修复就会一直落在便宜的那一层，且每一次都会被记成「已修复」。

**串联：** 10-22 缝合1 说修复半径由载体决定（谁维护载体就由谁修，私有脚本把 n 次修复摊成 n 次事故）。今天补一个方向：载体决定「谁来修」，成本决定「修哪层」。10-23 缝合1 的三档校验解决「读数可不可信」，本条解决「修复够不够深」，两条正交。

**新认知：** 同一症状第 2 次复发，禁止在同一层再改一次；必须换层，方向固定两条——往上找「谁应该结束它」，往下找「谁在消费它的结果」。给管理场景的用法：同一个客户投诉第二次出现，不许再调话术，必须去查流程断点；同一个部门第二次犯同样的错，不许再培训，必须改表单或审批节点。

**附带修正超时口径（承 supermind 今日）：** 抬一个不会被触发的上限，买到的是零。tea-daily 的 timeout 是 900s，实际 549s 就被 exec 层 terminate——900 这个数从未生效，10-23 算的「贴顶率 77.5%」分母本身就是错的。判据：修超时前先取三层读数（exec 进程实际被杀时长 / payload timeout / 网关 run 时长），以最短的那层为准，改最短的那层。

### 缝合3（主·治理层）变更的记账位置默认跟随执行者，不跟随使用者

**证据（今日，可复算）：** 逸凡 10:59:58 下发指令 → 11:00:38 新建 cron，11:00:44 改日提醒 payload，同一分钟内改完表格 5 条。载体变更 40 秒完成，是本周最快的一次落地。

但记账位置是：root workspace `memory/2026-10-24.md`（执行者 main 的位置）。lanshi 自己的 memory 里没有这一行。于是 lanshi 当晚 19:10 的复盘写：「表格本次未改动…等思安回话确认后如需统一改『是否日常』再动」。而我 22:40 后实读表格：5 条已经是「周提醒 / 进行中」。**两个主体，同一天，对同一张表得出相反读数。**

今日未造成客户可见错误（19:10 汇报内容本身是对的，因为它是临场读表），但错误记忆已经形成，下一轮推理会以它为起点。

**另加一层：** 同一批 5 条记录 2 分钟内被改两次（非日常/已完成 → 周提醒/进行中），表格只留备注、无时间戳。客户能看到这张表，但看不到「这条什么时候改的、改过几次」。客户可见字段的变更史不可审计。
