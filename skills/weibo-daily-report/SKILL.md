# 微博每日监测日报生成 Skill

## 适用范围
每天爬取24个茶饮品牌微博数据后，生成结构化日报。调用此 skill 前确保原始数据已采集完成。

## 数据过滤铁律（2026-08-22 新增）
- **日报只写24小时窗口内（抓取时刻往前推24h）发布的内容**，超窗内容一律不写
- 过滤逻辑必须在抓取脚本内完成：解析每条微博 created_at 为时间戳（Date.parse），与 Date.now()-24*3600*1000 比较，只保留窗口内条目
- 不靠事后人工判断"这条算不算今天的"，抓取时就直接过滤
- 每个品牌同时返回 latest（最新一条微博发布时间），无动态品牌标注"今日无动态（最新微博日期）"，不写"本周无动态"等模糊表述

## 口径与自检铁律（2026-10-19 新增，对应 10-18/10-19 连续两日缺陷）

1. **抓取只用 canonical 脚本** `tea-daily-crawl.mjs`（workspace 根目录，自动按运行日命名输出 /tmp/tea-raw-<日期>.json）。不要复制 `tea-daily-crawl-MMDD.mjs` 旧脚本，旧版会继承已修掉的缺陷。脚本内 WINDOW_END 在开抓前冻结一次，所有品牌同一时间点过滤；输出含 windowStart / windowEnd / crawlTime 与每品牌 ok / total / fetched / error / items.id。
2. **header 逐字引用 raw**：数据窗口写 raw 的 windowStart – windowEnd，抓取时刻写 raw 的 crawlTime，不按发稿时刻或印象反推。
3. **采集说明只写 raw 能读到的字段**：raw 没有 `ok` 字段就不许写"接口 ok=1"；写"24 品牌全部请求成功"必须同时给出错误数。`total=0 且 fetched=0` 的品牌写"接口无返回·待核实"，不写"无动态"。
4. **守恒式必须逐条交代，不是凑数**（2026-10-22 强化）：`窗口内条数 = 正文 bullet 数 + 剔除数（抽奖公示等）+ 合并数（多条合成一条 bullet）`。三个数写进 header 或采集说明，合并项不得静默吞掉。
   - **强制动作**：写报告前先读 `/tmp/tea-ledger-<日期>.md`（canonical 脚本自动生成，逐条列出 id/时间/前 60 字），每一条都要落到「某条 bullet 的素材」「合并到某条 bullet」「剔除＋原因」三者之一，逐行打勾。禁止用总数相减倒推出「合并 10 条」这种数字。
   - **反例（10-22）**：报告写 `38 = 23 正文 + 5 剔除 + 10 合并`，算术完全成立，实际合并只有 8 条，差额 2 条（爷爷不泡茶 10-21 18:01 小狗拯救世界、10-21 14:30 周三茶香 300 元奶茶卡）被静默吞掉——数字是按总数补出来的，不是数出来的。同日库迪 1 条帖被拆成 2 条 bullet（拆分 −1）刚好把窟窿填平，等式反而更「漂亮」。
   - 判据：等式成立不代表无漏报，只有台账每一行都能指到具体 bullet 才算闭合。
5. **24 品牌状态全列**：正文出现、无动态行、接口无返回三条路径必须覆盖全部 24 个品牌，不允许整体缺席。
6. **跨天去重（只比对昨日报告，不读昨日 raw）**：写报告前与 `memory/weibo_daily_<昨天>.md` 比对 id / 正文，重复帖标"昨日已报"或不计入，禁止无标注重复。**禁止为去重去读 /tmp 下昨日 raw**——10-20 报错即由此触发（一步无关读取失败把整轮 run 判 error，群交付被吞）。
7. **品牌内顺序固定**：新品上市 → IP联名/艺人宣发 → 营销活动，不得倒序。
8. **计数口径统一（2026-10-28 改写，废止「实质/抽奖」拆分）**：header 的"有动态"只统计有实质动作的品牌；仅有抽奖公示的品牌不列入"有动态"，归入无动态行；窗口内有帖但全部被判"昨日已报"的品牌也归入无动态行。**header 条数必须等于正文 bullet 数**（读者看得见的条数），抽奖公示与合并不计入，也不写"（实质 X，抽奖公示 Y）"拆分（10-26 逸凡口径，拆分属内部计数语言）。
   - **本条与旧版的区别**：10-22 版要求写"共 K 条（实质 X，抽奖 Y）"，K 取窗口内原始条数。10-28 实测该写法产生 32 vs 正文 27 条的 5 条差额，读者无法对账；10-27 更严重（header 43 条、正文 26 条、差 17 条无归属）。原始条数归台账与 raw，交付物只报读者数得清的条数。
9. **窗口右端不容差**：抓取脚本 `age >= 0`，抓取开始后发布的帖子不进本窗口（会自然落入次日窗口，不丢）。header 声称的 windowEnd 与正文最晚时间必须一致。
10. **接口无返回不得连续挂"待核实"**：某品牌 `total=0 且 fetched=0` 连续达 3 天，必须在 dreaming 做一次 profile 页人工核验（粉丝数/最新帖可见性），给出"停更/限流/需登录"结论并写进日报采集说明，不得无限期沿用"待核实"。
11. **windowEnd 用秒级原值**（2026-10-22 新增）：raw 的 `windowStart` / `windowEnd` 已带秒（如 `2026-10-22 11:00:12`），header 必须原样引用，不许截到分钟、不许套模板里的写死时刻。原因：窗口冻结在秒级，header 只写分钟时，11:00:07 发的帖看起来就是「窗口外混入」，属自造争议。抓取时刻仍用 `crawlTime`（HH:MM）。
12. **专名不得删**（2026-10-22 新增）：帖文里出现的合作方、联名对象、艺人、产地、产品专名，必须原样写进报告；合作性质无法从单帖确认时写「与 XXX 联动（合作性质待核实）」，不许抹名换泛称。抹名等于把一次可追踪的联名机会变成一句没有信息的「系列发布」。
13. **周边归类统一**（2026-10-22 新增）：杯具、盲盒、贴纸、卡片、毛绒、服饰等非饮非食物件一律进【IP联名/艺人宣发】或【营销活动】；【新品上市】只放可饮可食产品。同一物件不许今天算新品、明天算联名。
14. **排名断言必须跑脚本，且必须声明口径**（2026-10-23 新增）：凡写「互动最高 / 转发最高 / 评论最高 / 非抽奖类最高」，先跑 `node top-interactions.mjs /tmp/tea-raw-<日期>.json 5`，只许引用该表的名次与数字，句子必须带口径（总互动 r+c+l / 转发 / 评论）。
    - **反例（10-23）**：报告写爷爷不泡茶 iPhone 抽奖「本窗口互动量最高（转 2852/评 6568/赞 3447）」，实际瑞幸 KPL 榜总互动 20074 > 12867，第一是瑞幸；同段又写茉莉奶白 940 转「非抽奖类最高」，而瑞幸 3910 转是它的 4 倍，且该帖原文是「转发+关注，请 10 位宝喝茶」，本身带抽奖性质。一个窗口里三个「最高」互相矛盾，读者只会认定数据不可信。
15. **「昨日已报」必须 grep 命中才许写**（2026-10-23 新增）：`grep -c "<关键词>" memory/weibo_daily_<昨天>.md` 返回 0 就不许标注，改为按新官宣写。
    - **反例（10-23）**：报告写「茶百道遗忘之海、奈雪卡斯波和丽莎、沪上阿姨花小猪、茉酸奶自嘲熊均属昨日已报」，实际 grep 昨日文件只有前两个命中，花小猪、自嘲熊近 7 日首次出现；正文给树夏可可标「昨日已报预告」同样为假，昨日报告把树夏列为无动态。凭印象标「已报」等于把新动作降级成旧闻，比漏报更难发现。
16. **台账必须勾完并写进采集说明**（2026-10-23 新增）：`/tmp/tea-ledger-<日期>.md` 每一行 `[ ]` 改为 `[x]`，采集说明写「台账已勾选 N/N」。没勾完不许写「逐条台账已核对」——那是完成态声明，不是意图。
    - **反例（10-23）**：43 行台账 0 勾，采集说明照写「逐条台账已核对」。台账在生产端生成了，消费端没人用，机制等于不存在。
17. **存档即定稿**（2026-10-23 新增）：先 write 到 `memory/weibo_daily_<日期>.md`，发群时原样引用该文件内容；若发群版本经过改写，必须把改写版回写覆盖文件。
    - **理由（10-23）**：交付消息比存档文件多处 20 处措辞差异，存档还留着「无饮品上新」占位段。逸凡看到的是改后版本，memory 留的是草稿，事后复盘读到的不是他读过的那份。
   - **机械执行（2026-10-24 补，因 10-24 再次违规 153 字）**：发群一律走 `node chunk-report.mjs memory/weibo_daily_<日期>.md`，脚本按品牌块切成 4 段输出 JSON 数组，逐段原样发送，不许手抄、不许边发边改定语。切片后校验「各段拼接 == 文件」。
   - **反例（10-24）**：手抄分片时删掉了 header 里整句跨天比对说明，以及「是窗口内转发第三」这一定语，交付版比存档少 153 字。删的恰好是最能自证合规的句子，读者看到的版本无法核对去重逻辑。

18. **抓取脚本必须显式退出**（2026-10-24 新增，对应第 8 次同类 cron error）：canonical 脚本末尾必须 `process.exit(0)`（写完 raw 与台账、stdout flush 之后），不要 `browser.close()`——那是关掉用户的浏览器。原因：`chromium.connectOverCDP` 的 websocket 会挂住 Node 事件循环，数据写完进程不退出，exec 超时被 terminate，cron 判 `Process failed`，announce 投递被整轮跳过。
    - **反例（10-18 / 10-24）**：10-18 报 `Process: sharp-harbor failed`、10-24 报 `Process: delta-breeze failed`，两次 raw 与报告都完整，run 全判 error。10-24 已确认脚本只 `page.close()`、未退进程，修复已写入 canonical。
    - 排查顺序：`Process: <名字> failed` 先看 raw 与报告是否完整；完整属「进程退出」问题，不完整才重爬。

19. **效果断言不许用单条样本升规则**（2026-10-24 新增）：单条帖、单日窗口只能写「本条 X 转 Y 评」，不能写「说明这类内容没有扩散能力／对粉丝盘有效」。要下这类判断，至少 2 个独立对象同向，或 2 天样本。
    - **反例（10-24）**：M Stand 1 转 0 评 1 赞，正文写「说明只有氛围没有产品钩子的内容在微博几乎没有扩散能力」，行业信号 3 又把它当证据复用。一条帖证明不了内容类型规律，只能证明这一条没扩散。

20. **日报只写事实，不写数据与判断**（2026-10-25 逸凡第二次明确要求，第一次已说过，属重复违规）：
    - **禁止任何互动数据**：转发／评论／点赞数字、「总互动」「互动第一/第五」「转发第二」「r+c+l」口径说明，一律不写进日报。数据只进 raw 与台账，不进交付物。
    - **禁止任何效果判断与分析**：「对品牌而言，这是……」「说明……」「判断：……」全部删除。营销活动只写清做了什么、时间范围、玩法机制、赠品与规则。
    - **禁止内部质检语言**：采集说明、守恒式、台账勾选数、样本龄、跨天比对说明，全部不进日报正文（这些只留在 raw／台账／复盘文件）。
    - **禁止范围仅限品牌段**：品牌段里不写互动数字、不写「对品牌而言／说明／判断」这类单品牌效果推断。
    - **边界（2026-10-28 逸凡纠正，本条此前被我过度扩权）**：10-25 逸凡的原话只有「不需要赞藏数据、不需要日期」两项，**从未要求删除行业层面信号**。过往几个月日报一直有该栏目，属固定结构，不得擅自移除。我在 10-25 把「不需要额外判断依据」解读为整段删除行业信号，并写成本条子项，连续三天（10-26/27/28）漏发，属自主改动的错误，已撤销。
    - 判据：品牌段可原样转发给客户，不需要删任何一句；行业信号段独立成节，写跨品牌事实与判断，不写互动数字、不写发帖时间。

21. **自检命令不得用 grep 退出码当门禁**（2026-10-25 新增，对应第 11 次同类 cron error）：`grep -c '^- \[x\]'` 在匹配到 0 行时返回退出码 1，`grep -c '^- \[ \]'` 在「未勾选 0」时同样返回 1。今天台账实际 31/31 全勾，自检第一句打印「勾选数 31 未勾选 0」，紧跟一句 `(Command exited with code 1)`，整轮 run 被判 error、announce 交付被跳过。
    - **硬规则**：任何用于判定「通过/不通过」的自检命令，退出码必须恒为 0，判定结果靠打印出的数字；写法用 `awk` 或 `grep -c ... || true`，禁止裸 `grep` 结尾。
    - 排查顺序：先看自检打印的数字是否合格，再看退出码；数字合格而退出码非 0，是脚本缺陷不是内容缺陷。
22. **不写信息缺失声明**（2026-10-25 新增）：不写「未披露价格与杯型」「产品名与口味未披露」「未提及」这类句子。读者不需要知道品牌没说什么，只写品牌说了什么；确实信息不足就只写已有事实，句子自然结束。2026-10-25 重写版仍残留 3 处「未披露」，属规则 20「可原样转发给客户」的漏网写法。
23. **兜底发送必须留痕**（2026-10-25 新增）：走 message 工具兜底发群时，顺手写 `/tmp/tea-delivered-<日期>.json`，内容 `{"sentAt":"HH:MM","messageIds":[...],"chunks":N}`。原因：cron 的 `deliveryStatus` 只反映 announce 通道，run 判 error 时它必然写 `not-delivered`，而群内实际已收到（10-24、10-25 连续两天如此）。没有留痕文件，复盘只能靠翻 session 记录才能判断「到底送到没送到」，监控指标长期假阴性。
24. **日报不写任何时间**（2026-10-26 逸凡提出「也不需要时间」，覆盖此前所有时间相关表述）：正文每条 bullet 末尾不标发帖时间；无动态清单不标最新微博时间，写成一行「今日无动态：品牌A、品牌B」；header 不写秒级窗口，改写「统计区间：10月25日 – 10月26日（北京时间）」；header 第三行写「覆盖 24 品牌 · 有动态 N 家 · 无动态 M 家 · 共 K 条动态」，不写实质/抽奖拆分。
    - **内部核验不受影响**：秒级 windowStart/windowEnd、逐条时间、台账勾选仍留在 raw 与 `/tmp/tea-ledger-<日期>.md`，只是不进交付物。规则 2、9、11 在「交付物」层面由本条覆盖，在「内部核验」层面继续有效。
    - 原因：时间戳对读者无信息增量，客户转发的日报不需要知道哪条几点发；需要核验时效时看 raw 即可。

25. **台账必须写归属，打勾不算**（2026-10-26 新增，对应第 12 次同类 cron error 之后的真实内容缺口）：台账每行在文本后必须追加 `→ 正文：<正文片段>` / `→ 合并到 #<id>` / `→ 剔除：<原因>` 三种之一。`[x]` 只证明「看过这条」，不证明「这条落到了正文」。
    - **门禁命令（退出码恒为 0，看数字）**：`node ledger-check.mjs --raw /tmp/tea-raw-<日期>.json --ledger /tmp/tea-ledger-<日期>.md`，通过标志是「缺归属 0」。有缺归属时先补归属再发日报。
    - **反例（2026-10-26）**：header 写「共 24 条动态」，正文 21 个 bullet，24 行台账全部 `[x]`，看上去闭合。实际 24 = 21 正文 + 1 条瑞幸 09:00 帖合并 + 2 条柠季抽奖公示未披露；其中瑞幸 09:00 帖的「揪 10 位送饮品券、转发过 2000 加抽」整段没有进正文，既没合并说明也没剔除原因，靠打勾永远发现不了。
    - 与规则 4 的关系：规则 4 说「逐条交代，禁止倒推凑数」，本条把它变成可执行的门禁；规则 4 仍是判据，本条是执行路径。
26. **覆盖核对只作辅助信号，不作门禁**（2026-10-26 新增）：`node report-coverage.mjs --raw <raw> --report <日报>` 用最长公共子串比对 raw 每条与正文，输出「已覆盖／待判定」。用途是抓「整条丢失」，不是判「改写是否合格」——正文允许重写压缩，改写后 LCS 会低到 7 字，属正常。
    - **已知局限（实测）**：24 条里 4 条改写幅度大被判待判定（幸运咖、喜茶、茶百道、CoCo，LCS=7），全部实际已覆盖；反过来瑞幸 09:00 帖因长文本里含新品段，LCS=30 被判已覆盖，掩盖了抽奖段被丢。**因此它不能替代规则 25 的归属门禁，只能作为第二道人工抽查的线索。**

27. **行业层面信号段是固定结构，不得删**（2026-10-28 逸凡纠正后立）：每日日报在无动态品牌清单之后，固定输出 `**行业层面信号**` 一节，3-6 条。
    - **写法**：每条 `1. **结论句。**` 开头（加粗一句判断），接 2-4 句跨品牌事实，必要时末尾补一句判断。不写互动数字、不写发帖时间、不写采集说明。
    - **判据**：每条至少涉及 2 个品牌，成文后能回答「今天行业发生了什么变化」，而不是单个品牌的新品播报；单品牌单条样本不许升格为行业规律（规则 19）。
    - **误删记录（必须记住）**：2026-10-25 逸凡说「不需要赞藏数据、不需要日期」，我把它扩成「不要行业信号」，连续 10-26/27/28 三天漏发，直到逸凡在 10-28 11:05 指出「过往几个月 daily report 都有行业信号的拓展」。教训：**用户说不要 A，不等于不要 B；删除一个沿用数月的栏目属于不可逆改动，必须回问确认，不得自主执行。**

28. **发报前必跑结构门禁**（2026-10-28 新增，对应行业信号被误删 3 天没有任何机器拦下）：`node report-structure-check.mjs --report memory/weibo_daily-<日期>.md --ledger /tmp/tea-ledger-<日期>.md`，通过标志是「待修 0 项」。它查四类 ledger-check 查不到的东西：① 该有的栏目整体缺失（无动态清单、行业层面信号 ≥3 条）② header 三个数（覆盖/有动态/无动态）与正文实际品牌块、清单是否一致 ③ header 条数 ≠ 正文 bullet 数 ④ 台账多行标「→ 正文」却只落到同一条 bullet 的静默合并。
    - **为什么必须有**：ledger-check 只问「每条 raw 有没有归属」，所以行业信号整段消失、header 数字对不上、3 条 raw 挤进 2 条 bullet 这三种错都能拿「缺归属 0」通过。10-28 茉酸奶即实例（3 行正文 → 2 条 bullet，两行写同一片段）。
    - **退出码恒为 0**（规则 21），判定看「待修 N 项」与「提示 M 条」；提示项（出现时刻、说明类词）需人工确认是活动时间还是发帖时间。
    - **反例基准**：`memory/weibo_daily_2026-10-27.md` 跑该门禁会报「缺行业层面信号」「header 43 ≠ 正文 26」，可作为验证门禁有牙的固定用例（门禁不报，即门禁失效）。

29. **门禁的读数必须与校验对象同层**（2026-10-30 新增，对应两个门禁当天各自「误判通过」）：
    - **ledger-check 的合并目标允许两种写法**：10 位 `id`（`→ 合并到 #5359327197004254`）或台账序号（`→ 合并到 #4`，指当页第 4 条）。2026-10-30 修前只认 10 位 id，序号写法被当成「正文」，5 条合并静默消失，输出「正文 31」而正文实际 26 条 bullet，结论照样打「逐条闭合」。
    - **结构门禁不接受「路径被静默替换」**：`--report` 是唯一入口，位置参数 2026-10-30 起也认；修前传旧报告会静默去读今天文件并打印「结构通过」。台账与报告日期不一致时跳过归属交叉核对，并在 info 行写明「台账未配对」，不再输出假阳性「静默合并」。
    - **通用判据**：任何门禁通过时，必须先打印它实际读的文件路径 + 条数，读者能对上是哪一次的数据。只打印「通过」而不打印读数的门禁，一律视为没跑。
    - **当日实证**：`node report-structure-check.mjs <10-28 范例>` 修前 output 与今天文件一字不差；修复后正确报出 `header 32 ≠ 正文 27`，并指出 10-28 范例本身违反规则 8（该范例当天被当作唯一标杆，已降为备查）。

30. **发报前一条命令跑完两个门禁**（2026-10-30 新增）：`node gate-all.mjs`（可选 `--date`），输出写到 `/tmp/tea-gate-<日期>.txt`，结论只有两种：`PASS 两项门禁全过，可发` / `BLOCK 未过（先修再发，禁止带病交付）`。
    - 覆盖数按「本次 raw 实际抓了几个品牌」校验（10-30 抓 23 家、当日 19:10 才加第 24 家，若按 24 判会把合格日报判错）；raw 品牌数与 canonical 数组不等时只在头部提示，不阻断。
    - 留痕文件是「门禁跑过」的唯一证据。没有 `/tmp/tea-gate-<日期>.txt` 就说「门禁通过」，按未跑处理。

31. **引号内必须逐字**（2026-10-30 新增）：正文用 `「」` 引用品牌原文时，引号内一字不改；要压缩改写就去掉引号。当日反例：霸王茶姬原文「你发觉冬天来了，是因为什么？」，写成「冬天来了是因为什么」仍加引号——读者会当成原话，客户会当成引用错误。

## 产出标准

### 格式结构（固定三段式，不可改）

**精确Markdown格式要求：**

- 品牌名用 `**品牌名**`（粗体，不是Markdown ## 标题，不用标题层级）
- 分类标签用平文本 `【新品上市】`（不加 `###`、不加粗、不单独成段，紧跟首条 bullet 写在行首；2026-10-25 与 cron prompt 统一，旧写法 `### **【新品上市】**` 作废）
- 内容一律以 `【分类】` 开头接正文，同一分类多条时每条独占一行，不用 `- ` 列表符号
- 每条只写事实：产品名／卖点／原料与产地／技术工艺／联名对象／活动时间与机制，**不标发帖时间**（规则 24）
- 严禁写互动数字、严禁写品牌价值判断、严禁写效果推断

**【IP联名/艺人宣发】**
- 写清联名IP/艺人名称、联动形式（主题店/周边/短片/壁纸/花絮等）、上线时间、周边品类与获取方式

**【营销活动】**
- 写清活动内容、时间范围、玩法机制、赠品与抽奖人数、话题词

**无动态的品牌**：标题写 `**无动态品牌**`，正文一行 `今日无动态：品牌A、品牌B`，不写时间（规则 24）

**行业层面信号**：无动态清单之后空一行，写 `**行业层面信号**`，接 3-6 条编号段落（每条 `1. **结论句。**` 起头，接 2-4 句跨品牌事实，末尾可带一句判断）。不写互动数字、不写发帖时间、不写采集说明。

**品牌间空一行**

### 内容写作原则

1. **新品要写全事实** — 产品名、卖点、技术工艺、原料与产地写清楚，不替读者下结论
2. **营销活动只写机制** — 内容、时间、玩法、赠品、抽奖人数，写到能看懂怎么参与为止
3. **不确定的信息不写** — 上新时间未明确就不写，不编造
4. **零互动数据** — 不写转评赞、不写互动排名、不写 r+c+l 口径
5. **品牌段零判断** — 品牌段内不写「对品牌而言」「说明」「判断」「这意味着」类句子；跨品牌判断统一放进末尾行业信号段
6. **零内部质检语言** — 采集说明、守恒式、台账、样本龄不进交付物
7. **不要概览汇总表** — 直接进入品牌内容
8. **行业层面信号必须写** — 放在无动态品牌清单之后，3-6 条，只做跨品牌归纳，不写互动数字与发帖时间（规则 27，过往几个月固定结构，不得省略）

### 交付形态

header 三行封顶：标题（日期）、统计区间（日期级＋北京时间）、覆盖数＋条数、空行。正文按品牌分段，段间空一行，结尾无动态品牌清单。整份控制在手机一屏可读、可直接转发给客户的长度。
