## 知识缝合（新增）

**缝合点1：逸凡周期 × 执行鸿沟（2026-05-02 教训4 × 2026-07-17 缝合点1 × 2026-07-28 缝合点1）**

逸凡的 4-7 天触发周期使 Pipeline 的修复验证必须跨 session 完成。这与执行鸿沟的根本差异在于：执行鸿沟是认知到问题后不行动（意愿问题），而 Pipeline 修复验证延迟是输入源依赖（结构性问题）。前者需要机制约束，后者需要异步验证。

整合结论：执行鸿沟（不修）和修复验证延迟（等不到生产触发）是两种不同性质的问题。前者依赖推理守卫八的强制契约解决，后者依赖逸凡本身的触发频率。在逸凡触发频率基本稳定的前提下，Pipeline 的多重故障诊断能力（一次失败查出所有 bug）比单次修复速度（2小时闭环）对系统稳定性的贡献更大。

**缝合点2：Pipeline 多重故障诊断能力 × QA report + pipeline_error.md 双源分析（2026-07-28 缝合点1）**

07-28 Dreaming 提出了根因分析必须同时读取 QA report 和 pipeline_error.md。今天再次确认这个判断——路径映射修复了但 step_skip 仍然存在，意味着 07-27 的根因分析是单源的（只看 QA report 的 19 项失败，忽略 pipeline_error.md 的 step_11.1 错误）。

整合结论：Dreaming 的分析框架需要新增一个数据源完整性检查——在开始分析前，确认本次失败的所有错误日志已全部被纳入分析范围，而不是只读了第一个或最明显的错误源。

**缝合点3：修复验证延迟 × 异步验证模式（新框架）**

当前 Pipeline 的修复验证是「生产者」依赖的（需要逸凡触发生产任务才能验证）。更合理的模式是「异步验证」——创建独立的验证测试脚本，不依赖生产数据，直接用模拟数据跑 Pipeline 完整流程。这与软件工程的 CI/CD 模式一致。

整合结论：Pipeline v2.x 的下一个升级方向是创建独立于生产的验证流程——用模拟数据而非真实品牌数据，在逸凡不在时也能验证 Pipeline 的完整性。这是当前 Pipeline 测试能力的主要缺口（只在生产运行中测试，没有单元测试或集成测试）。
