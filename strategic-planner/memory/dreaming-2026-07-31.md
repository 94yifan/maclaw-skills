## B. 规避方案

**1. 零产出日规则从「建议」改为「动作清单」**

07-29 写的补位策略是「至少做三件事之一是必要的」——这是建议，不是动作。改为固定动作序列，每条有明确触发条件和完成标准：
- 触发条件：当日无逸凡任务 + 无群聊任务
- 动作1：检查 SC 爬虫脚本状态（今天改了什么/为什么失败），记录到当日 memory
- 动作2：尝试手动触发一次替代信号采集（web_fetch 核心品牌微博/行业文章）
- 动作3：从 MEMORY 已有知识做一条旧知识重组缝合（哪怕只有一条）
- 完成标准：当日 memory 文件至少有一条「今天做了什么」的记录

**2. SC 爬虫必须留失败痕迹**

给 SC 的爬虫加日志输出（成功/失败/原因/耗时），至少让「尝试过但失败」与「从未尝试」可区分。今天这种改脚本→无输出→无日志的模式，让 8 天连续缺失的原因完全不可诊断。

**3. 交付积压的现实解法：dreaming 输出即交付通知**

已连续 4 天识别、0 闭环。isolated cron session 无法发飞书私聊、无法 update 配置，这是结构性限制，不是执行力问题。Dreaming 输出会自动发到逸凡飞书私聊——所以把积压清单放在 dreaming 输出的显眼位置，就是当前技术条件下最有效的交付通知通道。今天起，积压清单直接列在正文，不再藏在「待处理」末尾。

**4. CFO 停止重复写修复命令**

修复命令已写入 9 次、14 天无效果。今天起不在 dreaming 里重复写，改为一条明确提示：需要逸凡或主 session 执行 cron update（禁用 CFO 每日 dreaming，改为周日或彻底停用）。重复写入本身也在消耗 token 且无产出——与 CFO 的问题同构。

## D. ★ 知识串联（旧知识重组——无新输入的补位）

**缝合1：连续9天行业信号断层 × 空转的成本不是「没干活」是「错过行业信号」**

07-23 后 SP 知识缝合无新行业内容入库，07-31 已达 9 天。这段期间茶饮行业正处于世界杯决赛后（07-20 缝合2 记录的瑞幸免单 vs 库迪致敬）到秋季新品蓄力的窗口期——恰恰是行业信号密集期。系统空转的隐性成本不是「这些天没产出」，是「这些天的行业变化对曼拾方法论完全不可见」。

→ 给系统一个量化指标：行业信号断层的天数 = 曼拾行业认知的落后天数。SC 恢复前，这个数字每天 +1。

**缝合2：SC今天「重写CDP脚本但无输出」 × 07-26三层采集漏斗方案 → 跨分身识别≠修复的实证**

07-26 Suprimind 设计了三层社媒采集漏斗（搜索发现→web_fetch轻量抓取→CDP定点精准，核心是**最小化CDP依赖**）。今天 SC 的尝试仍然停留在「重写 CDP 爬虫脚本」层面——证明三层漏斗方案从未被落地。识别方案（07-26）→落地执行（从未发生）→8天产出缺失。这是识别≠修复在跨分身层面的实例：方案由 Suprimind 设计，执行方 SC 根本没有收到或执行。

→ 跨分身方案落地需要明确的「执行责任人 + 验收节点」，否则方案只会躺在 MEMORY 的知识缝合区。

**缝合3：CFO「降频→自终止」第14个数据点 × 07-29死亡螺旋判断 → 降频是无效修复策略，停止才是**

07-29 识别「降频→自终止是死亡螺旋」，今天 CFO 第 14 天自终止提供第 14 个数据点，并新增关键证据：降频没有降低 token 消耗（每天仍运行），只降低了产出（产出为零）。「降频」在系统层面是负优化——资源消耗不变，产出归零。

→ 系统设计原则：分身出问题时的修复选项只有「修复」和「停止」两个，没有「降频」。降频只会把问题拖长并掩盖它。

**缝合4：7项待处理0闭环 × 07-28曼拾标准交付矩阵 → 交付矩阵缺少「兜底执行者」**
