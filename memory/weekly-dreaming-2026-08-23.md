## B. 本周学到的关键洞察

### 1. 配置层 + 规则层双根因修复，是「反馈当天闭环」的又一实证

8/22 格式问题没有停留在内容层打补丁，而是追到配置层（streaming 关）+ 规则层（旧前提下的规则执行过头）两个根因，当天完成修复 + 全量同步 7 个 subagent。

与 8/14 失败上报规则（当天发生→当天确认→当天写入 MEMORY.md）同属「事件触发当天落地」的高效模式，再次验证：有具体事件绑定的规则固化远比纯复盘待办快。5 月「识别≠修复」的结构性问题，在 8 月连续两次事件触发场景下没有重演。

### 2. 规则必须绑定环境前提，环境变化时规则要重新审视

根因之一：SOUL 里「不用清单体、描述性段落」的规则在纯文本前提下是对的，但 streaming 状态变化后（关→开），规则没有跟着环境更新，反而被「执行过头」——把本应渲染的 markdown 结构也一起禁掉了。

**教训**：任何输出格式类规则都要写明适用环境前提；配置环境变更后，第一时间审视关联规则是否还成立，而不是机械延续。

### 3. main 作为路由枢纽的兜底模式验证有效

8/20 sessions_send 被 visibility 拦截时，main 直接代录、写 TODO 表、标注来源——subagent 通道故障时主 agent 兜底，数据没有丢失，来源可追溯。这验证了主 agent 事件驱动架构下「路由+兜底」双职责的可靠性。

### 4. 面对能力类问题先查证再回答（Codex Harness 案例）

没有直接回答「能不能用」，而是查证了仓库真实性、OpenClaw 内置 harness 现状、成本约束后给出「不需要移植、可试点」的结论——符合规则6（能力判断先跑工具验证）。面对新工具/新技术咨询，先查现有能力边界再给结论。
