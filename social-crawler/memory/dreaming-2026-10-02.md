## B. 规避方案（每条对应 A 项，落定为下次执行铁律）

1. **payload 模板补 header 必填三行（对应 A1，含覆盖行）**：在 tea-daily-report payload 格式模板**最前面**写死——
   - `# 茶饮品牌微博日报 <今天YYYY-MM-DD>`
   - `（监测窗口：<昨天> 11:00 至 <今天> 11:00，共 23 个品牌）`
   - `覆盖：23 品牌 | 有动态 N | 无动态 M`
   覆盖行连续 2 天缺，正是「靠模型发挥」不稳的直接证据
2. **抓取侧自动重试（对应 A2，新增）**：把「品牌条目整体为空（error 或 items 为空且非静默）」纳入自动重跑条件，而不是靠人发现后手写 retry 脚本；或把 `retry-*.mjs` 的 432 重试逻辑**并入主爬虫收尾步骤**（主脚本跑完后自查错误品牌→自动重爬→合并 raw，一次成型）
3. **dreaming timeout 300→600（对应 A3，第 28 天，仅主 session，建议全舰队一起调）**：`cron_jobs` 中 `dreaming-*` 全量 `payload_timeout_seconds` 改 600；依据 9/22–10/1 连续十晚舰队齐超 300s，10/1 本 job 自身连超 2 次
4. **交付兜底 + payload 加「运行内工具禁令」（对应 A4，第 20 天）**：①把交付从「run 成功才发生」解耦为「文件写好即发」；②payload 加三条硬约束——写完报告立即结束不得再调工具 / run 内禁止 cron 操作 / 收尾校验默认不跑（必须跑时加 `|| true`）
