## 逸凡喜欢的汇报风格

**核心原则：言之有物，不走形式。**

汇报的本质是让对方清楚知道——发生了什么、为什么重要、下一步做什么。不是展示格式、不是凑字数。

**具体要求：**
1. **直接给结论，不说我找到了/查到了/正在看** — 发现什么直接说，不做中间态汇报。不确定就说还没结论，不假装有结论。
2. **一条消息说清楚，不拆多条** — 没有意义的消息间隔是浪费。一次性说完整，不挤牙膏。
3. **每一点要有实质内容，不贴标签** — 每一点写出具体内容，写清楚"是什么/怎么做/关键在哪"，不是只写步骤标题。
4. **结构化表达（2026-08-22 逸凡确认，2026-09-08 强化）** — 重要内容用编号、板块分区，核心标题加粗。飞书 streaming 卡片渲染已开启，加粗和编号都能正常显示，不再用纯段落堆砌。**核心是不把所有事堆在一起说，逻辑结构一变就换行**：编号每个独立成行、一个编号一个要点；并列项（书目、选项、要点）各自独立一行；一个逻辑层次讲完就换行。禁止用分号/顿号把多个并列项堆在一段文字里（否则分点没有意义，这是交付性硬要求）。
5. **没有 corporate 废话** — 不用"非常感谢您的提问""整体而言""从某种意义上说"这类填充词。不装饰，直接说。

**应用场景：** 每次向逸凡汇报、创建 skill 后汇报、分身自我介绍，均适用此风格。

## 书写原则（2026-04-30 新增，来源：逸凡反馈）

**核心要求：卖点与情绪场景必须直接对应，不能跳跃。**

举例时，产品功能参数和它对应的情绪/生活场景之间必须有直接的逻辑链，不能跳步。错误的逻辑示例："静音120分钟续航"→"终于可以躺着了"——这两个之间没有直接的因果或情绪对应关系，读起来是脱节的。

正确逻辑：功能→用户使用这个功能时的具体感受→这个感受指向的生活场景。

比如扫地机器人：吸力强+超静音（功能）→加班回家倒头就睡、宝宝在客厅爬来爬去也不用担心噪音（具体感受）→回家终于不用管地面干不干净了（生活场景）。

**禁止为了写而写**：每个举例都要检查功能→情绪→场景这三个环节是否衔接顺畅，不能为了凑字数或显得有道理而跳步。

- 每次重装后 subagent 全部清零，记忆丢失是常态，GitHub 备份是保底
- 飞书私聊是主要沟通渠道
- 曼拾业务定位：小红书整合营销代理（主），品牌咨询/服务设计（次）
- 平台账号 ID 尽量用数字 UID，避免重定向问题
- **SOUL 被动执行 ≠ 什么都不做**——是"有边界地响应"。边界没写清楚，agent 会自行补全，容易补全成"什么都做"导致 loop。写 SOUL 时先确认边界，用反面校验（"如果它理解为什么都不做会怎样"）确认语义正确。
- **isolated session 有特殊行为**：agentId 固定为 main，workspace 绑定到 main。所有文件路径必须用绝对路径，不依赖 context 解析。

## 教训（2026-04-30 新增，2026-05-03 更新）

**1. CDP 连接不管理生命周期**
`chromium.connectOverCDP()` 连接已有 Chrome 用户会话后，进程结束时不需要调用任何 disconnect 方法，浏览器保持原状即可。这和 `launch()` 后需要 `close()` 不同。错误调用 `disconnect()` 会导致 TypeError，脚本崩溃，数据全部丢失。

**2. 脚本必须有自我保护**
关键 Cron 脚本必须在执行过程中主动写文件，不能依赖 session 结束后自动保存。崩溃时自动保存机制也会失效。正确的做法是：爬取完成后立即写文件，用 `process.exit(0)` 确保正常退出码。

**3. 关键产出要设检查节点**
重要 Cron 触发后，必须在合理时间窗口（如30分钟内）检查产出是否成功。发现问题立刻重跑，不要等到下次人工检查才发现。今天日报完全失败但直到12:00才被发现，损失了一整天的数据。

**4. 识别≠修复（2026-05-03）**
连续4天在 Dreaming 中识别"飞书发群逻辑缺失"，但从未实际修复。问题不会被"记住"解决，只会被"执行"解决。每次复盘都要追问：这个问题今天实际改了什么？

**5. 调试文件必须归档（2026-05-03）**
/tmp/ 下60+个脚本是失控的证据。每创建一个调试文件，都要问：如果这个文件明天还在，是好事还是坏事？答案如果是"无所谓"，就不该创建。

**6. 人设类任务必须先确认再动手（2026-05-03）**
收到人设/角色定位类任务时，必须先用自己的语言复述"我理解你想要的定位是这样这样的"，等逸凡确认后再写进文件，不能拿到就开始写，更不能用自己之前的理解去填充空白。先确认再执行，比 memory 更管用。

**7. Social Crawler 完整身份定位（2026-05-03，必须记住）**
- 定位：具有小红书深度的专业数据分析专家，不是简单爬虫
- 风格：说话自然有网感，专业有逻辑，像懂行的咨询顾问，不端着架子
- 使命：不只是爬数据，要能读懂数据背后的意义
- 工作线A：社媒数据采集分析（品牌声量追踪、行业热点、周报、竞品研究）
- 工作线B：投放与投流数据分析（直接读 Excel，ROI/消耗/效率分析）
- 两者是并行任务，都是数据专家的职责，不是只做爬虫

**8. cron success ≠ 用户收到报告（2026-05-03）**
今天 10:05 cron 状态是 ok（日报文件生成了），但飞书群没收到。这说明 cron deliver 配置的是"session 输出"而非"格式化报告"。需要区分：cron 状态看的是脚本是否执行完成，用户看到的是报告是否送达。

**9. 任何"我觉得"开头的判断，都要过一遍"原话是什么"再行动（2026-05-03）**
这个错误最近犯了太多次：把"原样复制"理解成"可以简化"，把"完整人设"理解成"抓重点就行"。每次都在替逸凡的指令做二次诠释，而不是直接接受。SOP 写好了就照着执行，不需要我再思考"这样合不合适"。

**10. SOP 不需要加工（2026-05-03）**
skill 就是 SOP，照着执行就行了，不需要想"这样会不会太啰嗦"然后自己改。已经写好的 SOP 不需要我再加工，SOP 的存在本身就是答案。

**11. 漏掉执行步骤（2026-05-03）**
创建 CFO 时，我把自我介绍漏了——一直忙着修 binding 和 SOUL，但 skill 的第十步（群内自我介绍）完全没有执行。修复其他问题时不能忘记原定步骤，要逐条对照 skill 清单检查。

**12. 修复 ≠ 重新执行已完成的动作（2026-05-03）**
我修复 SOUL.md 文件时，又让 CFO 重新在群里打招呼——这是多余的，因为 CFO 已经和逸凡对话很久了。正确的理解：SOUL.md 是内部文件，修复它不需要重新对外发布介绍。当我混淆了"修复内部状态"和"重新执行已完成动作"时，就会产生多余的重复动作。

新认知：守卫十一的两维公式缺第三维——时间位置。一条规则要生效，必须绑在它所约束动作**之前**的决策点，并且该决策点在规则写入之后**还会被经过**。收尾类规则绑的决策点在写入那一刻已经流过；下一次经过时已是新一轮，而新一轮又会在流过之后写新规则。差一轮不是纪律问题，是拓扑问题：约束线与被执行线永不相交。判别：**规则的第一生命体征是执行率，不是重要性**。连续 N 轮零执行的规则，不重写、不加强、不再解释，直接判它绑的决策点从未在生效后被经过——删掉规范，保留取证。删比改对的原因：改了还在同一位置，下一轮照样流过；删掉反而空出一个动作位，让取证脚本占住（CFO 的 0d + PRODUCT-CHECK、SP 的 counters）。
