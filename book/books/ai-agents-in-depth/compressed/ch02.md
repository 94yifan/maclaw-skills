# 第2章 上下文工程

## 本章核心论题

上下文工程系统性地设计、组织和管理 Agent 在每个决策点看到的全部信息。核心洞察：%%H%%模型本身的智力只是基础，上下文的质量才是 Agent 能力的真正关键——一个中等能力的模型配上精心组织的上下文，往往能胜过一个顶级模型在信息匮乏下的盲目摸索。%%/H%%本章从 API 消息结构出发，展开 KV Cache、提示工程、Skills、状态栏和压缩策略，最终回答：怎样以更低成本向模型提供信息充分的上下文？

## 关键论点与框架

### 1. 上下文是 Agent 能力的上限，而非模型参数量

**核心论点**：Agent 发挥价值的决定性因素不是参数量，而是每个决策点能获得多少、多精准的上下文。

**论证与机理**：天才工程师不知道产品架构和技术债务也难以发挥。Coding Agent 需要实时代码上下文、流程规范、环境信息。Linux 内核以高度透明、文档驱动的文化运转三十多年——创造了对 AI 友好的环境。推导：%%H%%构建 AI 原生团队，首先是一场文档化运动，而不只是部署新工具。%%/H%%

**出处**：2.1 节；引述 OpenAI 研究员翁家翌：%%H%%"人和模型一样，最重要的是 Context。AI 短时间内无法取代人的最大原因也是 context——因为 AI 跟人并不在同一个环境里面。"%%/H%%

**ReAct 锚点**：决策形式化为 π(a_t | c_t)。关键洞察：%%H%%Agent 的下一步行动取决于截至当前的完整交互上下文，而不只是眼前这一条输入。%%/H%%

### 2. API 消息结构定义了上下文工程的物质基础

**核心论点**：Agent 框架核心工作就是管理 messages 列表——在合适时机追加消息、把列表送给模型；所有上下文工程技术本质上都在优化这个列表。

**论证与机理**：模型 API 无状态，每次调用须重新构造上下文。请求 = 静态前缀 + 轨迹：系统提示词和工具定义不变，对话历史随交互增长。四种消息角色（system/user/assistant/tool）。核心循环：while True，若有 tool_calls 则执行工具继续，否则输出退出。生产须设 max_iterations。

**出处**：2.2 节；实验 2-1（0.6B 小模型在合理提示词下也可靠完成工具调用）。

### 3. KV Cache 将前缀稳定性从性能优化升级为架构约束

**核心论点**：%%H%%系统提示词和工具定义一旦确定就不要改——任何改动，哪怕多一个空格，都可能改变 token 序列，使首个不同 token 及其后的缓存无法复用。%%/H%%

**论证与机理**：
- **KV Cache 原理**：模型每层缓存已计算 token 的 Key-Value 向量，后续只算新增。修改第 k 个 token，k 之后需全部重算。
- **KV Cache vs Prompt Cache**：前者为模型内部单次复用，后者为推理引擎跨请求优化。缓存读取约为首次计算的十分之一。
- **经典反例**：客服 Agent 系统提示词注入 `Current time: {{now}}`，首 token 延迟从 0.5 秒涨到 3-5 秒，账单翻倍。

**三条核心结论**：
1. 系统提示词和工具定义一旦确定就不要改。
2. 动态信息永远追加到末尾——作为新消息，不修改已有提示词。
3. 使用标准 API 格式，禁止自行拼接消息。

**Claude Code 实践**：系统提示词用缓存边界标记一分为二，之前全局缓存，之后为用户特定信息。子 Agent 继承上下文需逐字节匹配。

**出处**：2.3 节；实验 2-2、2-3。

### 4. 提示工程的本质是把业务规则写成模型能执行的指令

**核心论点**：提示工程核心对象是系统提示词。%%H%%大语言模型的优势在于遵循复杂指令和从长上下文中提取信息，但不应该在业务规则制定上被赋予过多的自由裁量权——通过清晰的操作框架解放模型的认知资源，使其专注于真正需要思考的部分。%%/H%%

**语气与风格**：大写字母（`NEVER do X`）比 `Please avoid` 更能引起注意，但过度稀释效果，保留给关键约束。

**结构化提示**：XML 标签携带语义信息，与 Markdown 协同——XML 负责机器可解析，Markdown 负责人机共读。

**流程驱动 vs 规则堆砌**：SOP 格式分解为 Validation→Classification→Preprocessing→Execution→Verification。消融实验：有序流程拆散后成功率下降超 30%，Agent 常跳过验证。

**业务规则细化**：帮用户打电话降费为例——按提成计费仅限于谈判降低现有账单；退款和取消不能用提成；成功率分步评估（>60% 可退款，<30% 直接拒绝）。%%H%%在优秀的 Agent 公司里，提示词一般由产品经理来设计，基于线上数据、用户反馈和运营经验迭代优化。%%/H%%

**Few-shot 示例**：两三个高质量示例胜过等量抽象规则。示例应保持字节级稳定。2026 年起向渐进式披露演进——tool_search 按需加载 schema。

**出处**：2.4 节，实验 2-4（工具描述去文本后错误率+45%）。

### 5. 提示注入：上下文安全的核心威胁

**核心论点**：%%H%%提示注入在 Agent 系统中比在普通聊天机器人中更加危险——Agent 拥有工具调用能力，被注入的指令可能导致文件删除、邮件发送、隐私泄露等不可逆操作。%%/H%%

**攻击面**：每个感知工具都是潜在注入入口——网页隐藏元素、PDF 元数据、图片 EXIF。

**上下文层防御三条**：
1. **来源标记**：用 `<external_content source="...">` 包裹外部内容。
2. **结构化角色**：严格利用 Chat Template 角色体系——把工具结果混入 user 消息等于抹掉模型辨别来源的依据。
3. **输入清洗**：过滤可疑模式，仅作辅助——易被措辞变体绕过。

**新攻击面**：Skills 和状态栏也是注入面——第三方 Skill 可能藏有恶意指令。上下文层防御是分层防御第一道防线，无法万无一失。

**出处**：2.4.7 节；实验 2-5。

### 6. Agent Skills：渐进式披露的能力模块化

**核心论点**：不把所有知识一次性塞给 Agent，而是让它按需加载——每个 Skill 是自包含的知识模块，可独立开发、测试、版本控制和分享，使能力扩展从集中式提示词编辑转变为分布式社区驱动生态。

**三层渐进式披露**：
- **元数据**：SKILL.md 的 YAML frontmatter，description 写成路由条件——"何时该用我"比"我能做什么"更重要。
- **核心流程**：Agent 判断需要该 Skill 时才加载完整内容。
- **细则**：通过文件引用深入子文档。

**编写方法**（引述宝玉《图解Skill》）：角色与读者说明→核心原则配正反例→禁止清单记录高频错误和合法例外→参考资料。

**上下文位置与 KV Cache**：目录在正文前可见；完整正文在调用时注入末尾——"少量目录常驻、完整正文按需加载"，末尾追加不破坏缓存。Skill+通用执行器模式下工具数量始终很少（第五章仅需七个核心工具）。

**出处**：2.5 节；实验 2-6、2-7。

### 7. Agent 状态栏：将隐式状态提炼为可检索的显式知识

**核心论点**：%%H%%上下文学习本质上更像检索而非推理——模型擅长从已有内容中查找信息，但不擅长主动归纳和统计。Agent 状态栏正是通过提前算好结论、放进上下文末尾，补上那台"只有一半的检索引擎"缺失的提炼层。%%/H%%

**理论基础**：以"打了 3 次电话是否继续拨打"为例——已打几次的知识分散在 KV Cache 中，模型每次决策都要重新统计。写入"本次是第 3 次呼叫该商家"后，模型立即发现达限制。研究验证（Distill, Don't Retrieve）：弱模型+状态栏涨 40-54 个百分点，2B 小模型追平不带状态栏的前沿大模型；强模型省下一个数量级思考量。

**三条血泪教训**：
1. **状态栏用代码维护，别拿大模型维护**——20 行正则可达标准答案级准确度，前沿大模型批量统计反而在大多数格子出错。
2. **不要删掉原始上下文**——状态栏是有损投影，落在未覆盖维度上的问题准确率断崖式崩塌。
3. **把状态栏准确率当一线生产指标**——模型几乎无条件信任状态栏。

**五种具体技术**（实验 2-9）：时间戳跟踪、工具调用计数器、TODO 列表管理（启用后 15 次迭代 vs 禁用 21 次且常遗漏）、详细错误信息（替代方案成功率 60%→95%）、系统状态感知。

**实现与缓存代价**：状态栏作为 user 消息追加末尾。每轮替换使移除点后缓存失效但范围有限；持久追加完全缓存友好但陈旧状态累积。

**出处**：2.6 节；实验 2-8、2-9。

### 8. 上下文压缩：蒸馏优于堆砌，隔离优于压缩

**核心论点**：%%H%%上下文压缩不只是解决"装不下"的问题——即使上下文窗口足够大，把所有原始信息堆在上下文里也不是最优选择：压缩把需要思考才能得到的结论变成可以直接检索的知识。%%/H%%更根本的思路是子 Agent 上下文隔离。

**压缩的双重动机**：长度和成本约束；提升思考质量——将散落原始结果转为可直接使用的精炼知识。

**内部机制验证**："100 笼子 90 黑 10 白"例子——不启用思维链时模型无法直接统计（注意力擅长查找不擅归纳），启用每次要重新数。若提前写入"黑猫 90，白猫 10"，模型立即检索。揭示：%%H%%上下文学习更像一种快速适配机制而非真正的学习：它允许模型在推理时快速调整行为以适应特定任务，但这种调整是暂时的、浅层的。%%/H%%

**上下文腐化（Context Rot）**：窗口装得下但找不到——无关内容过多时决策质量下滑。%%H%%与其期望模型从冗长的上下文中自动学习，不如主动地、显式地进行知识提炼。%%/H%%

**六种压缩策略**（实验 2-10，Kimi K3）：无压缩→第 5 次超 128K 失败；个体摘要→压缩率 10.9% 但碎片化；组合摘要→4.3% 但需截断；**上下文感知压缩**→纳入查询意图，7 次迭代/40,157 token，压缩率约 3.0%（147,877→1,963 字符仍保留关键信息）；带引用→有损+无损索引；自适应窗口化→80% 阈值触发批量压缩。

**生产级分层压缩**（参照 Claude Code）：工具结果预算控制→噪声删除→API 微压缩→归档摘要→全量压缩（含熔断器）。

**四条设计原则**：信息非均匀分布；语义完整性；任务相关性；压缩即理解。

**保留优先级**：架构决策→不得摘要；变更记录→完整保留；验证状态→必须保留；未解决 TODO→必须保留；工具输出→可仅保留 pass/fail。

**子 Agent 上下文隔离**：%%H%%这本质上是用隔离代替压缩：压缩是有损的、需要额外 LLM 调用的事后补救；隔离则让噪声从一开始就与主上下文绝缘，主 Agent 的 KV Cache 前缀也完全不受影响。代价是子 Agent 看不到主 Agent 完整上下文，任务描述必须自包含。%%/H%%

**出处**：2.7 节；实验 2-10。

## 原则清单

1. 系统提示词和工具定义一旦确定就保持字节级稳定——任何改动使首个不同 token 及其后的缓存无法复用。
2. 动态信息永远追加到上下文末尾（作为新消息），不修改已有系统提示词。
3. 始终使用标准 API 消息格式（四种角色+tools 字段），禁止自行拼接纯文本流。
4. 关键指令用大写强调（如 `NEVER`），仅保留给真正关键的约束，避免稀释。
5. 提示词采用流程驱动而非规则堆砌——SOP"步骤+条件分支"组织，混乱导致成功率降 30%+。
6. 业务规则由产品经理细化到可执行程度——模型不应在规则制定上被过多赋予自由裁量权。
7. Few-shot 示例覆盖边界情况、保持字节级稳定，两三个高质量示例胜过十个大同小异。
8. 所有外部内容进入上下文前用来源标记包裹，区分指令与数据。
9. Skill 的 description 写成路由条件而非功能介绍，明确使用与不使用的边界。
10. Skills 采用"少量目录常驻、完整正文按需加载"的渐进式披露——正文注入末尾不破坏前缀缓存。
11. Agent 状态栏用代码维护，不用大模型批量统计——20 行正则远超前沿大模型准确度。
12. 状态栏追加但保留原始上下文——状态栏是有损投影，落在未覆盖维度上的问题准确率断崖式崩塌。
13. 把状态栏准确率作为一线生产指标监控——模型几乎无条件信任状态栏信息。
14. 优先做分层压缩而非全量压缩；定义保留优先级：架构决策完整保留，工具输出可仅保留 pass/fail。
15. 上下文接近窗口 80% 时触发批量压缩，而非每轮压缩——频繁压缩破坏缓存。
16. 大体积中间任务委派给子 Agent 隔离执行，只回传结论——隔离优于压缩。
17. 压缩后保留源引用实现有损+无损索引的结合；优先用上下文感知压缩。

## 失败模式与反例

1. **动态系统提示词**（最经典反例）：注入 `Current time: {{now}}`，每次前缀缓存失效——首 token 延迟放大数倍、账单翻倍。
2. **滑动窗口对话历史**：只保留最近 N 条破坏前缀一致性，第 2 轮文件到第 15 轮已滑出窗口，错误率上升。
3. **文本格式化**（最破坏性）：将结构化消息转纯文本，偏离训练格式，导致重复执行、忽略工具结果。
4. **工具定义动态排序**：按使用频率排序导致缓存失效，固定顺序对选择能力几乎无影响。
5. **模糊业务规则**："根据任务选择计费类型"——同一任务不同时间分类不同。正确：写 `NEVER use percentage for refunds`。
6. **让 LLM 批量统计生成状态栏**：前沿大模型在大多数格子出错，下游准确率比不用状态栏还差。
7. **上下文腐化（Context Rot）**：窗口远未满但 Agent 找不到关键信息——无关内容稀释注意力。
8. **Skills 误触发**：description 太宽泛导致路由失准，浪费 token 降低精准度。
9. **提示注入的 Skills 攻击面**：第三方 Skill 藏有恶意指令，安装前须审查。
10. **Chat Template 角色误用**：工具结果作为普通 user 消息，Chat Template 误清理之前的思维链。

## 关键术语表

- **上下文工程**：系统性设计、组织和提供 Agent 完成任务所需的全部背景知识，Harness 中"上下文与工具"层面的核心实现。
- **消息角色**：API 消息四种角色——system（系统指令）、user（用户输入）、assistant（模型输出）、tool（工具结果）。
- **ReAct 循环**：Agent 的 Thinking→Action→Observation 循环，API 层体现为发送→调用→执行→送回的 while 循环。
- **KV Cache**：模型推理时缓存已计算 token 的 Key-Value 向量，后续只算新增。修改前缀任意 token 使其后缓存失效。
- **Prompt Cache**：推理引擎跨请求优化——相同前缀跨请求复用，缓存读取约为首次十分之一。
- **Chat Template**：将 API 结构化消息转换为线性 token 流，用特殊标记划分消息边界和角色。
- **上下文学习（In-Context Learning）**：模型不重训练，仅凭输入中指令和示例适应新任务。本质上更像检索。
- **提示工程**：通过设计系统提示词引导模型行为，核心对象是 role: "system" 的消息。
- **提示注入**：攻击者通过外部内容（网页、邮件、文档）将伪装指令混入上下文，劫持 Agent 行为。
- **Agent Skills**：将能力模块化为独立、可按需加载的知识包，三层渐进式披露，可独立开发、测试和分享。
- **渐进式披露**：先给目录摘要，需要时加载完整内容——"少量目录常驻、完整正文按需加载"。
- **Agent 状态栏**：上下文末尾注入结构化元信息（进度、调用计数、环境状态），弥补模型不擅归纳的不足。
- **上下文腐化（Context Rot）**：窗口远未满但决策质量下滑——无关内容稀释注意力。
- **上下文蒸馏**：将隐式状态提前计算为显式结论注入上下文，状态栏是其最日常形态。
- **上下文感知压缩**：将查询意图和已积累信息纳入压缩决策，引导生成任务相关精简摘要。
- **子 Agent 上下文隔离**：主 Agent 将产生海量内容的任务委派给独立子 Agent，只回传结论——"隔离优于压缩"。
- **注意力储存池（Attention Sink）**：序列第一个 token 吸收异常高注意力的现象，softmax 数学特性导致。
- **位置偏好（Position Bias）**：模型对上下文开头和结尾分配更高注意力，中间易被忽视。

## 高亮核心论断与金句

%%H%%模型本身的智力只是基础，上下文的质量才是 Agent 能力的真正关键——一个中等能力的模型配上精心组织的上下文，往往能胜过一个顶级模型在信息匮乏下的盲目摸索。%%/H%%

%%H%%AI Agent 就像一个永远的新员工：给足背景信息，它能干得很好；什么都不告诉它，再聪明也是白搭。所以构建 AI 原生团队，首先是一场文档化运动，而不只是部署新工具。%%/H%%

%%H%%人和模型一样，最重要的是 Context。AI 短时间内无法取代人的最大原因也是 context——因为 AI 跟人并不在同一个环境里面。%%/H%%

%%H%%Agent 的下一步行动取决于截至当前的完整交互上下文，而不只是眼前这一条输入。%%/H%%

%%H%%系统提示词和工具定义一旦确定就不要改——任何改动，哪怕多一个空格，都可能改变 token 序列，使首个不同 token 及其后的缓存无法复用。%%/H%%

%%H%%当 Prompt Cache 的经济效益足够显著时，缓存一致性会反过来主导系统的架构选择。%%/H%%

%%H%%大语言模型的优势在于遵循复杂指令和从长上下文中提取信息，但不应该在业务规则制定上被赋予过多的自由裁量权。%%/H%%

%%H%%在优秀的 Agent 公司里，提示词一般由产品经理来设计，基于线上数据分析、用户反馈和运营经验来迭代优化规则定义。%%/H%%

%%H%%提示注入在 Agent 系统中比在普通聊天机器人中更加危险——Agent 拥有工具调用能力，被注入的指令可能导致文件删除、邮件发送、隐私泄露等不可逆操作。%%/H%%

%%H%%上下文学习本质上更像检索而非推理——模型擅长从已有内容中查找信息，但不擅长主动归纳和统计。%%/H%%

%%H%%上下文学习更像一种快速适配机制而非真正的学习：它允许模型在推理时快速调整行为以适应特定任务，但这种调整是暂时的、浅层的。%%/H%%

%%H%%与其期望模型从冗长的上下文中自动学习，不如主动地、显式地进行知识提炼。%%/H%%

%%H%%上下文压缩不只是解决"装不下"的问题——即使上下文窗口足够大，把所有原始信息堆在上下文里也不是最优选择：压缩把需要思考才能得到的结论变成可以直接检索的知识。%%/H%%

%%H%%这本质上是用隔离代替压缩：压缩是有损的、需要额外 LLM 调用的事后补救；隔离则让噪声从一开始就与主上下文绝缘，主 Agent 的 KV Cache 前缀也完全不受影响。%%/H%%

%%H%%状态栏要用代码维护，别拿大模型去维护——一个 20 行正则函数就能达到"标准答案"级别的准确度。%%/H%%

%%H%%模型几乎无条件地相信状态栏——你写"打了 3 次"，它就当真是 3 次，既不会偷偷去核对，也不会自己重算。%%/H%%

%%H%%循环的瓶颈在验证器，而不在模型——衡量改进的"尺子"必须扎根真实观测，否则循环会悄无声息地空转。%%/H%%

%%H%%让大体积的中间信息根本不进入主上下文——压缩是在信息已经进入上下文之后做减法，隔离则让噪声从一开始就与主上下文绝缘。%%/H%%
