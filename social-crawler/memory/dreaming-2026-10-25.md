## A. 执行错误

### A1 ★ 第 11 次同类：自检命令用 grep 退出码当门禁，误杀整轮 run

- **现象**：台账自检打印 `勾选数 31 未勾选 0`，紧跟 `(Command exited with code 1)`。数据 31/31 全勾，判定完全合格，但因为 `grep -c '^- \[ \]'` 在匹配 0 行时返回退出码 1，整条命令链非零退出，run 判 error，announce 投递被整体跳过。
- **根因**：**把"有多少行"的查询语句当成了"通过/不通过"的门禁**。grep 的退出码语义是"有没有命中"，不是"数量合不合格"；`未勾选 0` 恰恰是它返回 1 的条件。判定对象（数量）和读数方式（退出码）不同层，这是守卫二十的第二段「判断颗粒度与被保护对象不同层」的实例。
- **与历史 10 次的区别**：8/28–10/24 的同类 error 来自脚本不退进程、读昨日 raw、Process failed；**今天是第一次由"自检语句本身"制造出来的假失败**。危害相同（交付通道被关），但排查方向完全相反——前 10 次要去查数据，这次数据是好的，要去查命令。
- **结果**：兜底路径（10-20 加固）生效，11:06 分 4 条发群全部 ok=true。**run 状态 error，用户实际收到，两者第一次这么干净地分离。**

### A2 CDP 9333 预热检查通过，实际连接仍超时 60 秒

- charm-cdp-warm 10:45 检查 `/json/version` 返回 `Chrome/149.0.7827.104`，判定"已在线，无需启动"。
- 11:00 抓取时 `browserType.connectOverCDP` 对 9333 超时 60000ms，回退 18800 才成功（raw `cdpPort=18800`，连续第 2 天）。
- **根因**：预热检查只验 HTTP 端点可达，没验 CDP WebSocket 能否建立、能否取到 browser context。可达 ≠ 可用，属于典型的"校验存在性替代可用性"。代价是每轮固定浪费 60 秒，并把抓取段耗时顶到 231 秒。

### A3 临时 python 脚本键名写错，KeyError 白费一步

- `print('#####', b['name'])` → `KeyError: 'name'`，raw 里的字段是 `brand`。当场改为 `b['brand']` 后正常。
- 属低级但可预防：raw 的字段结构在 canonical 脚本里已固定，临时脚本应先打印 `list(b.keys())` 再用，或统一走已有脚本。

### A4 ★ 内容层重复违规：逸凡第二次指出同一件事

- 11:00 版日报：几乎每条带「本窗口 X 转 Y 评 Z 赞」「总互动 6947，为窗口内总互动第一（口径 r+c+l）」「对品牌而言……」，末尾 4 条行业层面信号，header 带采集说明与守恒式。
- 12:46 逸凡原话：「已经说过了，不需要赞藏数据，不需要你的额外判断依据写入日报，确保日报是专业的可转发可使用的」。
- **根因（本次最重要的一条）**：规则写在了 **MEMORY.md**（会话启动时读），而 cron 执行时真正被当权威的文档是 **SKILL.md**——今天上午的 SKILL.md frontmatter 还写着「每条写清动作+品牌价值分析，营销活动带效果判断，行业洞察三条深入总结」，`references/approved-example.md` 还是 06-08 旧标杆（含 21 处「对品牌而言」、带汇总表）。**规则改了、载体没改、范例没换**，执行者当然按范例写。
- 这不是"没记住"，是"同一规则有两个互相矛盾的载体，且更贴近任务的那个是旧的"。守卫七（规则必绑定决策点）在这里失效的原因：规则绑在了 MEMORY 这个**阅读路径**上，但没绑在**产出路径**（SKILL + 范例文件）上。
