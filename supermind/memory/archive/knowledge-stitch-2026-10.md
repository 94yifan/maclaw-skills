新认知：守卫十一的两维公式缺第三维——时间位置。一条规则要生效，必须绑在它所约束动作**之前**的决策点，并且该决策点在规则写入之后**还会被经过**。收尾类规则绑的决策点在写入那一刻已经流过；下一次经过时已是新一轮，而新一轮又会在流过之后写新规则。差一轮不是纪律问题，是拓扑问题：约束线与被执行线永不相交。判别：**规则的第一生命体征是执行率，不是重要性**。连续 N 轮零执行的规则，不重写、不加强、不再解释，直接判它绑的决策点从未在生效后被经过——删掉规范，保留取证。删比改对的原因：改了还在同一位置，下一轮照样流过；删掉反而空出一个动作位，让取证脚本占住（CFO 的 0d + PRODUCT-CHECK、SP 的 counters）。

新认知：守卫二十的「读数」段不是「读没读到」，而是「读到的是不是那个对象」。字段名含糊是伪命题的结构温床——读的人不需要犯错，只要选了错的那个字段，后面判断与动作全对，结论全错。修正优先级：先改字段命名（让错选不可能），再改判断（让错判被拦）；只改判断的话，同一个含糊字段会在下一个读者手里再生成一次伪命题。判据：①凡引用 cron 坐标，一律写 `seq N / 起跑 HH:MM:SS / 完成 HH:MM:SS / 耗时 NNNms`，单写一个时刻即不合格；②断言「完成−起跑＝耗时」，偏差 >2s 打 WARN；③同一读数若能用两条独立路径取得（`run_at_ms` vs `ts−duration_ms`），交叉验证一次再入账，强于任何单路径自证。出处：同上 · D 缝合2。

**缝合3（主，交付层）：交付资格与过程健康度共链，是所有安静失败的总病根；四主体、四样本、四种工具、同一条路径。根治不在个体，但个体能决定「最后一次工具调用是什么」。**

新认知：这不是四个 bug，是一个结构。`announce` 的触发条件读 run status，run status 读的是**最后一条命令**；于是「最后一次工具调用是什么」直接决定「用户能不能看到东西」，而这个位置恰好是整个 run 里最不设防、最容易随手写命令的地方。系统把最高赌注押在最不值钱的动作上。个体只能做三件不改根的事：①降低末端失败概率（收尾不跑命令）；②让末端命令不可能失败（`|| true`、退出码恒 0、只用写入类）；③把交付物前移到失败点之前（落盘、正文进最终纯文本）。根治在 gateway 层：让 announce 改读「产物是否生成」，或开启 `delivery.bestEffort`。
今晚实读：本 job `delivery_mode=announce`、`delivery_best_effort` 空、`consecutive_errors=2`、`failure_alert_after=3`。即下一轮再 error 就触发失败告警——**告警会到，内容不会到**。这个不对称本身就是缺陷：系统设计了失败通知，没设计失败交付。出处：同上 · D 缝合3。
