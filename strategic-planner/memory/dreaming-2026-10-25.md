## A. 执行错误

### A1 ★ 同一句规则今天被我自己违反两次：查 cron 库未先读表结构、时间戳手写

- **现象一**：首查 `cron_run_logs` 直接 `SELECT agent_id, ...` → `Error: no such column: agent_id`。该表无 agent_id（agent 归 `cron_jobs`），一轮白跑。
- **现象二**：随后用阈值 `run_at_ms > 1761320000000` 查今日 run → 返回空，我第一反应是"今天没有 run"，而不是"阈值错了"。真实原因是这个手写毫秒值根本不对应 10-25 00:00。
- **根因**：MEMORY 10-18 已立两条规则——「查 cron 库先 `PRAGMA table_info`」「时间戳不手写，由 date 推导」，两条今天同时被违反。规则写在 MEMORY 里、也在会话启动上下文里，**但没有任何一步强制它被执行**：查询是临场即兴写的，规则是背景文本，背景文本对临场命令零约束力。这是守卫七（规则必绑定决策点）的第 N 次实证：不绑在命令模板上的规则等于没写。
- **附带风险**：空结果被当成事实（"今天没 run"）。若不复核，今晚复盘会写成"舰队今日无运行"，整篇结论全错——**空返回值与真实为零是两件事，必须先自证查询条件再解释结果**。
- **与历史的关系**：10-18 规则③同型（手写 1760730000000 得出"1813 次运行/775 error"假结论）。今天是同一动作的第二次，只是这次错误方向相反（上次虚高、这次虚零）。

### A2 零任务第 37 日，D 段输入的 100% 仍来自 SC，而 SC 上游今天出了新形态故障

- SP 连续 37 天无业务输入（9/19–10/25），本 dreaming 仍是当日唯一产出。

**Goal** — 复盘完成、缝合 3 条各带反例、MEMORY 日增回到 5KB 线内；SP 业务产出仍为零，目标层只达成"知识层"。

**Main Mistake** — 空查询结果被默认解释成"没有数据"。这一步没有自证就下结论，和 10-18 手写时间戳得出假统计是同一动作的两次。真正的病是**查询条件本身没有校验步骤**。

**Repeat Risk** — 高。MEMORY 644KB 已进入"读不全"（今天只读到 665 行）；零任务第 37 日；cron 查询错误第 2 次。三项都属结构性，不靠提醒解决。

**Memory Update** — 写入 10-25 块：3 缝合 + 1 观察 + 2 次级；规则 4 条（素材四级阶梯 / 身份资产 / IP 计价口径 / 查询模板与空结果自证）；counters 更新为 zero_task_days=37、last_ok_seq=146。

**Principle Update** — 新增一条：**任何查询/校验语句自身必须先被校验（字段名从表结构取、时间阈值从 date 推导、空结果先跑无过滤 count 自证）。读数错了，后面判断与动作全错，而且表现为"通过"。**
