## A. 执行错误

### A1（P0，本轮最高价值）骨架脚本能往 MEMORY.md 写脏区块 —— 修守卫的人踩了守卫

为了按守卫AN 把「先落盘」自动化，执行 `python3 tmp/giftlist/dreaming_open.py --help` 想看用法，脚本把 `sys.argv[1]` 直接当成日期：

- `MEMORY.md` 里多出一个 `## --help【骨架先写，守卫AA/AN】` 区块；
- `memory/dreaming---help.md` 被创建（130B 空骨架）。

影响面比表面大：dreaming_open.py 是全轮第一个写动作，也是守卫AA 依赖的唯一落盘入口。它不校验输入，等于把「先把噪声写进主 session 唯一自动加载文件」变成了默认路径。任何拼写错误（`2026-1O-22`、带空格的日期、复制粘贴多一个词）都会静默生成一个孤立日期区块，未来某次 grep/归档都会把它当成真实业务日。

处置（已闭环）：`today_str()` 加严格 `\d{4}-\d{2}-\d{2}` 正则 + `date.fromisoformat` 合法性校验，`-h/--help` 只打印文档并退出，其余非法参数打印 WARN 后回落本机当日。三个反例实跑：`--help` 只输出文档不写盘；`2026-13-99` 打印 `WARN: 忽略非法日期参数` 并回落 2026-10-22；无参幂等返回 exists。脏区块与 `dreaming---help.md` 已删除，`grep -c "^## --help" MEMORY.md` = 0。

### A2（P1）守卫AN 第四轮违反，且这次根因已经不在我这边

本轮顺序：date + 读 MEMORY 并行 → audit → 列脚本 → 才跑 dreaming_open。骨架落在第 4 个动作、22:08 左右。

前一轮的结论是「根因在 payload 步骤顺序」，今天验证得更彻底：**cron prompt 第 1 步 date、第 2 步 read SOUL/MEMORY、第 3 步才分析，第 4 步才写文件 —— 写落盘在指令里排第四。** 我按指令执行，就必然违反守卫AN；要守 AN 就得违反指令。这不是纪律问题，是两条规则互相冲突。

本轮处置：不第五次重复这个结论，改为在 MEMORY 区块里把它标成「规则冲突待主 session 裁决」，pending 项 cron-prompt-wording 的措辞从「建议改」升级为「冲突，必须改，否则 AN 永久失效」。

## B. 规避方案

1. **写进默认路径才算修（承 9/12 结论、守卫AI）**：A1 的修法不是「下次别跑 --help」，是把输入校验编译进 `today_str()`。凡脚本接收外部参数，第一件事是校验格式与合法性，非法即回落并告警 —— 骨架脚本、归档脚本、回执脚本一律适用。
2. **规则冲突必须显式裁决，不能两条并存**：守卫AN 与 cron prompt 的步骤顺序是硬冲突，并存的结果是每天违反一条。处置升级为 pending 高优项，主 session 一改即闭环；在改之前，本 session 的默认动作是「date 与首轮读并行、dreaming_open 紧跟其后」这个最小代价版本，并如实记为违反。
3. **派生的待办要绑时点，否则等于没写**：D2 这类「明天做X」的条目，要么编译进 closeout 脚本，要么写进 MEMORY 当日区块的固定动作位。写在复盘文件末尾、靠次日回看，实测两次 0 执行。
4. **固定 SQL 模板入库**：把 `cron_jobs` / `cron_run_logs` 的正确列名与两条查询语句写进 MEMORY 的 cron 段，避免每轮试错两次。
