## B. 本周学到的关键洞察

### 1. 失败域第三次迁移：超时已经成为主因，不再是收尾

上周 18/22 次失败发生在写完文件之后的验证/归档环节，本周 54/61 次失败是 300s 硬超时（47 次卡在模型调用起点）。含义：agent 单轮任务量已经超过 300s 预算，且**卡点从"任务的尾巴"移到了"任务的头部"**。系统加固的节奏依旧落后缺陷迁移一步——上周修的是尾，这周烂的是头。

### 2. 产出存在与 run 成功脱钩的规律，本周反向成立

5 月教训 23 写的是「产出存在 ≠ run 成功」，本周补上了反向那一半：**run 失败终于开始吃掉产出**。ceo 缺 2 天、cfo 缺 2 天、supermind 9/24 复盘完全丢失。上周还能靠"双指标交叉验证"说系统其实没事，本周不能再这么说——复利已经开始结算。

### 3. 重试机制在起作用，但代价已经可见

全系统自发用"重试轮"自救：book 每晚补跑 2-3 轮（22:22 / 22:39 / 22:55 三段），brain-mining 靠重试轮补写，cfo 连续 5 轮撞 300s（自记 consecutive_errors=9）。机制有效，但每轮都是全量重跑——book 自己的规则 12 已经指出「重试轮会再生 ahead-1，修复动作复制故障」。token 与时间成本在滚动放大。

### 4. 失败在时间上高度聚集仍是结构问题，且比上周更严重

8 个分身的 dreaming 仍全部排在 22:00-22:18，间隔 2-4 分钟，同时读写同一个 git 仓库、同时调模型。上周建议"拆窗口"，本周失败量翻近 3 倍（22 → 61）说明窗口不拆，同一个故障会按天复利。**cfo 与 supermind 本周 9 连败 0 成功**，是最固定的两个失效点。

### 5. 密集窗口期的正向验证：tea-daily 修复真的生效了

上周 tea-daily-report 5/7、失败带 300s 特征；本周 7/7 全绿。同一周内 dreamiing 集群恶化、茶饮链路转好，说明问题不是"系统整体在变差"，而是**dreaming 集群的排期与预算结构问题**。定位收窄了，修复方向就清楚了。

### 6. 零告警依然是最大盲区

61 次失败的 notifyPolicy 全部为 silent（含 main 自己的 dreaming-omni 今晚这一次），没有任何人被通知。上周提的"打开 failureAlert"本周未见落地证据——这是唯一一项"提了、没做、代价翻倍"的建议。
