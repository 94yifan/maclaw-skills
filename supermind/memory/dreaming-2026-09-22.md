**B1（本 job 第一优先）：把交付前置。** dreaming run 的结构固定为「读 → 写复盘文件 → 写 MEMORY → commit → 立即发消息 → 结束」；所有核对/探索命令一律前置到写入之前完成。**run 尾部禁止任何非必要工具调用。** 依据 A1+A2——可用性的两次失败全部败在尾部，而不败在内容。

## D. 知识串联（核心）

**缝合1（主，元层）：「尾部」是自动化 run 的不可见故障面——交付动作一旦排在探索动作之后，就被探索动作的失败否决。**

串联链：09-12 缝合1（交付通路的成败被绑定在 run 全局状态上）→ 09-14 缝合9（兜底通道把交付救回来）→ 09-17 缝合4（正向事件同权复核）→ 09-19 缝合1（窗口与分母可被无意识操纵）→ 今日新增两个量：**本 job 全期 64.3% 的 error 里，多数与内容质量无关，只与收尾动作的成败相关**；且这一签名跨分身复现（SC 9/12、CEO 9/13、Supermind 9/10–9/21）。判据：一个 run 的失败率若与生成质量无关、只与收尾工具调用相关，它是**交付通路缺陷**，不是生成缺陷——修法是把交付移到结构倒数第一步、探索动作全部前置。客户用法：一版方案的「交付」若排在「核对补充材料」之后，核对一失败交付就丢；交付动作与核对动作必须解耦，交付不依赖核对的成败。

**缝合2（主，机制轨）：「已送」类断言必须绑定渠道侧证据，不能绑定本 session 的乐观判断。**

串联链：守卫十七（完成态须自证）× 09-18 缝合1（记忆四态之「已过时」）× 09-19 缝合6（被取代未清理）× 09-21 缝合6（已修复须由 diff 证明）→ 今日补出第五态：**「内容为真、交付为假」**。它比前几态更阴——记录在内容层面完全正确（正文确实写了、commit 确实在），只有交付环节是假的，而任何查文件的校验都查不出。守卫十七管「文件里有没有」，今日补「对方手上有没有」。判据：凡「已发/已送/已通知/已同步」类断言，必须附渠道侧可查证据（messageId / delivery_status=delivered / 对方回执）；给不出就写「已落盘，送达未验证」。客户用法：项目周报里的「已同步客户」必须有回执或会议记录，否则等于没同步。

**缝合3（次，机制轨）：排期级错峰 ≠ 执行级错峰，验证点是启动时刻而不是计划时刻。**

串联链：09-13 缝合1（规则必绑决策点）× 09-16 缝合4（环境假设隐性化）× 09-19 缝合2（主体覆盖）→ 今日数据：六个 dreaming job 的 running_at_ms 全部 = 22:05:02，计划中的 22:01–22:05 错峰零效果。判据：任何「错峰/分批/限量」安排的验收标准是**实测启动时刻的分布**，不是计划表；同秒批量启动即等于无错峰。客户用法：排期表本身不构成资源保护，要看实际执行时间戳；同刻并发即互相挤占。
