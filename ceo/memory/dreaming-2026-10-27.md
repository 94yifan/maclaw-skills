## D 知识串联（核心）

### 缝合1（主·治理层·命名日）：运营全绿与价值归零可以同日出现——run 成功率度量的是「系统按设计运转」，不度量「设计是否还有人需要」

证据链同日闭合：①舰队 14 跑 0 error，52 天来首次（回溯至 9-01，唯一另一天为 9-05）；②同日 8 跑 not-requested，其中 SC 与 CFO 的 dreaming 是 `delivery_mode=none`——不是这次没发，是从来没有出口；③BM 自记「两晚约 42KB 写作、8 条判断，消费量为 0，这不是勤奋是空转」；④SP 自记 59 个缝合块在 39 天零业务里未被任何任务调用；⑤CFO 自记「7 轮 7 条守卫，0 条与业务能力相关」。

串联 10-21 缝合1（有效绿：分母不是运行次数，是含判断的运行次数）+ 10-19（绿 = 历史失败率决定的期望存活长度）+ 守卫二十一（无消费者动作停例行）。

**新认知：健康度必须双列——「跑了几次」与「有几次被读」。单列前者，会奖励一种最隐蔽的失败：跑得干净、零差错、零人读。** 判别动作：报任何一个 100% 之前，先问「这个 100% 的分母里，有几条进入了某个人的决策」。

**管理同构：一个部门周报连续 12 周准时零差错、无人打开，运营指标会把它评成标杆；它其实已经从组织里掉出去了，只是没人通知它。销售也一样——拜访量满格、纪要齐全、零成单，考核拜访量的体系会给他满分。凡是只度量「动作是否按设计发生」的体系，都会在无人消费时给出最高分。**

### 缝合2（主·知识调用层，接 supermind 今日缝合1 + SP 今日 A1）：知识越过单次读取阈值后，「写下来」与「可调用」分离；分段读是绕过，不是修复

三方同日读数：SP MEMORY 665,296B，单次 read 在 128KB 截断，缝合区必须 grep 行号；supermind 95,118B，read 输出明示 50KB 上限、只显示 451–663 行，它靠分段读完并自认「绕过去了不等于问题不存在」；我 113,181B，距 128KB 余 14.8KB，约两天缝合量。

串联守卫十一（规则效力 = 加载路径 × 决策点）+ supermind 今日补的第三维（检索成本）。

**新认知：公式是三段——加载路径 × 决策点 × 检索成本。体积是唯一会单调恶化的变量：知识越多越读不到，越读不到越只能靠当场推理，于是知识库的存在反而降低推理质量，因为读者以为自己有知识库。** 这解释了 10-04 以来反复出现的「规则写对了但没执行」——不是不执行，是执行时读不到。

判据三条：①自动加载文件超单次上限 60% 即改「索引 + 分文件」，主文件只留一行索引；②接非例行任务第 0 步固定 grep 关键词，再动笔；③一次没读全的文件不得作为「已了解」的依据，读完必须能说出总行数与覆盖区间。

### 缝合3（主·口径层·当日跨主体实证）：同一个差额，读的人决定它是缺口还是分类账——17 与 3 的差别不在数据，在口径

SP 22:12 判「header 43 vs 正文 26，缺口 17，第 4 次不闭合且历史最大」；supermind 22:18 核出台账 43 = 正文 23 + 合并 14 + 剔除 6，真实差 3 条，17 是把合并与剔除当成了丢失；我独立复算：`grep -c '^【'` = 26，台账 `[x]` = 43，header 写 43。

串联 10-22 缝合1（余数项吸收差错）+ supermind 今日缝合2（口径混用是守恒式第三种失效形态）+ 守卫十二。

**新认知：SP 在同一天写下了「余数项会吸收差错」这条规则，随后自己用余数项制造了一个不存在的缺口。写规则的人不读自己的规则，这是规则治理里最稳定的失效路径**——不是忘记，是那条规则没有绑在「读别人的数」这个动作上。判据：看到差额先问「两边是不是同一口径」，能列出余数构成的不是缺口；真缺陷是 header 未声明口径，修法是 header 由正文 count 派生、禁止独立生成。

### 缝合4（商业层·跨层同构）：今天所有跑得动的机制，共同点是「让外部能自己算」；今天所有出问题的系统，共同点是「外部算不出」

商业侧四个当日样本：①瑞幸 KPL 十位选手各配一杯 → 粉丝能算「我那杯」；②幸运咖积分商城上徕芬/华为/小米 → 用户能算「1 积分值多少钱」（此前只有自有周边，无市价锚，积分只能当抽奖）；③库迪每日前 200 份免单、茉莉奶白每日 40 个气球 → 门店能算「今天能做多少」；④霸王茶姬打底香/托香/收尾三段、茶百道西非产区 + 先品后搅 → 客户能算「这杯和那杯差在哪」。

系统侧同日的三处缺陷：header 43 与「9 家无动态」互斥（客户可当场查证、算不出）；隔离测试只验「产物在预期位置」不验「真实对象未被改」（CFO 今日实证，靠 git 还原）；知识库 665KB 单次读不到（读者算不出）。

串联 10-24 缝合1（提醒价值由决策节律决定）+ 10-26 缝合3（机制必须标归属三类）+ 守卫二十六（口径必须写到可被客户反算）。

**新认知：可复算是所有对外交付的一级属性。一个数字客户能自己重算，它是资产；算不出，它就在下一次争执里变成负债。** 报价同构：能算的行（店数 × 单价、每日配额 × 天数）不吵架；算不出的行（深度改造、预热期授权）最后一定变成「这不该收钱」——10-26 那条「预热内容授权费金额可以为零但必须存在」讲的是同一件事的合同版本。

**曼拾直接用法：月报与报价单各加一句「客户如何自己复算这一项」。答不出的项，要么补计量单位，要么重新定价，要么删。**

### 观察（不入缝合）：积分体系的两种读法同日独立出现

SP 从用户侧说「积分必须有外部市价锚才像钱」，BM 从会计侧说「积分商城是递延负债，家电兑换是 breakage 设计」。同一现象、两侧各说对一半，互不引用。按守卫十五单样本只记观察；若两周内出现第二例（会员权益同时被算成资产与负债），再升为「同一机制必须同时给用户账与公司账」的规则。

## E 结论

今晚真正值钱的不是「52 天来第一次零 error」，是它同时暴露的东西：**一个系统可以在运营指标上达到历史最好，同时在生产出没有人读的东西，而这两件事不会互相告警。** 前者由 `cron_run_logs` 记录，后者只能靠四个分身各自在复盘里写下来——今天它们同时写了，这本身是这条认知成立的唯一证据。

**给逸凡的一句话（今晚只保留这一条）**：SC 日报的 header 与正文互相矛盾（写「共 43 条动态」，同时把含这 5 条的柠季、东方墨兰列入「今日无动态」），客户点开微博就能当场查证；它连问两天要一个口径，改法很短——**header 删掉总条数，改由正文 count 派生**。回一个「改」即可，SC 当天可落。

（`bestEffort` 那条我不再提了：今晚实读，任何相关会话都没有改 cron 的权限，它从第一天就没有执行者。）
