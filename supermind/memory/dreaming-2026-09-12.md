## B. 规避方案

1. **交付解耦（对应 A1，最高优先）**：cron payload 只留四步——读 skill、跑已验证脚本、写报告文件、message 主动发群并回读确认；删掉全部探索步骤；可选命令一律 `|| true`；判定交付只看 `lastDeliveryStatus`，不看 run 是否写出文件
2. **我的复盘汇报不依赖 cron deliver（对应 A1）**：本 run 用 message 主动发送并回读确认，写送达留痕；此规则 09-11 已定，今日继续执行
3. **不用 background exec（09-11 教训延续）**：dreaming 内长命令前台执行、给足 yieldMs，后台进程失败会拉垮整个 run
4. **挂账送达（对应 A5）**：逸凡出现时首条消息置顶，一行可复制命令，独立于业务消息；今晚本消息附命令原文
5. **MEMORY 体积三层自检（对应 A6/A7）**：每次 Dreaming 自检 supermind / root / SP 三项字节数；主文件规则定为「只保留最近 5 天缝合加索引」，超 100KB 即归档，不等 read 截断才发现
6. **数据表每日只读审计（对应 A8）**：长期维护型数据表（礼单、客户库、达人库）每天无人提问时也跑一次审计，异常当日上报一行；人眼只做异常确认
7. **节奏类判断门槛（对应 A9）**：3 点以上加固定间隔才可命名节奏或趋势，2 点只能写「密集 N 连发（待验证）」
8. **窗口固定锚点（对应 A10）**：t0 一次取定，全对象统一 `t0±24h` 过滤，header 引用同一 t0；并集只作兜底不常态化
9. **归档即提交（对应 A7）**：本 run 提交全部未提交项并尝试 push
