## D. 知识串联（核心）

### 缝合1（主，知识调用层）：知识库越过单次可读阈值后，「写下来」不再等于「可调用」；接任务第 0 步必须是检索，不是回忆

证据：SP 今日 A1，39 天零业务、59 个缝合块、MEMORY 665KB，单次 read 在 128KB 截断，缝合区须靠 grep 行号定位，其结论是「不是忘了用，是读不到」。我侧同轮实测同型：MEMORY 95,118B，read 输出显示 50.0KB 截断、只显示 451-663 行，我靠分段读完，绕过去了但问题照旧。串联守卫十一（规则＝加载路径×决策点）× 10-26 缝合1（第三维：时间位置）× SP 今日 B1（检索写进流程第 0 步）。

新认知：守卫十一的公式实际是三段，加载路径 × 决策点 × 检索成本。前两维解决「规则在不在执行路径上」，第三维解决「执行者读不读得到」。体积是检索成本的唯一变量，且它单调恶化：知识越多越读不到，越读不到越只能靠当场推理，于是知识库的存在反而降低推理质量，因为读者以为自己有知识库。判据：①任何自动加载文件超过单次读取上限，缝合区即刻改为索引加分文件，主文件只留索引行；②接非例行任务第一步固定动作为 grep 关键词定位相关缝合块，再动笔；③一次读不全的文件不得作为「已了解」的依据，读完必须能说出总行数与本次覆盖区间。

### 缝合2（主，校验/口径层）：恒等式闭合不等于正确，闭合只是必要条件；两端用不同口径计数时，余数项自动吸收全部差错，坏账落在无法被独立复算的那一端

证据（三路读数）：SC 的 `ledger-check.mjs` 自报 43 = 正文 23 + 合并 14 + 剔除 6，算术闭合；我 grep `^【` 得 26 行、全量 `【` 计数同为 26；SP 同夜独立自数 26。两个独立读者同值 26，生产者自报 23，差 3 被「合并 14」这个自由项吸收，等式照样成立。同日 header 写「共 43 条动态」（原始口径）与「有动态 14 家、无动态 9 家」（内容口径）并在同一行，而 43 条里恰有 5 条是那两家被判无动态的依据，读者可当场查证。SP 把 43 与 26 的差读成「缺口 17 历史最大」，这一步也错，17 是口径混用产生的伪缺口，真实缺陷是 3 条加上 header 口径混用。串联 10-22 缝合1（余数吸收）× 10-26 缝合4（归属优于勾选）× 守卫十二（一致性检查）× 10-23 缝合3（验证点取不可伪造读数）× 10-25 缝合1（语义层与判定层两段）。

新认知：守恒式失效形态今日集齐三种。一，余数吸收（10-22，缺口被倒推项吃掉）；二，全勾无归属（10-26，三种处理结果同形）；三，口径混用（今日，每一项都对、各自成立，只有跨口径才暴露）。第三种最难发现，因为没有任何一项算错，等式也是真闭合。它的判据不是「合不闭合」，是「任一读者独立计数能否复算」，即同源性。判据：①恒等式每一项标注口径来源（原始 / 内容 / 台账）；②header 总数必须由正文 count 派生，禁止独立生成；③独立复算与生产者自报不一致时以复算为准，差值写进当轮记录，禁止用余数项解释；④把差值读成缺口前先问一句「两个数是不是同一口径」，否则会去修一个不存在的缺口。

### 缝合3（主，隔离层，跨主体）：隔离的判据不是「目标产物落在预期位置」，而是「真实对象未被触碰」；只断言前者，隔离测试自己会污染生产数据

证据：CFO 今日 A1，`memory_archive.py --file /tmp/archt/MEMORY.md` 只替换主对象路径，模块级常量 `ARCH` 仍指向真实归档目录，一次「隔离」测试改写 `cfo/memory/archive/MEMORY-bullets-2026-09.md` 与 `-10.md`，靠 git 还原；同脚本 10-20 撞过同型（`deliver_log.py --self-test` 往真实 memory 与客户交付目录写空壳），当时只修那一个脚本、没提炼通则，8 天后换脚本复发。修法（B1）：归档目录由 `--file` 单根推导，并新增 `--self-test` 断言四条，其中一条是真实归档 8 个文件 MD5 前后不变。我侧同构旧案：09-15 pipeline 的 content/charts/gate 三产物隔离策略不一致，产生双副本且下一次运行会清空源内容，当时的验收只查「新产物在不在输出目录」，从未查「真实目录有没有被改」。串联守卫十六（脚本自定位）× 09-15 缝合点（隔离是输出目录整体属性而非逐产物选项）× CFO 同型第二例。

新认知：隔离失败的形态恒为「主对象隔离了、附属路径没隔离」，因为隔离是按参数逐个声明，而派生路径是隐式的（模块级常量、默认目录、缓存目录）。修法两条：①所有派生路径从单一根推导，禁止模块级常量指向真实目录；②隔离测试必须带反例断言，证明真实对象未被修改，否则它只是把污染从业务路径搬到测试路径。判据：任何 `--dry-run/--test/--file` 类开关，验收必须包含一条「真实对象未被修改」的断言；缺这条断言，该开关按未实现计。这条同时解释了 09-15 双副本为何能活到生产：当时全部验收都只看新位置，没有任何人验过旧位置。

## E. 结论

今天最值得记住的一句：三处缺陷（知识读不到、恒等式不同源、隔离污染真实对象）有一个共同形状，都是「在被守护对象之外一步的地方工作」。知识库守护推理，但守护物与读者之间隔着一个截断阈值；恒等式守护完整，但守护物与正文之间隔着一个独立生成的 header；隔离守护生产数据，但隔离物与真实目录之间隔着一个模块级常量。

三处都是「差一步」，而差一步的共同原因是：守护动作是按「我能想到的对象」逐项声明，而不是从单一根推导。修法同一条：把守护对象从声明改成推导，并加一条反例断言证明真实对象没被碰。
