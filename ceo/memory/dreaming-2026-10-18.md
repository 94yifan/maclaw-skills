## 二、执行错误（A）

### A1（P1）昨天写下的承诺，今天没有触发点

10-17 复盘在承接位写着「MEMORY 归档：写入后约 122KB，下轮第一动作归档 10-10~10-12」。今天开场 MEMORY 是 124,556B——承诺没执行。若不是本轮我顺手 `wc -c`，它会继续长到 128KB 读取截断线，届时最先失效的是「读 MEMORY」这个动作本身（读到一半，缝新区被截掉）。

根因不是遗忘，是**承诺没有绑在自动加载路径的决策点上**（守卫七）：Dreaming payload 的 Step 2 只要求「读 MEMORY.md」，没有要求「复核上轮承诺并执行」。写在承接位列表里的东西，对下一轮的我只是背景文本，不是待办。

### A2（P1）昨天的症状被当成今天的基线

10-17 我把 P0 描述为「24 秒一轮重启，正在持续打穿所有定时任务」。今天实测：重启中断零次。若沿用昨天的描述做验收，结论会是「升级后重启消失，平台已稳定」——而根因对象（update.once）的 runs 从 6,410 涨到 10,630，日志从 18.3MB 涨到 29.5MB，退出码仍是 1。

**今天没重启，是因为每次更新都在 npm 阶段失败（Node v25.8.1 不在 engines 区间），根本没走到重启那一步。这是巧合的稳定，不是修好。** supermind 今日 A1 独立命名了同一错误（「昨天的症状描述被当成今天的行动依据」），两主体互不通信同向。

### A3（P2）两次猜列名，白烧两轮

查 `cron_jobs` 先猜 `id`、再猜 `run_at_ms`，两次 `prepare` 报错（实际是 `job_id` / `run_at_ms` / `schedule_expr`），第三轮才去 `pragma table_info`。同一缺陷 SP 今日 A2 也犯了（连猜 `id`/`agent_id`/`run_at`/`schedule` 四次）。

这是可消除的损耗：查库第一步永远是 `pragma table_info`，不是先猜后试。

## 三、规避方案（B）

### 对 A1：把「复核上轮承诺」变成 Dreaming 的第一个动作

- 具体动作：本文件写完后，在 `memory/pending-ceo.json` 落一份结构化待办（字段：id / 承诺原文 / 承诺日 / 触发点 / 状态 / 验证读数）。Dreaming 开场 Step 0 读它，逐条跑验证读数，未完成且无阻塞原因的直接在本轮做掉。
- 为什么不用文本：文本承诺已经在承接位放了 30 多天、零执行（10-10 缝合1 已证）。**能自动加载的只有 payload，能强制执行的只有脚本。** cron run 内不能改 payload，但可以改 workspace 里的文件——所以本轮退一步：用「一个必读的 json + 开场固定动作」替代，等主 session 有机会时再把它写进 payload。
- 判据：任何一个「下轮做 X」的承诺，必须同时写清三件事——X 的验证读数、X 的执行载体（脚本/文件/命令）、X 的失败后果。三缺一，下一轮必丢。

### 对 A2：验收锚定根因计数，不锚定症状

- 具体动作：任何「故障缓解/恢复」的结论，先跑三条根因读数——进程 `runs` 计数、最近退出码、关键版本号。三项里两项仍向坏的方向增长，判「未修复，只是换脸」。
- 今天的三条读数已跑：runs 10,630（增长中）/ exit 1（失败）/ Node v25.8.1（不满足）。结论：**未修复**。10-17 的「待逸凡按一下」今天仍然有效，且它是唯一能把这条 P0 关掉的动作。
- 判据：症状读数只能当「影响面」证据，不能当「修复」证据。这条与 10-11 缝合1（假自愈）、10-15 缝合2（恢复须自证归因）同族，今天补的是第三态。

### 对 A3：查库三步固定

`pragma table_info(<table>)` → 看列名 → 再写 SQL。省下的是两轮工具调用，而两轮工具调用在收尾轮就是一次 run error（今天 SM/BM/book 三个 job 全死在收尾工具链上）。

### 对 A4：先让自己在视野里，再谈能力

- 具体动作：每次 Dreaming 的摘要里带一条**只有 CEO 能给的东西**（跨主体对账、质量门禁、制度清单），不发「今日无事」。本周可交付的一件：把今天暴露的「可见层质检清单」写成脚本级 checklist，交给 supermind 的 pipeline 用——这是唯一能让 CEO 的存在变成别人流程一部分的方式。
- 判据：判断一个能力有没有被使用，不看它声明了什么，看过去 7 天它产出的东西有没有出现在别人的输入里。零次即路由缺口，修法是把产物嵌进别人的流程，不是再解释自己会什么。

### 对 A5：跨 agent 引用必须带时点

引用格式固定为「某人 X 时点读数：… ；本会话 Y 时点重读：…」。两者不一致时以重读为准，并在复盘里写出差值。

## 四、书写质量（C）

1. **标题过载。** 10-17 的标题塞了 7 个并列事项、200 多字，读者第一眼拿不到主判断。改为：标题只放「日期 + 一个主判断」，其余进正文第一段。今天的标题就是「症状迁移日」一件事。
2. **事实与判断混排。** 多处同一句里既有读数又有推论（「说明 X 已经失效」），读者无法分辨哪句可核对。改为：事实段只放「命令 + 数值 + 时间戳」，判断另起一段，开头写「判断：」。
3. **单位不统一。** 同一份文件里出现 115789ms / 115.8s / 1 分 55 秒三种写法。统一为「秒（原始 ms 括注）」，首次出现时给原始值。
4. **「第 N 天」缺依据。** 天数类断言容易漂移（10-17 自己就把 D2/D3 写混）。改为「自 X 起第 N 次（依据：SQL/文件 mtime）」。
5. **承接位过长。** 长期挂账 9 条并列，读者无法分辨哪条是今天要动的。改为每轮只留「1 条本轮要动的 + 分组的其余」，其余折叠成一行索引。

## 五、知识串联（D，核心）

### 缝合1（主·系统层·本日最高价值）：症状迁移是「假缓解」——验收必须锚定根因对象的计数

- **证据**：10-17 症状＝重启风暴（7 job 全灭、47 小时空窗）；10-18 实测 `interrupted by gateway restart` ＝ 0；但同一对象 `openclaw.update.once` 的 runs 6,410 → 10,630（+4,220 / 22.8h，约 19 秒一轮）、日志 18.3MB → 29.5MB、exit code 恒 1、Node 版本未变。supermind 10-18 A1 独立同向。
- **关联**：10-11 缝合1（假自愈：缺陷消失≠修复）＋ 10-15 缝合2（恢复必须自证归因）＋ 10-17 缝合1（三层隐身：告警同源/阈值吞单次/missing 不成态）。
- **新认知**：假家族第六态——**假缓解**。旧症状消失、根因计数继续增长。它比假自愈更危险，因为「症状消失」本身是强好转信号，而且常常由无关巧合造成（今天每次更新都死在 npm 阶段，走不到重启）。
- **判据**：任何「缓解/恢复」结论，先读根因对象自身的三条计数（进程 runs、退出码、关键版本）。两项仍向坏的方向增长 = 未修复，只是换脸。症状读数只作影响面证据。
- **管理同构**：客户投诉从 10 件降到 2 件，先问「是同一批问题少了，还是投诉渠道被堵了/被客服私下消化了」。渠道没变、根因没动，数字下降只是换了表现。

### 缝合2（元层·告警机制）：告警阈值的两个反向错误——该设的没设，该设 1 的设成 3

- **证据**：`tea-daily-report` 的 `failure_alert_after = None`，连续 3 次 error 零告警，而它是全生态唯一有外部读者（客户/团队）的日报；8 个 dreaming job 设了 `after: 3`，而单次失败的代价是「一整天记忆蒸发」。
- **关联**：10-17 缝合1②（阈值吞单次）＋ 10-12 缝合2（授权链落地）。
- **新认知**：阈值应绑「单次失败的不可恢复代价」，不绑「失败次数」。代价 ≥ 一个业务周期 → `after=1`；代价可累积但事后可补 → `after≥3`。
- **判据**：上线任何告警前先填一句「这一次失败，多久之后无法补回」。答「一个周期」就是 1；答不出就是没想清楚，先别设 3。
- **管理同构**：不是「连续三次迟到才谈话」，而是「错过一次就补不回来的岗位，一次就要报」。用统一的「三次」去管所有事，等于把最贵的那类失败降级成噪声。

### 缝合3（机制层·新形态）：人肉兜底固化——补发成为常规动作后，缺陷从账面消失

- **证据**：茶饮日报今日 11:00 error（802,657ms / Process: sharp-harbor failed / not-delivered），文件 11:18 在盘，人工重抓 → 重写 → 分 3 条补发；同型第 6 次（8/28、8/31、9/3、9/6、9/12、9/14、9/19、10-18）。自动链路 0 分，业务连续性 100%。
- **关联**：09-19 缝合（绿＝期望存活长度）＋ 10-11 缝合1（假自愈）＋ 守卫二十一（无消费者即停例行）。
- **新认知**：人工兜底会把「故障率」改写成「故障次数」——前者是系统指标，后者只是运维日志。一旦兜底固化，故障永远进不了修复队列，因为没有人被它伤到。
- **判据**：同一机制的人工补发/手动重跑 ≥3 次，必须同轮开一张代码层修复单（写清 owner、触发点、验证方式）；开不出就视为已接受该缺陷，从「故障」降级为「流程」，并在报告里明写「已接受」。
- **管理同构**：能人加班补流程漏洞，洞会一直在，因为账面上没有洞。要治的不是加班，是让洞重新可见——补发次数单独计数、单独公示。

### 缝合4（次·记录完整性）：按自然日划窗口，跨零点交付会掉进两份记录的缝里

- **证据**：supermind A3——PITAKA 的实质工作（34 个内容文件、80,105 字符、QA 11/11、392KB docx）落在 10-18 00:01–00:10；10-17 复盘写于 23:48（早于该段）；10-18 memory 首条是 06:32。这段工作在两份记录里都不存在，只存在于 run 时间戳与文件 mtime。
- **关联**：10-17 缝合1③（missing 不成态）＋ 守卫AM（判交互读真源）＋ 10-12 缝合1（派生目录不能当真空缺证据）。
- **新认知**：复盘窗口应按「业务单元」闭环，不按自然日切。跨零点交付归「完成日」，并在起始日复盘补一行指针（双向各记一条，成本一行字）。
- **判据**：任何跨零点的连续工作，检查两侧记录是否至少一侧完整覆盖；两侧都缺＝记录黑洞，且它不会报错——只会在某天有人问「这活谁干的、什么时候干的」时暴露。
- **管理同构**：跨班次交接最容易丢，不是谁不负责，是两班的记录本都不覆盖那一小时。

### 缝合5（商业层·乙方视角）：交付的可见层优先于内容层——一次格式事故能否定 8 万字

- **证据**：PITAKA 报告 34 文件 / 80,105 字符 / QA 11/11 全过，客户第一轮反馈是「该做表格的地方没做成表格」。实测 2 处 Markdown 管道表退化（5 行 + 21 行，共 30 个竖线段落），根因 `typeset.py` 只认 `|---`，带空格的 `| --- |` 漏判；修复后表格 10→12、残留竖线 0、非管道段落 489 段逐段一致。
- **关联**：10-09 缝合4（资产科目 vs 消耗科目）＋ 10-13 缝合4（联名资产栏）＋ 10-10 缝合3（复用性光谱）。这里补的是「交付工程化」这一层。
- **新认知**：客户验收顺序是 **可见层（表格/封面/页码/图）→ 结构层（章节/逻辑）→ 内容层（数据/论证）**。可见层在第一秒被看见，修复成本最低、信任损失最大。内容 QA 全过不保护可见层。
- **判据**：交付前先跑「可见层质检」清单（表格是否真表格、图表是否渲染、页码目录、字号统一、竖线残留），排在内容 QA 之前；任何格式类返工 ≥1 次，就把该检查编译进脚本 + 加用例，不进人脑。
- **乙方含义**：排版工程化（typeset 脚本 + 正则用例 + 就地修复工具）是可复用资产，属交付基础设施，应按资产计价，不是美工工时。

### 缝合6（组织层·曼拾自应用）：激励走到第三层，考的不是金额，是控制权与退出

- **证据**：今日 CFO 12:29–12:41 处理《合伙协议》模板，用途是为员工期权激励搭有限合伙持股平台（40 条修订 + 修订标记稿）。接 10-08 缝合3（建组织制度实做期：招人→建带宽→接激励）＋ 10-12 缝合3/4（绩效纪律线 + 奖金激励线 + 计提基数决定行为方向）。

- **曼拾含义**：这一层已超出「分钱」，进入治理结构。建议单建一份「股权/合伙决策清单」，把不可逆条款（回购价、成熟期、投票权、竞业）单列，任何一条改动都要逸凡本人确认。

### 缝合7（次·管理层·CEO 自应用）：路由由「最近可见产出」驱动，不由「能力匹配」驱动
