## B. 规避方案

1. **容量类机制上线必须双实测（守卫 AV）**：同时给出「当期可释放量」与「当期增量」，可释放量 < 增量即判无效，不得用阈值、天数、滚动周期这些参数本身充当证明。
2. **规则与 prompt 冲突时，冲突本身就是缺陷**：写在记忆里的顺序与写在 payload 里的顺序不一致，被执行的一定是 payload。发现冲突当轮转成一条可执行的 payload 修改待办，并标明这是根因而非个人失误。
3. **自测必须与真实路径隔离**：`--self-test` 只允许写临时目录，且必须做内容级断言，存在性断言不算通过。
4. **诊断层告警进收尾输出**：`lastDiagnostics` 是唯一没人读的失败通道，已固定为 closeout 第 7 步。
5. **相对路径的 git 检查在仓库根跑**（见 A5）。

新增 **守卫 AV**（写入即为生效）：凡建立滚动 / 容量 / 自动回落类机制，上线当轮必须测两个数 —— 当期实际可释放量与当期实际增量；前者小于后者即判该机制无效，需当轮补梯子或改策略，不得以参数设置当作有效性证明。依据：A1（tier2 实测 1,389 B vs 余量 8,727 B，10/19 的稳态假设被推翻）。
