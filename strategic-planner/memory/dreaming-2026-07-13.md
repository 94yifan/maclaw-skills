## A. 执行错误

**1.【未修复】SP Dreaming Cron failureAlert 仍未配置——第三次说"这次做完就配置"**

07-05标记为P0 → 07-11再次标记为"本次完成后执行" → 07-12再次标记 → 今天检查发现仍未配置。这不是一个认知问题，这是一个**系统性的"识别≠修复"执行鸿沟**。每次Dreaming都在说"这次做了"，但每次Dreaming结束程序就退出了，没有留下任何自动执行的机制来确保修复落地。

根因分析：failureAlert配置需要调用`cron update`以patch的方式给job添加failureAlert字段。这条命令在Dreaming结束时没有人去手动执行。Dreaming报告写得再详细，也只是文字，不是自动化的触发行为。

**2.【多个分身cron同时失败】dreaming-social-crawler（error, 13m前）/ dreaming-brain-mining（error, 9m前）/ dreaming-omni（error, 24h前）**

三个分身的dreaming cron都在今晚失败了。上周（07-05分析）SP的cron连续21天超时，本周换到了其他分身上。模式是相同的——22:00时段的模型调用超时。因为所有分身共享同一API提供商（deepseek/deepseek-v4-flash），22:00是系统负载高峰，模型响应变慢，300秒的timeout不够用。

## B. 规避方案

**1. P0：从"报告里说修复"变成"自动执行修复"**

failureAlert已经连续4次Dreaming说"本次执行"但从未落地。根因是没有把修复变成自动化动作。方案：

在Dreaming报告的末尾加入固定的自动执行块——check if failureAlert is set on this cron, if not, set it directly via `cron update`。不能只写成文字，必须让exec或cron工具自动执行这个配置。

从现在开始，本报告末尾执行以下动作：
- 获取当前cron配置，检查是否有failureAlert
- 如果没有，执行cron update添加 failureAlert（连续3次失败→发逸凡飞书）

**2. 22:00时段系统性超时方案**

所有22:00运行的分身cron共享deepseek/deepseek-v4-flash模型在高峰期的不稳定性。方案：
- 所有22:00 dreaming cron配置fallback模型（如deepseek-chat或最小模型）
- 或者所有cron增加timeout到600秒
- 高优先级的dreaming（如SP）考虑迁移到23:00错峰运行

**3. Supermind的Pro使用可见性修复**

逸凡通过Token消耗判断模型使用，spawn子任务对她是不可见的。以后逸凡要求Pro时，直接在main session切换模型写报告，或者确保子任务的Pro调用在main session有可见记录。与supermind同步此规则。

**4. 数据采集只验证过一次不能算确认**

Supermind今天发现顽皮天猫数据远超预期——之前报告的评估是"缺乏品牌存在感"，实际有30+付款SKU。这说明之前的数据采集方法论有缺口：只看品牌声量（微博/抖音）而不看渠道店铺数据，会严重低估一些品牌的真实体量。以后做品牌摸底时，必须先做店铺数据扫描（天猫/京东旗舰店），不能只看营销声量。

### 串联一：顽皮天猫被低估 × 比乐「制造90分品牌40分」→ "品类纵深"是"品牌弱"的前提修正

**新发现**（Supermind今天）：顽皮（中宠旗下品牌）在天猫有30+个付款SKU，回头客6万，遍布猫粮/狗粮/零食/罐头/磨牙棒全品类。这个渠道表现与比乐完全不同——比乐靠单一爆款（鸭肉梨）打在热销榜，顽皮靠品类宽度做复购。

**已有连接**（07-12 Dreaming）：比乐"制造90分品牌40分"——有爆品没有爆品牌，品牌资产主要存在于购买漏斗。

**新串联判断**：
"品牌弱"需要进一步分解。比乐的"弱"是」品牌认知弱（搜索漏斗），但产品力强（购买漏斗中有指名购买），顽皮的"弱"才是真正的存在感弱——品牌声量和消费者品牌记忆都弱，但渠道运营和产品矩阵纵深扎实。两者的"弱"不是一个层面的弱。

→ 给曼拾做客户诊断时的补充维度：品牌弱 = 用户层弱（搜索/认知/口碑）/ 渠道层弱（货架占有率/复购）/ 产品层弱（SKU矩阵/品类纵深）。三个维度的弱需要三种完全不同的策略方案。

### 串联三：22:00时段多分身cron集体故障 × 07-11/12系统监控盲区分析 → 高峰时段模型可用性成为系统最大风险

**已有连接**（07-11/12）：SP dreaming cron 19天连续超时 → cron稳定性不可靠 → 需要failureAlert。
