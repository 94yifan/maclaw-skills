# alice-agent-methodology

## 元信息

- **skill name**: alice-agent-methodology
- **source**: Alice 工程方法论（https://alice.miyang.cn/methodology/）by 洛小山
- **scope**: AI Agent 工程的完整方法论体系，从架构哲学到落地清单
- **适用场景**: 设计新 Agent、评估现有 Agent 架构、做技术决策、排查问题根因

---

## 核心洞察（最重要的三条）

**洞察一：状态管理是 Agent 产品的核心复杂度，不是模型能力。**
在同一个框架上，强模型（无上下文管理）任务成功率约 40%；弱模型（精心设计的上下文压缩+记忆注入+工具结果截断）成功率约 65%。换更好的模型可以让 65% 变成 85%，但工程资源优先投入状态管理的回报率，远高于投入模型选择和 Prompt 调优。

**洞察二：System Prompt 是宪法，不是便签纸。**
KV Cache 机制要求 System Prompt 前缀在多次调用间逐字节一致才能命中缓存、降费用。把时间戳、动态上下文放在 System Prompt 开头，每次变化都导致全量重新计算。正确做法：System Prompt 只写几乎不变的基础信息，时间戳和动态内容追加到 User Prompt 末尾。

**洞察三：工具是声明式契约，不只是函数。**
框架需要知道的远不止「函数接收什么参数、返回什么」，还要知道：这个工具能否并发执行？是否需要权限确认？是只读操作吗？把元数据和执行逻辑一起声明，调度器、权限系统、并发管理器才能做出正确的自动决策。

## 五大设计哲学

### P1. 接口长寿（Interface Longevity）
实现可以丢弃，接口必须稳定。最重要的两个接口：工具声明格式（名称/描述/输入格式/能力标签）和事件流类型（文字/工具开始/工具结束/错误/完成）。

违反代价：每次加新工具需要同时改三个地方，系统不会报错只是静默行为异常。

### P2. 状态优先（State First）
新功能设计第一步：先梳理状态图——这个功能涉及哪些状态？住在哪里？什么时候读？什么时候写？写了之后谁能看到？如果状态边界还没清，不写代码。

### P3. 结构隔离（Structure Isolation）
工具（AI 可见，影响对话历史）和内部服务（框架使用，AI 不可见）必须严格区分。判断标准：这个操作是用户视角有意义的动作吗？如果是，做工具；否则做服务，不暴露给 AI。

反面教训：把上下文压缩做成工具让 AI 自己决定何时压缩——模型会在不该压缩时压缩，压缩本身又产生新的工具调用记录导致上下文不减反增。

### P4. 可丢弃组件（Disposable Components）
每个组件必须有降级路径：KV 服务挂了不崩溃只是召回质量下降；向量数据库挂了不崩溃只是降质处理。降级是质量下降，不是功能消失。

反面教训：向量检索结果直接拼接进 System Prompt，向量数据库崩导致整个 Agent 循环无法启动。修复：包一层 try-catch，失败返回空数组。

### P5. 可观测性（Observability）
每个关键决策带 reason 字段，每次 LLM 调用记录完整 prompt 和 response，每次工具执行记录触发原因。这样出问题靠证据排查，不靠猜测。

## Agent 循环设计要点

### 终止条件（缺一不可）
- LLM 没有发起工具调用（正常完成）
- 达到最大迭代次数（防无限循环）
- 接收到用户取消信号
- 发生不可恢复错误

### 消息整形两件事
1. **修复孤立的工具调用**：上一轮有工具调用没有对应执行结果（中断产生），注入合成错误结果，防止模型格式错误
2. **注入动态内容**：把当前日期、权限拒绝摘要追加到 System Prompt 末尾（不放在开头，保护 KV Cache）

### 写入口消息
有工具调用时，丢弃伴随的文字内容，只保留工具调用。这条是 Alice 最反直觉的设计之一。

### 循环出口选事件流
生成器模式（yield）优于回调/Promise。好处：消费者控制节奏，背压自然形成；取消干净，关闭生成器后整条调用链都收到停止信号。

## 工具系统核心清单

### 四种流派
| 流派 | 代表 | 优势 | 劣势 |
|---|---|---|---|
| JSON Schema 声明流 | OpenAI Function Calling | 标准化程度高 | 不声明并发安全性/权限需求 |
| 函数装饰器流 | LangChain/AutoGen | 开发效率高 | 多工具并行只有串行/全并行两个选项 |
| 任务委托流 | CrewAI/MetaGPT | 多 Agent 场景清晰 | 抽象层次太高，灵活组合时障碍 |
| 声明式契约流 | Alice | 元数据完整 | 工具注册复杂度高 |

### 必须声明的元数据维度
- **权限需求**：读文件不需确认；写文件需要；命令执行高风险
- **只读性**：决定计划模式下是否真正执行
- **并发安全**：能否与其他工具并行执行
- **加载层级**：核心层（常驻）/ 能力层（按需）/ 扩展层（MCP，低频）

### 先读后写校验（血泪教训）
没有这条校验时：模型会基于幻觉编辑文件，覆盖用户真实内容。校验逻辑：写入工具检查当前会话上下文是否包含目标文件的读取记录，没有则拒绝执行并返回错误消息。

**核心原则：不要信任模型的记忆，只信任工具返回的事实。**

### 工具数量临界点
超过约 30 个工具后，全量注入导致选择准确率急剧下降。解决方案：分层注入（核心层/能力层/扩展层）。

### 并发调度
按并发安全属性分批：连续并发安全的工具并行执行，其余串行。不要全部并行（竞态），不要全部串行（性能灾难）。

## 上下文压缩：分层策略

### 消息价值密度差异
- 用户第一条需求描述：价值极高，整个任务的锚点
- 中间大量探索性操作：价值主要体现在最终结果
- 工具执行日志：价值低，可大幅压缩

### 四层递进压缩（从轻到重）
1. **轻量裁剪**：删除最早一批工具调用对，零 API 成本
2. **本地替换**：重复调用替换为说明文本，零 API 成本
3. **摘要压缩**：LLM 摘要 + 保留最近消息，中等成本
4. **全量压缩**：全量 LLM 压缩为结构化摘要，最高成本

触发顺序：轻量裁剪 → 本地替换 → 摘要压缩 → 全量兜底

### 并发安全：防压缩递归
多个压缩任务同时触发会互相覆盖。解法：压缩任务携带来源标记，循环检测到该标记后跳过。

### 记忆写入时序
**记忆写入必须在对话结束后统一处理**，不能在对话进行中写入。如果写了，下一轮检索会把刚生成的内容当历史记忆召回，产生信息自我强化循环。

## 多 Agent 协作三模式

### 父子模式（Subagent）
父 Agent 创建子 Agent，给隔离上下文，子 Agent 返回结果摘要。适用：任务边界清晰，数量事先可知。**只读任务可并行；写任务需串行。**

### Coordinator 模式
专门协调者负责任务分解和结果综合。协调者原则：先并行研究再行动，读写分离，新 Worker 独立验证，不委托理解。

### Swarm 模式
去中心化，多 Peer 共享任务队列，各自领取。核心工程问题：多个 Peer 同时轮询时，如何保证任务只被一个领取？解法：原子性领取（查看+标记合并为不可分割操作）。

### 子 Agent 隔离机制
- **进程隔离**：独立线程或进程
- **上下文隔离**：不与父 Agent 共享上下文
- **工具隔离**：工具集是父 Agent 的受限子集
- **降级机制**：独立线程不可用 → 降级到主线程

### 记忆隔离
子 Agent 输出不进用户记忆。子 Agent 对话是内部工作流，不是用户表达。来源是「系统为用户搜索了什么」，不是「用户说了什么」。

### 角色系统
每个子 Agent 有独立人设：系统提示不同 / 默认工具集不同 / 并发性不同。人设必须独立，否则专业约束和主 Agent 情感性人设混在一起两方面都做不好。

## 权限系统：五种模式

| 模式 | 行为 | 适用 |
|---|---|---|
| 只读规划 | 所有工具读类放行，写操作全部阻断 | 不确定任务，先看计划 |
| 默认模式 | 高风险确认，低风险放行 | 日常使用 |
| 自动编辑模式 | 文件编辑自动，命令仍需确认 | 代码开发 |
| 智能自动 | AI 分类器判断，自动处理低风险 | 信任度高的重复任务 |
| 完全绕过 | 无任何拦截 | CI/CD 自动化 |

### AI 分类器（最有争议）
用轻量 LLM 判断操作是否安全。**两种错误代价不对称**：误判高风险（把安全判危险）代价是任务中断；漏判高风险（把危险判安全）代价是灾难性的。必须偏向保守，宁多拦不漏放。

### 拒绝追踪
每次操作被拒后维护本次会话拒绝记录，注入系统消息防止 AI 反复碰壁。

### 渠道安全白名单
不是所有渠道都允许触发工具调用。默认：私聊可触发，群聊不可。外部渠道（微信等）的消息和桌面端直接对话信任等级完全不同。

## MCP 协议：边界与取舍

### MCP 解决了什么
把 Agent 和外部服务的关系从点对点硬连接变成总线模型。Agent 只需知道 MCP Server 提供了哪些工具，调用协议统一。

### MCP 没解决什么
- 工具质量问题（描述模糊、报错空字符串）
- 发现问题（没有中心化注册中心）
- 安全审计（无沙箱机制）

### 自建 vs MCP 取舍
| 维度 | 倾向自建 | 倾向 MCP |
|---|---|---|
| 核心程度 | 核心能力（文件/Shell） | 可选增强（SaaS 集成） |
| 安全敏感度 | 高 | 中低 |
| 维护成本 | 低（接口稳定） | 高（外部 API 经常变） |

经验法则：**适配外部 API 变化的做成 MCP；优化与 Agent 循环配合的做成内置。**

### 懒连接
连接阶段只保存配置，不建立连接，首次使用该 Server 工具时才连接。连接失败不影响 Agent 启动，只影响该 Server 工具不可用。

## Skill 系统：让用户定制 AI 行为

### Skill vs 工具 vs System Prompt
- **工具**：原子能力，代码实现，开发者创建
- **Skill**：操作手册，Markdown 文件，用户可写，按需激活
- **System Prompt 指令**：全局生效，不区分场景

### Skill 元数据关键维度
- **触发条件**：正向条件 + **反向排除**（反向排除常被忽视但价值极高）
- **工具白名单**：最小权限原则，Skill 激活时只暴露白名单内工具
- **主动性控制**：是否允许 AI 主动激活（默认开启），关闭时只能被显式调用

### Skill 自动改进
每次对话使用 Skill 后异步分析效果，检测到改进点则触发写入流程：
- 用户确认门控（不自动生效）
- 版本备份 + 回滚
- 改进幅度约束（小幅增量，不大范围重写）

### 四种退化风险
1. 过度特化（特殊场景改进后在常见场景变差）
2. 语义漂移（多轮后核心意图被稀释）
3. 指令膨胀（只增不减）
4. 反馈循环偏差（只在表现差时收到反馈）

## 自进化：信任边界设计

### 分层权限（从轻到重）
1. **人格反思**：只改偏好区域，低频，风险可控
2. **配置热更新**：接收服务端配置变更
3. **代码级进化**：生成 Widget 和自定义页面，最高风险

越重越需要严格的安全管控。同一套「可修改自己」的权限无法覆盖所有场景。

### 进化可撤销
执行操作前快照文件内容并推入撤销栈。撤销机制持久化到磁盘，重启后可继续撤销。**可撤销让用户敢于尝试，试错成本接近零。**

### 根本原则
AI 的自主性永远服从于用户可控性。进化提议不直接执行，只提出提案；执行必须用户确认；所有修改可撤销。

## 模型路由：多模型策略

### 不只绑一家的原因
- 可用性（任何一家都会宕机）
- 成本（不同场景对模型能力要求差异大）
- 地域（国内用户用 Qwen/Doubao 延迟最低）

### Alice 方案：用户自选 + 场景默认
用户选主对话模型（用户有明确偏好），系统为不同内部场景预设默认（用户不感知，系统替用户选最优）。

| 场景 | 需求 | 模型策略 |
|---|---|---|
| 主对话 | 最高质量 | 最好的可用模型 |
| 记忆提取 | 够用就行，大量调用 | 低价模型 |
| 权限分类 | 低延迟简单判断 | 小快模型 |
| 上下文压缩 | 长文本理解 | 长上下文模型 |

### 流式超时保护
连接建立但中途停止时：断开并重试（同一模型同一消息，获得新连接）。连续超时才向用户报错建议换模型。

### 重试退避
选指数退避 + 随机抖动，避免多客户端重试同步。

## 安全体系

### 桌面 Agent 的特殊性
Web Agent 运行在云端沙箱，桌面 Agent 有 Electron 进程全部权限：读写任意文件、执行任意 shell、发起任意网络请求。安全威胁不是学术假设。

### 零知识加密
API Key 加密存储，即使应用数据文件被完整窃取也无法解密。代价：**忘记密码永久丢失，没有后门。**

### 三层安全
1. **静态安全层**：数据保护（加密存储、敏感字段隔离）
2. **动态安全层**：行为控制（权限分级、工具过滤）
3. **渠道安全层**：外部输入审查（渠道级/工具级/用户级白名单）

## 可观测性

### Agent 可观测性的特殊挑战
- 执行非线性（图状/环状，不是树状）
- 因果链长且隐蔽
- 归因跨越多个层级
- 时间跨度大（一次任务可能几分钟）

### 调用来源字段（Agent 可观测性最重要的字段）
每次 LLM 调用记录来源（主对话/压缩/记忆提取/分类器/子 Agent……）。有了这个字段，可以做成本归因、性能诊断、行为异常检测。

### 等待时间和执行时间分离
如果不区分「等用户确认」和「系统执行」，日志里工具执行看起来会花很长时间（实际上大部分是在等用户点击）。

## Prompt 工程核心原则

### KV Cache 优化
**把几乎不变的基础信息放 System Prompt 前缀（稳定缓存）；所有动态内容（时间戳、权限拒绝摘要、压缩记录）追加到 User Prompt 末尾。**

### 工具描述四要素
1. **是什么**：一句话功能，避免模糊动词，用具体动词
2. **什么时候用**：触发条件要具体
3. **什么时候不用**：明确排除场景（这条经常被忽视但价值可能最大）
4. **输出说明**：告诉模型会拿到什么格式

### 提示词分层注入
| 层级 | 内容 | 变化频率 |
|---|---|---|
| 第一层 | 人格定义 | 极低 |
| 第二层 | 能力边界（工具集） | 低 |
| 第三层 | 上下文注入（记忆/画像/Skills） | 中 |
| 第四层 | 动态追加（时间/拒绝记录） | 高 |

### 调优准则
- 具体优于抽象
- 排除优于包含
- 示例优于规则
- 靠前内容比靠后更容易被遵循
- 多模块拼接时避免自相矛盾

## 十二个工程范式

1. **声明式契约优于函数**：元数据让调度器、权限系统、并发系统能自动做正确决策
2. **事件流作为系统边界**：核心逻辑和消费层解耦，生成器模式天然背压可控
3. **分层压缩策略**：不同触发阈值对应不同成本的策略，从廉价到昂贵依次触发
4. **互斥守卫防止递归副作用**：所有被动触发机制必须有防递归标记
5. **最小权限的结构化实现**：「用户同意一次」≠「永远允许」，是两个不同层级
6. **懒加载防止启动雪崩**：只在真正需要时才建立连接
7. **可撤销的不可逆操作**：快照在操作之前，撤销历史持久化到磁盘
8. **细化的可观测性**：记录对诊断有价值的结构化信息，而非记录一切
9. **读写分离的并发安全**：只读并行，写串行或加锁
10. **分层记忆对应分层生命周期**：内存/项目文件/向量库/SQL，各有最优用途
11. **接口稳定，实现可丢弃**：接口不变时实现随时可替换
12. **防呆优于依赖正确性**：框架捕获和纠正概率性行为的偏差，而不是假设 AI 总做对

## 架构决策清单

### B1. 状态管理
- 这个功能涉及哪些状态？
- 生命周期是什么（会话级/项目级/永久）？
- 住在哪里（内存/文件/数据库/向量库）？
- 谁能读？谁负责写？并发读写安全吗？

### B2. 工具 vs 服务
「如果 AI 主动触发这个功能，是用户期望的行为吗？」
- 是 → 做成工具
- 否 → 做成内部服务，不暴露给 AI

### B3. 工具设计检查
- 名称唯一有意义
- description 含四要素（是什么/何时用/何时不用/返回什么）
- 只读属性正确标注
- 并发安全属性正确标注
- 破坏性属性正确标注
- 大结果有大小上限？超出时写文件？
- 子 Agent 是否应该能使用这个工具？

### B4. 并发安全
- 多实例同时写同一资源时，有无冲突？
- 读写操作是否分离？
- 定时任务/阈值触发是否有防递归守卫？

### B5. 降级路径
- 这个组件挂了，系统是否崩溃？
- 降质的具体表现是什么？
- 是否显式实现了降级 fallback？

### B6. 可观测性
- 关键操作是否有结构化日志？
- 决策是否携带 reason 字段？
- 现有日志能否定位根因？
