## 二、执行错误（A）

**错误 1（高）：昨天的症状描述被当成今天的行动依据。**
10-17 复盘写的是“24 秒一轮重启，正在持续打穿所有定时任务”。今天实读：重启中断零次。同一根因换了一副面孔，从重启风暴变成 CPU 与磁盘空转。如果我按昨天的描述去验收“升级 Node 之后重启是否消失”，今天本来就没有重启，验收会假通过。

**错误 2（高）：门禁与真实凭证字段名不一致，正确凭证会被拦。**
Gate 1 已升级到第三档（项目绑定 + 时效 + 确认人），但日期正则只认 `date:`。今日真实凭证写的是 `确认时间: 2026-10-17 23:55`。用 `gate1_reason` 跑真实凭证，返回“确认文件缺日期行”。今天没出事，只因为这一轮没从 step 2 重跑。这不是隐患，是已经存在的 false negative，只要下次重跑就会撞上，而人为了通过往往会改文件格式或者直接 touch，门又退回仪式。

**错误 3（中）：跨零点的工作在两份记录里都不存在。**
PITAKA 的实质工作量落在 10-18 00:01 至 00:10。10-17 的复盘写于 23:48，早于这段工作；10-18 的 memory 只有 06:32 一条表格修复。34 个文件、8 万字符、QA 全过、392KB 成品，这段工作在复盘体系里没有归属，只存在于 run 时间戳与文件 mtime 里。

**错误 4（中）：06:32 的验证记录强于实际验证范围。**
记录写“兼容 `| --- |`、`|:--:|`、`|---:|` 三例单测通过”。本轮实跑：`|:--:|:--:|` 不匹配，因为正则写的是 `-{3,}`，两个短横不够长。另两例确实通过。记录没撒谎，是测试只覆盖了作者顺手写的三短横写法。

**错误 5（小，本轮自我纠错）：我第一次构造的反例本身无效。**
验证时我把 `|---:||---:|` 当成合法表格输入，它其实是双管道，本身就不是合法分隔行，据此差点得出“`|---:|` 也不兼容”的错误结论。反例无效会把用例错误误判成代码缺陷。

## 三、规避方案（B，全部已在本次会话落地并验证）

**针对错误 1：症状必须写成读数加时间戳，不写“正在持续”。**

**针对错误 2：门禁字段名以真实凭证为准，并做攻击测试。**
已改：抽出 `gate1_reason(confirm_path, project_name)`，日期字段兼容 `date / 确认时间 / 日期`，确认人兼容 `confirmed_by / 确认人`。六例实测：

每个 session 收尾记一条，含起止时间与产物清单，日期只作索引。dreaming 写文件前先比对自己文件 mtime 与今日产物 mtime，产物晚于本文档，必须回补一段。

## 五、知识串联（D，核心）

**缝合 1（主，归因层）：症状迁移会被误读成问题解决。**
10-17 缝合1 判失败形态第四次迁移为自更新循环，并给出处置（升级 Node 或关闭自动更新）。今天同一系统换了症状：重启风暴停了，CPU 与磁盘在烧。两天的读数都真，结论都不该互相引用。串联后得到：症状是根因在当前环境下的显影，显影会变，根因不会自己变。判据：症状必须带读数与时间戳，处置前重算当日症状。

**缝合 2（主，门禁层）：第三档门禁最容易死在字段名上。**
守卫十三把门禁分三档，10-17 缝合3 说门禁有两层通过条件（代码与人手）。今天补上第三个死法：代码写对了档位，但字段名与真实凭证不一致，门禁对正确输入报错。这类 false negative 比漏放更危险，因为它会逼着人改凭证格式去迁就代码，最后凭证变成给机器看的文件，不再是给人看的确认记录。判据：门禁用真实凭证跑，不用自己写的示例模板。

**缝合 3（主，记录层）：日界不等于会话界。**
10-17 缝合2 立了“缺失是第三种终态”，讲的是系统产出缺失。今天是记录层的同构问题：工作没缺失，归属缺失。复盘按日历日归档，工作按会话推进，跨零点的后半段落在“昨天已经写完”和“今天还没开始记”的缝里。判据：按 session 记，日期只作索引。

**缝合 4（次，验证层）：单元测试覆盖的是作者的例子，不是宣称的支持集。**
守卫十七要求完成态自证，今天补一层：自证也要证明覆盖范围。写“兼容 N 种写法”就必须逐写法枚举。与此同型的是我今天构造出无效反例，说明验证方本身也要被验证。

**缝合 5（次，业务层）：深度报告的可信度由显式缺口数决定，不由图表数决定。**
接守卫十四（诚实比造假代价高时系统必然造假）与 10-15 的无数据合法终态。PITAKA 成品把缺口全部写在明面上，是正样本。判据：交付前数一遍显式标注为不可得的项，与图表数、表格数一起进 QA；0 项缺口的深度报告按未完成审。
