## B. 规避方案

**1. Dreaming cron 稳定性修复**

既然已经确认 deepseek/deepseek-v4-flash 在 cron 上下文可用，根因不是模型能力，而是 cron job 配置本身可能未指定模型，导致 fallback 到一个默认模型（可能是 minimax）。7/5 的 dreaming 写了"核查 cron 的 model 配置"但从未执行。

**方法**：每次 dreaming 开始时，如果发现与上次 dreaming 间隔超过 2 天，主动标记为"cron 有断点"并记录具体天数。断点超过 3 天则在报告末尾追加一段"cron 健康检查"，
记录异常间隔作为系统状态的可视化指标，不依赖 cron 自我修复。

**2. 记忆流失止损**

没有记忆就没有连续性的根本原因是 daily memory 写入的节奏没有建立。每次对话恢复上下文全靠 MEMORY.md 和文件系统——如果中间有大量未归类的信息，恢复成本极高。

**方法**：只要在 dreaming cron 中恢复上下文阅读时发现有超过 3 天的无记录空白区间，就补写入一条日期占位记录（"YYYY-MM-DD 无记录"）。这样至少能区分"这天没有产生数据"和"这天系统完全离线"。

**3. Excel 生成后的联动归档**

今天生成的樱桃地址和礼单 Excel 是宝贵的业务数据，但纯 Excel 文件在 memory 目录里很快会被忽略。应该生成一个补充说明的 memory 条目。
