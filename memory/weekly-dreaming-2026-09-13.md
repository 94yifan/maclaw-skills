## B. 本周学到的关键洞察

### 1. 失败几乎全部集中在"交付层"，这一周得到最强的一次验证

09-12 SC 日报 cron run 报 error，但报告 11:08 前已完整落盘——爬取与写作均成功，唯一失败点是交付（announce 被跳过）。近 50 次 run 中同型失败第 8 次（8/20、8/23、8/26、8/31、9/1、9/3、9/6、9/12），其中 8/26 与 9/12 失败点完全同款。

**这意味着什么**：系统的问题域已经从"能不能生产"迁移到"能不能送达"。5 月 MEMORY 里记录的 22 天 pipeline 断裂是生产层问题，现已被"subagent 自托管 cron + 生产端稳定"解决；剩下的第 8 次同型失败说明**交付层被反复证明是唯一未加固的环节**，而且这个结论跨分身重复出现（supermind 也缝了"投递盲区"）。

**对应动作**：待办清单里的 tea-daily-report payload 改造（删探索步骤、明确 message 发群、可选命令加 `|| true`）是这批失败的直接修复项，连续挂账未执行。

### 2. 手动补跑必须做"并集"，不是"覆盖"——差点漏掉当日最高互动

09-12 手动补跑时，若直接以补跑结果覆盖原结果，沪上阿姨与林里会被写成"0 条动态"（11:42 那轮被判超窗返回空）——当日最高互动（林里转发 14935）会被整条漏掉。做了 raw 并集后才补全。

**可复用规则**：重跑不等于覆盖。同一时间窗的两次抓取结果应取并集，尤其当失败原因是超时/超窗而非"无数据"时——超窗返回空与真的无动态在返回值上无法区分，只有并集能兜住。

### 3. 飞书审批的不可逆操作必须预判——已提交后无法补附件

09-11 竹篮礼盒单先提交、后补到发票，尝试补附件失败，最终走 `cancel + 重新创建`：新实例 BAE9DB8F，并去掉"发票后补"备注。同时确认 cancel 接口需 `user_id_type=open_id` + 传 open_id。

**可复用规则**：凡"必填但 API 未强校验"的字段（附件、关联审批、account 类型收款账户），提交前的判断是**一次性窗口**——宁可等发票到齐再提（白茶单就是这么做的），也不要先提后补。已提交只能撤销重提，产生废单和审批噪音。

### 4. "待逸凡执行"清单连续 12 天不清零——授权型阻塞是结构性的，不是执行惰性

09-12 的待办清单标注"连续第 12 天，命令可直接复制"：crontab 删污染项、SC dreaming cron 调模型/超时、CFO cron 调超时 + failureAlert、tea-daily-report payload 改造、飞书云文档存档恢复。

**根因判断**：这些全部需要 terminal/root 或 subagent 配置权限，main 无执行权。所以清单挂在记忆里的净效果为零——这与上周复盘的结论互相印证：**待办挂在事件驱动架构里永远不会被推进，只有写进固定动作或显式 cron 才能闭环**。区别是：上周的待办靠"主动核查"终结了 1 项；本周这批属于**权限不在 main 手里**，核查只能确认"仍未执行"，无法推进。

**对应改进**：这类清单不应每周重复罗列同一条，而应合并为一条"待逸凡授权执行"的固定清单，标注首次提出日期与累计天数，每周只更新状态，避免每周复写同样的 5 行。

### 5. 隔离原则的落地方式已成型：main 做文件名/时间戳级巡检

本周巡检 8 个 subagent 只取文件名、时间戳、文件数量，不读内容。这个方式既能判断"有没有断档"，又不越界。上周首次尝试，本周已成为稳定做法。
