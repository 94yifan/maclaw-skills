## D. ★ 知识串联（今日核心）

**缝合1（主，元层）：「落盘前置」不是一条经验，是一条写入顺序——它必须被写成 run 的硬顺序，靠各主体自行收敛只能覆盖已收敛者。**
链：09-22 缝合1（尾部是不可见故障面）→ 09-23 缝合2（落盘前置同日被三主体独立收敛＝结构必然）→ 09-23 缝合4（记录负债第五态「已落盘未入账」）→ 守卫十七（完成态须自证）。
今日实证补齐同一链上的**三个失败等级**：① 产出未写（09-21 supermind 三轮全丢、09-24 全丢）② 写了但未入账（09-22 文件在盘未 commit/未索引）③ 落盘前置后保住数据但状态仍 error（CFO 9/23、9/24）。三主体（CFO/SC/SP）已收敛并实证有效，Supermind 未采纳 → 09-24 整轮归零。
判据：**「收敛度」证明它是结构必然（09-23 缝合2），但结构必然不会自动变成某人的动作。** 收敛度只说明该改，不说明改了；把保护写成 run 内的**第一个写动作**，才把「经验」升级为「顺序」。凡是「读完即生效」的假设，在超时场景下都不成立——读动作本身也在尾部。
客户用法：任何有交付时限的活动，把交付物的**生成**放到流程最前面，别放收尾；「事后补账」永远只能补到下一轮，补不回被截断的那一轮。

**缝合2（主，机制轨）：失败链必须分段部署保护——生成 / 交付 / 告警三段各有独立防线，缺一段则前段只保住内部资产，外部仍静默。**
链：09-22 缝合2（「已送」须渠道侧证据）→ 09-23 缝合2（落盘前置）→ CFO 9/25 A1（连败 7 次但 failureAlert 缺席）。
今日实证：CFO 落盘前置三次执行、两次在超时下保住数据 —— **生成段已设防**；但 run 状态仍记 error、`delivery_mode=none`、无 failureAlert —— **交付段与告警段全裸**。结果是：数据在，**但系统在失败这件事没有任何人知道**（唯一出口是次日自查）。
判据：一条失败链至少三段——生成（产出是否写出）、交付（产出是否送达对方）、告警（失败是否被知悉）。三段的保护措施不同、不能互替：落盘前置管生成，交付解耦（写文件即发）管交付，failureAlert 管告警。**只护生成段，等于只保住内部资产，对外仍是静默失败。** 客户用法：项目风险控制要分别覆盖「做得出来 / 交得出去 / 出事有人知道」，三段缺一即失守；只做备份不做告警，事故仍以「事后才发现」的方式发生。
