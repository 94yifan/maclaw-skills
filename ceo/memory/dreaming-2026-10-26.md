## D 知识串联（核心）

### 缝合1（主·治理层·本日最高价值）：待决项不是死在注意力，是死在权限边界——没有执行者的待决项会退化成每日复述

**证据链（三段全部实读）**：
1. SM 昨日待办、SM 今日状态块、BM 今日 B6，三处独立写「新增 `delivery.bestEffort` 是否开启——待逸凡一句话」，最早可追至 10-24。
2. 我今晚尝试执行，`cron update` 返回 `Cron tool is restricted to the current cron job`——restricted run 只允许删除自身。
3. 七个 dreaming 的 `session_target` 全部是 isolated，即全部在这个权限档位里。

**串联**：守卫二十一（无消费者的动作即停例行）→ 10-22 缝合1（修复半径由载体决定）→ 10-25 缝合1（委派同源失效）→ 今日权限实测。

**新认知**：一个待决项要能被决定，必须同时具备三件——**提出者、决策人、执行者**。缺执行者时，它不会报错，不会告警，只会每天以「待逸凡一句话」的形式被复述一次，读起来像在推进，实际上是守卫二十一说的零消费者动作。这解释了为什么同一个 ask 能连续挂 11 天而系统毫无异常：**它从没进入过任何一条可执行路径。**

**判据（写任何「待 X」前过一遍）**：①X 决定之后，谁执行？②那个执行者的会话有没有这个权限？③如果没有，这条应该写成「待 <有权限的会话> 执行：<具体命令>」而不是「待 X 决定」。三问答不出，这条不写。

**管理同构**：分公司提的采购申请走不进总部审批系统，就永远停在邮件里，且每周例会上都会「再提一次」——提的人很努力，系统里没有这条路径。客户侧同构：客户口头同意改上线时间，但没人有权改系统里的排期，于是排期永远不改，每周都对一次「已经说过了」。

**新认知**：规则有三种载体，效力严格递增——

|---|---|---|

**新认知**：一个 campaign 的报价必须三行分列，缺一行就在那一行上亏——

1. **广度层**：物料包 × 店数 + 配送 + 店员贴装工时（单位成本低、可复制）。
2. **深度层**：软装 + 施工 + **店员培训（动作脚本）+ 履约补贴**（单店成本高一个数量级）。
3. **时间层**：预热期是否落在授权期内；预存类是否含 breakage 与退款条款。

**判据**：客户说「做 150 家门店」，第一句问「几家要改造」，第二句问「预热什么时候开始」。两问答不出，报价必然在深度层或授权期上亏一次。

**曼拾用法**：报价模板加两列（层级 / 撤装与复原责任），并单列一行「预热内容授权费」——金额可以为零，但必须存在，因为**零和不存在在合同上是两件事**：写零是双方确认过的，不存在是事后吵的。
