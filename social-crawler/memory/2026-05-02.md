### 错误1：cron 触发仍然失败，但这次有"救火"机制了 ⭐

**现象：**
- 10:05 AM cron 触发，状态 `error`（CDP 9333 不可用）
- 12:09 有人手动运行了 `tea-crawler-manual.mjs`，成功爬取 19/19 品牌
- `/tmp/tea-report-2026-05-02.md` 生成（46,722 字节，1794 行）
- `social-crawler/memory/weibo_daily_2026-05-02.md` 存档完成

**根因：**
cron 触发失败 → CDP 9333 上午不可用（连续第3天：4月30日、5月1日、5月2日都是10:05 AM失败）。手动运行脚本是临时救火，不是系统正常运行。

**怎么修复（P0，明天就要做）：**
```
问题不是脚本本身，而是：
1. CDP 9333 上午不稳定是规律性的（yifan 的 Chrome 开机时间/remote debugging 启动时间不固定）
2. 脚本没有内置自动等待 + 重试机制
3. cron 触发 → 快速失败 → 没有重试 → 直接放弃

正确做法：
- cron 触发后，CDP 连接失败时等待 30 秒重试，最多重试 3 次
- 等待期间 Chrome 可能自己启动好（yifan 开机/解锁 Mac mini）
- 只有 3 次全失败才退出
```

**预防：**
内置 CDP 重试机制是唯一解。外部提前检查端口不可靠（时间差问题），必须脚本自己处理。

**怎么修复（明天必须实现）：**
```javascript
// 飞书发群函数（必须内置在脚本里）
async function sendFeishuReport(reportContent) {
  const hookUrl = '飞书群机器人 Webhook URL';  // 需要配置
  const today = new Date().toISOString().slice(0, 10);
  
  // 飞书单次消息最多4000字，分段发送
  const header = `📊 茶饮日报 ${today}\n\n`;
  const chunks = reportContent.match(/[\s\S]{1,3800}/g) || [];
  
  for (let i = 0; i < chunks.length; i++) {
    const text = i === 0 ? header + chunks[i] : chunks[i];
    await fetch(hookUrl, {
      method: 'POST',
      headers: {'Content-Type': 'application/json'},
      body: JSON.stringify({ msg_type: 'text', content: { text } })
    });
    if (i < chunks.length - 1) await new Promise(r => setTimeout(r, 1000));
  }
}
```
