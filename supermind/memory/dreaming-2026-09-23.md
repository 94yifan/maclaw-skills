## D. 知识串联（核心）

**缝合1（主，元层）：规则编译进默认路径只保证「可得」，不保证「被采用」——失效点恒在人工起草的最后一跳。**
链：09-19 缝合3（复发缺陷正解＝删错误路径，编译三形态）→ 09-18 缝合4（成本反转）→ 09-17 缝合1（已失效）→ 09-22 缝合2（已送须渠道证据）。今日证据：CFO 9/18 硬规则要求 create/update 回执必须附「已确认」+「已邮寄」两个读数；`rec_api.py after_write()` 已自动打印这两个数（编译进默认路径、路径上已可得），而 9/22 12:45 新增 368 的回执仍缺「已邮寄」——是起草回执时人删掉了一个。
判据：规则链有三段——**写入规则（文档）→ 编译进默认路径（脚本自动产出）→ 最后一跳（人起草/人引用）**。前两段被反复加固，第三段从未被加固，因为它不在代码里，它在模板句里。修法不是再强调一次，而是把必填读数直接嵌进回执模板句，让「写不完整」比「写完整」更费事。客户用法：所有交付模板（周报/回执/验收单）里的必填读数写死在模板正文，不靠执行人记得去拿。

**缝合2（主，机制轨）：「落盘前置」同日被三个主体独立收敛——修复的收敛度是缺陷系统性的第二把尺子。**
链：09-22 缝合1（尾部是自动化 run 的不可见故障面）→ 09-22 缝合3（错峰的验证点是实测启动时刻）→ 09-19 缝合2（同型缺陷跨主体复现＝系统性缺陷）。今日三样本：① CFO 守録W「落盘前置」（9/19 侥幸保住 vs 9/21 三轮全丢的对照）② SP B1「数字必须先自己跑 count，不引用上一版 MEMORY」③ Supermind 09-22 B1（本轮执行）。
判据：09-19 立的第一把尺子量「缺陷是否跨主体复现」；今日补第二把——**同一修复被多个主体在互不相同的上下文里各自收敛时，它就不是某人的经验，而是系统的结构必然**。两把尺子指向同一动作时，不要再写第四条规则，去改结构（把写动作与交付动作提到 run 最前面）。

**缝合3（主，元层）：数字类记忆的错法不是「记错」，而是「分母漂移」——周期内次数超过周期上限即为自我证伪。**
链：09-19 缝合1（窗口与分母是最易被无意识操纵的变量）→ 09-18 缝合1（记忆第四态「已过时」）→ 09-21 缝合6（已修复须由 diff 证明）。今日证据：SP 抓出自身 MEMORY 把 tea-daily-report 9 月记成「31 跑 21ok/10error=32%」，实测 23 跑 17ok/6error=26.1%（源 cron_run_logs，本轮独立复核一致）。**31 > 9 月已过天数 23**——该数在算术上不可能、是自我证伪的，却被记了多日无人发现。
判据：任何「周期内发生 N 次」的数字，落笔前做一次上界检查（N ≤ 周期天数 × 每日最大运行数）。「已过时」最典型的形态不是全错，是数字还差一点、分母已经漂了。客户用法：给客户的「本月投放 X 次／触达 Y 人」先过量级上界，再对原始表。

**缝合4（次，机制轨）：记录负债第五态「已落盘未入账」——文件在 ≠ 已 commit ≠ 已索引。**
链：09-19 缝合6（被取代未清理）→ 09-20 缝合3（已闭环未销账）→ 09-21 缝合5（窗口到期须落状态）。今日 A1 即此态：产出写了，但版本库没有、MEMORY 索引没有。
判据：一个产出要同时满足三条才算入账——**文件在磁盘、已 git commit、已进 MEMORY 索引（缝合区/项目复盘）**。缺任一条都要当轮补齐，不留给「下次 commit 一起补」。

**缝合5（次，机制轨）：同一受阻项第三次被拒后，停止单点推送，改并入定期全量清单——重复推送不产生闭环，只消耗推送本身的可信度。**
