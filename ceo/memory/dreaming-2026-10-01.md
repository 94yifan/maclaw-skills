## A. 执行错误

### A1（P0，舰队级，第 27 天+）：dreaming 全舰队 timeout=300s 未上调，今夜近乎覆盖全队

- 事实（本会话 sqlite 实证）：今夜 22:00–22:53，SC/CFO/SP/supermind/BM/book/CEO **七个 job 全部出现 300s 打满或工具失败**；唯一最终转 ok 的是 SC（第 3 次重试，297s）。`cron_jobs` 实读：`dreaming-*` 全部 `payload_timeout_seconds = 300`，`failure_alert_after` 全空。

### A2（P0，CEO 自身，今日最重发现）：「自指断言的观察边界」——run 无法观察自己的生命周期

- 事实（跨主体对照）：CFO 守卫AB（本日新增）——dreaming 运行时读 `cron_jobs.last_run_*` / `consecutive_errors`，读到的一定是**上一轮**结局；CFO 9/30 区块记 `consecutive_errors=12 / 连续 8 轮撞限`，实际窗口结束后为 `ok / 0`。book 规则16（本日新增）——run 能观察自己的产物（文件、commit），不能观察自己的生命周期是否被调度器超时终止，后者只存在于 cron 遥测。

## B. 规避方案（每条对应 A 项）

1. **自指断言以外层遥测为证（对应 A2，本会话已立缝合1）：** 凡对 run 自身生命周期的断言（未超时/未截断/已投递/正常结束），run 内结构性不可自证 → 必须以 cron 遥测（status/duration/diagnostics）为证，取不到写「待外部核」。CEO 自应用：本文件 A1/事实表中的 run 结局均来自 `cron_run_logs`，不写 run 内推导的完成态断言。
2. **落盘排序按「不可恢复性」（对应 A2 配套，缝合2）：** 先写不可恢复的（MEMORY.md），再写可补的（dreaming 文件）。本会话已按此顺序执行（MEMORY 先于本文件）。
3. **归属判定用 `git log -- <path>`（对应 A3，缝合3）：** 判定「已提交/已推送」必须看 author + 时间戳，不能只看 `git status`；关键产物当轮自行 commit，不依赖他者清扫。
4. **dreaming timeout 300→600 + failureAlert(after:3, announce)（对应 A1，仅主 session/逸凡）：** 并入下一次全量清单推送（本轮不单点重复推送）。
5. **SC header 三行（含覆盖行）写进 payload 模板首行（对应 A4）：** 字段不进生成侧模板，校验永远没有对象。
