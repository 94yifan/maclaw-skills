## B. 规避方案（根因层）

**B1 系统状态类记忆绑定对账源（对应 A1，今日最高优先级，新）。**
任何写入 MEMORY 的「系统状态」陈述（cron 清单/天数/job 存在与否/交付状态），落笔前必须在 `~/.openclaw/state/openclaw.sqlite`（`cron_jobs` / `cron_run_logs`）或真实源上复核，并写明复核时间与来源；无法复核的标「待验证」。范式：不写「Dreaming cron：12:00+22:00」，写「SP cron 仅 1 个 job（874aef37，2 22 * * *），sqlite 核实 09-18」。已同步进 SC 与 SP 两侧 MEMORY 纪律。

**B2 对账输出必须带二值判定（对应 A5）。**
「变了什么」只是中性的，必须补一句「这个变化是好是坏/是否需要动作」。CFO 已把它编译进 `audit.py` 的数据质量扫描（已确认但无收件信息 / 收件信息含换行），并实跑报出 4 条 + 12 条。

**B3 校验的性价比 = 真需动作比例，不是覆盖完整性（对应 A5 反面）。**
上线任何表级扫描前先跑一遍看命中数；命中里真需动作比例低于 20% 就不是校验，是噪声，这种扫描上线即失效。CFO 差点把「收件信息首段==名字」写成表级校验，实测命中 **90+ 条且 0 条需动作**；已把「为什么不查」写进脚本注释（反面资产：阻止的下一个错误比修掉的那个更贵）。

**B4 计数口径编译进默认路径，不写临时脚本（对应 A4）。**
约束写成可执行判据：**凡为一个数字写第二个脚本，先停下来问能不能加进 audit.py；能加就加。** 防它的唯一办法是把成本反过来，让「加进 audit.py」比「新写一个」更快。

**B5 实时写 MEMORY，不留到当晚（对应 A4/A6）。**
当天每完成一类动作就落一行到 MEMORY 当日区块。dreaming 是校订通道，不是主写入通道——9/17 已证明 dreaming 本身会失败且无人被告知。

**B6 payload 加「运行内工具禁令」+ cron failureAlert（对应 A2/A3/A6，需主 session）。**
三条硬约束写入 payload：写完立即输出正文并结束，不再发起工具调用；run 内禁止 cron get/update/remove；可选命令加 `|| true`。SC dreaming cron 改 model=deepseek-v4-pro + timeout 600；CFO cron 加 failureAlert（after:3, mode:announce）+ timeout 600。**这些是明确授权请求，不是待拍板。**

**B7 自查清单必须覆盖全部禁止项（对应 A7）。**
自查只扫三项就宣称「零违规」等于没查。每次自查按 SOUL 禁止项逐条过（引号/星号/破折号/填充词/emoji/corporate 废话六项）。

**B8 大文件重写三件套（对应 A8）。**
① 动之前先备份（`cp` 或确认 git 干净）；② 重写脚本必须在循环后显式接上尾部，并打印「新文件字节数」与「首末尾标志行是否都在」两项断言；③ 完成后比对字节数量级（差异 >20% 必须停下看原因）。判据：重写类脚本的输出验证不能只看「文件生成成功」，要看「该在的东西还在不在」。

## D. ★ 知识串联（核心环节）

**缝合点1（主，元层）：记忆的第四种状态「已过时」——曾经为真使它比「已失效」更难被发现（SC A6 × SP A1 同日独立暴露 × 守卫十七「已失效」× 守卫十六「脚本自定位」× 09-13 缝合1 决策点绑定）**
SC 的 MEMORY 写「日报无 cron、靠手动」，而 `cron_jobs` 表里 tea-daily-report 创建于 6/29、已跑 110 次；SP 的 MEMORY 写「Dreaming cron 12:00+22:00」，而 SP 名下只有 1 个 job。两处同日由两个 agent 各自用同一把尺子（sqlite 对账）发现，都已挂约 13 天、无校验点暴露。串联 09-17 缝合1 的「已失效」（文档声称已编译而脚本里没有）：记忆体系现有四态——**未编译 / 已编译 / 已失效 / 已过时**。已过时最阴，它曾经是真的，所以读起来最自然可信；而且「曾经为真」使它比已失效更难证伪（已失效可以 grep 脚本，已过时看不出破绽，只能靠对账源）。判据：凡记忆内容描述的是「随时间会变的系统状态」（job 是否存在、天数、清单、交付状态），写入时必须绑定对账源 + 复核时间；描述「不变的规则/认知」才可不带源。客户用法：交付物里的系统说明（客户后台配置、投放账户结构、排期表）不能靠记忆转述，每次引用都要回源核一次，否则描述与真实系统会静默分叉。

**缝合点2（主，机制轨）：对账的第五阶「变得对不对」——对账不带判定，读者读到第 20 条就麻木（CFO A5 × 09-13 缝合2 三阶 × 09-16 缝合2 四阶 × 09-15 缝合6 误报吃可信度）**
CFO 字段级对账忠实记录了序号 5「地址被清空、电话清空，但勾了复核」，但无判定，混在 28 条变化里过去了；直到加了数据质量扫描才浮出 4 条寄不出去的记录。对账阶位序列：有多少 → 差几个 → 少了谁 → 谁的哪个字段被改成什么 → **这个变化是好是坏/要不要动作**。前四阶解决「看得见」，第五阶解决「看得懂」。缺第五阶的后果已实证：最危险的一条（寄不出去）与 27 条良性变化同权重展示。客户用法：一切长期维护表的审计输出（客户库/达人库/礼单/排期）最后必须落到行动短句——N 条需处理，其中 X 条影响交付，已标出。

**缝合点3（主，机制轨）：校验的性价比 = 真需动作比例；坏的校验会污染同一条输出里的好校验（CFO B5 × 09-15 缝合6 误报吃掉可信度 × 09-14 缝合4 规则编译持续维护 × 09-17 缝合3 规则要回答正确长什么样）**
CFO 差点把「收件信息首段==名字」写成表级校验，实测命中 90+ 条、0 条需动作——上线即等于把一个真异常埋进 90 条噪声里。09-15 缝合6 讲误报消耗告警可信度，今日补出**量化判据与反面资产写法**：表级扫描上线前先算命中数，真需动作比例 <20% 即不上线（噪声 >5 条不做表级扫描）；把「为什么不查」写进代码注释，阻止未来的自己再加一条噪声扫描。判断方法：加校验前不是问「它能不能查」，是问「它查出来的东西里几条要人动手」。客户用法：客户侧风控/监测规则上线前先跑历史数据看误报率，误报高的规则宁可不上，否则它会拖垮同一条告警里真规则的可信度。

**缝合点4（次，机制轨）：临时脚本是理性选择，所以难防——防它只能靠成本反转（CFO A4/B6 × 09-12 缝合1 编译进路径 × 09-16 缝合4 编译是持续维护 × 守卫九 临时修复合并回源文件）**

**缝合点6（次，机制轨）：悬而未决的配置项，代价不是「一直没修」，而是「不知道它什么时候开始造成损失」——挂账收据在 29 天后到达（CFO A6 9/17 run error 实证 × 09-15 缝合4 系统债改尾动作 × 09-16 缝合3 触发点缺失）**
