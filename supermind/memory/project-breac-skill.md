## 一、已确认的决策

### 1. 命名与版本
- Skill 名保留 `breac-industry-brand-scan`，做成燃创面向所有客户的**通用版**（不是比乐专属）。
- 另一个 proposal `brand-report-orchestration` 的内容并入这个名字，最后废掉重复的。
- 两个 proposal 目前都 pending，未 apply。

### 2. breac-industry-brand-scan 与昨天 orchestration 的关系
- 是「初版 → 升级泛化版」的关系，同一件事的两代。
- 初版（7/12 比乐项目）是项目专属的 10 步快照，视野窄。
- 昨天沟通的 orchestration 是在 V12 报告全流程跑通后泛化出的通用版：范围补全（完整 skill 链而非只有图表）、去项目化、补了协同关系图和缺口分析。
- 后者是前者的超集和升级。最终把 orchestration 内容灌进 breac 这个名字。

### 3. orchestration 与 skill 的区别（后台固化视角）
- **skill 是容器，orchestration 是内容**。
- skill = 后台一个实实在在的文件（SKILL.md + 附属脚本/模板），被索引、有版本、有 pending→applied 生命周期，跨会话持久可复用。这是「固化」的物理形态。
- orchestration = 协调逻辑本身（先采什么、用哪个模型、何时切模型、步骤间契约、验证卡点），是过程、是方法论。
- 后台没有独立的 orchestration 引擎；「固化 orchestration」= 把编排逻辑写进 SKILL.md。
- **关键实话**：固化成 skill 也不是能自动执行的代码，而是一份我每次读进来手动照着跑的说明书。执行仍是实时的。

### 4. 核心痛点与总原则：打折问题
- 逸凡洞察：我不会真正每次把 SKILL.md 完整读一遍照做，所以做完的 orchestration 我会打折。
- **根因**：当前架构下执行主体是「我读文本 + 凭判断照做」，只要中间是自由裁量就一定有损耗（不触发去读、读了漏细节、读了中途偏离）。SKILL.md 越长打折越狠。这是「文本说明书 + 人肉执行」模式的天花板。
- **总原则（贯穿全项目）**：把尽可能多的环节，从「我判断」搬到「代码执行」和「显式契约传入」。搬得越多，打折越少。
- **统一哲学**：凡是依赖「我记得/我自觉」的都会漂移或丢失；解法永远是下沉到不依赖我的固定载体。执行靠代码，文风靠校验，记忆靠文档。三件事是同一个动作。

### 5. 降打折的四层设计（从最治本到最缓解）
- 第一层（最强，零打折）：**确定性环节代码化**。图表生成、docx 装配、质检、数据提取全部写成固定脚本。代码每次跑都一样，不会忘规则。对应昨天暴露的三个技术缺口（docx 自动化、图表→文档管道、电商采集标准化）。
- 第二层（次强）：**流程 subagent 化 + 契约内联**。每步规则写进派给 subagent 的 task prompt，显式传入，绕开「读不读、读全没读全」。主 session 只调度。
- 第三层（治触发）：**硬红线上提到自动加载层**。SKILL.md 是被动读取，SOUL.md 每次会话主动注入。把最致命红线（可溯源、图表中文标签、五维一致、单品牌不跨比、文风）从 skill 正文抽到 SOUL/AGENTS。代价是 SOUL 不能无限膨胀，只放最高频最致命的。
- 第四层（缓解+可核对）：**带门禁的 checklist 卡点**。每阶段强制输出可核对的中间产物，不交付不进下一步。把隐性规则变显性强制交付物（如：生成图表后必须贴出 xAxis 数组确认是中文名才进下一步）。超长流程用 taskflow 做有状态的状态机。

### 6. 两种差异的区分（关键认知，逸凡纠正后确立）
- **第一种：结构和颗粒度的随机差异**（这章漏了、维度颗粒度不齐、图表没标签、五维不一致）——这是**缺陷，必须彻底焊死**。V1→V12 反复返工的绝大部分就是这种。是真正吃时间的元凶。
- **第二种：分析判断的差异**（同样数据，不同客户切入点不同）——这**不是 bug，是咨询价值所在**，不能也不该固定。
- 结论：结构和颗粒度 100% 能焊成代码；判断内容不能焊死但能被结构强约束。
- 逸凡补充：第二种交给 DeepSeek V4 Pro，只要对它的分析颗粒度和内容层次提出明确要求，它能自己形成独立的好内容。

### 7. Schema 驱动 + 分析契约（地基的两块）
- **Schema（报告结构合同）**：机器可读的骨架定义文件（JSON/YAML）。规定几章、每章几节、每节哪些维度、每维必含哪些要素、每部分写几段、数据源到章节的映射。管「长什么样、必须有什么、各多少」。静态、名词性。质检脚本拿它对照成品，缺章缺维缺要素就报错。
- **契约（行为约定）**：管「每一步怎么做、交出来的东西什么格式」。动态、动词性。两种：
  - **分析契约**：给 DeepSeek Pro 的产出标准，内联进每次调用的 prompt。固定两样：①内容层次——每维走「现象层（数据事实）→归因层（为什么/驱动力）→判断层（对品牌意味着什么/信号）」三层，即判断先行有支撑再收尾判断；②颗粒度基准——锚定 V12 深度，深度品牌每维1-3段、每段落到具体数据或动作、不许空泛。
  - **接口契约**：pipeline 里上一脚本的输出格式必须正好是下一脚本能吃的输入格式。让脚本能自动串成流水线。
- 一句区分：Schema 定义成品形状，契约约束每一步动作和交接。
- **完整地基 = schema（结构+颗粒度框架，保证长得一样）+ analysis contract（对 Pro 的层次+深度要求，保证深得一样）**。Pro 在两个约束里只做「这个客户的具体判断是什么」。

### 8. 文风固化的定位（引号/破折号/星号/AI腔）
- 三层协同，真正焊死在第三层：
  - SOUL 层：自动注入，让我默认往干净方向写（预防）。
  - 分析契约层：内容是 Pro 写的，文风要求必须内联进每次给 Pro 的 prompt（预防）。
  - **代码校验层（真正焊死）**：qa_check 脚本用规则扫描——数引号「」『』""''、星号、破折号数量超阈值报错；比对 AI 填充词库（当然、其实、本质上、整体而言、从某种意义上说、值得注意的是），命中报错打回重写。
- **可推广判断**：凡是能被规则检测的约束（文风、格式、字号、结构完整性），全部下沉到代码校验层焊死；只有需要判断的（内容深度、洞察质量）才靠契约+我。文风属前者，所以能被彻底解决。

### 9. 跨天记忆持久化机制
- 现状问题：被动（靠逸凡提醒才写）、散（信息散在多个文件）、恢复靠我自由裁量读哪些又会打折。
- 更好的做法：
  - 建**唯一权威项目活文档**（就是本文件 project-breac-skill.md），所有东西只写这一个，不散落。每次继续第一个动作就是读它。
  - **固定状态机结构**：已确认的决策 / 当前状态 / 待办 / 关键约束清单 / 下次继续入口。给记忆本身上 schema。
  - **机制化固化**，不靠提醒：会话结束前强制更新；可挂 cron 定点触发整理；每敲定一个决策立刻追加。
  - 本活文档最终会长成 skill：项目完成时其【已确认决策】【关键约束清单】固化进 SKILL.md 和 schema/契约。它是正在长大的 skill 半成品。
- 本质：把 Harness 层会丢的上下文，下沉到文件（Infra 层存储）。和对付执行打折、文风漂移是同一哲学。

### 10. 架构分层认知（Infra / Harness / Orchestration / Pipeline / 代码 / Skill）
从下到上五层：
- **Infra（地基水电）**：Mac mini、OpenClaw Gateway、模型 API、飞书通道、文件系统、cron。平台给定，不动。
- **Harness（运行时脚手架）**：把 LLM 套成 agent 的整套控制框架——prompt 组装、记忆注入(SOUL/MEMORY/AGENTS 自动加载)、skill 加载、工具执行循环、结果回灌、多轮循环、subagent 管理。就是 OpenClaw agent runtime 本身。Harness ≠ prompt，prompt 只是它最可塑的一部分。
- **Orchestration（任务编排）**：完成某任务的作战流程（研报：采集→分析→图表→装配→质检的顺序、模型分工、卡点）。我们真正在设计的第一层。
- **Pipeline（管线）**：orchestration 固化成的自动化流水线（run_report.py 串起各脚本）。
- **代码/脚本**：流水线上的具体工位（generate_charts.py 等）。
- **Skill**：横跨中间几层的打包单元——正文写 orchestration，内嵌脚本是 pipeline/代码，附带 schema/契约是约束，「能被加载」靠 Harness。
- 类比（工厂）：Infra=厂房地皮水电；Harness=运营系统+工人岗位控制台（我=工人）；orchestration=工艺流程图；pipeline=自动传送带；代码=机械臂；skill=完整生产手册+配套专用机械的复用包。
- **点破**：Infra 和 Harness 是平台给的舞台，我们动不了；能设计固化的是 orchestration→pipeline→代码三层。「让我不打折」=把活从 Harness 层（我临场判断）下沉到 pipeline 层（代码固定执行）。

### 11. 用户能否个性化 Harness（逸凡问，已澄清）
- Harness 分两部分：
  - **平台写死、不改源码动不了的核心机制**：工具执行循环、上下文窗口管理与截断、系统 prompt 最外层骨架、消息路由。
  - **开放给用户配的（决定 agent 行为的绝大多数）**：人格/写作风格（SOUL/AGENTS/USER/IDENTITY）、能力加载（skill）、模型与 thinking 级别、工具白名单、记忆结构与自动注入、cron 调度、群聊 requireMention。
- **结论**：我们这三天做的每件事（SOUL 加红线、写 skill、建活文档、schema、契约、pipeline）本质就是在个性化我的 Harness。逸凡早就在做，且比多数用户深，不需要求平台方。
- 边界：若要改核心机制（工具循环、截断逻辑、底层新行为）才需动 OpenClaw 源码（开源可改），那是「改平台」不是「配 agent」，风险维护责任不同，不建议轻易碰。做这个研报 skill 完全在配置范围内，一行源码不用碰。

## 四、关键约束清单（会焊进最终 skill）

- 事实数据必须可溯源，缺数据标「待验证」不编造（P0 底线，教训13）。
- 图表 X/Y 轴必须中文品牌名，禁止纯数字（教训23）——将焊入 generate_charts.py 校验。
- 每品牌五维必须一致（市场渠道/品牌力/产品/趋势/人群），缺数据不是跳过维度的理由（教训22）——将焊入 qa_check.py。
- 单品牌分析严禁跨品牌对比（教训21）。
- 分析结构所有品牌一致，深度品牌每维1-3段、汇总品牌每品牌1段+趋势综述（教训22）。
- docx 操作用 python-docx 按样式定位边界，再 lxml 元素级操作，不混用引用（教训24）；addprevious 用 reversed 顺序插入（教训26）。
- 写作：结论先行（判断→数据→收尾判断），禁引号做概念强调、禁星号破折号、禁 AI 填充词，自然段落像咨询顾问说话。
- 模型分工：DeepSeek V4 Pro 写全部分析；GLM 5.2 写 docx/coding；GLM 5V Turbo 截图审查。
- 交付格式优先级：信息完整 > 排版可读 > 视觉优雅。永不为排版不好看而延迟第一次信息交付。
