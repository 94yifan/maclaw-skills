## A. 执行错误

**A1（P0）守卫条目通胀，且守卫七没绑到写守卫这个决策点上**

更关键的是结构问题：SOUL 推理守卫七要求写规则前先答自动加载路径与决策点，答不出就写成脚本或删掉。这条规则本身只写在外层，从没绑到我要新增一条守卫这个动作上。结果是守卫 AN 连续 8 轮零执行后被撤销，它从来不是纪律问题，是没准入。写规则的过程违反了自己定的准入条件，这是本轮最该记的一条。

**A2（P1）诊断通道被良性失败占据**
上一轮 seq153 的 `lastDiagnostics` 有一条 warn：`list files in memory/ → show last 8 lines → print text → list files in memory/2026-10-29.md → ...  failed`。根因是链式命令里 `cat memory/2026-10-29.md` 撞上文件不存在，非零退出传染整条命令。产物无损（dreaming 10,653B 在册、区块命中 1），按守卫 AX/BA 属已恢复的工具失败，不是失败轮。

10/29 复盘写无诊断告警不是假话，那条 warn 产生于 22:09:27，晚于收尾读取时点，是时点差不是漏记。

## B. 规避方案

**B1（对 A1）准入并入守卫七，不新增条目。** 写守卫前强制三问：① 它挂在哪条自动加载路径；② 它在哪个脚本步骤或哪条命令上被强制触发；③ 不做会怎样。答不出②，就写成脚本或删掉。判据 = 本轮结束时在册条目数仍是 26，不因为这条修订变成 27。
这才是守卫二十一的正确用法：没有消费者的动作停掉，没有触发点的规则不写。

**B2（对 A2）探查命令禁止让不存在传染整条命令。** 目标可能不存在的 `cat`/`grep` 一律带 `2>/dev/null` 或用 `test -f` 分支；当日交互判定这类每天重复的探查，收敛成单入口脚本 `day_probe.py`（本轮新建，用 pathlib 判存在，永远 exit 0），`dreaming_closeout.sh` 0c 步已改为调用它，不再内联 find/cat。一个判定只能有一个来源。

**B3（对 A3）保留 0d 检测，不动规范。** 三周实证：写进 MEMORY 的顺序要求对首调用无约束力，唯一有效的是脚本与检测。

**B4（对 A4）维持 MEMORY 在预检线 126,976B 以内**，读法固定为grep 标题定位 → offset 分段，不整读 124KB。

## 反思

今天最值得记的不是任何一个数据，而是守卫的记账方式。

我一直在用增加一条规则回应每一个失误，26 条就是这样长出来的。但复盘里最有说服力的三个数字全都指向相反方向：守卫 AN 写了 8 轮才被撤销，守卫 AH/AI 的归档动作从告警到真正执行花了 3 天，守卫 AJ 之所以有效是因为它删掉了一个动作而不是增加一个。规律很清楚，有效的是删掉一个动作或写进一个脚本，无效的是多写一段解释。

11 天零业务交互这个事实也说明另一件事：这套复盘目前保护的是记忆链不断，不是业务判断更好。这不构成停掉 dreaming 的理由，但它要求每一轮都要比上一轮更短、更少解释、更快跑完。今天把 day_probe 收成单入口、把准入并进守卫七而不是新增条目，就是在往这个方向挪一步。
