# 第1章 AI Agent 入门

## 本章核心论题

从五个真实 Agent 产品出发，建立对现代 AI Agent 的直觉理解，然后系统拆解核心公式 Agent = LLM + 上下文 + 工具，说明三者缺一不可。本章的核心判断是：模型能力正在商品化，真正的竞争优势落在 Harness 工程——围绕模型构建的上下文管理、工具接口、约束、验证与纠正机制。所有后续章节的设计原则皆从此出。

## 关键论点与框架

### 1. Agent 的本质公式：Agent = LLM + 上下文 + 工具

**论点**：现代 Agent 的最小工程实现由三个不可分割的组件构成——LLM（决策大脑）、上下文（感知之眼）、工具（执行手脚）——三者缺一则 Agent 退化为无行动能力的聊天机器人、盲目的循环执行者或纸上谈兵的文字生成器。

**论证与机理**：该公式有三个抽象层次——直觉层"大脑+眼睛+手脚"、实现层"LLM+上下文+工具"、学术层映射到策略/观察空间/动作空间。上下文是观察和历史在 Agent 内部的表示，不等于整个观察空间；工具定义的是 Agent 可用的接口，工具背后的文件系统、数据库等仍属环境。Harness 负责把环境观察转换为上下文，把模型行动转换为工具调用——没有进入上下文的信息对模型如同不存在，没有被动作接口允许的操作只能停留在文字建议上。

**书中案例/证据**：五个 Agent 产品按这三个维度对号入座：Cursor 等 Coding Agent 的眼睛是代码片段和终端输出，手脚是文件读写和命令执行，策略是增量开发循环；Pine AI 等个人办事 Agent 的眼睛是账户记录和账单，手脚是打电话、发邮件、填表单，策略是多步骤协商。消融实验（实验 1-1）验证了每个上下文组件的不可替代性：去掉工具定义→丧失行动能力；去掉工具执行结果→陷入无限循环；去掉思考过程→前后决策矛盾；去掉历史消息→重复执行已完成步骤。

**出处锚点**：§1.1 及表 1-1；实验 1-1。

### 2. 扩展观察空间与动作空间是最主要的能力杠杆

**论点**：在底层模型固定时，提升 Agent 任务表现最主要的系统工程手段就是重新定义或扩展观察空间与动作空间——许多看似需要"更聪明模型"的问题其实只是接口问题。

**论证与机理**：将任务所需数据纳入上下文或所需操作封装成工具，原本不可解的任务就可能变得可解。Agent 产品能力的演进本质上就是观察空间与动作空间的演进，而非简单地更换更强模型——将工程重心从"等模型变强"转移到"为模型设计更好接口"。

**书中案例/证据**：Manus 取三类 Agent（Deep Research、Coding、Computer Use）的观察空间与动作空间之并集——虚拟浏览器扩大观察空间，文件系统、代码执行与命令行执行扩大动作空间——使同一个 Agent 跨越原有产品边界。OpenClaw 更进一步，通过 WhatsApp、Telegram 等消息渠道和本地 Gateway 连接云应用，让分散的数字文件进入同一观察空间。Manus 后来也加入本地访问和云连接器，再次印证这一规律。（§1.1.1，脚注 1）

**出处锚点**：§1.1.1。

### 3. ReAct 循环：思考→行动→观察的迭代闭环

**论点**：Agent 执行任务的核心机制是 ReAct（Reasoning + Acting）循环——模型先思考当前应该做什么，然后调用工具行动，再观察工具返回的结果并继续思考下一步，"想→做→看"不断重复直到任务完成。Agent 的上下文 = 静态前缀（系统提示词 + 工具定义）+ 轨迹（动态消息历史）。

**论证与机理**：每次 LLM 调用时，模型看到的完整上下文由静态前缀和不断增长的轨迹组成，这意味着每次调用都能看到完整执行历史。这赋予 Agent 对任务的全局认知和高可解释性：用户消息、模型回复（思考过程+工具调用）和工具执行结果被结构化地区分开来，形成可审计、可调试的轨迹。轨迹数据还可用作知识库更新和强化学习训练的闭环优化输入（第八章）。最小运行骨架揭示了三个参与者的分工边界——Model 只决定下一步，Harness 组装上下文并校验执行，Environment 产生真实状态变化。

**书中案例/证据**：多币种收入汇总任务展示了完整的 ReAct 轨迹：第一轮 Agent 分析任务后并行调用三个货币转换工具；第二轮基于转换结果调用代码解释器做汇总计算；第三轮确认完成后生成最终答案。全程 3 次迭代、4 次工具调用。Kimi K3（实验 1-2）在 Agent 任务中能连续执行 200-300 次工具调用而保持思考一致性，远超多数模型在数十次调用后就开始退化的表现。GPT-5.6（实验 1-3）在 ReAct 循环中引入意图澄清环节——执行前先通过提问确认真实需求，弥合了"用户说了什么"和"用户真正想要什么"的差距。

**出处锚点**：§1.1.5；图 1-4；实验 1-2、1-3。

### 4. Harness 工程与 Model–Harness 边界结构

**论点**：Agent = Model + Harness，其中 Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正。模型让 Agent "能做事"，Harness 让 Agent "不做错事"。在生产级 Agent 中，Harness 的绝大部分代码在做约束、验证与纠正，模型能力越强，Harness 反而越关键。

**论证与机理**：Harness 是 Agent 边界内、模型之外的运行与治理层。上下文管理和工具接口是其核心能力；约束设定行为边界、验证自动判断操作对错、纠正在发现问题时自动修正或回退——三者围绕上下文和工具构建，确保生产环境可靠运转。Harness 可创建、隔离或代理环境，但不包含环境自身的状态与转移规律。

随模型能力增强，Harness 是否会被模型内化？作者立场是"方向认同，节奏务实"——不怀疑模型会持续吃掉 Harness（工具调用、长程规划都曾靠外部编排，今为原生能力），但这远比直觉慢：训练以月计，模型无法一次内化所有业务约束。Harness 工程不是对 Sutton《苦涩的教训》的抵抗，而是这一教训在工程时间尺度上的实践：模型还做不稳的，Harness 先补上；模型每内化一层，Harness 就卸下一层，转而兜底新前沿。

**书中案例/证据**：以 Claude Code 为例，Harness 中绝大部分代码是约束、验证与纠正，而非工具本身。保障机制包括流程状态管理、多层上下文压缩、权限分类、熔断器、错误恢复机制。LangChain 在 Terminal Bench 2.0 上从 52.8% 提升到 66.5%（从 30 名开外跃升至前 5），改变的不是模型，而是 Harness：让 Agent 自动检查执行结果、检测重复循环、优化思考策略。（§1.2 开篇及 §1.2.1）

**出处锚点**：§1.2；图 1-1。

### 5. 从提示工程到 Loop 工程的范式演进（五层包含关系）

**论点**：AI 应用工程经历了五波范式演进——提示工程 → 上下文工程 → Harness 工程 → Loop 工程 → Graph 工程——这不是替代关系，而是层层包含。每一层在前一层的基础上扩展了工程师的关注半径。

**论证与机理**：提示工程优化自然语言指令→上下文工程系统管理模型能看到的全部信息→Harness 工程扩展到模型外运行与治理机制→Loop 工程将视野扩展到跨轮次的持续自主运转→Graph 工程将循环、确定性程序和人工审批组织成显式执行图。当模型能力趋同，竞争优势转移到模型之外的工程实践。

**出处锚点**：§1.2.1。

### 6. 编排模式的选择原则：保持简单，从工作流到自主 Agent

**论点**：在构建 LLM 应用时，应遵循"先优化单次 LLM 调用 → 再考虑工作流 → 最后才引入自主 Agent"的渐进路径。Agent 系统以延迟和成本换取任务性能，需要谨慎权衡。

**论证与机理**：工作流通过预定义代码路径编排 LLM 和工具，核心优势是严格流程控制和安全性——业务规则通过代码强制执行，攻击面被限制在单个节点内；局限是缺乏变通性。自主 Agent 由 Agent 根据环境反馈实时决定执行路径，适合开放式问题，但成本和复合错误风险更高。实践中两者常混合：关键合规流程走工作流、灵活决策切到自主模式。Anthropic 的经验表明，最成功的实现往往采用简单可组合的模式，而非复杂框架。

**书中案例/证据**：以订机票 Agent 为例对比两种模式。工作流模式定义"核实身份→搜索航班→付款→确认预订"四个固定节点，确保"付款前不能预订"。自主 Agent 模式则由 Agent 自行决定：先搜索航班→发现需要登录→核实身份→搜索到最便宜航班（需转机）→主动询问用户是否接受→用户拒绝→调整搜索。n8n 框架在同一系统中支持工作流节点和自主 Agent 节点的混合编排。

**出处锚点**：§1.2.5；图 1-6、1-7。

### 7. 护栏分层防御：输入侧、执行侧、输出侧三重防护

**论点**：护栏是 Harness 中约束、验证与纠正机制最核心的落地手段，按照防护位置分为输入侧、执行侧和输出侧三类，通过分层防御构建韧性系统。护栏评估需要同时测试"应拒绝的请求是否拦截"和"允许的请求是否正常完成"。

**论证与机理**：输入侧在请求到达前拦截（相关性分类器、安全分类器、内容审核、基于规则的保护）；执行侧在工具调用时按可逆性、权限等级和财务影响做风险评级；输出侧在响应返回前做 PII 过滤和内容检查。人工干预在超过失败阈值或高风险操作时触发。需注意越狱（用户自己绕过安全限制）与提示注入（攻击者通过外部数据间接操纵）的本质区别。

**书中案例/证据**：Anthropic 的 Constitutional Classifiers 是分类器护栏的工业实践代表——用自然语言"宪法"生成合成训练数据训练输入输出分类器，采用上下文联合判断（同时检查用户提问和模型回答以识别暗语），两级筛查（轻量探针先过、强分类器复审）以降低误报对用户体验的影响。（§1.2.6，脚注 5）

**出处锚点**：§1.2.6。

### 8. 模型选型的四个关键维度

**论点**：选对模型往往比优化提示词更有效，选型应基于四个维度——能力（在自身任务上评估，不止看排行榜）、策略边界（模型厂商是否允许特定用途）、思考能力（绝大多数 Agent 任务需要 reasoning 能力）和辅助特性（输出速度决定了端到端延迟，多模态能力是硬性要求）。

**论证与机理**：闭源模型能力领先但成本高且受限 API 策略；开源模型与闭源差距在 6 个月内，成本显著更低，适合对能力要求不高或有合规需求的场景。同一任务在聊天产品、Coding Agent 和 API 中可能得到不同结果——需在自身真实任务上测试模型是否愿意执行、接口是否暴露能力、条款是否允许。易被忽视的是输出速度：Agent 需多轮推理，每轮等待输出完成，输出速度直接决定端到端响应延迟。

**出处锚点**：§1.2.4。

## 原则清单

1. **保持简单优先**：直接 API 调用优于复杂框架，清晰代码优于聪明抽象——每多一层抽象都是新的调试盲区。
2. **先优化单次 LLM 调用**：能用提示词和上下文示例解决的，不引入 Agent 系统。
3. **扩展接口优先于升级模型**：先检查任务数据是否在观察空间内、操作是否有对应工具，再考虑换更强模型。
4. **工具设计防呆（Poka-yoke）**：从 Agent 视角设计接口（ACI），让误用在设计层面就不可能发生。
5. **通用工具组合探索，专用工具约束高风险**：代码解释器需隔离沙盒运行；支付、删数据等操作封装为参数明确、权限受限、全程可审计的专用工具。
6. **约束、验证与纠正是架构内置，而非上线前补丁**：安全贯穿模型、上下文、工具、协作和社会五个层面。
7. **建立评估机制才可能有进步**：评估让迭代方向不再依赖直觉（第六章展开）。
8. **人工干预是"优雅移交"**：失败阈值超限或高风险操作时，将控制权和上下文一并移交给人。
9. **护栏评估需双向测试**：既测"应拒绝的请求是否被拦截"，也测"允许的请求是否正常完成"。
10. **在名词流行之前就实践**：驱动实践的动力来自对 Agent 能力上限有极高要求的真实业务和持续反馈的评估机制。

## 失败模式与反例

1. **消融实验揭示的四类退化**（§1.1.4，实验 1-1）：去掉工具定义→丧失行动能力；去掉工具执行结果→"盲执行"无限循环；去掉思考过程→前后决策矛盾；去掉历史消息→"失忆"重复流程。生产环境中工具结果缺失可由网络超时、API 异常、解析失败引起。

2. **自主 Agent 的死循环与过度执行**（§1.2.5.2）：无明确停止条件时自主 Agent 易陷死循环。应设计熔断器：连续失败自动停试、回退人工判断。

3. **误拒绝——护栏的隐藏成本**（§1.2.6）：为降低危险请求被放行的概率，可能同时拒绝合法但形式敏感的任务。护栏评估不测试"允许的请求能否正常完成"会产生盲区。

4. **框架过度抽象的陷阱**（§1.2.3）：很多 Agent 失败非因模型不够强，而是框架增加了不必要抽象层。每多一层抽象都是调试盲区。

5. **模型"策略边界"陷阱**（§1.2.4）：基准测试具备能力≠产品允许调用。不同厂商策略边界不同，同一任务在聊天产品、Coding Agent 和 API 中可能结果不同。

6. **"过早声明完成"**（§1.2.7）：Anthropic 发现长时运行 Agent 中模型倾向于过早声称任务完成，需 Harness 层面的结构化干预（任务分解、交接产物）。

## 关键术语表

| 概念 | 一句话定义 |
|------|------------|
| **Agent** | LLM + 上下文 + 工具的智能系统，能自主规划、调用工具、根据反馈调整策略 |
| **上下文** | Agent 在每个决策点收到的全部信息表示——系统提示词、工具定义、对话历史、工具结果 |
| **工具** | Agent 感知或改变外部世界的接口，包括工具定义、调用协议和适配器 |
| **ReAct 循环** | "思考→行动→观察→再思考"的迭代机制 |
| **轨迹（Trajectory）** | Agent 执行过程中不断积累的消息历史——用户消息、模型回复、工具执行结果 |
| **Harness** | Agent 边界内、模型之外的运行与治理层，负责上下文管理、工具接口、约束、验证、纠正 |
| **约束 / 验证 / 纠正** | Harness 三层保障：设定行为边界 → 自动判断对错 → 发现问题后自动修正或回退 |
| **工作流（Workflow）** | 通过预定义代码路径编排 LLM 和工具的确定性执行模式 |
| **自主 Agent** | 执行路径由 Agent 根据环境反馈实时决定的动态执行模式 |
| **护栏（Guardrails）** | 保障 Agent 行为安全的分层防御机制（输入侧、执行侧、输出侧） |
| **模型即 Agent** | 模型通过后训练将工具调用决策策略内化为原生能力，无需外部编排框架 |
| **Loop 工程 / Graph 工程** | 从单次运行扩展到跨轮次持续自主运转；进而将循环、程序和人工审批组织为显式执行图 |
| **提示注入** | 攻击者通过外部数据（网页/文档）向上下文嵌入恶意指令，间接操纵模型行为 |
| **越狱（Jailbreak）** | 用户自己试图绕过模型安全限制 |
| **ACI** | 从 Agent 视角设计的工具接口（Agent-Computer Interface） |
| **熔断器（Circuit Breaker）** | 错误连续发生时自动停止重试，防止系统级崩溃 |
| **消融实验（Ablation Study）** | 逐步移除系统组件以判断每个组件贡献的诊断性实验 |
| **思考 / 推理** | 本书术语约定：reasoning = 思考（展开推导），inference = 推理（部署运行） |
