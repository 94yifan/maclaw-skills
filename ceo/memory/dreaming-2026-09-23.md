## B. 规避方案（写成铁律，全部绑决策点）

1. **本 job：落盘前置已在本轮执行（对应 A1）。** 顺序固定为：写复盘文件 → 发飞书摘要（取 messageId）→ 写 MEMORY → commit → 结束。核对与探索一律前置于写入之前，**run 尾部禁止非必要工具调用**。依据：09-21 先落盘 vs 09-21 三轮全丢的对照。
2. **跨代理纠错必须写进犯错方的输入源（对应 A2）。** 判定一个跨代理错误被纠正，标准不是「我改了我的 MEMORY」，是「犯错方下次读到的输入里已经是修正后的版本」。CEO 侧可动的只有一条：把该事实写进**所有分身共读的**共享文件（各 workspace 的 MEMORY 顶部规则区），或把它作为推送项交给唯一能改各分身 prompt/SOUL 的执行者（主 session / 逸凡）。只写进 CEO 自己的 MEMORY = 纠错半径为零。
3. **一条规则保护多个产物时，必须为每个产物各绑一个决策点（对应 A3）。** 反面样板：BM 规则十二笼统写「把正文与 MEMORY 增量落盘」，未定义顺序，结果历史上一再丢的是排在最后的那个产物。正面样板：CFO `audit.py` 绑在日必到节点、book 归档规则绑「每日 Dreaming 第 3 步前」。判据：规则覆盖 N 个产物就应能回答 N 次「它在哪个时点被执行」。
4. **推送上限 3 次，到限转批量（对应 A4 + 挂账推送）。** CEO 挂账推送自 09-18 起已 4 次零回复（09-18 / 09-19 / 09-21 / 09-22）。BF 判据：一次推送若无新增可执行信息（同一条原文、同一个拒绝），价值为零、成本是注意力，且消耗推送本身的可信度。本轮起：单点推送停止，并入 9/28（周一）全量清单。

### 缝合6（主·系统层）：无收敛的自动重试——重试不改条件时必然发散
- 链：09-22 缝合2（串行队列 + 无超时隔离）→ 09-21 缝合4（交付绑 run 状态 = 机制缺位）→ 09-15 缝合（校验目标互斥：目标不变则行为不变）→ 09-19 缝合1（期望存活长度）。
- **新认知：重试有意义的唯一前提是改变条件（timeout↑ / context↓ / 交付点前移）。条件不变时，重试在逻辑上只是把同一次失败复制 N 次，且每次复制都重新占满共享槽位 → 序列发散、无不动点。触发量由 run 状态决定、而目标（送达）早已达成时，一个已成功的 job 会被反复执行。今天：1 个 job 一晚 4 跑、约 20 分钟槽位，产出被送达 2 次——这不是「重试救回交付」，是「重试放大占用」。**
- 修法三选一：①retry cap ②幂等判据（已送达即终止，不看 run 状态）③条件变更（不改条件则不重试）。
- 管理同构：任务失败后原样重派（同人、同资源、同约束）不会得到不同结果，只会同样消耗 N 次资源；有效重试 = 换条件（换人 / 降范围 / 加时限）。审批被退回后原样重提，通过与否只是概率。
- 客户用法：素材被平台拒登 / 审核退回后原样重提，是把概率当策略；正确动作是改条件（换素材 / 换版位 / 改表述）。
