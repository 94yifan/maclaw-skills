## B. 规避方案（写进 memory）

**B1：机制类结论必须附「一条可复跑命令 + 其原始输出」，否则只能写「观察」。** 判据：任何「同刻/并发/同时/批量」类断言，先问「用哪条 SQL 查的、返回几行」。依据 A1/A2——三个代理都写了「实测」，都拿不出命令。

**B2：跨代理共识不得升级为「已确认事实」——除非各代理附各自的命令与输出。** 共用数据源 + 共用读法时，N 个代理 = 1 个样本。三代理今晚同错，正是「共识 ≠ 交叉验证」的实证。处置：凡多方共指同一系统事实，一律标「待主 session 复核源数据」。依据 A2。

**B3：本生态的真机制是「串行队列 + 单 job 全量占槽」，修法不是加错峰。** 优先级：①降单 job 自身耗时（SP MEMORY 479KB、BM MEMORY 357KB 是最大头，先做只读增量）②fail-fast + 交付前置（写盘后立即交付再退出，不等收尾探索）③槽位超时即释放（并发隔离）。依据 A1 的机制更正。

**B4（沿用）：交付判定取当日末次 seq；「已送」类断言必须绑渠道证据（messageId / delivered=1）。** 无证据写「已落盘，送达未验证」。

## C. 书写质量

- 今日生态最大的书写缺陷是 **A1 的「读数方向写反」**：把「被堵住」写成「撞车」，且用「实测」二字给结论背书。这类缺陷比错别字危险——它直接导向错误的修复方案。

## D. 知识串联（核心）

### 缝合1（主·系统层·CEO 自应用）：跨代理「独立复现」在共用数据源与共用读法下退化成一个样本——共识 ≠ 交叉验证

**串联链：** 09-21 缝合1（自述态：写规则的动作被当成执行）→ 守卫十七（完成态须自证）→ 守卫八（一致性检查）→ 今日新增实证：三个代理在同一晚、对同一机制、给出同一个错误结论，且三个都写「实测」。

**新认知：** 此前记的「独立复现」是有条件的——独立的前提是**独立的源或独立的读法**。当三方读同一个 sqlite、用同一种「取一批 run 看时间戳」的读法时，它们的「一致」只证明了一件事：这个读法会产生这个（错的）结果。**「三处一致」在证据分级上应低于「一处 + 可复跑命令」，因为前者可以是同源的复制，后者必须自己经手。** 判据：跨代理/跨部门共识要升格为事实，必须满足「各自附命令 + 各自附原始输出」；给不出即为单一读法的三份复本。

**管理同构：** 三个部门报同一个数（都从同一张总表抄），老板若当成「三方交叉验证」就会放过一个错；真交叉验证要求三方各有自己的取数口径。客户同构：代理商、平台后台、第三方榜单给出同样的数，不等于印证——先看是不是同源。

### 缝合2（主·系统层·CEO 自应用）：串行队列里，超时的成本 = 单次超时 × 排队位置——「共享资源 + 无超时隔离」

**串联链：** 09-21 缝合4（交付绑 run 状态 = 机制缺位，而非 N 个 bug）→ 今日补出第二层机制：不是「交付绑 run 状态」，而是「**run 状态绑槽位占用，槽位占用绑全队列**」。

**新认知：** 一个 300s 超时的 job 不只丢自己的交付，还把它后面每一个 job 的起跑各推后约 5 分钟；6 个 job 一轮最多 30 分钟，9/21 因三轮重试跑到 80 分钟（22:00→23:19）。所以失败率的真实代价不是「1 次 error」，是「1 次 error × 下游 N 个 job 的推迟」。修法的杠杆顺序也随之定死：**先砍单 job 耗时（治本）→ 再 fail-fast/交付前置（治损）→ 最后才谈并发（治标且风险最高，会同时放大模型侧争抢）**。三代理今晚的「加错峰」建议方向错误，恰因未识别串行。

**管理同构：** 一个卡住的人占着唯一的会议室，拖的不是他自己的半天，是全公司当天的排程；共享资源上，个体耗时是被广播给全队列的。客户同构：一条素材卡在审核，整波排期顺延——报价里「加急/免排队」卖的就是排队位置，不是工时。
