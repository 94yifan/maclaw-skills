## D. 知识串联（核心）

### 缝合1（主，验证层）：验证层是唯一「错误输出长得像结论」的层；读数到结论中间是两段，不是一段

**证据（同日四种三类）**：tea 的 grep 退出码 1 表示「未勾选 0 行」，而门禁把 1 读成不通过，语义方向恰好相反；我的 `ls memory/2026-10-24.md` 失败被读成整轮失败；SP 的手写毫秒阈值返回空集，被读成今日无运行；CFO 的归档器 rc=0 被读成已归档，实际释放 0 字节。

**串联**：守卫二十（10-08，读数 × 判断 × 动作三段）、守卫二十二（10-18，命令缺失与对象异常须先分开）、10-24 缝合1（成功读产物不读退出码）、10-22 缝合1（缺口吸收，等式天然留余数）。

**新认知**：守卫二十的「判断」段实际由两层组成，此前一直合着写，所以三种假信号看起来是三种错，其实是一种错的两个位置。

1. 语义层：这个读数是什么意思。exit 1 有三种含义（命令不存在 127 的近亲 / 没有命中 / 真的失败），rc=0 只有一种含义（程序跑完了），空集有两种含义（真没有 / 被过滤光了）。
2. 判定层：这个含义相对标准合不合格。

四样本里，语义层错三次（tea、SP、CFO），判定层错零次。也就是说我的校验体系一直在加固阈值，而漏的是语义翻译。

**为什么集中在这一层**：业务命令失败的输出是「没了」（报告不存在，一眼看见）；验证命令失败的输出是「一个判决」（error / 空 / 成功，长得跟正常判决一样）。验证层是唯一自己产出结论的层，所以它的错误不需要任何人误读，会被直接当成事实往下传。

**判据三条，各自对应一种假信号**：

1. 假失败（退出码非 0 但打印值合格）：先判退出码的语义类别，再看数值。合格判定只认打印出来的数字，不认退出码。
2. 假零（结果为空）：先跑无过滤 count 自证分母不为 0，再下无记录结论。空返回值和真实为零是两件事。
3. 假成功（rc=0）：必须跟一个效果读数（释放字节、产出文件、变更行数）。效果为 0 视同失败，写 WARN。

**客户侧同构**：交付前的自查清单、投放后的数据核对、客户回执的判读，全部适用。客户说「收到了」等于 rc=0，不等于效果读数；要看的是他有没有在群里 @ 到执行人、有没有点开附件。

### 缝合2（主，执行器与交付）：交付绑产物不绑 run status；而 run status 绑的是最后一条命令，于是最后一条命令的成败决定了用户能不能看到东西

**证据**：今日与昨日四样本，产物 100% 在盘（我的 16,071B、tea 的 5,885B、SP 的 13,451B、CFO 的 120,764B MEMORY），其中三个 delivered=0。唯一被救回的是 tea，因为它有独立于 run status 的兜底发送通道（10-20 加固，11:06 四条全 ok）。我和 SP 没有兜底，复盘内容一个字没到逸凡手上。

**串联**：10-20 缝合3（三正交：status / 产物 / 送达）、10-24 缝合1（完成与退出负相关）、守卫十九（前置类改动的验收标准是「谁还在崖下」）、09-23 落盘前置、10-05 入账前置。

**新认知**：前三次「前置」（落盘、入账）解决的是产物会不会丢，今天这层是交付会不会被跳过。两者的保护范围不同：产物前置把产物搬到保护点之前，交付却排在自检之后，于是自检一失手，产物在盘、用户零收获。

**这是守卫十九的第二次完整应用，且范围要再扩大一格**：改动完成后必须列出本轮全部对外动作（写入磁盘 / commit / 交付到飞书），逐个标注是否在保护点之前。今天四个样本里，写入与 commit 都在崖上，交付全在崖下。

**判据**：

1. run 内固定顺序 = 产物 → 交付 → 记账 → 自检。自检永远最后，因为它最容易失败，而它失败时前面的都已兑现。
2. 自检结果只允许写 diagnostics 或 warning 字段，不允许翻转 run status。
3. 最后 3 次工具调用只允许写入类，禁读取类。收尾回读是最常见的自杀动作，今日我自己就死在这里。
4. 没有兜底通道的例行交付等于没有交付保障；兜底必须与主通道不同构（不同发送路径、不同判定依据）。

### 缝合4（治理，规则形态）：黑名单规则必然漏，白名单才闭合；而且规则要落在执行时被读的那个文件上

**证据一**：SC 的规则 20 是黑名单（禁互动数据、禁显式判断、禁内部质检语言），12:48 重写版仍漏三类：未披露 3 处、轻度推断 2 处、header 混血 1 处。黑名单只命名了已知的违规形态，未被命名的行为空间照旧敞开。SC 今日已补规则 22（不写信息缺失声明），仍是黑名单式补丁，下一个洞口会是别的形态。

**证据二**：SC A4 的根因更狠。规则改在 MEMORY（会话启动时读），而 cron 产出时真正被当权威的 SKILL.md 与 `references/approved-example.md` 还是旧版（范例是 06-08 的，含 21 处「对品牌而言」）。规则改了、载体没改、范例没换，执行者当然按范例写。这不是没记住，是同一规则有两个互相矛盾的载体，而更贴近任务的那个是旧的。

**串联**：守卫十一（规则必绑决策点）、10-19 缝合5（载体排序：脚本 > 门禁字段 > skill 步骤 > MEMORY 规则段 > dreaming 待办）、10-20 缝合1（分发断裂）、10-24 缝合3（第 2 次违犯即升级载体）。

**新认知两条**：

1. 黑名单的漏出率等于未被命名的行为空间大小，白名单的漏出率为零，代价是可能误杀。所以：交付类门禁用白名单（只允许出现什么），过程类止损用黑名单（禁止什么），两类不混用。SC 今天交付层三次返工，全部发生在黑名单门禁上。
2. 「规则有效 = 加载路径 × 决策点」这个公式还缺一项：加载路径必须与执行路径重合。规则写在 A 文件、执行时读 B 文件，等于规则不在执行路径上。约束自动产出的规则必须写进产出路径被读的文件（SKILL、范例、脚本）。MEMORY 只对交互会话有效。
