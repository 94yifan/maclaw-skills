**来源：** book 9/30 轮复盘写下「本轮未被 300s 截断，上述动作全部完成」+ 本会话 cron 遥测（该槽 `last_run_status=error`、`last_duration_ms=300151`、`last_diagnostics=timed out (last phase: model-call-started)`）+ 守卫十七（完成态表述须自证）+ 运行规则 14（断言须晚于其证据）+ 规则 15（跨轮继承的断言须重新取证）+ 守卫十六（审计颗粒度须与风险发生的层级同层）。

**串联判断：** 9/30 轮的两件「事实」并存且都真实——产物确实在 22:29:23 / 22:29:50 落盘（3b8c39f、acc6e74），而它所属的 run 也在 300s 处被调度器终止（status=error、duration≈300150ms）。run 从产物推出「我未被截断」，错在把「产物存活」当「run 正常结束」。根因不在推理松懈：**run 能观察自己的产物，不能观察自己的生命周期。** 「我是否被超时终止」只存在于调度器（run 之外），run 内部无论怎么查自己的文件都取不到它。守卫十七要求完成态断言附「本会话命令输出」，但规则 14、15 与守卫十七都隐含一个前提——证据可在本 run 内（17/14）或跨轮（15）取得；它们未覆盖第三种情形：**证据结构性地位于 run 的观察边界之外，run 内不存在任何命令能取到它。** 这与守卫十六同构：截断风险发生在调度器层级，run 却在产物层级自查——审计颗粒度与风险层错配，于是「自查通过」与「实际被截断」可以同时成立。四层合看：内容层（十七，断言是不是事实）、时序层（14，断言是否晚于证据）、继承层（15，跨轮断言是否重新取证）、观察边界层（16 新，证据是否根本不在观察范围内）。

**新的见解：** **任何关于「自身状态」的断言（我没超时／没被截断／正常运行／已投递），若其证据位于观察者边界之外，则在本体内结构性不可自证——必须改为以边界外的一手记录（此处 cron 遥测）为证，取不到即标「待外部核」。** 判据：写「本轮未 X」前先问「X 的证据在哪一端——我这一端还是系统那一端」；在系统那一端，就禁止由我这端的产物反推，必须调系统记录。与守卫十七族互补：前三条管断言的正确性、时序、继承，本条管断言的**证据可达性**——证据不可达时，任何措辞（含「实测」「已验证」）都不改变其待验证地位。

### 串联3（主，机制轨 × 规则12 × 守卫九 × 假失败/假成功谱系）：完成判据的覆盖缺口——判据只校验链路的一段，等于没校验整条链路

**来源：** 今日 A2（10/01 槽产物全部未提交，工作区脏：`M MEMORY.md` + 三个 `??` 文件，均为 10/01 22:25-22:27 落盘）+ 本会话 cron 遥测（10/01 槽 `status=error`、`durationMs=300163`、末阶段 model-call-started）+ 运行规则 12（退出条件 = book 侧无未推送提交，`ahead 0`）+ 9/26 串联3（ahead 是仓库全局量 vs book 侧量，假失败）+ 9/30 串联4（run status 是 run 结局量 vs 产物量，假失败）+ 守卫九（门禁只校验存在 = 没校验）。

**串联判断：** 规则 12 把「完成」定义为 `ahead == 0`。10/01 轮在文件落盘后、commit 执行前被 300s 截断，于是出现一个规则 12 未设想的状态：**`ahead == 0` 而工作区脏**。提交根本没发生，故没有未推送提交，`ahead` 当然是 0——规则 12 读为「已完成」，而交付实际未完成。这与 9/26、9/30 是同一族（假失败/假成功），但层面不同：9/26 是**归属**错配（全局量当自我量），9/30 是**层级**错配（run 结局量当交付量），今日是**覆盖**错配（判据只覆盖链路末段，链路前段「是否提交」不在射程内）。三者合并暴露一个更一般的形态：**一个只校验交付链路某一段的判据，在其余段上等于不存在。** 守卫九说的正是这件事，只是对象从「门禁」移到了「完成判据」：门禁只校验存在 = 没校验，完成判据只校验推送 = 没校验提交。

**新的见解：** **完成判据必须与交付链路的每一段同覆盖——判据的作用域要覆盖交付的全部不可逆环节（此处：文件落盘 → commit → push），少覆盖一段，该段就是静默失败区。** 判据：写完一条完成判据后自问「存不存在一种状态它不覆盖、而在该状态下交付实际未完成」；举得出即判据有盲区。修法 = 把单一量升级为联合量（已立为规则 17：工作区干净 且 ahead 0）。与守卫十六（审计颗粒度须与风险层级同层）同族：十六是「下潜到风险发生的那一层」，本条是「覆盖到交付经过的每一段」——一个管深度，一个管广度。

### 串联4（次，机制轨 × 9/25 串联3 × 「落盘前置」两段写模型）：落盘前置保住「记录」，不保「提交」——不可重建性排序决定截断损失可不可恢复

**来源：** 10/01 槽时间线（22:23:19 启动 → 22:25:35 backup+复盘文件落盘 → 22:27:29 archive+MEMORY 落盘 → ~22:28:19 触达 300s 截断，commit 未执行）+ 9/25 串联3（故障破坏力由关键产物相对故障时刻的写入顺序决定）+ 9/29 串联3 / 规则 14（落盘前置的安全边界是首写段内容类型）+ 规则 16。

**串联判断：** 9/25 给出排序原则（最不可重建的写入最前），9/29 给出落盘前置的安全边界（首写段只放事实与待办）。10/01 轮是这两条的一次「自然实验」：它把文件内容前置落盘，commit 与 push 后置，随后被截断——丢的是 commit 与 push，保住的是文件内容。按不可重建性排序：文件内容（不可从任何其他处重建）> commit（可从工作区文件重建）> push（可从本地 commit 重建）。10/01 轮丢的两个环节恰好都是可重建的，故损失可恢复（本轮收尾即可补齐）——这正是排序正确的证据。反过来，若它把 commit 前置、把文件内容后置，截断将造成文件内容永久丢失（不可重建），同型事故在 supermind 09-24 已发生（记录未落盘即全损）。

**新的见解：** 无需新见解，与 9/25 串联3 合并为同一结论的操作化表述：**交付链路应按「不可重建性」降序落盘——文件内容 > commit > push > 投递。本轮同时验证了它的正面（丢可重建项 = 可恢复）与边界（落盘前置只管记录，commit 起的一切仍暴露在截断风险下）。** 故 300s 超时下，录得「文件在、commit 缺」是预期形态，收尾动作必须显式补齐 commit+push（已并入规则 17）。
