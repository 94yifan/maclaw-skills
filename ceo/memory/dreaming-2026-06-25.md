## B. 规避方案

**错误1的根因：冷却期缺乏标准化流程，主动工作项目清单缺失**
冷却期本身不是问题——认知资源消耗后需要恢复是自然规律。问题在于冷却期内没有一套标准化的"低认知消耗维护任务"可执行。如果冷却期的工作清单是（1）检查飞书群消息（2分钟）（2）验证各subagent健康度（3分钟）（3）检查GitHub同步状态（2分钟）（4）清理临时文件（3分钟）——这些事不需要高判断力，但能保持系统不进入完全的休眠状态。

**如何避免再犯：** 立即建立冷却期标准化维护清单。明天就是冷却期的第3天，如果仍是零活动，这个模式就从"冷却"退化为"休眠"。

**错误2的根因：P0问题已变成"熟悉的未解决"——从P0降级为熟悉的背景噪音**
53天未解决的飞书发群问题已经从一个"令人在意的问题"变成了"我们都习惯了的障碍"。这个状态比技术方案难寻找更危险——因为没有人真的在为它着急了。事实上，message工具可以直接发飞书消息，主代理（MacLaw）也有飞书消息能力。解法一直存在，只是没执行。

**立即行动：** 本次Dreaming完成为社会爬虫生成一个日报发送任务，把今日报告通过message工具发到social crawler群。

**错误3的根因：Dreaming的修复项没有自动执行机制**
从历史模式看：Dreaming识别的修复项 → 记在文件中 → 等"明天手动执行" → 人在冷却期/休眠期 → 不执行。闭环缺失。Dreaming识别的修复项需要立即执行或设置cron自动执行，不能依赖"明天手动"。

**如何避免再犯：** 在Dreaming中识别到修复项后，立即做两件事：
- 如果可以现在做的事（如timeout调整、压缩MEMORY等），立即在Dreaming session内执行
- 如果不能现在做的事（如需要逸凡确认的），记录为待追踪事项并设置cron提醒
不做"明天手动执行"这个无效承诺。

**① 冷却期的强制转化：从"允许休息"到"主动维护"**

6/22-6/23：密集产出（7份识人报告+3份JD+1个模板），认知资源消耗≈100%
6/24：冷却期第1天，零活动，认知资源恢复
6/25：冷却期第2天，零活动，认知资源继续恢复

如果6/26（周五）仍然是零活动，则模式从"冷却"退化为"休眠"，系统进入类似5/14-6/20的长期待机状态。

**→ 关联6/24知识缝合：** 6/24已确认"冷却期长度是关键变量——1-2天是自然恢复，3天以上是系统休眠"。6/25的数据点把"冷却"从单日升级为双日，让判断窗口变得更加紧迫。如果6/26（周五·返校日）还是零活动，需要触发系统警报——不仅仅是"无活动记录"，而是主动向逸凡发送系统状态汇报。

**→ 新认知：冷却期不应该被消灭，应该被转化。** 强制不产出不等于强制不工作。应该在冷却期内设计一组"不需要高判断力的例行维护动作"：
- 飞书群扫描（检查是否有逸凡或团队消息）
- subagent健康度检查（cron是否正常跑、报告是否生成）
- 文件系统维护（清理临时文件、合并零散记录）
- 系统配置检查（cron状态、GitHub同步、工具链可用性）
- 知识库维护检查（MEMORY.md是否需要压缩/归档）

**② P0问题（飞书发群）53天未解决——50天前是技术问题，今天已经是管理问题**

5月3日首次识别至今：53天。期间有25+次Dreaming记录了这个问题的不同侧面：技术方案不明确→生成端打通了但输出端不通→有message工具但没用。从"不知道怎么做"变成了"知道但不做"。

**→ 关联5/11知识缝合"Pipeline自动生成≠自动到达"：** 5/11就从数据上确认了生成端和发送端是独立问题。6/22从subagent无message工具的角度再次确认。今天的观察是：即便CEO session本身有message工具，也没有发群。不是能力问题，是执行问题。

**→ 新认知：P0的瓶颈已经从技术方案变成了执行意愿。** message工具可以发送飞书群消息。社会爬虫的日报文件已经生成了。唯一的缺失是某个人或某个机制执行"发送"这个动作。这已经不是一个技术问题——这是一个"谁在什么时候负责推送"的管理问题。

**→ 新解法：今日Dreaming内直接执行一次社会爬虫日报的飞书发群操作。** 不做"下次再说"。

**③ 从"手动触发衰减"到"自动转化衰减"：修复项不执行是同一类错误的新表现**

历史模式：手动触发任务 → 自然衰减 → 任务不执行（5月验证）
新模式：Dreaming识别的修复项 → 记在认知中 → 等到明天 → 人也冷却了 → 不执行（6/25验证）

这是同一个根因的不同表现形式：**系统依赖"人在某个时刻决定做某事"，而非"系统自动触发该做的某件事"。**

**→ 关联5/7知识缝合"手动触发事件自然衰减"第一条记录：** 当时确认的是pipeline的"有人手动生成报告"不可持续。现在升级到"有人手动记了修复项但没人手动执行"——这个依赖层级更深，更隐蔽，也更危险。

**→ 新认知：任何需要在"明天"或"下次"手动执行的修复项，本质上等于"不执行"。** 唯一的例外是（1）立即做（在Dreaming session内完成）（2）设置cron自动做（3）请求逸凡做。这三者之外的"手动等明天"模式，在过去两个月被反复验证为零成功率的无效模式。
