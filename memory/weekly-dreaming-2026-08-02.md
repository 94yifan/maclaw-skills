## B. 本周学到的关键洞察

### 1. 静默失败模式是 token 黑洞：convert 返回空数组不报错

这次 bug 的本质是「静默失败」——接口失败但不抛错、不重试、不提示，调用方以为成功。这种失败模式最危险，因为它不会触发任何人的警觉，只会让系统在错误路径上反复消耗资源（subagent 反复重试整个写入流程，token 爆炸）。

**复用价值**：任何自动化 pipeline 的接口调用，都必须验证「返回值是否符合预期」而不是「调用是否抛错」。空结果 = 失败，必须显式判定。这条原则从 5 月的"输出可用性检查"教训延续至今，这次是又一次验证：静默失败是系统性风险，不只是偶发 bug。

### 2. SubAgent 单方面建立的协议，必须经过逸凡确认才生效

CEO 在 7/18 单方面确认"固定交付节律"（每周五飞书云文档），逸凡完全不知情，7/31 第三次执行时踩坑。这不是 CEO 的错——是系统设计缺陷：subagent 有自主建立协议的自由，但没有「协议必须经过逸凡确认」的约束。

**复用价值**：任何 subagent 提出的新交付方式/新协议，必须先向逸凡说明并获得确认，不能单方面长期执行。这次的教训是「固定交付节律」这种看似无害的协议，一旦踩中基础设施 bug 就会变成大问题。

### 3. 高质量修复的标准流程：根因 → 三处修复 → 三重验证 → 双备份

这次修复流程值得作为范例：逸凡报问题（现象）→ 定位根因（convert 接口静默失败）→ 三处针对性修复（重试、显式报错、一步写入）→ 三重验证（正常/边界/压力）→ 双备份（修复前原版 + 修复前即时版）→ 明确影响范围（所有 subagent 受益）。

对比 5 月的教训（识别≠修复、修复无统一入口），这次是「识别 → 修复 → 验证 → 归档」完整闭环。说明系统的执行能力在 6-7 月的迭代后确实提升了。
