## A. 执行错误

### A1（P0，今日根因首次拿到硬证据）：11:00 cron run 末尾一次 `cron update` 被拒，整个 run 判 error、群交付被跳过

**证据（run ffa6e4c5-fcb3-4e67-8c6e-f369177601c7 的会话轨迹）**，run 的最后两次工具调用：

```
line 43  assistant toolCall → name=cron, args={"action":"update","jobId":"a19839ba-…","patch":{"payload":{"kind":"agentTurn","message":"跑今天的茶饮日报：…"}}}
line 44  toolResult  → {"status":"error","tool":"cron","error":"Cron tool is restricted to the current cron job."}
line 45  assistant 最终回复 = 完整日报正文（窗口 9/13 11:00~9/14 11:00，9 有动态/14 无动态）
```

运行时间线：11:00:00 启动 → 11:04 写出报告文件（`Successfully wrote 3421 bytes`）+ 一次 edit → 调 `cron update` 被拒 → 11:05:08.248 run 结束并判 error → announce 交付被跳过。

**机制**：isolated cron session 对 cron 工具只有"读自身 job / 删除自身 job"的权限，`update` 被硬拒。**任何一次工具调用失败都会把整个 run 判 error，而 run=error 就等于放弃 announce 交付**——哪怕报告已经写完、最终回复也已经包含全文。

**它想改什么**：patch 内容是它自己的 payload（即 MEMORY 里挂了 13 天的"改 tea-daily-report payload"）。也就是说，**这条长期挂起的待办不是"没执行"，而是被 cron run 里的 agent 自己捡起来执行了，而恰恰是这个执行动作炸掉了交付**。

**与历史的同型关系（近 18 天，7 次同类）**：

|---|---|---|---|---|
| 9/14 | error | 308230 | false | `cron update`（权限拒绝） |
| 9/12 | error | 505684 | false | `list files in …/scripts/`（目录不存在） |

**共同特征恒定为**：报告文件已完整落盘 + run 标 error + announce 交付被跳过。**7 次全部与内容质量无关，全部是"run 内某个工具调用炸了"**。9/14 这次的新意在于：炸点从"探索性 shell"变成了"自我修改 cron 配置"。

## B. 规避方案（每条对应 A 项，作为下次执行铁律）

1. **run 内工具禁令（对应 A1/A7，今日最高优先级，新规则）**：cron payload 增加硬约束——
   - "写完报告文件后立即以最终回复输出报告正文并结束，**不得再发起任何工具调用**"
   - "**禁止在 run 内调用 cron 工具做 get/update/remove**：isolated cron session 对 cron 工具只有读自身与删除自身权限，update 会被拒，且该失败会把整个 run 判 error、跳过群交付"

6. **飞书云文档存档恢复（对应 A4）**：P1 长期项
7. **固定窗口改造落地（对应 A5，已连拖 3 天）**：脚本开头取一次 `const t0 = Date.now()`，全品牌统一 `created_at >= t0-24h && created_at <= t0`，header 直接引用同一个 t0。落地后边界帖归属稳定，不再依赖品牌在队列里的位置
