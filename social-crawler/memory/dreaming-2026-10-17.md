## A. 执行错误

### A1（P0·本日核心）：10-16、10-17 连续两日零日报，且 10-16 复盘断档
- 事实：两日无 raw、无日报、无 10-16 dreaming；11:00 排期点在 run log 中**连失败记录都没有**。
- 定性：**不是日报链路的问题，是宿主进程的问题**。过去 12 次失败样本全是「跑了但交付失败」（文件在、delivery 丢），今日是**根本没跑**。把这两类混为一谈会继续在 prompt 和脚本层修一个进程层故障。判定方法必须升级：`run log 无记录` = 调度层/宿主层故障；`run log 有记录且 error` = 执行层故障。

### A2（P0·根因）：`openclaw.update.once` 死循环 6390 次，每次 SIGTERM 网关
- 事实链完整：Node v25.8.1 不在目标版本区间 → npm preinstall 失败 → update 进程杀网关重启 → launchd 重投任务 → 再失败。`runs=6390`、`immediate reason=inefficient`（launchd 自己都判定为低效重复）。
- 后果：网关可用性接近零，所有 cron（7 个 agent、11 个 job）全部失效，不只是日报。
- **这不是「模型抖动」，也不是「Provider 故障」**。10-15 那次的 `LLM request failed` 是 provider 层；今日是**安装/升级层 + 进程监管层**。失败形态第四次迁移。

### A3（P0·放大器）：网关未被 launchd 托管，被杀后无自愈
- plist 存在但未 bootstrap，`launchctl print` 查无此 service；当前进程是手动前台运行。
- → 单点人工依赖：网关死了必须有人手动敲命令，否则一直死。两天空窗不是「没发现」，是「没人拉起」。

## B. 规避方案（落定为铁律）

### B1（P0·需逸凡或主 session 执行）停掉 update 死循环
- 动作：`launchctl remove gui/501/openclaw.update.once`（或先 `kill -TERM 86543`）。
- **验证标准（必须三查，缺一不算修好）**：① `launchctl list | grep openclaw.update` 无输出；② `/tmp/openclaw-update.log` mtime 停止增长（间隔 60s 两次 `ls -la` 比对）；③ 网关存活时长 >10 分钟（此前存活天花板 <1s）。
- **本会话无权限执行，且属系统级动作，不自行操作**（守卫：不可逆/高风险先确认）。本文件只记录命令与验证标准。

### B2（P0）：恢复网关 launchd 托管
- 动作：确认手动进程退出后 `launchctl bootstrap gui/501 ~/Library/LaunchAgents/ai.openclaw.gateway.plist`。
- 验证：`launchctl print gui/501/ai.openclaw.gateway` 能查到；`kill -TERM` 网关进程后 10s 内自动重启（KeepAlive 生效实测）。
- 意义：这是**唯一能让「网关死了会自动起来」的机制**。没有它，任何一次被杀都是无限期停机。

### B3（P0）：Node 版本与 update 目标对齐后再升级
- 二选一：`brew install node@24`（切到 24 LTS）或升到 `>=26.1.0`；随后再执行 `openclaw update --tag 2026.10.4`。
- **禁止**：在 Node 仍是 25.8.1 时再次触发 update。**每一次失败重试都在杀网关**，重试成本不是「浪费流量」，是「全站停摆」。
- 升级前置校验（固化为一条命令，先跑后升）：`node -v` 输出必须匹配目标版本 `engines` 区间。

### B4（P1）：故障判定分层（写进 MEMORY，替代旧的单一 status 判据）
- 第 1 层 调度层：`cron_run_logs` 有无记录。无记录 → 查网关进程与 schedule 是否被推走。
- 第 2 层 执行层：有记录且 error → 看 error 文本三类：`interrupted by gateway restart`（宿主层）/ `LLM request failed`（provider 层）/ `Process failed`·node 脚本（脚本层）。
- 第 3 层 交付层：文件是否落盘 + `delivery_status` 是否 delivered。
- **任一层的结论不得跨层套用**（守卫二十：读数 × 判断 × 动作逐段对齐）。

### B5（P1）：补跑不等于补数据
- 断档补跑必须显式声明窗口：`上次成功窗口右端点 → 本次实际抓取时刻`，并在报告 header 标注「空洞区间」与「重叠区间」。今日应记：**10-16 11:00 – 10-17 23:35 为数据空洞（约 36.5 小时）**，其中 10-17 23:35 之后的内容可抓，之前的不在 24h 窗口内的需明确标注为不可回溯。

### B6（P1）：给日报加「调度层」guard
- 现在只有「跑完但失败」的兜底设想，缺「根本没跑」的检测。方案：11:10 由独立轻量 job 检查 `/tmp/tea-raw-<今天>.json` 与 `memory/weibo_daily_<今天>.md` 是否存在，缺失即发群告警（不发报告，只报警）。
- 注意：guard 自己也要能在网关死时报警——**网关全死场景下唯一可用的外部通道是 launchd 级的 watchdog 脚本**（独立于 OpenClaw 进程），这是本次最重要的一条架构结论。

### B7（P1）：header 自校验（第 2 天未落地）
