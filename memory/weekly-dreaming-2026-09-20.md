## B. 本周学到的关键洞察

### 1. 失败域完成第二次迁移：送达层 → 收尾层

上周结论是交付层未加固（announce 同型失败 8 次）。**本周 announce 类失败退场**（tea-daily 5/7 成功），但暴露出新的一层：dreaming 的**收尾工具步**。

18/22 次失败发生在写完文件之后的验证/归档/提交环节。含义很直接：上周的教训是"生产出来了不等于送达了"，本周补上后半句——**送达了不等于 run 成功地收尾了**。系统加固的节奏总是落后缺陷迁移一步。

### 2. 失败在时间上高度聚集，指向并发争用或共享资源冲突

8 个分身的 dreaming 全部排在 22:00-22:18，间隔仅 2-4 分钟，每晚必死 2-4 个。它们同时读写同一个 git 仓库、同时调模型。最稳定的失败点是 **cfo 的 22:01**：9/19 超时 300s、9/20 Process kind-ember failed，连续两晚同一时刻同一分身。

这不是随机故障，是排期结构问题。集群窗口不拆，同样的事下周还会发生。

### 3. tea-daily 的失败带 300s 特征——payload 首次改造没吃透

成功 run 244-299s，失败 run 308/310s（9/18 例外 500s 成功，所以不是硬上限，但失败高度贴近 300s）。与"payload 里探索步骤吃掉预算"的判断一致。

09-14 记录过 payload 闭环首次破 0（挂账首次闭环），说明改过一轮；但 9/19 换了个失败形态复现。**改了一次不等于改对了。**

### 4. 连续成功不等于修复——本周被系统层独立验证

09-17 记录交付三连绿 + morning-crawl P0 闭环，信心抬升；09-19 tea-daily 立刻失败。"三连绿"只是窗口内没触发缺陷，不是缺陷被消除。这正是分身本周自己缝出来的判断，在系统层被独立撞到——规律跨层成立，可信度反而更高。

### 5. 无告警的失败等于没有失败信号

22 次失败全部 notifyPolicy=silent，无人被通知。所以系统"知道自己失败"却没让任何人知道，只留下一个 22 的数字。**沉默的失败会以任务积压的形式复利**——报告里写"待逸凡执行清单连续 12 天不清零"，本质是同一个机制。
