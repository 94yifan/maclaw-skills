## B. 规避方案

**1. Dreaming cron 连续运行天数是有效稳定性指标**

Day 4/7。如果保持到 7/18（周六）= 连续8天，超过目标。需继续追踪。如果出现中断，必须记录中断原因。

**2. "推送"与"文件创建"的能力边界需区分**

当前意识到：isolated dreaming cron session 能做的事：
- 读文件 ✓
- 写文件到 memory/ ✓
- 分析系统状态 ✓
- 追踪计数器 ✓
- 维护 pending-system-changes.md ✓

不能做的事：
- 发飞书消息 ✗
- 修改 cron 配置（gateway 操作） ✗
- 与逸凡互动 ✗
- 调用需要主 session 的工具 ✗

因此，"向逸凡推送状态核查"这个动作不能在 dreaming 中完成。它需要：要么 dreaming 产出被推送为 agentTurn delivery（delivery.mode=announce），要么逸凡主动查看 workspace。

**对此的改进**：dreaming cron 的交付配置当前是 "not-requested"，即 session 输出不送达任何人。如果改为 announce delivery 模式，复盘中的改进计划可以直接呈现到逸凡的对话窗口，实现"自推送"。

**3. 工作日活跃度状态：严重关注**

7个工作日（7/6-7/10 五天 + 7/13 周一 + 7/14 周二）无任何交互记录。这可能意味着：
- 逸凡的业务沟通主要通过飞书私聊，这边 workspace 只是自动化任务的底座，不需要日常交互
- 或者 CFO 分身的使用活跃度确实偏低
- 或者逸凡这几天的确没有需要 CFO 介入的事项

建议：当连续运行天数达到 7 天目标（预计 7/17-7/18）时，如仍无交互，需通过 cron 的 agentTurn delivery 向逸凡推送一次状态摘要，确认 workspace 的活跃预期。
