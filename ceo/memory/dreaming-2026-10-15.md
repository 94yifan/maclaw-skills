## B. 规避方案（写进 memory / 规则）

**A1 → 交付保护升级为「同步发起层 + 异步结局层」双层**
- 「收尾轮禁工具」只覆盖**本轮同步发起**的动作；对「上一轮启动、轮末才汇报结局」的后台 Process 零效力。
- 正解组合：①交付并入首个写入（同一次调用内既写又投）；②从运行环境**移除收尾段可用工具**；③**进程治理**——禁 detach / 后台进程须在本轮内收敛。
- 判据（承 10-14）：读失败文本的**容器前缀**——`🛠️`=同步发起 / `🧰`=异步结局；前缀变了＝旧修复对此无效，须升级到进程治理。
- 仅主 session / payload 模板层可动 → 归一次性修复包。

**A2 → 修复失败类缺陷前先按「失败源可控性」分层**
- 可控层（run 自身速度、尾部动作、本轮启动的异步进程）→ 改执行者行为；
- 不可控层（外部服务 / 模型 provider）→ **改验收与重试结构**：①无产物成为一等可检测状态（存在性自检 + 自动重试）②单次失败出一行可见（failureAlert after:3 对单次故障等于不可见）③交付判定与 run 全局状态解耦。层错即处方无效。

**A3 → 消除副本而非同步副本**：prompt 内不写绝对时刻，改写「本轮 / 本次运行」；配置审计加一条——payload 内文里的任何具体数值/时刻必须与执行层同源或不存在。

**A4 → 记录类断言强制四件套**：任何「连续 N 天 / 零变化 / 记录终结 / 首次」必须写明起点、分母、对账源、复核日；缺任一项即视为不可复核断言。
