## A. 执行错误

### A1（P0 · 判断层 · CEO 自曝）连推 32 天的「唯一决定项」是从未被推导过的假处方

- 事实：见头条一。两夜 7 个 error，timeout 型仅 1 个（14%）；我却在 30+ 个夜晚把「timeout 300→600」作为唯一决定项推送，从未按失败原因分层。
- 根因：**处方是继承物，不是推导物。** 一个被标为「最高优先级」的挂账项，会在每个夜的头部格里被原样复述；复述产生「已在处理」的完成感，从而免于被重新推导（承 10-05 缝合5「假完成是不动点」）。
- 二次损伤：**头部格是容量为 1 的资源（10-03 缝合2）。** 假处方占住头部格 = 真根因（孤立会话工具可用性）32 天进不了诊断队列。**挂账项的代价有两笔：延迟执行 + 遮蔽诊断，后者从未被计价。**

### A2（P0 · 交付层 · 承接 10-05）10-05 书稿交付停在 open 态，且无机制收口

- 事实：10-05 交付的 2.55 万字书稿与「62 vs 64 页」的待确认问题一并送达；逸凡未回复；今日零交互 → 交付实际处于「已送达但未闭合」。
- 问题：遥测侧读 delivered（送达成功），业务侧未完成（待决问题悬空）。**「已送达」被当成了「已闭合」。** 且 open 态无失效期——不主动收口就会无限期悬空（同 09-27 缝合1「负面结论默认寿命无限」）。
- 根因：交付缺一个终态维度（closed / open），只按投递结果记账。

## B. 规避方案

1. **（对应 A1，落为硬约束）「提高阈值」类处方出手前必做失败原因分层；分层表未出，处方不得进入头部格（唯一决定项）。**
   - 决策点：每晚 dreaming 摘要末尾「唯一决定项」的生成处。
   - 动作：写决定项前先跑一次两夜 run log 分层（`cron_run_logs` 取 status/error/duration），按 超时 / 工具失败 / 逻辑失败 / 交付污染 四类计数；**主因占比 < 50% 则该处方降级为「记录项」，不得占唯一决定项。**
   - 本会话已执行（两夜分层表见头〇），并把 timeout 处方从「唯一决定项」降为「记录项」，同时改为「拆治」：①阈值（主 session）②孤立会话 sqlite3/git 工具可用性（新识别，主 session）。
2. **（对应 A2）交付记两个终态字段：`delivered`（投递）+ `closed`（无待决问题）。** open 态必须在下一轮摘要里带「待决项 + 我方可继续动作」复述一次，并绑一个决策时点（默认动作或截止日），不靠等回复。
3. **（对应 A3）failureAlert 与 SOUL 守卫编号合并为「一次性系统修复包」，不再日推**——避免每晚重复推送消耗头部格（本条即是 A1 的自我应用）。
4. **（对应 A4）凡拟引用跨主体收敛结论，先在本会话用原始源独立重算一次；重算不出或方向不同，降级为「待复核」。**

## D. ★ 知识串联（核心）

### 缝合1（主 · 元层 · CEO 自应用）：「假处方占据头部格」——未经验证的最高优先级处方，代价是遮蔽诊断，不是延迟执行

- **今日证据：** ①timeout 处方 32 天、每晚占 CEO 唯一决定项，今日两夜全量复核证明它只覆盖 1/7（14%）；②真根因（孤立会话 sqlite3/git 工具失败，6/7）32 天从未进入诊断——因为头部格被占；③SC/supermind/BM 今夜各自独立得出同一修正。
- **关联：** 10-03 缝合2（头部只有一格：机械挂账动作在容量 1 的槽位里永远最后）+ 10-04 缝合1（收敛度 = 诊断的重复，不是动作的落地）+ 守卫七（规则须绑决策点）+ 守卫十七（完成态须自证）+ 10-05 缝合5（假完成是不动点）。
- **新认知：** 10-03 说「挂账动作抢不到头部格」；今日补出反面且更狠一层——**头部格被一个「未验证的处方」占据时，它的成本不是「没被做」，而是「正确诊断进不来」。** 复述一个继承来的处方会制造「已在处理」的完成感，从而免于被重新推导。判据：凡一个动作被连续 ≥3 轮标为「最高优先级」而未执行，第五轮的正确动作不是再推一次，而是**先验证它是不是真因**（分层统计）。**一个假处方在头部格待的天数，等于真根因被延后的天数。**
- **管理同构：** 公司里挂在「头号战略议题」上三年的假设（例如「增长靠开新店」），三年没被执行，也三年没被证伪——它占着唯一的战略议题位，把真问题（单店模型）挡在门外。处方本身没被验证，却因为「一直挂在最高优先级」获得免检权。

### 缝合2（主 · 交付层 · CEO 自应用 · 承接 10-05 缝合1）：已送达 ≠ 已闭合——交付的第二个终态字段

- **今日证据：** 10-05 书稿 5 次全量重发后停在「62 还是 64 页」待确认；逸凡未回；10-06 零交互 → 交付 delivered=true 但业务未完成（open 态）。10-05 缝合1/2/3 已立「交付层零守卫」（重发 5 次、页数自相矛盾、一致性检查滞后），今日补出第四个缺口维度。
- **关联：** 10-05 缝合1（守卫体系继承观察对象形状）+ 10-05 缝合3（一致性检查须前置为交付门）+ 09-27 缝合1（负面结论默认寿命无限）+ 09-21 缝合4（交付绑 run 状态 = 机制缺位）。
- **新认知：** 交付的终态此前只有一个字段（delivered：投递是否成功）。今日补出第二个——**closed：交付物是否已无待决问题。** 两者正交：`delivered=true, closed=false` 即 open delivery。**open 态不会自然闭合，也不会自然过期**——它需要「下一轮主动复述待决项 + 绑一个决策时点（默认动作或截止日）」，否则静默死亡。判据：凡交付物内含「请确认 X」的问题，交付完成度按 closed 记，不按 delivered 记；下一轮摘要必须带该问题，直到 closed。
- **管理同构：** 给客户发提案 + 一句「报价请您确认」，客户没回 = open delivery，不是交付完成。乙方若只统计「已发出份数」，会把一堆悬空交付记成已完成。
