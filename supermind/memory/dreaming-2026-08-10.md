## A. 执行错误

### A1. pipeline step_2 崩溃：写 pre_research.md 时父目录不存在（pipeline_error.md 新失败）
**事件**：16:51 pipeline_error.md 记录 step_2 失败：`No such file or directory: .../output/content/pre_research.md`。查看 pipeline.py step_2 代码（line 310-347）：step_2 用 `open(research_path, "w")` 直接写文件，但**没有先 mkdir 父目录**。首次运行（或 Step 0 清理后）output/content 目录不存在时必然崩溃。同日后续运行成功是因为 content 目录已被创建。
**根因**：step_2 缺少 `research_path.parent.mkdir(parents=True, exist_ok=True)`。v1.6 P0-1「Step 0 自动清理 content/charts 历史文件」会删除目录内容，配合这个缺陷，首次运行必崩。
**分析偏差**：08-09 Dreaming 检查 pipeline_error.md 时 mtime 是 08-04（无新失败），今天 16:51 的新失败被 Step 0 新鲜度检查捕获——这是 07-31 固化的规则第一次在实际生产中抓到新失败，规则有效。

### A2. 品牌名拼写错误：杜亚 → 度亚（17:10 早期版本 7 处）
**事件**：17:10 产出的第一版 docx 中，品牌名被写成「度亚」7 处（64pt 封面标题、第4章标题「度亚（DUYAAR）」、附录A标题等），英文名也错成 DUYAAR（正确 DOOYA）。最终版（22:25）已全部修正为「杜亚 DOOYA」，且 commit 25f80bb 覆盖了错误版本 b53230c。
**根因**：早期运行中品牌名在某一环节（config 输入或内容生成）被写成同音字「度亚」，且**没有任何检查环节拦截**——QA D-6 只查文件名格式，不查品牌名正确性。这个错误是运气好被后续重跑覆盖了，不是被机制拦截的。
**严重性**：品牌名是客户交付的红线——一旦带错别字的版本发到逸凡/客户手里，是直接事故。这是推理守卫三（归属准确性）在生产链路上的缺口：守卫管住了数据来源，没管住品牌名本身。

## B. 规避方案

1. **step_2 加父目录创建**（针对 A1）：pipeline.py step_2 写 pre_research.md 前加 `research_path.parent.mkdir(parents=True, exist_ok=True)`。一行修复，杜绝首次运行崩溃。这是 07-28 养生堂「连续失败 2 次强制诊断」规则之外的另一个防御点——崩溃原因要能自愈。

4. **替代采集 SOP 升级为多通道 failover 清单**（针对 A4，SP 已提出）：按通道健康表顺序尝试（微信搜狗精确品牌词 → Bing 加引号品牌全名 → 搜狗网页验证码则跳过当日 → 红餐网/垂直媒体首页），每次执行后把通道可用状态写入 memory，平时维护不现场试错。

## D. ★ 知识串联（核心）

### 缝合点1：智能窗帘赛道 = 供应链品牌 vs 生态品牌 vs 渠道品牌三态并存 × 品牌三层战场（05-17）× 品类纵深 vs 品牌溢价（07-15）

杜亚项目提供全新行业样本：杜亚（宁波电机厂出身，B 端供应链基因，13 品类全行业最全，价格带 499-3099 全覆盖）vs 米家/Aqara（互联网生态打法，全屋智能入口）vs 欧瑞博/如鱼得水/摩力克（全屋智能/窗帘布艺渠道商）。这印证并扩展了 05-17 品牌三层战场框架——三层战场回答「竞争维度」，杜亚案例补充了「竞争主体类型」：同一赛道的竞争不是同构品牌互搏，而是**供应链品牌（成本/品类深度）、生态品牌（连接/入口）、渠道品牌（服务/场景）**三种物种的跨物种竞争。杜亚用 13 品类+全价格带覆盖做防御（品类纵深逻辑，07-15 缝合点3），但 C 端品牌认知弱——「全品类覆盖」是 B 端供应链思维，不是 C 端品牌思维。整合结论：给客户做智能家居/硬科技品类诊断时，先判断竞争主体类型（供应链/生态/渠道），再套三层战场分析——跨物种竞争里，「品类最全」不等于「品牌最强」。

### 缝合点2：证据层级生成端缺失 × 推理守卫三升级路径（07-14 缝合点3 × 07-26 缝合点4）→「从提醒到机制」只完成一半

07-14 提出输出完整性守卫（每个信息单元带身份标签），07-26 缝合点4 宣称「推理守卫三从 SOUL 提醒升级为 Pipeline 内置硬检查」。杜亚 E-4（97% 未标注）证明这个升级只完成了一半：QA 端有 E-1~E-4 检查规则，但生成端 content_gen 没有强制输出 tier——检查器很严，生成器不配合，等于白查。整合结论：**任何「检查机制」必须与「生成机制」成对落地**——QA 规则新增时，必须同步在生成 prompt 中强制对应输出格式，否则 QA 永远在抓「生成器根本没做」的错。这是 v2.0 证据层级系统的第二次补课（第一次是 07-27/28 的路径断裂），说明「单端落地」是 Pipeline 特性升级的系统性陷阱。

### 缝合点3：品牌名错字 × 推理守卫三（归属准确性）→ 守卫体系的「实体身份」盲区

杜亚→度亚（+DUYAAR 英文名错误）暴露推理守卫三的盲区：守卫三管「数据有没有来源、能不能指出出处」，但品牌名/公司名这类**实体身份**本身没有被校验——数据来源正确但实体名写错，同样是归属错误。整合结论：推理守卫三需要补充「实体身份校验」子规则——报告中的品牌名、创始人名、公司名必须与 config 或权威来源逐字比对，同音错别字（度亚/杜亚）和形近错误（DOOYA/DUYAAR）都要拦截。QA 层落地为品牌名正确性检查（见 B2）。这也是「输出完整性守卫」的实体维度补全。

### 缝合点4：SC 单通道依赖 × SP 替代采集单通道 SOP × 08-07 双轨信号源 → 单点依赖是系统级结构缺陷

08-07 缝合点3 确立双轨信号源（替代源保广度、主源保精度）。今天双轨同时断：SC 主源缺失 3 天，SP 替代源（搜狗）也被验证码拦截。SP 复盘正确指出：替代采集 SOP 是单通道依赖，与 SC 日报的 CDP 单通道依赖同构。整合结论：**「单点依赖」是跨 workspace 的系统级结构缺陷**——SC 依赖 CDP 单通道、SP 依赖搜狗单通道、Dreaming 依赖晚间模型单时段。凡依赖单一通道的机制，都必须预设 failover（多通道清单+通道健康表+降级路径）。这扩展了 07-31「验证尝试缺乏标准路径」：不仅要有标准路径，路径本身必须多通道冗余。

### 缝合点5：茶底军备竞赛（SP 今日串联1）× 时令鲜果三段论（05-20）× 品类定义权（05-12/05-16）→ 竞争主轴迁移的三段论验证
