# 第4章 工具

## 本章核心论题

工具是 Agent 连接"大脑"与真实数字世界的"手脚和感官"。本章系统回答三个递进问题：五类工具各自的设计重点是什么？事件驱动的异步架构如何让 Agent 在真实世界中可靠运行？当工具数量膨胀到成百上千时，Agent 如何高效发现并使用它们？整章论证围绕一条暗线——工具的"表达形式"与"组织方式"同等重要，后者在规模变大时甚至决定前者能否生效。

## 关键论点与框架

### 1. 五类工具按"调用方向 × 作用对象"区分，事件触发工具的"注册/触发"二阶段使其独树一帜

五类工具：感知工具（Agent 主动获取信息）、执行工具（Agent 主动改变世界）、协作工具（Agent 驱动其他 Agent 或人类）、用户沟通工具（Agent 向用户传递信息）、事件触发工具（Agent 注册、外部触发）。前四类由 Agent 主动调用，最后一类涉及两个时刻——注册时声明关心什么事件，触发时外部事件异步回调唤醒 Agent。

%%H%%工具类型不仅决定设计重点，更决定 Agent 的时空存在方式：前四类定义 Agent "能做什么"，事件触发工具定义 Agent "什么时候做"。%%/H%%

> 出处：4.1 节，表4-1。

### 2. Agent 能力有两种根本表达形态——专用代码工具 vs Skill + 通用执行器——选择取决于参数复杂度、变更频率和模型能力

专用工具确定性高、可测试，但每个占据数百 token，数量膨胀破坏 KV Cache。Skill + 通用执行器用自然语言描述操作流程，Agent 通过终端或代码解释器执行，只需少量通用工具即可覆盖大量场景。例如"部署应用"的 Skill 写成 `npm run build → docker build → kubectl apply`，Agent 通过 bash 逐步执行，无需为每一步创建专用工具。

%%H%%选择的关键三维权衡：参数嵌套复杂用专用工具（schema 引导传参），频繁变化用 Skill（改文本比改代码快），SOTA 模型可以多靠 Skill 来减少工具总数。%%/H%%

> 出处：4.2.1 节。

### 3. 工具粒度的核心标准是功能相似性和使用场景重叠度——100 个工具即达 LLM 选择瓶颈

以文档处理为例，`extract_pdf_text`、`extract_docx_content` 等应统一为 `read_document`，通过 `file_type` 参数区分格式。整合使 LLM 只需记住一条规则，也便于扩展新格式。但图片 OCR 和视频关键帧提取虽都是"内容提取"，参数形态和延迟特性差异大，强行合并反而模糊语义。当功能相似但参数集差异大、或使用频率极高时，保持独立更合理。%%H%%超过 100 个工具时，即使最先进的 LLM 也容易选错。%%/H%%

> 出处：4.2.2 节。

### 4. 通用工具优于专用工具（除非有明确安全/权限/性能理由）——利用 LLM 代码生成能力而非限制它

与其提供四则运算计算器，不如提供通用 `code_interpreter`，在沙盒中安装 sympy、numpy、pandas 等库，让 Agent 通过 Python 完成任意计算。%%H%%一个 Python 解释器代替数十个特定工具，还给 Agent "元能力"来处理预先未想到的边缘场景。但涉及生产数据库写操作时，专用工具能提供更精细的权限控制。%%/H%%

> 出处：4.2.3 节。

### 5. 工具描述的核心是告诉 LLM "什么时候用"而非"能做什么"——反例和示例比规范约束更有效

说"搜索相关内容"远不如说"当需要获取实时信息或查找未知事实时使用"。文件搜索工具应明确"只能基于文件名匹配，不能搜索内容"——大多数调用失败的根因不是模型不知道工具能做什么，而是不知道它不能做什么。%%H%%参数描述用具体例子而非抽象规范："2024-03-15T14:30:00Z" 而非 "RFC3339 格式"，模型在执行复杂多工具任务时注意力分散，例子让它直接套用。%%/H%% 加入 1-5 个真实调用示例后，准确率可从 ~72% 升至 ~90%。

%%H%%当 Agent 频繁选错工具，优先修正工具描述而非怀疑模型能力——描述修正的投入产出比通常远高于模型升级。%%/H%%

> 出处：4.2.4 节。

### 6. 参数传递保真性是比功能缺失更隐蔽的反模式——静默转换制造了模型无法诊断的系统性偏差

两个典型反例：（1）Cursor 2026 年初版本中参数传递层将中文弯引号 \u201c/\u201d 静默转为英文直引号，模型看到的内容和工具操作的内容不一致，反复报"未找到匹配"却无法诊断原因。（2）某 IDE 的 bash 工具在所有 `git commit` 中静默注入标记参数，旧版本 Git 不支持的参数导致永续报错，模型反复调整提交信息均失败。

%%H%%模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差。若必须规范化处理，需在描述中声明并在返回中告知模型。%%/H%%

> 出处：4.2.5 节。

### 7. 工具设计经历三代演进：API 封装 → ACI（Agent-Computer Interface）→ 示例驱动 + 动态发现 + 代码编排

ACI 研究 Agent 如何与计算机交互，核心是让工具对 Agent 友好。第三代优化三问题：工具如何被准确调用（示例驱动）、如何被发现（动态发现）、如何被串联（代码编排执行）。%%H%%代码编排的核心洞察：传统方式像每做一步写邮件汇报——这些来回即 token 消耗。代码编排让 LLM 一次性生成脚本，中间变量留在执行环境，token 消耗可降低约两个数量级。%%/H%%

> 出处：4.2.6 节。

### 8. MCP 统一互操作但上下文开销随接入膨胀——延迟加载和渐进式披露是工程必要补充

MCP（Anthropic 2024 年底发布）采用客户端-服务器架构，定义三类原语（工具、资源、提示模板），支持 stdio（本地）和 Streamable HTTP（远程）。%%H%%一次开发处处可用——一个 MCP 服务器可同时被 Cursor、Claude Desktop、OpenClaw 等任何兼容客户端使用。%%/H%%

但仅 5 个 MCP 服务器就可能引入 ~55,000 token 的工具定义开销。Cursor 的缓解方案是将工具描述同步到文件夹，Agent 默认只看索引——A/B 测试显示相关任务 token 总量减少 46.9%。Pi Coding Agent 甚至核心刻意不内置 MCP，优先把能力封装成 CLI + Skills。社区扩展 `pi-mcp-adapter` 展示折中：模型默认只看 ~200 token 代理工具，通过"搜索→查看→调用"按需发现。

%%H%%是否采用 MCP 作为互操作协议与是否在会话启动时暴露所有 MCP 工具定义是两个独立决策：后端可保留 MCP 生态兼容性，前端以渐进式披露收敛 token 开销。%%/H%%

安全风险：（1）工具描述投毒——恶意服务器的 description 直接注入模型上下文夹带指令；（2）供应链攻击——后续更新引入恶意行为；（3）同名工具遮蔽——混淆路由；（4）凭证管理风险。缓解：接入前审查描述、锁定版本、最小权限凭证。第五章将用 Simon Willison 致命三要素（私有数据 + 不可信内容 + 对外通信）做系统风险评估框架。

> 出处：4.3 节。

### 9. 多模态感知有三条路径：原生多模态（上限最高）→ 工具化分析（灵活经济）→ 提取为文本（最省 token 但损信息）

原生多模态通过 ViT 将图像分割为 Patches，与文本共存于共享嵌入空间，模型可直接"看到" PDF 的页面布局和图表。提取为文本的两阶段过程对纯文字 PDF 更省 token（一页截图上千 token vs 文字几百 token），但丢失所有版式和图表信息。工具化分析（`analyze_image`、`analyze_pdf`）接受多模态文件和自然语言问题，内部调用多模态模型，上下文只保留简短问答。实验 4-2 在 `multimodal-agent` 项目中系统比较三种策略：原生模式理解图表和布局最佳，文本提取模式对纯文字文档成本效益最高，工具化模式在交互场景中灵活——低成本处理多数查询，需要时再深度分析。

%%H%%三种多模态路径本质是"精度 vs token 效率"的权衡：原生多模态理解最深但消耗最大，工具化是当前 SOTA 模型不支持原生时的最实用折中。%%/H%%

> 出处：4.4.1 节，实验 4-2。

### 10. 执行工具安全需五层防护——输入验证 → 权限控制 → 提议者-审核者审查 → Sidecar 门控 → 沙盒隔离

输入验证要快速失败而非"智能"修正。权限控制中黑名单不能是唯一手段——攻击者可变形命令绕过简单字符串匹配，需结合语义解析理解命令实际意图（第五章详述）。%%H%%提议者-审核者的核心设计：两个模型来自不同家族但能力相近（引入认知多样性、不同背景不易犯相同错误），约束一致但关注点不同（提议侧任务完成、审批侧风险控制），审批失败作为"工具调用失败"的自然结果加入轨迹。%%/H%% 事后验证的要诀是模态切换——生成文档后渲染为视觉输出再检查排版，而不是让第二个模型重读相同内容。作者还提出了完整的执行安全骨架伪代码：从解析 schema、权限检查、风险分类、独立审查到沙盒执行、结果验证——其中输入隔离是关键边界，Reviewer 只看到工具名、解析后参数和权限元数据，不接触可能携带提示注入的完整轨迹。

Sidecar 机制与主模型流式输出并行运行，对每次工具调用做独立安全判断。关键设计是输入隔离——只读结构化字段（`{tool: "bash", command: "rm -rf /tmp/data"}`）不读主模型思考过程，防止提示注入绕道。配备拒绝熔断器：连续多次拒绝后回退到人工判断。%%H%%Sidecar 与提议者-审核者的本质区别：前者做简单安全分类（轻量模型胜任），后者审查开放式思考（需相似能力模型）。%%/H%%

沙盒隔离按强度：进程级（同用户权限）→ 容器（Docker，独立文件系统网络栈，共享内核）→ microVM（Firecracker，独立内核，硬件级）。Python venv 不是沙盒——只隔离包依赖，对文件系统和网络无约束。应视部署场景选择隔离层级：本地开发用进程级即可，生产环境或处理不可信输入需容器乃至 microVM。

执行工具还面临感知工具无须考虑的问题——取消与超时下的副作用判定。核心对策是幂等性：操作携带唯一标识使服务端能去重；不可幂等操作（如发送邮件、对外转账）应采用"预检-确认"两段式——第一段校验预演返回确认令牌，第二段凭令牌执行，失败后不盲目重发而是交回上层重新走预检。此外，执行工具还需完善的可观测性：详细日志（调用时间、参数、结果、耗时）、审计追踪（谁在什么上下文下为什么执行）、性能指标（频率、成功率、耗时）和告警机制。

> 出处：4.5 节，实验 4-3。

### 11. 协作工具的核心是子 Agent 生命周期原语 + 上下文来源标注——后者既是组织问题更是安全防线

子 Agent 价值在专业化分工——各自独立优化提示词、工具集和知识库，避免冲突。三组原语：启动与取消（`spawn_subagent`、`cancel_subagent`——任务失去意义时及时终止止损）、消息传递（子 Agent 运行期间补充指令或追问，反向也可以汇报进展或请求澄清）、发现（`list_agents`，与 MCP 的 `tools/list` 同思路但列出的是 Agent）。在这组原语之上可承载同步调用、异步调用、流式协作和多轮交互四种协作形态（第十章详述）。

提示词关键：上下文来源明确标注 `[FROM_MAIN_AGENT]`、`[FROM_USER]`、`[TOOL_RESULT]` 防混淆与提示注入——子 Agent 可能接收多来源信息，未标注时极易混淆指令来源。任务边界需明确界定什么归自己管、什么需转交上报。

HITL 需建立学习闭环：(1) 超时和降级策略——"5 分钟无响应则采用保守策略"，紧急多渠道通知、普通只发邮件；(2) 人类批准/拒绝附带理由作为反馈数据——可归纳的判断原则进知识库/Skill，高维而隐式的偏好进后训练数据（第八章详述如何评价轨迹并选择更新载体）。

> 出处：4.6 节。

### 12. 事件驱动异步架构的根本矛盾是"训练同步 / 部署异步"——LLM 期望严格的同步序列，但真实世界事件随时可能打断

同步架构像排队柜台，异步像多线程秘书——多个待办事项根据紧急度动态切换。%%H%%LLM 训练范式假设同步——工具调用后下一条消息必须是工具结果；真实部署却要求异步——用户随时打断、多任务并发推进。这一矛盾贯穿本节所有工程取舍。%%/H%%

OpenClaw 提供 Hooks、Cron、Heartbeat 三种内置机制，但只有后两者是时间驱动的，对第三方事件源缺乏即时接入通道。PineClaw 案例生动证明：Agent 代表用户打真实电话时，客服要求实时 OTP 验证码，若依赖 Heartbeat 轮询导致延迟，通话会失败。解决方案是引入 Channel 机制——在 Gateway 和外部 API 间建立实时事件通道。

> 出处：4.7.1-4.7.2 节。

### 13. 事件处理的三种并行策略——取消式、队列式、并行式——本质是对"安全点"的不同操作

事件循环骨架：每轮从队列取事件 → 追加轨迹 → 调用 LLM → 执行工具 → 回到循环。事件只在循环边界被消费。

处理的前提是理解——所有输入需被建模为结构化事件，包含来源（用户本人/联系人/陌生人/系统）、渠道（电话/短信/即时消息/邮件/定时器触发/异步工具回调）、内容（消息文本/情感色彩/紧急度）、上下文（是否回复/与当前任务关联）。统一建模后，Agent 才能以一致方式处理异构事件，避免将用户输入误当成工具结果，或将藏有指令的工具结果误认为用户指令。

取消式（紧急事件）提前制造安全点——中断当前、清空队列、一次性追加到轨迹、立即重新调用 LLM。队列式（常规事件）等当前完成后批量处理，效率最高。并行式另起推理会话处理独立轻量查询（如任务中突然问天气），结果追加到主轨迹标记"并行执行"。

%%H%%紧急度判定（建议轻量分类 LLM 作为事件路由器）和批量处理时的注意力分散（需 `[未处理事件 N/M]` 标记和末尾汇总提醒）是工程关键细节。%%/H%%

> 出处：4.7.6 节，实验 4-5、4-6。

### 14. "训练同步/部署异步"的工程解法：常态保持完美同步轨迹，打断时才插入占位符修复格式

五条规则：（1）LLM 输出时立即记录 assistant message；（2）工具完成时才记录 tool result；（3）工具执行中的打断——为未完成工具生成占位符（"工具正在后台执行，请优先处理新事件"），追加打断事件，重调 LLM——从 LLM 视角看格式完全合法；（4）思考中的打断——直接丢弃，不写入轨迹；（5）非打断事件入队列等批处理。

示例：Agent 起草邮件→调用 `search_contacts`→未返回时用户说"先帮我查天气"→生成占位符 tool result→追加天气查询→重调 LLM→天气回复后 `search_contacts` 结果到达→继续起草邮件。

%%H%%核心优势在常态下 LLM 看到完美同步轨迹——仅在打断时引入占位符妥协。但仍有幻觉风险：模型可能"编造"占位符工具的结果，因此只在真正紧急时打断。%%/H%%

更根本策略是从工具接口设计拥抱异步——将"启动"与"完成"解耦（`initiate_phone_call` 立即返回任务 ID，进展通过事件通知），工具名称本身传达异步语义。

根本出路需在模型训练层面发生范式转变。下一代模型需通过异步环境中的强化学习获得三种核心能力：理解轨迹中事件的异步穿插（工具调用后不一定跟工具结果、思考被打断但中间状态应保留）、恢复被打断的任务（回答完天气问题后自然地等待原来还在执行的数据分析工具返回，避免幻觉以为已完成）、批量事件综合处理。而"持续思考"模型提供了中间路线：用约两百行编排逻辑将现成思考模型变成 continuous-time Agent——整个交互建成不间断思维流，随时合上 `&lt;think&gt;` 块、注入新观察、让模型接着解码。它利用模型每秒生成上百 token 的能力，把工具调用和用户说话的等待时间化为"边听边想、边做边想"的白赚算力。

> 出处：4.7.7 节。

### 15. 主动工具发现使 Agent 从"被动接受"变为"主动发现"——动态加载需"追加到末尾"破解 KV Cache 失效

传统做法全量注入 schema，工具上千时上下文被"说明书"塞满。检索式预筛选按初始查询一次性匹配，无法预见后续跨领域工具需求。MCP-Zero 的主动发现：不预置任何 schema，Agent 生成结构化请求块，系统通过服务器级→工具级两层语义路由匹配注入——约 2800 工具上比全量注入省 ~98% token。工程等价方案是提示词中保留基础工具加"工具搜索工具"，Agent 用自然语言检索加载。

%%H%%层次化匹配（服务器→工具两层语义搜索）将搜索空间从数千工具缩小为数十服务器×每服务器数十工具，省算力也减少跨领域语义混淆。%%/H%%

KV Cache 破解：新工具 schema 追加到上下文末尾保持前缀稳定，加载后固定在轨迹原位置，不是每轮搬运。

**Skills：更轻的发现范式**——不依赖嵌入索引，Agent 启动只看到薄目录（name + description，数百 token），需时用通用文件阅读能力按需查阅。更像人使用参考资料——顺着目录按需精确查阅。Skills 对编写者更友好（自然语言、局部修改不破坏全局），但对模型要求更高（需处理不同平台的命令行转义规则）。参数复杂时仍建议用模型原生工具。

### 16. 虚拟身份与隔离执行环境是 Agent 独立行动的基础设施——独立身份不削弱信任反而增强真实性

直接管理用户个人账号一旦 Agent 出错或被攻破，数字身份全部暴露。稳妥方案是赋予 Agent 虚拟身份（专属邮箱、电话、存储、计算环境），以透明身份代表用户工作。虚拟电脑/手机提供 OS 级隔离——7×24 运行、误操作只影响虚拟环境。两大挑战：反机器人机制（数据中心 IP 被拦截，需住宅代理网络）；访问用户真实账号时采用 HITL 认证（VNC/RDP 让用户亲眼看到操作界面并亲自登录）。

> 出处：4.7.5 节。

## 原则清单

1. **工具描述先问"什么时候用"再问"能做什么"**——边界说明比能力描述更重要。
2. **参数描述用具体例子**："2024-03-15T14:30:00Z" 而非 "RFC3339 格式"。附 1-5 个调用示例可使准确率从 ~72% 升至 ~90%。
3. **参数传递保持透明，严禁静默转换和静默注入**——若必须规范化，在描述中声明并在返回中告知。
4. **Agent 选错工具→优先修正工具描述，而非换更强模型**。
5. **执行工具安全五层防护**：输入验证（快速失败）→ 权限控制（黑名单不能唯一）→ 提议者-审核者（不同家族相似能力）→ Sidecar（只读结构化字段 + 拒绝熔断器）→ 沙盒隔离（venv 不是沙盒）。
6. **操作后立即自动验证**：写入代码后运行 linter，构建"执行-验证-反馈"闭环。
7. **长输出显式截断，不静默省略**——注明省略量、如何读取剩余部分。
8. **感知工具天然适合缓存与并行**——只读特性无副作用，与执行工具根本不同。
9. **子 Agent 提示词标注信息源**：`[FROM_MAIN_AGENT]`、`[FROM_USER]`——既是组织问题更是安全防线。
10. **异步工具接口将"启动"与"完成"解耦**——工具名称和描述本身就传达异步语义。
11. **批量事件在状态栏做显式标记** `[未处理事件 N/M]`——防止模型只关注最后事件。
12. **接入 MCP 服务器前审查工具描述**——description 可能夹带恶意指令（提示注入变种）。
13. **动态加载工具追加到上下文末尾**——保持前缀静态、KV Cache 复用。
14. **工具不再是"内置"而是"可发现"的**——Agent 声明缺口、系统按需注入。

## 失败模式与反例

1. **静默弯引号转换（Cursor 2026）**：传递层将 \u201c/\u201d 转为直引号，模型看到的内容和工具操作的内容不一致，反复"未找到匹配"无法诊断。
2. **静默 Git 参数注入（某 IDE bash 工具）**：所有 `git commit` 被追加标记参数，旧版 Git 不支持导致永续报错。
3. **5 个 MCP 服务器吃掉近三成上下文**：~55,000 token 工具定义在 200K 窗口已占 ~27%。
4. **检索式预筛选遗漏跨领域工具链**："Debug the file" 的初始匹配无法预见后续的文件访问、代码分析等需求。
5. **PineClaw Heartbeat 轮询导致通话失败**：客服等待实时 OTP 时用户迟迟收不到通知，依赖轮询不可接受。
6. **批量事件时模型只关注最后事件**：缺少 `[未处理事件 N/M]` 标记时信息被忽略。
7. **占位符导致模型"编造"工具结果**：模型可能误认为占位符工具已返回有效数据，基于虚构结果决策。
8. **Python venv 被误认为沙盒**：venv 只隔离包依赖，对文件系统、网络和进程无约束。
9. **同名工具遮蔽**：多 MCP 服务器同名工具使恶意服务器能"遮蔽"正规工具，诱使 Agent 路由调用。
10. **同步 ReAct 不支持并行**：搜索未返回结果时用户"先查天气"必须等待——真实助理场景需要异步架构。

## 关键术语表

- **ACI（Agent-Computer Interface）**：研究 Agent 如何与计算机交互，核心是让工具对 Agent 友好。
- **MCP（Model Context Protocol）**：Anthropic 2024 年底发布的开放标准，统一 AI 模型与外部工具/数据源的通信协议，定义工具、资源、提示模板三类原语。
- **Sidecar**：与主模型流式输出并行运行的轻量级 LLM 调用，独立判断每次工具调用安全性。只读结构化字段防提示注入绕道。
- **提议者-审核者**：用独立第二视角检验第一视角产出的安全范式，两个模型不同家族但能力相近，约束一致关注点各异。
- **事件循环**：异步 Agent 骨架——每轮取事件→追加轨迹→调用 LLM→执行工具→回到循环。事件只在循环边界被消费。
- **安全点**：事件循环中允许新事件被消费的位置（推理结束或工具返回）。
- **占位符响应**：为被异步打断的未完成工具调用生成的临时 tool result，用于修复轨迹同步格式。
- **静默输入转换**：工具参数传递层在模型不知情时修改输入参数，制造模型无法诊断的系统性偏差。
- **代码编排执行**：LLM 一次性生成脚本串联多工具，中间变量留执行环境，token 消耗可降约两个数量级。
- **幂等性**：同一操作执行多次对外部世界影响相同（安全重试）。不可幂等操作用"预检-确认"两段式。
- **渐进式披露**：不一次性展示所有信息，按需逐步提供——Skills 目录只展示 name + description。
- **虚拟身份**：Agent 的独立数字身份（专属邮箱、电话、计算环境），以透明身份代表用户工作。
