# 第6章 Agent 的评估

## 本章核心论题

本章回答一个根本问题：**怎么判断 Agent 变好了还是变差了？** 评估的对象不应只是模型，而应是模型与 Harness 的组合体——同一个模型在不同 Harness 中表现差异悬殊。本章从评估指标体系（Pass@k 能力上限 vs Pass^k 业务可靠性）、评估环境与数据集设计、自动化评估方法（LLM-as-a-Judge、失败归因、配对比较）三个层次构建完整体系，最终将评估结果转化为模型选型、架构优化和持续迭代的行动指南。核心理念是：%%H%%评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。%%/H%%

---

## 关键论点与框架

### ① 评估的对象是"模型 + Harness"，而非单独模型

**论证与机理：** 同一模型在不同 Harness 中可能表现差异悬殊——一些团队仅通过优化 Harness 就显著提升了同一模型在终端类任务上的表现。当 Agent 评估表现不佳时，改进方向可能不是换模型，而是优化 Harness 的某个组件（提示词、工具设计、反馈循环）。因此完善的评估体系必须能区分"模型能力不足"和"Harness 设计缺陷"两类本质不同的问题。

**区分手段：** 两种互补实验——**模型替换实验（model swap）**：固定 Harness，只更换更强/更弱的模型，观察分数变化幅度。换强模型分数不涨 → 瓶颈在 Harness；换弱模型分数大跌 → 瓶颈在模型能力本身。**消融实验（ablation）**：逐一关闭 Harness 的某个组件看整体性能如何变化，定位 Harness 内部哪个部件重要。

**书中证据：** 第五章详述了仅靠 Harness 优化就显著提升同一模型表现的案例。本章 6.9 节 AndroidWorld 案例中，仅调整 Harness 如何表示界面（accessibility feed → UIAutomator 元素树），就将 Wi-Fi 设置任务成功率从 25% 提高到 100%，全程未更换模型。

**出处锚点：** §6 开篇"评估的对象不应只是模型，而应是模型与 Harness 的组合体"；模型替换与消融实验的区分。

### ② Pass@k 看能力上限，Pass^k 看业务可靠性——两个数字差距可达数十倍

**论证与机理：** Pass@k 的逻辑是：同一任务运行 k 次，只要至少有一次通过就算通过（或取 Best@k）。这衡量的是"探索预算拉长后终于出现突破性轨迹"的能力上限。Pass^k（Pass consecutive k）则要求同一任务连续运行 k 次，每一次都通过，且不能触发安全、合规或幻觉等一票否决项。它回答的是"Agent 能否稳定可靠地交付"。

数学关系：`Pass@k = 1 − (1−p)^k`，`Pass^k = p^k`。当单次成功率 p=0.6、k=5 时，Pass@5≈99.0%（几乎总能至少成功一次），但 Pass^5≈7.8%（连续五次不出错极难）。前者适合探索性任务（科研发现、漏洞挖掘、开放式创作），后者适合支付、退款、权限变更、生产部署。

**书中案例：** Manus 和 OpenClaw 早期产品的复杂任务成功率并不高、token 成本极高，但 Pass@k 高，这些"技术奇观"在社交网络上被大量分享，是产品成功的关键。Anthropic 讨论的让 Agent 自主工作一周写 C 编译器、发现几十年安全漏洞等，属于 Pass@k 逻辑。

**关键警示：** 评估报告必须写清 k 次尝试的口径——是同一任务的 k 次独立采样，还是生产流水线上连续 k 个任务。对于会产生副作用的操作，不能在真实环境中"重试直到成功"，应在沙盒环境中采样。

**出处锚点：** §6.2.1-6.2.2；Manus/OpenClaw 案例；p=0.6 时 Pass@5 vs Pass^5 的数学对比。

### ③ 人机交互型评估的核心设计原则是"渐进式信息透露"

**论证与机理：** 大多数 benchmark 一开始就把完整需求全盘托出，但现实中用户很少能一上来就清晰描述需求——他们往往只会说"我的航班好像有问题"。Agent 通过主动提问来澄清需求的过程本身就是能力的重要体现。因此，评估中不能一开始就把模拟用户的所有信息暴露给 Agent，信息应按需、渐进地在对话中透露。

**τ-bench 方案：** 用另一个 LLM 扮演用户角色，根据预定义的指令与 Agent 对话。模拟用户接收任务指令（如"我需要取消明天的航班"），在对话中逐步透露必要信息、回应询问。提示词要求模拟用户"不要一次性透露所有信息，只提供当前步骤必要的内容"、"不要编造指令中未提供的信息"。模拟用户设置有限耐心，沟通效率低时可终止对话 → 任务失败。

**τ²-bench 改进：**（1）双控环境（Dual-Control）——用户模拟器也能操作同一个共享环境（如 Agent 指导用户切换飞行模式，用户操作真正改变环境状态），更贴近技术支持等需要用户动手配合的真实场景。（2）更精确的任务规范与组合式任务生成——成功条件的歧义更少、任务实例可参数化批量生成。

**验证体系：** 数据库状态检查（预订状态是否改变）+ 对话内容关键词搜索（是否向用户确认关键信息）+ 流程合规性（工具调用序列分析）。任务层面二元奖励——全部检查通过才得 1 分，代价是"操作准确但漏掉某个非关键字段"与"完全失败"同分。

**出处锚点：** §6.3.3；τ-bench vs τ²-bench 对比；渐进式信息透露多轮对话示例。

### ④ LLM-as-a-Judge 必须建立在结构化 Rubric 之上，且必须防范长度偏差和奖励作弊

**论证与机理：** 对开放式任务（客服对话、报告撰写），没有标准答案可自动对比。LLM-as-a-Judge 通过让语言模型根据专家定义的 Rubric 评判，在自动化规模和人类专业判断间取得平衡。但评判模型有已知局限：长度偏差（倾向于给更长回复打高分）、同源模型偏见（Agent 学会利用评判模型的盲点）、多次评判波动。

**Rubric 四准则（Scale AI）：**
1. **基于专家指导**——反映领域知识，捕捉核心事实和推理步骤（如医疗 Rubric 需含诊断标准和必须避免的医学错误）。
2. **全面覆盖**——涵盖事实准确性、逻辑连贯性、完整性、安全性，且明确定义陷阱（Pitfall）——高风险常见错误。
3. **标准重要性权重**——分为必要项（Essential）、重要项、可选项、陷阱项。支持**一票否决（Veto）**：幻觉（编造虚假信息）是典型否决维度——无论其他维度多优秀，出现虚假信息即否决。
4. **自包含评估**——每个评价项独立可操作，不依赖评价者领域知识。避免"回应展示了深刻理解"这类抽象标准，改为"引用了至少两个权威理论并准确解释如何支持结论"。

**聚合骨架（确定性优先于 LLM）：** 底线项先由环境真值或规则否决，LLM 只评价难以形式化的质量维度；低置信度或评委分歧进入人工复核。

**书中案例：** 用户记忆 Agent 的完整 Rubric（跨两次对话关联"女儿=Lily"和"Lily的医生=Dr. Chen"），包含四维度评分标准和边界案例。180 次评判中，幻觉否决触发了 28 次，证明一票否决项不是装饰。

**多源评判缓解同源偏见：** 使用不同模型家族的多个 LLM 分别评判（Agent 用 Claude，评判用 GPT-5 和 Gemini），不同家族偏见正交，Agent 难以同时欺骗所有评判者。部署阶段用单一模型快速评估，定期用完整多源评判做质量审计。

**出处锚点：** §6.5.1；Scale AI 四准则；用户记忆 Rubric 示例；28/180 幻觉否决触发统计。

### ⑤ 失败归因必须定位"首个导致任务偏离的错误"，而非最后一个报错

**论证与机理：** 端到端评估只给出"成功/失败"，不回答"为什么失败、从哪一步开始失败"。归因对象是轨迹中首个导致任务偏离的错误——后续错误往往是连锁反应，不能把最后一个报错当成根因。生产 Agent 的 bad case 来自三类信号：用户明确纠正、用户点踩/负面反馈、事后规则验证器或 LLM 评审发现不该做的事。

**Coding Agent 的六类错误分类：**
- **流程与规范缺失**：未执行单元测试就提交、未写设计文档就改代码 → 定位第一次违反流程的动作
- **工具调用错误**：同一文件反复编辑失败、JSON/参数格式错误 → 记录第一次失败的编辑及原始请求
- **作用域敏感的文档格式错误**：中文引号与英文引号混用、代码注释与语法混淆 → 定位首个符号所在文档片段及其语法角色
- **精确复制错误**：old_string 差一个字符/空格/Unicode code point → 沿"原始字节→工具返回→序列化→模型输入→模型输出→工具匹配"逐层定位首次分歧
- **模型执行异常**：输出截断、无故停止、超时 → 区分模型停止/Harness 超时/工具故障
- **任务完成度与逻辑判断**：只完成部分目标、未穷尽方案就宣布不可能 → 定位第一次遗漏或错误判断

**关键原则：** 多个类别同时出现时，按"最早且能解释后续失败"的原则选主因，其余保留为次因。归因记录需结构化（JSON/YAML），引用具体步骤号、工具名和观察证据，区分根因与后果，给出置信度。完整保存任务目标、环境状态、Agent 版本和轨迹以便回归测试。

**出处锚点：** §6.5.2；Coding Agent 错误分类表；精确复制错误的逐层定位链路。

### ⑥ 端到端回归与轨迹前缀回归互补，后者对生产级 Agent 更重要

**论证与机理：**
- **端到端回归任务**：从初始状态和用户请求开始，让 Agent 完成整个任务，检查最终状态和必要输出。最接近生产结果，但难以判断失败究竟发生在哪一步。
- **轨迹前缀回归任务**：把已有的上下文、对话、工具返回和环境状态冻结下来，只要求 Agent 输出下一步或下几步可观察动作。成本更低，能隔离单个策略或工具问题。答案应定义为可接受动作集合（如"先读仓库规则""先询问用户""拒绝危险操作"），而非唯一动作或答案。

**书中案例：** 用户记忆的轨迹前缀边界实验——对同一组 11 个边界用例，用 JSON Cards、Markdown、Python-like 三种等语义表示，每种 11 个用例 × 3 种表示 = 33 个单元。三种表示总成绩都是 6/11，但失败位置不同：Markdown 通过了"仓库规则未知时先检查"却多失败了一个作用域冲突用例。结论：改变上下文表示方式不会自动修复应用策略。

**来源区别：** 真实用户反馈通过用户纠正、点踩、状态检查和 LLM 审计三种信号转化为回归任务——这些实时数据通过错误分类和影响分析，转化为零错误的最终结果。

**出处锚点：** §6.5.3；Coding Agent 的流程缺失→端到端回归、工具错误→轨迹前缀回归的映射；§6.10 内部评估基础设施连接生产 bad case→回归任务。

### ⑦ 评估数据集的五大核心挑战：每一个都有对应解法

**论证与机理：**

1. **明确性与开放性的张力**——任务必须足够明确以确保评估可复现，又不能过于死板限制 Agent 创造性。GAIA 范例：目标明确（找到特定宇航员及其太空时间），但搜索/筛选/验证路径完全由 Agent 自主决策。

2. **真实性与可控性的平衡**——SWE-Bench 原始版直接取自 GitHub 真实 issue，但导致描述模糊、测试不完整。SWE-Bench Verified 引入人类专家验证，从 2294 题筛选至 500 题（淘汰率 71%），在保持真实性的同时提升可控性。

3. **多样性与系统性的协调**——AndroidWorld 的 116 个任务横跨 20 个真实应用，每个任务标注核心能力（多步规划、视觉理解、时间推理），使评估结果能揭示特定能力维度强弱。通过参数化机制可生成几乎无限的任务变体。

4. **评估成本与覆盖范围**——前沿模型完整跑完一个评估数据集需数千美元。GAIA 精选 466 题分三级难度，SWE-Bench Verified 从 2294 题筛选至 500 题、成本降低约 80%。

5. **数据泄漏防范**——各基准采用不同策略：GAIA 依靠答案独特性（需组合多个信息源）+ 专门创建的附件文件（互联网不存在）；τ²-bench 通过动态参数生成（用户姓名/订单号/日期每次随机生成）；AndroidWorld 验证基于最终 UI 状态而非操作序列；Terminal-Bench 嵌入 canary GUID 使泄漏可跟踪；SWE-bench-Live 持续收录模型训练截止日期后的新 issue。

**出处锚点：** §6.4.1；五大挑战详述；SWE-Bench Verified 29% 通过率筛选过程。

### ⑧ 从 Benchmark 报告到系统改进，必须遵循"观察→假设→实验→验证"的科学方法

**论证与机理：** 本章以 AndroidWorld Wi-Fi 设置任务调优为案例，展示了完整闭环：

- **第一轮（H1）**：假设 Agent 只是"不知道路"，补充 Wi-Fi 导航提示和最终状态检查。成功率 25%→25%，无效。**结论：提示写得更详细也补不回 Agent 根本没有看到的信息。**
- **第二轮（H5）**：发现真正问题是 Agent"看不见界面"——accessibility feed 在 API 35 上不兼容。切换到 UIAutomator 元素树。成功率 25%→100%，但 token 用量膨胀至 2.5 倍。
- **第三轮（H5C）**：精简元素树，删除不可见、无文字、不可操作容器节点。成功率保持 100%，token 降至对照组的 0.5 倍。

**核心教训：**（1）遇到失败先检查输入，而不是继续堆提示词。（2）输入不是越多越好——完整元素树解决了"看不见"却带来大量无用 token。（3）全程没有更换模型，仅调整 Harness 如何表示界面就先后解决了"能不能做成"和"做成是否划算"。（4）小范围实验（仅 4 个任务）通过后，必须进入完整复测——在 116 个任务 × 各 5 个随机种子上验证，确认成功率不降、token 不超过 75%、延迟不超过 1.5 倍。

**出处锚点：** §6.9.1-6.9.4；AndroidWorld 三轮 H1/H5/H5C 实验数据表。

### ⑨ 模型选型不是"选最强的"，而是多维度的评估驱动权衡

**论证与机理：** 模型选择需在以下维度间权衡：

- **吞吐与延迟**：区分 Prefill（首字延迟 TTFT，上下文越长越慢）和 Decode（后续出字速度和思考时长）两阶段。思考 token 数差异可达数倍，且与任务效果不一定正相关。
- **成本**：不是简单的 token 定价——多轮推理、工具调用和上下文累积使成本非线性增长。配套实验表明：八轮客服任务中，启用 KV Cache（稳定前缀）+ 压缩历史可节省 30% 成本，但两项合用效果不是各自节省比例的简单相加（28.3%+17.5%≠30%，因为压缩历史缩短了可命中的缓存前缀）。
- **性能指标组合**：日常场景看 Pass@1，关键操作优先 Pass^k，探索性任务看 Pass@k/Best@k。
- **预算—能力曲线**：短预算领先不能外推成长时间能力。RE-Bench 的人机对照：2 小时预算下最佳 Agent 约为人类 4 倍，但人类从增加时间中获益更大，32 小时时超过 Agent 约 2 倍。

**行为策略维度：** 模型选型还要比较"模型默认怎样做"。同一 Coding Harness 下，GPT-5.6-sol 首次修改前平均调用工具 6.89 次、读取 4.67 个文件，Claude Sonnet 5 分别为 4.56 次和 3.56 个文件——差距在局部任务中最明显，跨模块任务中收敛。这支持的是"行动策略随模型而变"，而非"多读或早改必然更好"。

**出处锚点：** §6.6.1-6.6.2；成本四组对照实验表；RE-Bench 的人机比较；Coding Agent 行动阈值实验。

### ⑩ 生产级 Agent 需要将评估内建为基础设施，而非偶尔做一次的考试

**论证与机理：** 以 OpenClaw 与头部 Coding Agent 的实践为代表，五大组件构成评估驱动的产品工程：

- **消融基础设施**：每个主要特性可独立关闭，系统内置总开关创建"裸模型"基线。定期运行消融实验（如每次大版本发布前）可发现"特性债务"——那些曾经有效但随着模型进化已不再必要的特性。
- **AB 测试方法论**：多臂（非二元）设计揭示剂量-效应关系；区分机制指标（改变的东西）和目标指标（真正关心的东西）；设置护栏指标（不能变差的底线）。
- **双层特性开关**：编译时开关在构建阶段将代码物理移除（内部专用特性在外部构建中不存在）；运行时开关配置服务端下发+本地缓存，通过实验平台（如 GrowthBook）分配 AB 测试组。
- **提示词敏感性评估**：系统提示应该是可确定性渲染的，建立版本化快照机制，每次提示词变更在评估集上运行回归测试——就像代码变更需要跑 CI。
- **隐私感知分析**：通过类型系统强制的编译时检查保证数据收集合规，类型名本身就是审计线索（"我已验证这不是代码或文件路径"）。

**核心转变：** %%H%%外部评估告诉你"Agent 有多好"，内部评估基础设施告诉你"哪个改变让它变好了"。%%/H%%

**出处锚点：** §6.10.1-6.10.6；OpenClaw 消融开关、AB 测试案例、双层特性开关设计。

### ⑪ 仿真环境是评估到后训练的桥梁：Rubric 就是奖励函数，但训练对 reset 和吞吐有更高要求

**论证与机理：** 评估侧已积累的资产可无缝转为训练信号——一套定义清晰的 Rubric 或验证器本质上就是一个可验证奖励（RLVR）的奖励函数。但训练提出评估阶段不必操心的新要求：（1）可靠的 reset 语义——数百万个 episode 每个都要能重置到确定、干净的初始状态；（2）远高于评估的吞吐——评估几千次就够，训练要上百万次。

**数字环境：** AWorld 框架为 GAIA 任务构建 26 个 MCP 服务器、126 个工具函数的可控沙盒，通过分布式架构将串行 7695 秒加速到 525 秒（14.6 倍）。

**具身环境：** RoboTwin2 基于物理引擎构建双臂操作任务，通过领域随机化（Domain Randomization）——随机化物体位置、朝向、外观、物理参数、视觉外观、传感器噪声——缩小仿真与现实差距。

**核心红线：** 可以复用的是环境的构造机制，评估集本身的那些具体题目必须与训练数据严格隔离。

**出处锚点：** §6.11；AWorld 框架 14.6 倍加速；领域随机化概念；评估集与训练数据隔离红线。

## 原则清单

1. **先建指标再搭环境**：定义"什么算成功"（Pass@k/Pass^k 口径）优先于搭建评估环境和编写数据集，否则"测什么"的决策会被工具和数据牵着走。
2. **Rubric 必须可验证**：每个评分档应给出可验证的具体行为描述（如"准确回答 Dr. Chen，且关联到女儿 Lily"），而非抽象判定（如"展示了对记忆的深刻理解"）。
3. **一票否决项与质量维度分开**：幻觉、严重安全违规等零容忍项应与普通质量维度分开设计，避免总分掩盖致命错误。
4. **确定性验证先于 LLM 评判**：底线项先由环境真值或规则否决，LLM 只评价难以形式化的质量维度。低置信度或评委分歧进入人工复核。
5. **失败归因定位首个错误而非最后报错**：后续错误往往是连锁反应，按"最早且能解释后续失败"的原则选主因。
6. **小范围实验通过后必须进入完整复测**：子集上的 4/4 不能写成系统整体 100%。在标准环境完成足够规模的运行后才能讨论部署。
7. **每次改动只变一个变量**：对比实验和消融实验每轮只改一个变量，逐一验证假设，比同时堆上许多改动更容易说清因果。
8. **评估集必须与训练数据严格隔离**：可复用环境构造机制，但具体题目必须隔离。参数化模板生成的训练实例不应复用评估实例的参数空间。
9. **长度偏差必须单独防范**：在 Rubric 里显式惩罚冗长、对配对比较先控制长度再评、定期审计评分与回答长度的相关性。
10. **多源评判优于单模型评判**：使用不同模型家族的多个 LLM 分别评判，Agent 难以同时"欺骗"所有评判者。
11. **指标必须在评估报告中写清口径**：Pass@k 的 k 是同一任务的独立采样还是流水线上连续任务？对会产生副作用的操作，在沙盒中采样，每次失败记入可靠性。
12. **系统提示应纳入 CI 体系**：提示词版本化、确定性渲染、每次变更在评估集上跑回归测试——就像代码变更需要跑 CI。
13. **预算—能力曲线而非单点成绩判断长程能力**：短预算领先不能外推，在接近真实任务时长的多个预算点上比较。
14. **区分机制指标和目标指标**：你改变的东西（如计划文件长度）和你真正关心的东西（如会话级成本）是同一个吗？不是的话以目标为准。
15. **每个主要特性应可独立关闭**：定期验证每个特性的实际贡献，发现"特性债务"。
16. **看到分数下降时先检查评测系统再动 Agent**：运行环境资源不足、评分器 bug、测试用例脱节，都可能表现为模型退化。
17. **统计显著性不可忽略**：分差超过噪声、在配对分析中成立、且能够复现，才值得据此切换模型或发布改动。

## 失败模式与反例

1. **Pass@k 高就认为系统可靠**：60% 单次成功率的 Agent 在 k=5 时 Pass@5≈99%，但 Pass^5≈7.8%。如果评估报告只写 Pass@k 而不写 Pass^k，决策者会严重高估可靠性。支付、退款、权限变更等场景必须用 Pass^k，且 k 要匹配业务风险敞口。

2. **混合方案不一定优于单一方案**：配套实验中用户记忆的混合系统（高级 JSON Cards + RAG）总体成功率 66.7%，与纯 JSON Cards 的 68.3% 几乎持平，但 RAG 在跨会话隐藏关联题上仅 15%。混合方案在 3 道题上做到了两种单一方案都没做到的事，却在 8 道题上不如表现更好的单一方案。实验数学支持了混合方案的自然预期被推翻。

3. **"有 KV Cache"+"压缩历史"各自节省不能直接相加**：配套实验八轮客服任务中，仅稳定前缀节省 28.3%，仅压缩历史节省 17.5%，两者合用仅节省 30%——压缩历史的同时缩短了可命中缓存的前缀。

4. **把机制指标当作优化目标**：如果测试"缩短 Agent 的计划文件长度"，计划长度是你直接改变的东西，但真正的目标可能是"降低会话级成本"。缩短计划可能因为不够详细导致更多编辑-检查-编辑循环，反而增加总输出量。

5. **看到分数下降就改 Agent 代码而不先检查评测系统**：运行环境资源不足导致进程被杀、评分器 bug 把正确答案判失败、测试用例与生产场景脱节——这些问题在结果数字上跟模型退化一模一样，只有审查完整轨迹才能区分。

6. **短窗口表现好就外推为长程能力**：RE-Bench 实验中 2 小时预算下最佳 Agent 远超人类，但 32 小时时人类得分约为其 2 倍。预算—能力曲线是必要的。

7. **LLM-as-a-Judge 的同源模型偏见**：当 Agent 和评判模型来自同一家族时，Agent 可能学会利用评判模型的偏好和盲点，还会逐渐避开评判模型不擅长检测的错误类型。——古德哈特定律的直接体现：当一个度量指标变成优化目标时，它就不再是好的度量指标。

8. **忽视轨迹与结果的双重覆盖**：Agent 说"订票已完成"是轨迹层面信息，数据库里确实生成订单才是结果层面验证。只看轨迹会漏掉"说了但没做到"，只看结果看不出中间步骤走歪了。

9. **评估集是静态一次性构造而非持续回流**：今天线上暴露的失败模式应成为明天守住的回归用例。不做生产轨迹→评估集回流的团队，评估集会逐渐脱离真实用户分布。

10. **在"技术奇观"的语境下推广能力**：Manus 和 OpenClaw 的早期产品 Pass@k 高但成功率不稳定、成本极高。社交网络分享的"奇观"不能等同于日常可靠性——用户在社交媒体看到的印象与日常体验之间出现裂痕。

11. **把多个改动一次性推上去，说不清哪项真正有效**：AndroidWorld 实验中，H1/H5/H5C 三轮每轮只改一个变量，逐一验证，比同时堆上许多改动更容易说清因果。

## 关键术语表

| 术语 | 一句话定义 |
|------|-----------|
| **Pass@k** | 同一任务运行 k 次，至少一次通过即算通过（或用 Best@k 取最佳得分），衡量能力上限。 |
| **Pass^k（Pass consecutive k）** | 同一任务连续运行 k 次，每一次都通过，且不触发一票否决项，衡量业务可靠性。 |
| **Rubric（评分标准）** | 专家定义的多维度评分准则，是 LLM-as-a-Judge 评判的依据，需满足四准则（专家指导、全面覆盖、权重分层、自包含）。 |
| **一票否决（Veto）** | 特定维度（如幻觉、严重安全违规）一旦触发即否决整体评价，不因其他维度优秀而豁免。 |
| **LLM-as-a-Judge** | 用语言模型根据 Rubric 自动化评判开放式任务输出的方法，在自动化规模和人类专业判断间取得平衡。 |
| **失败归因（Failure Attribution）** | 从整条失败轨迹中定位首个导致任务偏离的错误及其类别，区分根因与后果。 |
| **轨迹前缀回归（Trajectory Prefix Regression）** | 冻结失败前的完整上下文，只要求 Agent 输出下一步可观察动作的评估任务，成本低、能隔离单个决策问题。 |
| **端到端回归（End-to-End Regression）** | 从初始状态跑完整任务并检查最终状态的评估任务，最接近生产结果但难以定位具体失败步骤。 |
| **渐进式信息透露（Progressive Information Disclosure）** | 人机交互型评估的核心设计原则：模拟用户不一次性暴露所有信息，信息按需、渐进地在对话中透露。 |
| **用户模拟（User Simulation）** | 用 LLM 扮演用户角色与 Agent 对话以自动化人机交互评估的方法。 |
| **双控环境（Dual-Control）** | τ²-bench 引入的设计：用户模拟器也能操作共享环境，Agent 必须通过工具调用观察到用户侧操作结果。 |
| **模型替换实验（Model Swap）** | 固定 Harness 只换模型，通过分数变化幅度区分瓶颈在模型还是 Harness。 |
| **消融实验（Ablation Study）** | 逐一关闭 Harness 的某个组件观察整体性能变化，定位哪些组件真正重要。 |
| **配对比较（Pairwise Comparison）** | 不依赖绝对分数的评估方式：让评判者选择"A 和 B 哪个更好"，通过 Bradley-Terry/Elo 模型从两两对决中提取排名。 |
| **Elo 评分** | 基于 Bradley-Terry 模型的在线排名算法：通过两两对决胜负预测更新评分，分差越大预期胜率越高。 |
| **位置偏差（Position Bias）** | 评判模型系统性地偏向出现在某个位置（通常是先出现）的候选。缓解方法是交换顺序各评一次取平均。 |
| **古德哈特定律（Goodhart's Law）** | 当一个度量指标变成优化目标时，它就不再是好的度量指标——Agent 越在某个评分系统上调优，越倾向于钻漏洞。 |
| **KV Cache** | 缓存已处理过的上下文避免重复计算，是 Agent 多轮对话中控制成本的关键机制。 |
| **TTFT（Time To First Token）** | 首字延迟，等于排队时间加 Prefill 时间，是用户感知的"反应快慢"。 |
| **p95 尾部延迟** | 95% 的请求都不会超过的延迟，比平均值更能反映真实用户体验。 |
| **预算—能力曲线** | 性能随墙钟时间/token/工具调用次数变化的曲线，避免短预算领先被误读为长程优势。 |
| **领域随机化（Domain Randomization）** | 在物理参数、视觉外观、传感器噪声等方面引入大范围随机变化，缩小仿真与现实差距。 |
| **可验证奖励（RLVR）** | Reinforcement Learning with Verifiable Rewards：评估判据直接作为强化学习奖励函数，Rubric 即奖励脚本。 |
| **trajectory vs outcome** | 执行轨迹（Agent 说了什么做了什么）与最终结果（系统变成什么样）是两件事，两类评测都应覆盖。 |
| **金标集（Gold Standard Set）** | 人工标注的校准用例集（如 100-200 个），用于测量 LLM 评判与人类标注的一致率（Cohen's kappa）。 |
| **Canary GUID** | 嵌入评估数据的特殊标识符，如果模型能输出含该 GUID 的内容，说明基准数据已泄漏到训练集中。 |
| **FAIL_TO_PASS / PASS_TO_PASS** | SWE-Bench Verified 的双重验证：修复前失败修复后通过（证明问题解决）+ 修复前后都通过（证明没有引入新 bug）。 |
| **特性开关（Feature Flag）** | 可远程控制的开关，决定功能对用户是否开启，同时服务于实验、渐进发布和紧急熔断。 |

## 高亮核心论断与金句

%%H%%评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。当一个更强或更便宜的模型发布时，拥有完善评估体系的团队能在数小时内得出切换决策，而缺乏评估体系的团队只能凭直觉或等待社区反馈。%%/H%%

%%H%%评估的对象不应只是模型，而应是模型与 Harness 的组合体。同一个模型在不同的 Harness 中可能表现差异悬殊。%%/H%%

%%H%%看到 Agent 表现下降时，应先检查评测系统本身，再动 Agent。一个常见误区是看到分数下降就立刻修改 Agent 代码，而忽略了评测系统本身可能先出了问题。%%/H%%

%%H%%好的 Benchmark 报告不只给出一个分数，还应写清结论适用于哪里、哪些底线没有通过、下一轮要验证什么。%%/H%%

%%H%%Pass@k 回答"Agent 能不能偶尔创造奇迹"，Pass^k 回答"Agent 能否稳定可靠地交付"——两者的数字可以差一个数量级以上。%%/H%%

%%H%%一定不要一次性透露所有信息，只提供当前步骤必要的内容——这是人机交互型评估与传统 benchmark 的根本区别。%%/H%%

%%H%%当一个度量指标变成优化目标时，它就不再是好的度量指标。Agent 越是在某个评分系统上训练或调优，就越倾向于钻这个系统的漏洞，而非真正提升能力。%%/H%%

%%H%%幻觉之所以列为一票否决项（veto）而非分级评分维度，是因为它与质量是正交的——一个流畅、详尽、礼貌的回答如果包含虚假事实，对用户的伤害远大于一个简短但准确的回答。%%/H%%

%%H%%归因对象是轨迹中的首个导致任务偏离的错误，后续错误往往只是连锁反应，不能把最后一个报错简单当成根因。%%/H%%

%%H%%端到端评估通常只给出"成功"或"失败"，却没有回答"为什么失败、从哪一步开始失败"。%%/H%%

%%H%%没有重置就无法公平复跑，只看回复会漏掉"说了但没做"，只看最终状态又无法定位过程违规。%%/H%%

%%H%%小范围实验通过后，只能进入完整复测；在标准环境完成 116×5 次运行后，才能讨论是否部署。%%/H%%

%%H%%外部评估告诉你"Agent 有多好"，内部评估基础设施告诉你"哪个改变让它变好了"。%%/H%%

%%H%%不是偶尔做一次评估，而是将评估嵌入到每一次产品决策中。%%/H%%

%%H%%模型选型不是简单地"选最强的模型"，而是根据应用场景在多个维度之间做评估驱动的权衡。%%/H%%

%%H%%提示词写得更详细，也补不回 Agent 根本没有看到的信息；遇到这类失败，应先检查输入，而不是继续堆提示词。%%/H%%

%%H%%评估集本身的那些具体题目必须与训练数据严格隔离——可以复用的是环境的构造机制，而非题目本身。%%/H%%

%%H%%每一轮证据只支持与它规模相称的下一步。%%/H%%
