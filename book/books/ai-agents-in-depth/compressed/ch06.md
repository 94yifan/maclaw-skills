# 第6章 Agent 的评估

## 本章核心论题

本章回答：**怎么判断 Agent 变好了还是变差了？** 评估对象应是模型与 Harness 组合体——同一模型在不同 Harness 中表现差异悬殊。从指标体系（Pass@k vs Pass^k）、评估环境设计、自动化评估方法（LLM-as-a-Judge、失败归因、配对比较）三个层次构建体系，转化为模型选型、架构优化和持续迭代的行动指南。%%H%%评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。%%/H%%

---

## 关键论点与框架

### ① 评估对象是"模型 + Harness"

同一模型不同 Harness 表现差异悬殊，评估须区分"模型能力不足"和"Harness 设计缺陷"。

两种实验：(1) **模型替换**：固定 Harness 只换模型——强模型分数不涨→瓶颈在 Harness；弱模型大跌→瓶颈在模型。(2) **消融实验**：逐一关闭 Harness 组件看变化。§6.9 仅调界面表示就使 Wi-Fi 任务成功率从 25%→100%，全程未换模型。
**出处**：§6 开篇

### ② Pass@k 看能力上限，Pass^k 看业务可靠性

Pass@k：运行 k 次至少一次通过，衡量探索预算拉长后突破性轨迹的能力上限。Pass^k：连续 k 次都通过且不触发否决项，回答"能否稳定可靠交付"。

`Pass@k = 1 − (1−p)^k`，`Pass^k = p^k`。p=0.6、k=5 时 Pass@5≈99.0%，Pass^5≈7.8%。前者适合探索性任务（科研发现、创作），后者适合支付退款权限变更部署。早期产品 Pass@k 高但成功率不稳定——"技术奇观"在社交网络分享是成功关键。

评估报告须写清 k 次口径——独立采样还是流水线连续。有副作用的操作应在沙盒采样。
**出处**：§6.2

### ③ 人机交互评估核心——渐进式信息透露

用户很少一上来清晰描述需求，Agent 主动提问澄清本身就是能力体现。

τ-bench：LLM 扮演用户，按指令与 Agent 对话。要求"不要一次透露所有信息""不编造未提供信息"。用户设有限耐心，沟通效率低→终止→失败。

τ²-bench 改进：(1) 双控环境——用户模拟器也能操作共享环境；(2) 精确任务规范与参数化批量生成。验证体系：数据库检查+关键词+流程合规，全部通过得 1 分。
**出处**：§6.3.3

### ④ LLM-as-a-Judge 须建立在结构化 Rubric 上

LLM-as-a-Judge 平衡自动化规模与人类判断，但评判模型有已知局限：长度偏差（给更长回复高分）、同源偏见（Agent 利用盲点）、多次评判波动。

Rubric 四准则：(1) 基于专家指导；(2) 全面覆盖——事实准确性、逻辑连贯、完整性、安全性，明确定义陷阱；(3) 权重分级——必要项、重要项、可选项、陷阱项，支持一票否决——幻觉是典型否决维度；(4) 自包含——每项独立可操作。

聚合骨架（确定性优先于 LLM）：底线项先由真值或规则否决，LLM 只评难形式化的维度；低置信度或分歧进人工。用户记忆 Rubric：180 次评判幻觉否决触发 28 次。

多源评判：不同模型家族多个 LLM 分别评判，不同家族偏见正交，Agent 难同时欺骗所有评判者。部署用单一模型快速评估，定期完整多源审计。
**出处**：§6.5.1

### ⑤ 失败归因定位"首个导致任务偏离的错误"

端到端评估只给"成功/失败"，不回答"为什么、从哪步开始失败"。归因对象是轨迹首个错误——后续往往是连锁反应。

六类：(1) 流程规范缺失——未测试就提交；(2) 工具调用错误——反复编辑失败、JSON 格式错；(3) 文档格式错误——引号混用；(4) 精确复制错误——old_string 差一字符，逐层定位首次分歧；(5) 模型执行异常——截断、停止、超时；(6) 任务完成度——只完成部分目标、未穷尽就宣布不可能。多类别时按"最早且能解释后续失败"选主因。
**出处**：§6.5.2

### ⑥ 端到端回归与轨迹前缀回归互补

端到端回归从初始状态跑完整任务检查最终状态，最接近生产但难定位失败步骤。轨迹前缀回归冻结失败前上下文只要求输出下一步——成本更低，能隔离单个决策问题。用户记忆实验：11 个边界用例三种等语义表示，总成绩相同失败位置不同——改变上下文不会自动修复策略。
**出处**：§6.5.3

### ⑦ 评估数据集五大核心挑战

1. **明确性与开放性**——GAIA：目标明确（找到特定宇航员），搜索路径自主。
2. **真实性与可控性**——SWE-Bench Verified 从 2294 筛选至 500（淘汰率 71%）。
3. **多样性与系统性**——AndroidWorld 116 任务 20 应用，每任务标注核心能力，可参数化生成变体。
4. **成本与覆盖**——前沿模型完整跑需数千美元。GAIA 466 题，SWE-Bench 筛选至 500 成本降约 80%。
5. **数据泄漏防范**——GAIA 靠答案独特性+专门附件；τ²-bench 动态参数；AndroidWorld 验证最终 UI；Terminal-Bench 嵌入 canary GUID；SWE-bench-Live 收录训练截止日后新 issue。
**出处**：§6.4.1

### ⑧ 从 Benchmark 到系统改进——科学方法

AndroidWorld Wi-Fi 调优闭环：

- **H1**：假设 Agent"不知道路"，补导航提示和状态检查。25%→25%，无效。**结论：提示写再详细补不回 Agent 根本没看到的信息。**
- **H5**：发现真问题——accessibility feed 在 API 35 不兼容致 Agent"看不见界面"。切换 UIAutomator 元素树。25%→100%，token 膨胀 2.5 倍。
- **H5C**：精简元素树删除不可见无文字不可操作节点。成功率保持 100%，token 降至对照 0.5 倍。

核心教训：(1) 失败先查输入非堆提示词；(2) 输入非越多越好；(3) 全程未换模型仅调 Harness 界面；(4) 小范围（4 任务）通过后须在 116×5 种子复测。
**出处**：§6.9.1-6.9.4

### ⑨ 模型选型——多维度评估驱动权衡

(1) **吞吐延迟**：区分 Prefill（TTFT）和 Decode（思考时长），思考 token 差异数倍且与效果不一定正相关。(2) **成本**：多轮推理成本非线性，KV Cache+压缩史可省 30% 但非简单相加（28.3%+17.5%≠30%——压缩史缩短可命中缓存前缀）。(3) **指标组合**：日常 Pass@1，关键操作 Pass^k，探索看 Pass@k。(4) **预算—能力曲线**：RE-Bench 2 小时 Agent 为人 4 倍，32 小时人被反超约 2 倍。同一 Harness 不同模型行动阈值差异显著。
**出处**：§6.6.1-6.6.2

### ⑩ 生产级 Agent 需将评估内建为基础设施

五大组件：(1) 消融基础设施——每特性可独立关闭，定期发现"特性债务"；(2) AB 测试——多臂设计，区分机制指标目标指标，设护栏指标；(3) 双层特性开关——编译时物理移除，运行时服务端下发；(4) 提示词敏感性——确定性渲染版本化快照，每次变更在评估集跑回归；(5) 隐私感知分析——编译时检查保证合规。%%H%%外部评估告诉你"Agent 有多好"，内部评估基础设施告诉你"哪个改变让它变好了"。%%/H%%
**出处**：§6.10.1-6.10.6

### ⑪ 仿真环境——评估到后训练的桥梁

定义清晰的 Rubric 即 RLVR 奖励函数。训练要求：(1) 可靠 reset 语义——数百万 episode 需干净重置；(2) 远高于评估吞吐。AWorld 为 GAIA 构建 26 个 MCP 服务器 126 个工具，分布式串行 7695 秒→525 秒（14.6 倍）。RoboTwin2 领域随机化缩小仿真现实差距。红线：评估集题目须与训练数据隔离，可复用仅环境构造机制。
**出处**：§6.11

## 原则清单

1. **先建指标再搭环境**：定义"什么算成功"优先于搭建环境。
2. **Rubric 必须可验证**：每档给具体行为描述，非抽象判定。
3. **一票否决项与质量维度分开**：幻觉安全违规零容忍不应被总分掩盖。
4. **确定性验证先于 LLM 评判**：底线项先由真值或规则否决。
5. **失败归因定位首个错误**：按"最早且能解释后续失败"选主因。
6. **小范围实验通过后必须完整复测**：4/4 不能写为系统整体 100%。
7. **每次改动只变一个变量**：比同时堆许多改动更容易说清因果。
8. **评估集须与训练数据隔离**：可复用构造机制，具体题目须隔离。
9. **长度偏差须单独防范**：Rubric 显式惩罚冗长，定期审计评分长度相关性。
10. **多源评判优于单模型**：不同家族多个 LLM 分别评判。
11. **指标须写清口径**：Pass@k 的 k 是独立采样还是流水线连续。
12. **系统提示应纳入 CI**：版本化，每次变更在评估集跑回归。
13. **预算—能力曲线而非单点成绩**：多预算点比较。
14. **区分机制指标和目标指标**：你改变的和真正关心的未必相同。
15. **每个特性应可独立关闭**：定期验证贡献，发现"特性债务"。
16. **分数下降先查评测系统**：资源不足评分器 bug 都可能表现如模型退化。
17. **统计显著性不可忽略**：分差超噪声、配对成立且能复现才值得切换。

## 失败模式与反例

1. **Pass@k 高就认为可靠**：p=0.6 时 Pass@5≈99% 但 Pass^5≈7.8%。支付退款权限变更须用 Pass^k。
2. **混合方案不一定优于单一**：用户记忆混合系统总体 66.7% 与纯 JSON Cards 68.3% 持平，RAG 在跨会话隐藏关联仅 15%。
3. **KV Cache 和压缩史不简单相加**：稳定前缀省 28.3%，压缩史省 17.5%，合用仅省 30%。
4. **把机制指标当优化目标**：缩短计划文件因不够详细致更多编辑循环反增总输出。
5. **分数下降就改 Agent 代码**：资源不足评分器 bug 测试脱节与模型退化表现相同。
6. **短窗口好就外推长程**：RE-Bench 2 小时超人类，32 小时被反超。
7. **LLM-as-a-Judge 同源偏见**：Agent 可能利用评判模型盲点——古德哈特定律直接体现。
8. **忽视轨迹结果双重覆盖**：只看轨迹漏"说了没做到"，只看结果无法定位过程违规。
9. **评估集静态不回流**：线上暴露的失败模式应成为明天的回归用例。
10. **"技术奇观"语境推能力**：社交网络"奇观"不等于日常可靠性。
11. **多个改动一次性推**：AndroidWorld 每轮只改一个变量逐一验证因果。

## 关键术语表

| 术语 | 一句话定义 |
|------|-----------|
| **Pass@k** | 运行 k 次至少一次通过，衡量能力上限 |
| **Pass^k** | 连续 k 次都通过且不触发否决项，衡量业务可靠性 |
| **Rubric** | 专家定义多维度评分准则，LLM-as-a-Judge 评判依据 |
| **一票否决（Veto）** | 特定维度触发即否决整体评价（如幻觉） |
| **LLM-as-a-Judge** | 用 LLM 根据 Rubric 自动化评判开放式任务输出 |
| **失败归因** | 从轨迹定位首个导致偏离的错误，区分根因与后果 |
| **轨迹前缀回归** | 冻结失败前上下文，只要求输出下一步动作 |
| **端到端回归** | 从初始状态跑完整任务检查最终状态 |
| **渐进式信息透露** | 模拟用户按需渐进透露信息 |
| **用户模拟** | 用 LLM 扮演用户实现自动化人机交互评估 |
| **双控环境** | τ²-bench：用户模拟器也能操作共享环境 |
| **模型替换实验** | 固定 Harness 只换模型，分数变化区分瓶颈 |
| **消融实验** | 逐一关闭 Harness 组件观察性能变化 |
| **配对比较** | 让评判者选"A 和 B 哪个更好"，Bradley-Terry/Elo 提取排名 |
| **Elo 评分** | 基于两两对决胜负预测更新评分 |
| **位置偏差** | 评判模型偏向先出现候选，交换顺序各评一次缓解 |
| **古德哈特定律** | 度量指标变优化目标时就不再是好指标 |
| **KV Cache** | 缓存已处理上下文避免重复计算 |
| **TTFT** | 首字延迟=排队+Prefill，用户感知反应快慢 |
| **p95 尾部延迟** | 95% 请求不超的延迟，比均值反映真实体验 |
| **预算—能力曲线** | 性能随时钟时间变化的曲线 |
| **领域随机化** | 物理参数外观引入随机变化缩小仿真现实差距 |
| **可验证奖励（RLVR）** | 评估判据直接作强化学习奖励函数 |
| **trajectory vs outcome** | 执行轨迹与最终结果两件事，都应覆盖 |
| **金标集** | 人工标注校准用例集，衡量评判一致性 |
| **Canary GUID** | 嵌入评估数据标识符，检测数据泄漏到训练集 |
| **FAIL_TO_PASS** | SWE-Bench 双重验证：修复前失败修复后通过 |
| **特性开关** | 可远程控制开关，服务实验渐进发布紧急熔断 |

## 高亮核心论断与金句

%%H%%评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。当一个更强或更便宜的模型发布时，拥有完善评估体系的团队能在数小时内得出切换决策，而缺乏评估体系的团队只能凭直觉或等待社区反馈。%%/H%%

%%H%%评估的对象不应只是模型，而应是模型与 Harness 的组合体。同一个模型在不同的 Harness 中可能表现差异悬殊。%%/H%%

%%H%%看到 Agent 表现下降时，应先检查评测系统本身，再动 Agent。一个常见误区是看到分数下降就立刻修改 Agent 代码，而忽略了评测系统本身可能先出了问题。%%/H%%

%%H%%好的 Benchmark 报告不只给出一个分数，还应写清结论适用于哪里、哪些底线没有通过、下一轮要验证什么。%%/H%%

%%H%%Pass@k 回答"Agent 能不能偶尔创造奇迹"，Pass^k 回答"Agent 能否稳定可靠地交付"——两者的数字可以差一个数量级以上。%%/H%%

%%H%%一定不要一次性透露所有信息，只提供当前步骤必要的内容——这是人机交互型评估与传统 benchmark 的根本区别。%%/H%%

%%H%%当一个度量指标变成优化目标时，它就不再是好的度量指标。Agent 越是在某个评分系统上训练或调优，就越倾向于钻这个系统的漏洞，而非真正提升能力。%%/H%%

%%H%%幻觉之所以列为一票否决项（veto）而非分级评分维度，是因为它与质量是正交的——一个流畅、详尽、礼貌的回答如果包含虚假事实，对用户的伤害远大于一个简短但准确的回答。%%/H%%

%%H%%归因对象是轨迹中的首个导致任务偏离的错误，后续错误往往只是连锁反应，不能把最后一个报错简单当成根因。%%/H%%

%%H%%端到端评估通常只给出"成功"或"失败"，却没有回答"为什么失败、从哪一步开始失败"。%%/H%%

%%H%%没有重置就无法公平复跑，只看回复会漏掉"说了但没做"，只看最终状态又无法定位过程违规。%%/H%%

%%H%%小范围实验通过后，只能进入完整复测；在标准环境完成 116×5 次运行后，才能讨论是否部署。%%/H%%

%%H%%外部评估告诉你"Agent 有多好"，内部评估基础设施告诉你"哪个改变让它变好了"。%%/H%%

%%H%%不是偶尔做一次评估，而是将评估嵌入到每一次产品决策中。%%/H%%

%%H%%模型选型不是简单地"选最强的模型"，而是根据应用场景在多个维度之间做评估驱动的权衡。%%/H%%

%%H%%提示词写得更详细，也补不回 Agent 根本没有看到的信息；遇到这类失败，应先检查输入，而不是继续堆提示词。%%/H%%

%%H%%评估集本身的那些具体题目必须与训练数据严格隔离——可以复用的是环境的构造机制，而非题目本身。%%/H%%

%%H%%每一轮证据只支持与它规模相称的下一步。%%/H%%
