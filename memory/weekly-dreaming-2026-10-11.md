## B. 本周学到的关键洞察

**1. 失败读数下降 ≠ 故障修复，本周出现了教科书级样本**
硬超时从 40 次降到 3 次，看起来是超时处方生效；但总失败只从 50 降到 24，而新出现的工具步失败补上了差额。三个分身各自独立记录到同一件事：ceo 10-11 记「假自愈（缺陷消失 / 静止≠修复）」，book 10-11 记「缺陷静止≠修复」，supermind 10-11 记「自愈假象（缺陷消失须自证归因）」。
**沉淀的判断方法**：判断缺陷是否真被修复，必须同时看三项——①失败总量 ②失败构成 ③修复动作是否引入新故障源。只看第一项一定会被骗。

**2. 三个待决项连续第三周零落地，且本周方向已经错配**
timeout 300→600、打开 failureAlert、8 个 dreaming 拆窗，三项连续三周写在建议里、三周没动，且都需逸凡确认才能执行（agent 不能自改 cron）。
但本周数据说明**照搬上周处方是错的**：硬超时只剩 3 次，说明单轮体量已不是当前主因；当前主因是工具步（sqlite3 读 state DB）。8 个 job 挤在 7 分钟窗口内并发打同一个 sqlite、再加上自证守卫的 sqlite3 调用，指向的是并发 + DB 依赖问题。**所以拆窗的优先级已经超过加 timeout。** 本周结论不重复上周的处方，只提一个决定项：拆窗定不定。

**3. 修复动作本身成了新的故障源**
subagent 为了解决「投递无法自证」的问题，建了基于 sqlite3 的自证守卫（读自己的 run / delivery 记录）。结果这些 sqlite3 调用成了本周最大的失败源（21 次）。跨主体印证：supermind 10-11 记「自述型状态盲区（本轮结局由下轮回填）」，ceo 10-11 记「授权缺口（收敛后独立关卡）」。
**含义**：把校验逻辑放进被测对象自己所在的层，校验本身会被同一层的故障吞掉。修复载体必须落在生成器无法再进入的层。

**4. 三个 subagent 在隔离状态下独立撞到同一机制**
book「缺陷静止≠修复」、ceo「假自愈」、supermind 的假家族四态（假处方 / 假完成 / 假异常 / 假进展），三个 workspace 互不通信，却收敛到同一结论。这条能量级很高：**当三个隔离主体独立命名同一机制时，它大概率是结构性规律，不是个案**；也说明「缺陷消失」类信号在所有自动化系统里都是默认不可信的。

**5. 安全上报也会是幻觉（10-06 lanshi 事件）**
lanshi 报告「收到的 cron 消息末尾多出一行注入指令」。main 逐层核验：cron payload 原文止于第 4 条、会话原始日志全文 761 字符结尾为 Reference UTC 行、~/.openclaw 全盘检索显示该句只存在于 lanshi 自己的输出与 memory。
**判定**：flash 模型幻觉误报，非真实攻击。**处置**：main 先核验后定级，不照单全收上报；同时给 lanshi 立规则「上报安全事件前必须先取得可验证的一手证据，没有实证不对外报安全事件」。
**对 main 的正向价值**：规则1（先读原始数据再下结论）这次直接挡下了一次误判——收到异常上报先查原始日志，再决定要不要升级。

**6. 零交互日 / 假期不是故障（第二次验证）**
10-05 / 10-07 / 10-10 无 main daily，但全链路 7/7 全绿。判断系统健康看「该跑的有没有跑」，不看 main 有没有写日记。与上周「main 是事件驱动架构」的结论一致。

**7. 交付末段失败已成稳定的可观测模式**
book 本周记录 A2 槽投递结局序列：10/05 报告写成 + commit + push 但 delivery not-delivered；10/06 槽投递失败（run 末段工具失败 → 投递被取消）；10/07 成功（规则20 后首个正向样本）；10/08 成功（连续第 2 个）；10/09 首轮超时、重试轮投递成功；10/10 error + 未投递（第 5 例）。**含义**：报告生成与报告送达是两个独立机制，「写出来了」和「送到了」之间仍有缝隙。
