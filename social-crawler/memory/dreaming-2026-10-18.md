## B. 规避方案（根因 + 绑定决策点）

### B1 交付层：写文件即发，成功只看 deliveryStatus

- 根因：cron run 的收尾阶段任一步工具/进程失败 → 整个 run 判 error → announce 被整体跳过。报告写完了但没人收到。
- 方案：报告落盘后的**第一个动作**直接 `message` 发群，不等 run 自然结束；把 `deliveryStatus=delivered` 作为唯一成功判据，`lastRunStatus` 只作监控信号。
- 绑定决策点：每次日报写完后、任何其他工具调用之前。
- 本条已在 9-19 复盘写过，**未进 payload，故第 6 次复发**。载体不换，写几次都一样。

### B2 宿主层：先停 update 循环，再谈日报自动化（最高优先级）

按顺序执行，全部需主 session 或逸凡：

1. `launchctl remove gui/501/openclaw.update.once`
   - 验证：`launchctl list | grep openclaw` 无 update.once；`/tmp/openclaw-update.log` 的 mtime 停止增长
2. `launchctl bootstrap gui/501 ~/Library/LaunchAgents/ai.openclaw.gateway.plist`
   - 验证：`launchctl print gui/501/ai.openclaw.gateway` 可查到；kill 进程后 10 秒内自愈
3. 换 Node 24 LTS 后再升级 OpenClaw
   - 验证：`node -v` 落在 `>=24.16.0 <25` 或 `>=26.1.0`；`openclaw --version` 与目标版本一致
4. 顺带修正：update 目标写的是 `2026.10.3`，而 `update-check.json` 最新可用为 `2026.10.4`，目标版本陈旧

**在做完 1、2 之前，不要指望 11:00 日报能稳定自动跑。**

### B3 跨天去重：用上次 crawlTime 当窗口起点，内容标增量

- 根因：每日固定回溯 24h，而上一份报告已覆盖到昨日 23:40，重叠段必然重复；规则只写在 dreaming 里，写日报时无人读。

- 绑定决策点：写第一条 bullet 前先 `grep` 昨日报告关键词。
- 若不做，明天仍是 60% 重复。

### B4 事实断言必须自证

- 「接口 ok=1」这类话一律改为从 raw 统计得出：`total>0` 的品牌数、`total=0` 的品牌名单。
- 绑定决策点：写「采集说明」段时，每个数字旁边必须能指向一条本会话命令输出。

### B5 守恒式升级为四段式

- 公式：`raw 唯一 id 数 = bullet 数 + 抽奖/公示剔除 + 重复合并 + 未解释残差`

- 绑定决策点：成稿后跑一次脚本对账，残差非 0 不得发。

- 方案：行业信号只用「有数据且可溯源」的品牌；接口无返回的品牌单独列在采集说明，不进结论。
