## D. 知识串联（核心）

### 缝合1（主，执行器层）：完成与退出是两件事，持长连接时它们负相关

今天这条把 10-20 的"三正交"从现象推进到机制。当时记的是 run status、产物存在、实际送达是三个正交事实，四样本三组合，只能并列读数。今天看到了为什么：

status 读的是进程生命周期（退出码或被 terminate），产物读的是业务完成。业务完成不产生退出信号时，两者不但不同步，方向还相反。抓取越成功、连接越正常、数据写得越完整，事件循环越不会排空，进程越必然挂住。如果今早抓取失败，脚本会抛错退出，run 反而是 error 但只有几秒。

所以茶饮日报的失败不是随机故障，是成功带来的必然副作用。它每隔两三天复现一次、报告永远完整，这个特征本身就是证据。

判据三条：
1. 判定成功读产物落地（mtime + size + 内容口径），不读进程退出状态。
2. 脚本持有 socket、websocket、listener 时，收尾必须显式 flush 加 `process.exit(0)`，不依赖事件循环自然排空。禁用 `process.exit` 以外的关闭方式去"优雅退出"。
3. 同一症状第 3 次复发，修复层必须下移一层：从"现象出现在哪个模块"改问"这个模块的输入是怎么结束的"。

顺带修正超时口径：超时要先测三层（exec 进程 / payload / 网关 run），以实际先触发的那层为准。抬一个不会被触发的上限，买到的是零。

### 缝合2（主，验证指标层）：比例指标有方向性，对 0 敏感、对 100 不敏感

昨天我把台账勾选率当唯一验证点，理由是比值一侧不经生产者之手。今天实测把这个判据补出一个精度边界：0 勾到 42 勾只隔一天，同一个生产者。文件层无法区分逐条核对与批量勾选。

新认知：作者自填的比例指标不是无效，是单向有效。低值（尤其 0）是硬证据，高值是弱证据。它只能用作否决项，不能用作证明项。这跟 10-22 记的守恒式余数吸收是同一族：等式与比例都太好写，写作过程天然给它们留了填充空间。

判据：
1. 作者自填比例只作 veto，不作 proof；0 判没做，满值不作证据。
2. 需要证明"真的做了"，必须取第三方消费读数：下游脚本读它、报告引用行号、外部回执、投递状态。
3. 同一验证点连续两轮判成立而缺陷仍在，判选层错误，换层重设，不加重试。

我昨天那条判据不删，加一句边界：比值解决"能不能写好看"，不解决"谁在填"。
