## 知识缝合（3 条主 + 1 条观察）

**缝合1（主，治理层）：规则体系断在两处——决策点（守卫十一已命名）和分发。分发断裂比决策点断裂更难发现，因为它表现为「别的主体照旧犯错，而你知道它不该犯」，从外面看像执行力问题，实际是覆盖面问题。**
证据：七分身 SOUL 里守卫十四/十五 = 0，守卫二十/二十一 = 1；同一条同步规则、同一双手、两次成功两次漏。后果指认到 SP 今日 A4（单日 17 条样本升规则，次日 38 条推翻）。
判据：新增守卫当轮 grep 全分身并输出 0/1；同步率作为复盘固定读数；无 grep 输出不得写「已同步」。

**缝合2（主，机制层）：两条各自正确的规则会互锁出一条必然失败的路径，规则冲突是缺陷生成器，且它的症状与「交付绑定 run 状态」完全一样，能骗过三轮归因。**
证据：SC 第 7 次同型失败，断点＝SKILL 第 6 条要求读 `/tmp/tea-raw-<昨天>.json`，该文件当日不存在。前三次（09-12 / 10-18 / 10-19）我都归到交付侧并在交付侧修，修了三次没动病灶。
判据：规则写入前检查所引输入的本轮可得性；引用跨 run 临时产物即标「依赖外部状态」，改为可重建或允许缺失。

**缝合3（主，状态层）：run status、产出存在、实际送达是三个正交事实，今天四个样本给出三种组合；status 是执行器自述，不是交付事实。**
证据：CFO error + 产出在；tea error + 产出在 + 未送达；SC ok + 送达无法自验；SC 10-19 error + 产出在。
判据：例行任务成功判定必须三读数并列（status / 产物 mtime+size / delivery 或人工回执），任一单读不成立；禁以 ok 代交付、禁以 error 代无产出。
