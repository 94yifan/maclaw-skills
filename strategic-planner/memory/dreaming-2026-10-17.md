## A. 执行错误

### A1（P0）连续两日零产出，且把「没跑」误读为「跑了没交付」
本次断档的形态与过去 12 次样本不同：过去是文件落盘、交付被吞（执行层），今天是 run log 里**根本没有记录**（调度层）。若继续沿用单一 `lastRunStatus=error` 判据，会继续在 prompt 和脚本层修一个进程层故障。**这是本日最重要的判断错误。**

### A2（P0）单点人工依赖被当成常态
网关被杀后不自愈，靠人手动拉起。两天空窗的持续原因不是「没发现」，是「没人拉起」。系统设计里少了一根自动扶起的柱子。

### A3（P1）重试没有出口
6391 次重试、错误文本 100% 相同、每次都以杀掉宿主为代价。launchd 自己已标记 `immediate reason = inefficient`，系统在喊停，但无人受理。**一个永远不会成功、却永不停止的重试，负价值高于不做。**

### A4（P1）我把「补跑起来」误读成「恢复了」
23:35 之后 dreaming 与 report 都被拉起，但数据窗口已永久丢失：SC 的 24h 抓取窗口覆盖不到 10-16 11:00 至 10-17 23:35（约 36.6 小时空洞）。**调度恢复 ≠ 数据恢复。**

### A5（P1）告警口径缺一层
failureAlert 能兜「单 job 失败」，兜不住「调度器整体不工作」。全站故障 36 小时，逸凡侧无任何主动告警，直到 catch-up 把任务一个个拉起来。

### A6（P2）payload 里的时间文本已漂移
payload 写「现在是每天晚上10点02分」，实际排期 22:12，今日 23:38 补跑。报告若照抄这句话，就是事实错误。**硬编码时间 = 每天都在说假话。**

## B. 规避方案（落成规则，非建议）

### B1（P0·须逸凡或主 session 执行，本 session 无权限且属系统级动作）
停掉 update 死循环：`launchctl remove gui/501/openclaw.update.once`（必要时先 `kill -TERM 87011`）。
**验证三查，缺一不算修好**：① `launchctl list | grep openclaw.update` 无输出；② `/tmp/openclaw-update.log` mtime 60 秒内不再增长；③ 网关存活 >10 分钟（此前存活天花板 <1 秒）。

### B2（P0）恢复 launchd 托管
`launchctl bootstrap gui/501 ~/Library/LaunchAgents/ai.openclaw.gateway.plist`。验证：`launchctl print` 能查到；`kill -TERM` 后 10 秒内自愈。这是唯一让网关死了会自己起来的机制。

### B3（P0）Node 对齐前禁止再升
先 `brew install node@24` 或升到 `>=26.1.0`，再 `openclaw update`。**前置校验固化为一条命令**：`node -v` 必须命中目标 engines 区间，不命中不许发起 update——每失败一次 = 全站停摆一次，重试成本不是流量，是可用性。

### B4（P1）故障判定三层，写进 MEMORY 作为唯一判据
- 第 1 层 调度层：`cron_run_logs` 有无记录。无记录 → 查网关进程与 schedule。
- 第 2 层 执行层：有记录且 error → error 文本三分类：`interrupted by gateway restart`（宿主）/ `LLM request failed`（provider）/ `Process failed`·脚本（脚本层）。
- 第 3 层 交付层：文件是否落盘 + `delivery_status`。
**结论不得跨层套用**（守卫二十：读数 × 判断 × 动作逐段对齐）。

### B5（P1）重试必须带出口（新规则）
任何自动重试：①发起前预检成功条件是否可能满足（今日：node 版本命中 engines）；②设最大次数与退避上限；③同型错误连续 N 次（建议 3）即停并告警，禁止 keepalive 无限重投。

### B6（P1）断档必须显式标空洞，不补造
今日口径：SC 数据空洞 = **10-16 11:00 → 10-17 23:38（约 36.6h）**。明日报告 header 必须写实际抓取时刻 + 空洞区间 + 重叠区间。24h 窗口之外的不可回溯，记 `data_unavailable`。

### B7（P1）补一层调度级 watchdog
11:10 由独立轻量检查判断 `/tmp/tea-raw-<today>.json` 与 `memory/weibo_daily_<today>.md` 是否存在，缺失即告警（只报警不出报告）。**但注意：网关全死时唯一可用的通道是 launchd 级脚本，独立于 OpenClaw 进程**——这是今天最值钱的架构结论。

### B8（P2）SP 自身：10-16 断档按缺失记录
不补写 10-16 复盘，只在 MEMORY 里记「10-16 缺失（宿主层）」。补造比缺失更坏。

## D. 知识串联

今日 SC 日报缺失，行业信号层无新增数据。**因此本次串联落在机制层**（这是今天唯一有真实证据的层面），并把 09 月以来积累的判断框架向前推一步。

### 缝合1（主）：故障分层判定 —— 观测口径决定修复方向
串联 守卫二十（读数×判断×动作）＋ 守卫十七（完成态必须自证）＋ 10-07~10-15 连续 12 次「收尾轮工具污染」复盘。
过去 12 天的所有修复都指向执行层（prompt 里加禁令、收尾轮零工具调用、timeout 300→600），因为唯一的观测口径 `lastRunStatus` 把「文件已产出但交付被吞」和「任务根本没启动」压成同一个 `error`。两天全站停摆因此不可见。
→ **任何监控指标一旦合并两个故障层，修复方向必然错层。判定顺序固定为：先问「有没有记录」，再问「为什么失败」，最后问「有没有送达」。**

### 缝合2（主）：无出口重试 = 负价值动作
串联 守卫十（校验目标不得互斥）＋ 守卫二十一（无消费者的动作即停例行）。
今日实证：成功条件（版本升级）在 node 25.8.1 上不可能满足，重试 6391 次，每次代价是杀掉宿主，零次收益。这与守卫二十一的结构相同但方向相反——守卫二十一停的是「没人看的推送」，这里要停的是「不可能成功的重试」。
→ **任何自动重试必须三件套：成功条件预检 / 上限 / 同型失败即停并告警。缺一条，它就会从补救机制变成故障源。**

### 缝合3（主）：串联单点 → 可用性相乘
串联 2026-07-22（全系统零产出日，首次确认 SP 依赖 SC）＋ 09-19 缝合3（账号马太效应）＋ 今日事实。
SP 的行业知识更新 = SC 抓取（单点 A）× 宿主进程（单点 B）。两段串联，可用性相乘：各 95% 则合起来约 90%，30 天里丢 3 天。今天是丢的第 2 天，且 24h 窗口不可回溯。
→ **知识供给链的每个上游都必须是可绕过的。至少一层要活在宿主之外（本地缓存/离线归档/手动回溯入口），否则一次宿主故障 = 知识永久缺口。**

### 缝合4（主）：存在 ≠ 生效（第 N 次，这次在基建层）
串联 守卫九（门禁只校验存在等于没校验）＋ 10-12 配置修复（只认 updated_at 变化）＋ 10-15 教训。
今日：`~/Library/LaunchAgents/ai.openclaw.gateway.plist` 存在、KeepAlive=true 写着，但 `launchctl print` 查无此 service——文件在，托管不在。这是同一个认识论错误从业务层（确认文件 touch 就开门）迁移到基建层。
→ **「文件/配置存在」在任何层都不能当「机制生效」。生效的唯一证据是运行时态：服务能查到、kill 后能自愈、读数在变。**

### 缝合5（业务层，data_unavailable）
10-15 承接位（霸王茶姬归云南·日照金山 10/16、林里×魔兽世界 10/16、东方墨兰黑糖珍鲜奶 10/16）**无法验证**——无 SC 日报、无 raw。按守卫十四记 `data_unavailable`，不以推测代替。
