## A. 执行错误

### A1（P0）上一轮的 status=error 是已恢复的工具失败，不是失败轮

判定依据不是猜测，是同一轮 session 的逐条实读：

1. 14:08:19Z，`apply_patch` 返回 isError=true，原文 `Invalid patch hunk at line 9: Expected update hunk to start with a @@ context marker, got: 'DIAG="$(sqlite3 ...'`。错因是我把一整行 shell 直接塞进补丁体，没有给上下文标记。
2. 14:08:23Z，同一轮改用 exec 写文件，返回 `patched / syntax OK`，改的是同一个脚本。
3. 14:09:17Z，closeout 二次运行，commit f7de2d2。
4. 14:09:22Z，最后一条 assistant 消息 `stopReason=stop`，正文为纯文本，没有悬挂的工具调用。
5. 本轮核对：`git merge-base --is-ancestor ca99e25 github/main` 与 `f7de2d2 github/main` 均成立，两笔提交都在远端。

所以产物、收尾、运行三个读数里，只有 status 这一项是负的。status 被中途那次补丁失败固定住了，而轮次本身完整跑完并交付。

代价有两个方向，第二个更危险：

- 计数污染：`consecutive_errors` 现在记 1。若再出现两次同类事件，after=3 的 failureAlert 会发一次误报，而误报会消耗逸凡对告警的信任。
- 真假同形：真失败（10/14 进程被杀、10/16 gateway 重启）与假失败（今天这种中途工具失败）共用一条 status 字段。只看 status 分不出，必须回到产物与收尾去对账。

另外还有一层：昨晚我在同一轮里已经踩过一次 apply_patch，改用 exec 三秒解决，但没有把「大段文本不要用补丁猜上下文」写成规则，于是这次仍然先试补丁。这是同一个动作的第二次踩坑。

1. **守卫AX（新增，已编译进脚本）**：失败轮判定必须三读数对齐，产物（commit 且为远端祖先）、收尾（最后一条 assistant 消息 stopReason=stop 且无悬挂工具调用）、运行（status / duration / error 文本）。仅 status=error、且错误文本不是超时、不是 gateway restart、不是进程被杀者，归「已恢复的工具失败」，不计失败轮。落点：`dreaming_closeout.sh` 第 6b 步按 error 文本自动归类，工具层失败时打印 WARN 要求核对三读数。
