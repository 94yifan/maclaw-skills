## A. 执行错误

### A1（P0 · 交付形态）同一产物在 20 分钟内被全量重发 5 次

- 事实：17:41–18:01，图片分批到达，CEO 每次收到新一批就重新生成并**全量重发**整个 2.55 万字文件（5 次）。逸凡 20 分钟内收到 5 个同名文件。
- 问题：交付触发点绑在「输入到达」而非「输入收敛」。流式输入 + 整体产物的组合下，这会把交付变成随输入漂移的中间态——用户拿不准哪一版是终稿（今日终稿的确认成本已经显现：页数对不上、需要回问）。
- 根因：任务开始时就应识别「输入是流式、产物是整体」，据守卫七把交付绑到收敛信号；但 22 天未处理过真实任务，该判断点从未被触发。

### A2（P0 · 一致性）页数计数前后矛盾，且核对滞后到被追问才做

- 事实：5 次交付文案的页/图数依次为 25 页 / 40 图 / 59 图 / 61 图 / 61 页书+2 简历；而末次核对 = 64 图、2 简历 → **62 页书**。核对的触发点是逸凡的追问，不是交付前。
- 问题：数量类断言（守卫三：事实陈述须过三问）在每次交付时未与原始图清单对账；守卫八要求的「交付前一致性检查」没有落成硬门。
- 根因：守卫八只规定「要查」，没规定「在哪一步查」（违反守卫七）——落点在交付之后（被人质疑时），而非交付之前。

### A3（P2 · 命名）用户称「三十六计」，产出命名为「36计」

- 事实：文件名 `团队激励36计_片段整理.md`。属对外交付物的命名，应与用户口径一致（用户原话「团队激励三十六计」）。

## B. 规避方案（落定为下次铁律）

### B1 流式输入任务 →「收齐再出稿」

- 判据：任务开始时先问一句「输入是一次性还是流式到达；产物是整体还是分块」。**输入流式 + 产物整体 → 交付只挂收敛信号**（逸凡说「发完了」或静默超时），流式阶段只回轻量进度（收到 N 页 / 累计 M 页），**不重发全量**。
- 落点（守卫七）：绑定到「收到新一批图片」这一决策点——该点只允许回文本进度，禁止调用 message 发送全量文件；全量交付由「收敛信号」或「用户催定稿」触发。

### B2 交付前硬门：数量对账 + 文案自洽

- 每次交付前跑两项对账：①原始图清单数 = 转录页数 + 明确弃用数（今日 = 64 = 62 + 2）；②本次文案里的数字与文件实际一致。
- 不通过则不出稿，先解决再交付。
- 落点：绑定到「调用 message 交付」前的决策点；把对账写成脚本（如 `build.py` 收尾自动打印「收图 N / 页 M / 弃用 K / 一致性 pass|fail」），使「想交付」时数字已被打印。

### B3 强断言配强证据

- 「逐字 / 一字不改 / 全部 / 完整」类断言，证据覆盖须与断言强度匹配：逐字类须全量或高比例（≥30%）机器回读校验，或改为「已尽力校对，抽查 N 页无误」的弱化表述。
- 承接 09-30 缝合4（负面/强断言须绑证据）。

### B4 命名口径 = 用户口径

- 对外交付物命名一律采用用户原话的写法（三十六计，不是 36计）。

## D. ★ 知识串联（核心环节）

### 缝合1（主 · 元层 · CEO 自应用）：守卫体系继承其观察对象的形状——只观察系统，就只长出系统层守卫

- **今日证据：** CEO 22 天 dreaming 长出的守卫（七~十、十七~十八）**全部针对系统层**（规则落点、门禁校验、校验目标互斥、完成态自证）。今日首次真实交付，连出两处**最原始**的错误——同一文件 5 次全量重发、页数自相矛盾——而现有守卫体系对「交付形态」**零覆盖**，一条都拦不住。
- **关联：** 守卫七（规则须绑定决策点）+ 守卫八（一致性检查须找同机制多样本）+ 10-02 缝合1（覆盖缺口四维）+ 10-04 缝合2（规避方案与其对象同命）。
- **新认知：** 守卫/规则不是通用物，它是**观察范围的函数**——你长期观察哪一类对象，就只长出该类对象的规则，对未被观察的对象形成**零覆盖**（observation-shaped coverage）。判别：当长期只有一类输入（系统/内部），全部规则都会长成该类对象的形状；真实活动一旦恢复，会立刻把「零覆盖对象」以**最原始的差错形式**暴露出来（不是「不知道该怎么做」，而是「储备再多也没覆盖到这里」）。修法：守卫清单按**对象清单**补全——先列对象（系统 / 对外交付 / 客户沟通 / 内部协作），每类至少一条，而不是按「出错次数」累积。
- **管理同构：** 只做内部流程复盘的公司，规则全围绕内部，一遇客户/市场就出最原始的错（报价错、交付错、版本错）；补法是先把「暴露面清单」列全，再逐面立规。

### 缝合2（主 · 交付层 · CEO 自应用）：增量任务下交付时机被「输入到达」绑定，而非「输入收敛」

- **今日证据：** 图片陆续到达，CEO 每批即全量重发整个文件（5 次）。
- **关联：** 09-30 缝合1（依赖全部输入完成的动作属「跨轮/末尾」）+ 10-04 缝合3（收尾工具调用污染：run 结局被尾部动作绑定）+ 10-02 缝合1（链路段覆盖）。
- **新认知：** 交付动作有两个可选触发点——**输入到达**（每批触发）与**输入收敛**（用户说「发完了」/静默超时触发）。前者把交付变成随输入漂移的中间态（版本轰炸 + 用户失去版本锚点），后者把交付绑定到收敛信号。判据：凡「输入流式到达 + 产物为整体」的任务，交付只能挂在收敛信号上；流式阶段只回轻量进度。
