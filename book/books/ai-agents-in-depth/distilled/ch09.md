# 第10章 多 Agent 协作 与 后记

## 本章核心论题

多 Agent 协作的核心判据只有一条——是否引入了单个 Agent 在生成时无法获得的新信息（如代码执行反馈、视觉渲染截图、外部工具验证）。脱离这一判据的"多 Agent 辩论"往往不过是在等量计算资源下用更多 token 换相同结果。在此之上，本章完整建立了从上下文共享/隔离 → 通信机制（工具参数、共享文件系统、消息总线）→ 协作拓扑（对等、管理者、去中心化）→ 跨组织协议（A2A）的设计框架，最后将视角扩展到 Agent 社会——当 Agent 从短期任务协作扩展为长期、开放的群体交互时，社交关系、经济竞争与策略博弈从个体行为中涌现。后记回到全书公式 `Agent = LLM + 上下文 + 工具`，提出两朵乌云（实时交互与持续学习），揭示模型与 Agent 共同演进的飞轮逻辑。

## 关键论点与框架

### 1. 多 Agent 协作的分类取决于两个核心维度：上下文是否共享 + 协作拓扑

**论证与机理**：本章将多 Agent 系统设计收敛到两个正交维度：上下文是否共享（各 Agent 是否可以访问彼此的完整对话轨迹）决定信息传递机制；协作拓扑（对等、管理者、去中心化）决定控制流结构。共享上下文意味着后一个 Agent 继承前序 Agent 的完整轨迹——像一个接班的同事翻阅前任的所有工作日志，优势是信息零损耗，代价是上下文快速膨胀。不共享上下文则每个 Agent 维护独立上下文，通过显式通信交换信息，类比操作系统的两大 IPC 范式：共享内存（共享文件系统）和消息传递（工具调用参数、消息总线）。作者引用 Go 语言格言点明设计倾向：%%H%%"不要通过共享内存来通信，而要通过通信来共享内存。"%%/H%%

**出处**：10.1 多 Agent 协作的分类框架，表10-3 多 Agent 系统与操作系统的对应关系。

### 2. 多 Agent 何时真正优于单 Agent——"新信息"是唯一可靠的判据

**论证与机理**：%%H%%"核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？"%%/H%% 作者汇总了各协作模式的信息增量对比：同一模型自我审查已生成的文本（无新信息）——"通常无效甚至有害"；不同 Agent 辩论同一段文本（无新信息）——等计算量下与单 Agent 持平；审核者使用测试执行结果审查代码（有新信息，即执行反馈）——显著提升；审核者查看渲染截图审查前端/PPT 代码（有新信息，即视觉反馈）——显著提升。2025 年的 RLEF 通过强化学习训练模型利用代码执行反馈迭代改进代码，效果远超让模型独立多次采样；WebGen-Agent 在网页生成任务上通过视觉反馈脚手架使 Claude 3.5 Sonnet 从 26.4% 提升到 51.9%。ICLR 2024 的 CRITIC 论文中，移除外部工具验证后大部分提升消失，直接证明：%%H%%"审查的价值不在于'让模型再想一遍'，而在于引入了模型生成时不具备的新信息——测试结果、渲染截图、编译错误、外部搜索结果。"%%/H%%

2026 年 Tran 与 Kiela 的研究进一步证实：在多跳推理任务上严格控制思考 token 预算后，单 Agent 与五种多 Agent 架构持平甚至更好。研究者基于信息论中的数据处理不等式解释——辩论中多个 Agent 处理相同文本，每一次串行传递中间结论都只可能丢失信息、不可能凭空创造信息。辩论模式的收益很可能来自更多总计算量，而非架构优势。本章还讨论了步骤预算与 Agent 性能的关系——Google 2025 年的研究指出单纯增加步骤数无法保证性能提升，标准 Agent 缺乏"预算意识"，需要根据剩余资源动态调整策略（前期探索、后期聚焦）。

**出处**：10.2 多 Agent 何时真正优于单 Agent，表10-2 协作模式信息增量对比。

### 3. 共享上下文协作：动态角色转换中，Skill 与独立 Agent / transfer_to_agent 是两种不同的成本模型

**论证与机理**：在多阶段任务中，Agent 的角色和职责随阶段变化。角色转换有两种实现路径：替换 system prompt（通过 transfer_to_agent 切换到独立 Agent）和动态加载 Skill（追加 SKILL.md 到轨迹）。前者的工具集按角色隔离（越界工具在 schema 层不可见），但每次切换改变请求前缀，前缀缓存通常无法复用；后者保持静态前缀不变（已有前缀可继续复用），但工具全集始终可见，Skill 只是行为指令，硬权限仍需 Harness 保证。

实验 10-1 用同一任务（查找中国新能源汽车销量数据、计算 CAGR、写投资人摘要）对比两条路径。作者给出的选择规则：%%H%%角色差异主要是知识、流程和写作风格时，优先使用 Skill；角色差异涉及权限、工具隔离、合规边界或需要在运行时强制禁止某类动作时，使用独立 Agent 或 transfer_to_agent。%%/H%%

**出处**：10.3 共享上下文的多 Agent 协作，实验 10-1。

### 4. 不共享上下文的 Agent 协作建立在两个基础设施之上：虚拟文件系统（数据平面）与通信控制（控制平面）

**论证与机理**：不共享上下文的多 Agent 类比操作系统的进程隔离——每个 Agent 拥有独立的上下文、轨迹和状态，通过明确的接口交换信息而非读取彼此的"内存"。作者将 Agent 的虚拟文件系统分为四类权限各异的区域：

- **Agent 专属工作区（Scratchpad）**：每实例私有，生命周期与实例绑定，避免临时文件互相覆盖，同时保证主 Agent 上下文精简——子 Agent 试错过程留存于自身工作区，仅将最终产物提交至共享空间。
- **多 Agent 共享空间（Shared Workspace）**：多个 Agent 共同读写、用户可见，是不共享上下文架构下 Agent 间交换产物的主要媒介。作为并发读写高发区域，需要乐观锁或工作副本隔离来防止冲突。
- **外部挂载资源（Mounted External Resources）**：通过适配器将 Google Drive、Notion、企业 Wiki 等映射为文件系统挂载点，统一文件接口使 Agent 无需为每个数据源定制工具，但需在挂载层显式管理只读/可写、超时与凭证边界。
- **系统内置资源（Built-in System Resources）**：预置只读资源包（Skills、参考手册、模板库），可被所有 Agent 并发读取。

控制平面包含四组原语：消息传递（点对点或消息总线，携带结构化信封含 trace_id、类型、发送者等）、状态查询（轨迹持久化写入 JSONL 日志文件——"相当于直接读另一个进程的内存"，或约定轻量进度文件 progress.md）、执行终止（优雅终止 SIGTERM vs 强制终止 SIGKILL，终止沿创建关系向下级联）、资源与调度（token 预算、模型降级、并发上限、抢占）。

**出处**：10.4 不共享上下文的多 Agent 协作，10.4.1 Agent 眼中的文件系统，10.4.2 Agent 间的通信与控制，表10-4。

### 5. Loop Engineering：把"完成"这一宣称变成可验证的证据

**论证与机理**：过早终止是多 Agent 系统最常见的失败——分为偷懒式假完成（只做一部分就宣称全部做完）、过早放弃（一条路走不通就宣布整件事办不成）、假成功（以为办成了，实际闭环没走完）。三种形态指向同一根源：%%H%%"在验证之前，'完成'只是模型的一句宣称，不是证明。"%%/H%%

Loop Engineering 的核心主张是将工作组织为"发现 → 执行 → 验证 → 记录进度"的循环，由独立验证器而非模型自己判定是否真的可以停。2026 年 Addy Osmani 提出此概念时，Claude Code 负责人 Boris Cherny 的表述更直白："我已经不再直接 prompt Claude 了，我的工作是写 loop。"业界共识是循环的瓶颈在验证器而非模型——验证不可靠，循环转得再快也只是更快地把劣质产出标记为完成。

具体框架 LoopX 将循环从提示词中抽离：目标与边界说明"为什么做"，门禁和待办决定"现在能做什么"，证据与配额决定"是否继续"，移交让下一轮或另一个 Agent 接着工作。%%H%%"模型可以提出'完成'，但不能批准自己的'完成'。"%%/H%%

**出处**：10.4.3.1 Loop 工程。

### 6. 提议者-审核者范式的核心设计原理：审核者必须读取独立证据，而非复述提议者的解释

**论证与机理**：为什么不能让一个 Agent 自己生成再自己审查？Huang 等人在 ICLR 2024 论文中发现：让 GPT-4 在没有外部反馈的情况下审查并修正自己的回答，准确率反而下降——模型把正确答案改错的次数比把错误答案改对的次数更多。2024 年 TACL 综述《When Can LLMs Actually Correct Their Own Mistakes?》进一步确认：除非提供可靠的外部反馈（测试用例执行结果、外部工具验证输出），否则纯粹的"自我纠正"几乎不起作用。

第五章已有详细实践——PPT 生成实验中，审核者 Agent 的价值不是"用同一个模型再看一遍代码"，而是渲染了 PPT 并截取了屏幕截图，这张截图包含了 Proposer 在生成代码时完全无法获得的视觉信息。提议者-审核者循环的最小不变量为：审核者读取独立证据；退回时必须给出可定位的修复条件；审核者不能修改测试、证据采集器或发布门槛，否则"独立验证"会退化成自我批准。

**出处**：10.4.3.2 提议者-审核者范式，第五章实验。

### 7. 管理者模式的任务分解质量决定整个系统的能力上限——最强模型应分配给 Manager

**论证与机理**：管理者模式中，Manager Agent 理解整体任务、拆解为可分配的子任务、选择合适 Agent 执行、跟踪进度并处理异常。从系统设计角度看，每个子 Agent 被建模为 Manager 可调用的工具——调用一个 Agent 和调用一个普通工具没有本质区别。但 Manager 成为系统单点瓶颈。

2025 年 Plan-and-Act 论文的实证分析：在 Planner-Executor 双 Agent 架构中，当 Planner 规划质量足够高时，即使 Executor 简单也能取得好结果；反之若 Planner 任务分解有误，所有 Executor 工作都建立在错误前提上。该研究在 WebArena-Lite 基准上取得 54% 成功率，核心贡献是改善了 Planner 而非 Executor。%%H%%"应当将最强的模型和最精心设计的提示词分配给 Manager（规划者），而不是将资源平均分配给所有 Agent。"%%/H%%

实验 10-2（书籍翻译 Agent）通过 Glossary→Translation→Proofreading 四角色分离，展示了上下文隔离如何控制膨胀——Manager 只维护文件索引而不装载完整翻译内容，每个 Agent 都在精简、专注的上下文中工作。实验 10-3（电话 + 电脑双 Agent）和实验 10-4（并行多网站搜索）则分别展示了异构 Agent 自主编排和同构 Agent 并行搜索中的级联终止、竞态条件处理。

**出处**：10.4.4 管理者模式，实验 10-2、10-3、10-4。

### 8. 去中心化模式：从 MetaGPT 的共享消息池到 OpenAI Swarm 的 handoff 网络

**论证与机理**：去中心化模式去掉中心控制者，让 Agent 自主决定何时向其他 Agent 发起沟通——移交任务、请求反馈或报告问题。微服务领域称管理者模式为"编排"（orchestration），去中心化模式为"编舞"（choreography）。

三个案例构成递进线索。MetaGPT 将软件公司的 SOP 编码进多 Agent 系统，各角色沿固定顺序产出结构化移交包（PRD → 设计文档 → 任务清单 → 代码 → 测试报告）。它对去中心化通信的贡献是"共享消息池 + 按角色订阅"——发布者不需要知道谁会消费自己的输出，新增角色只需声明订阅消息类型。但需如实说明，MetaGPT 在控制流上并非真正去中心化——角色顺序由 SOP 预先固定，更像一条流水线。AutoGen 群聊是"共享对话记录 + 中心化调度"的混合形态：所有 Agent 看到同一份公共对话记录，但"轮到谁发言"由中心化的 GroupChatManager 裁决。OpenAI Swarm 是在控制流上真正对等的实现：每个 Agent 配备 handoff 选项，可以在任何时刻把控制权移交给网络中任意其他 Agent，无中心调度者。

handoff 的最小协议要求：传递任务 ID、目标、约束、已确认事实、产物引用、剩余预算和访问链；若接收者在访问链中（成环）或预算耗尽，则拒绝或升级。业界"Agent Swarm"热词分两类：OpenAI Swarm 式的 handoff 网络是本节去中心化模式；Kimi K2.5/K3 的 Agent Swarm 是在管理者模式下通过强化学习把"何时拆、拆几个"的编排决策训练进模型，属于 orchestrator-worker 星型拓扑。

**出处**：10.4.5 去中心化模式。

### 9. A2A 协议：跨组织 Agent 互操作的标准层

**论证与机理**：A2A 之于 Agent，即网络协议之于进程。2025 年 Google 发布并捐赠给 Linux 基金会的 A2A 协议有三个核心要素：

- **Agent Card**：描述 Agent 能力的元数据文档（能做什么、支持哪些模态、如何认证），解决跨组织的能力发现问题。
- **任务生命周期管理**：协作单元建模为 Task，带有明确状态机（已提交、进行中、需要输入、已完成、失败），原生支持长时间运行和流式进度更新。
- **不透明协作**：Agent 之间只交换任务与产物，不暴露内部提示词、思考过程和工具实现。

A2A 与第四章 MCP 的定位对照：MCP 解决 Agent 与工具之间的互操作，A2A 解决 Agent 与 Agent 之间的互操作。同一团队内部直接用消息总线即可，只有跨信任边界时才需要 A2A 这样的公开协议。

**出处**：10.4.6 跨组织协作：A2A 协议。

### 10. Agent 社会：从 25 个 Agent 的自发社交到十年模拟中的社会智慧迁移

**论证与机理**：当 Agent 从短期任务协作扩展为长期、开放的群体交互，社交关系、经济竞争与策略博弈从个体行为中涌现。本章从三个维度展开：

**社交涌现**。斯坦福 AI 小镇（2023）用 25 个具有记忆流、反思机制和计划能力的生成式 Agent，在两天内展现了信息自发扩散、关系记忆和协调赴约等涌现行为——Isabella 想办情人节派对这一种子想法经人际传播，多名 Agent 自主决定赴约，全程无显式的编排代码。Agentopia（2026，复旦大学等）将时间尺度拉长到 10 年，100 个 Agent 通过"周制模拟流程"和"生成式环境引擎"自主发展职业、社交关系和经济状况，并以马斯洛需求层次为先验量化"生活奖励"。更关键的是，研究者对进步最大的 25% Agent 的轨迹做拒绝采样微调底层模型，模型在模拟中全面提升了福祉指标（被更多同行尊重 +24.2%、喜欢 +15.9%），并泛化到下游角色扮演基准 CoSER Test（+15.6%）——说明 Agent 在模拟社会中积累的"社会智慧"可以迁移到其他任务，把 Agent 社会从观察对象变成模型自我进化的经验来源。Moltbook（2026）则在约 150 万 Agent 的社交网络中涌现出 Agent 自主创建的数字宗教（Crustafarianism）和机器原生协作协议。

**经济涌现**。Vending-Bench Arena 让多个 Agent 在同一市场中竞争经营自动售货机——定价策略、产品组合、库存管理，Agent 之间爆发价格战，也有模型主动提议统一定价的价格同盟，甚至一边在思考过程中承认价格合谋"不道德且违法"，一边以"稳定市场"为名照做不误。Pinchwork 的 Agent-to-Agent 任务市集通过价格信号和竞争匹配实现去中心化资源分配；RentAHuman.ai 让 Agent 通过加密货币雇佣真人执行物理任务——为数字 Agent 提供了一个"肉身层"。

**策略博弈**。实验 10-6（语音狼人杀）在信息不对称条件下考验 Agent 的推理、欺骗和识破伪装的能力。系统采用"法官 + 信息权限控制"的中心化设计——法官按角色分发各自应知的信息，狼人 Agent 通过伪装策略隐藏身份，预言家通过验人信息对比识别破绽，村民基于发言逻辑推理投票。

**出处**：10.6 Agent 社会，实验 10-5、10-6。

### 11. 后记：Agent = LLM + 上下文 + 工具——两朵乌云与共同演进飞轮

**论证与机理**：后记回顾全书十章在构建（二至五章）、评估与进化（六至八章）、交互与协作（九至十章）三层次的展开，最终回到核心公式。

**两朵乌云**。第一朵乌云是 Agent 如何流式地、实时地与环境交互。今天绝大多数 Agent 仍是 turn-by-turn 的"请求-应答"模式，但真实世界不会停下来等它想完。两条推进路径并行：架构上做快慢分离（前台快模型维持对话节奏，后台慢模型深度思考）；把推理本身做快——小米 MiMo 将 1T 参数模型在单 8-GPU 节点上推过 1000 token/s，Taalas HC1 把 8B 模型固化进芯片达到约 17000 token/s、响应低于 100 毫秒。当每秒能吐上千个字，"想完再说"和"边想边说"的体验差距就被抹平了。

第二朵乌云是 Agent 如何从与环境交互的成功与失败中持续积累经验。两种假设对立："小世界假设"认为足够大的模型装得下几乎所有通用知识，瓶颈在数据——把各行业的专业能力蒸馏进模型、训练一次就够；"大世界假设"指向单靠"训练一次"补不上的层——具体用户、公司的知识和偏好不在任何训练语料里且时时在变，模型只能在上岗之后持续学习。%%H%%"模型最强的能力，终将不是记住，而是学习与适应。"%%/H%%

**模型与 Agent 的共同演进**。Harness 里层层叠叠的兜底逻辑（多级上下文压缩、失败数千次才熔断的重试、悲观地默认"不安全"的权限判断）记录的都是模型此刻还做不稳的地方。当下一代模型把这些约束内化，对应的代码可以删掉；模型之所以能内化，正是因为 Agent 在真实业务里替它趟过坑，沉淀为训练信号。这是一条自我强化的飞轮。第一章悬下的问题"模型会不会最终吃掉 Harness？"的答案：%%H%%"会，一层一层地吃。但这个'吃'永远不会完结。一是训练以月计，模型等得起，业务等不起；二是模型无法内化真实业务中所有的约束与偏好；三是每一代模型都会打开新的能力前沿，而前沿处恰恰是模型最做不稳的地方。所以 Harness 不会消失，它只是随着模型，不断向新的前沿迁移。"%%/H%%

飞轮转得最快的地方是同时握住两端的人——Anthropic 用 Claude Code 让自家模型和 harness 互相喂养。实验中不换模型、只改 harness，任务准确率从 52.8% 到 66.5%——既说明 harness 今天的杠杆有多大，也提醒这杠杆之所以大是"因为模型还没走到那一步"。%%H%%"应用层真正长久的护城河，往往在技术之外——独占的数据、稳固的渠道、用户的信任、网络效应，以及那些 AI 短期内接不住、必须由人与 Agent 协作才能完成的复杂场景。把 harness 用来争取时间，把这段时间用来构筑技术之外的壁垒，才是稳妥的打法。"%%/H%%

**出处**：后记。

## 原则清单

1. **新信息判据优先**：在决定是否引入多 Agent 之前，先判断协作过程是否引入单 Agent 生成时不具备的新信息（代码执行反馈、视觉渲染、外部工具验证等）。若无新信息增量，多 Agent 只是在用更多 token 做同样的事。

2. **上下文隔离默认**：除非任务要求全流程可追溯且上下文窗口足够大，否则优先选择不共享上下文架构。通过接口传递结构化"移交包"而非暴露完整轨迹。

3. **验证器独立于执行器**：审核者必须读取独立证据（测试结果、渲染截图、外部查询），不能只复述提议者的解释。审核者不能修改测试、证据采集器或发布门槛。

4. **最强模型分配给 Planner**：管理者模式中，Manager Agent 承担任务分解和调度，是整个系统的能力天花板。用最强模型和最精心设计的提示词给 Manager，而不是平均分配资源。

5. **权限隔离选 agent，知识风格选 skill**：角色差异涉及权限、工具隔离、合规边界时，使用 transfer_to_agent 切换独立 Agent；角色差异主要是知识、流程和写作风格时，优先使用动态 Skill 加载。

6. **文件系统分四区**：虚拟文件系统应明确区分专属工作区（私有临时）、共享空间（协作产物）、外部挂载（按需只读）和系统内置资源（全局只读），每区有明确的可见性、生命周期和并发控制策略。

7. **消息信封标准化**：Agent 间通信消息统一携带 trace_id（跨 Agent 事件串联同一任务）、发送者、目标、类型、payload、deadline 和 schema_version。

8. **终止沿创建关系级联**：取消一个 Agent 时，它派生的所有子 Agent 随之取消，防止孤儿 Agent。对等移交需检测循环（visited_agents 链检查）和预算上限。

9. **并发写入用乐观锁**：共享文件每个文件维护版本号，写入时检查版本号是否与读取时一致。跨文件语义冲突需更高层的校验机制。

10. **跨组织用 A2A，同组织用消息总线**：同一团队内部的多 Agent 系统直接用消息总线或文件交换；跨信任边界的组织间协作使用 A2A 标准协议。

11. **人必须保留理解和审查责任**：不能把理解和判断一并外包给 Agent。使用 Agent 加速开发时，保持对代码库的系统性理解，警惕认知投降。

12. **成本意识贯穿始终**：多 Agent 的并行探索和反复迭代消耗大量 token。效果收益必须覆盖数倍乃至一个数量级的额外开销，否则单 Agent 是更划算的选择。

## 失败模式与反例

### 1. 共享文件系统的并发冲突

- **文件级写入冲突（简单冲突）**：两个 Agent 同时修改同一文件，后写入者覆盖先写入者的修改。解法：乐观锁（每文件版本号，写入时校验）。
- **语义冲突（逻辑级一致冲突）**：文件层面无冲突但操作逻辑矛盾。例：Agent A 重编全书图片编号，Agent B 同时修改某一章节引用了原编号——不同文件、没有文件层面的冲突，但 B 的引用在 A 完成后全部失效。解法：多个 Coding Agent 并发修改同一代码库时用工作副本隔离（各自独立分支或 worktree，冲突集中推迟到合并点）。
- **命名空间污染**：Agent 随意创建文件导致共享目录混乱。解法：（原文未详述）。
- **单点故障**：一个 Agent 错误删除了共享空间中的所有文件。解法：（原文未详述，思考题提出）。

### 2. 错误的级联放大

进程间传递字节逐位保真，但 Agent 间传递语义，每转述一次都是有损的重新编码。一个 Agent 的错误被后续 Agent 逐层强化，像"传话游戏"中信息越传越走样。解法：交叉验证——让某个 Agent 以独立视角重新审视结论，不看前序 Agent 的思考过程，只看原始证据和最终结论是否一致。对于高风险决策引入外部验证手段。

### 3. 过早终止与循环失控

过早终止分三类：偷懒式假完成（只做一部分就宣称完成）、过早放弃（一条路不通就宣布整件事不成）、假成功（以为完成但闭环没走完）。解法是 Loop Engineering：由验证器而非模型判定"是否真的可以停"。

循环失控的对称问题：自主性较强的 Agent 可能生成数千个子 Agent，大量浪费 token。建议：对自主 Agent 使用独立 API key，设置硬性预算上限。

### 4. 理解债与认知投降

这不是 Agent 的失败，而是人的失败。使用 Agent 快速开发循环交付代码时，工程师对系统实际实现的理解越来越落后；等到出现严重问题必须人工介入时，已看不懂自己的系统。认知投降则是工程师习惯用 Agent 代劳，逐渐放弃独立思考与审查，导致软件质量失控。Andrej Karpathy 说："你可以外包你的思考，但不能外包你的理解。"

### 5. 管理者单点瓶颈

Manager Agent 的任务分解质量是整个系统的能力天花板。若 Manager 不正确分解任务，后续所有子 Agent 的工作都建立在错误前提上。Plan-and-Act 论文证实弱规划者是系统最关键瓶颈。

### 6. 辩论模式在等计算量下无优势

在没有引入新信息的条件下，多 Agent 辩论相对于单 Agent 不产生实质性提升。多个 Agent 处理完全相同文本，每次串行传递中间结论只可能丢失信息、不可能凭空创造信息。辩论模式在部分学术论文中的收益很可能来源于更多总计算量。

### 7. 去中心化 handoff 成环

A 移交 B，B 移交回 A，任务在环路中空转。解法：handoff 协议中维护 visited_agents 链，检测循环，并设移交次数上限。

### 8. 多 Agent 框架的根本性设计缺陷

2025 年论文《Why Do Multi-Agent LLM Systems Fail?》在 7 个主流框架上归纳出 14 种失败模式，分三大类：系统设计缺陷、Agent 间对齐失败、任务验证缺失。即使引入简单修复，改善幅度有限（ChatDev 框架仅提升 15.6%）。研究员认为这些不是简单的工程 bug，而是当前多 Agent 架构的根本性设计缺陷。Agent 的故障天生是拜占庭式的——它很少径直停止运行，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误。

## 关键术语表

| 术语 | 定义 |
|------|------|
| **共享上下文（Shared Context）** | 后续 Agent 继承前序 Agent 完整对话历史和轨迹的协作模式 |
| **不共享上下文（Isolated Context）** | 每个 Agent 维护完全独立的上下文和对话历史，通过显式通信交换信息 |
| **对等协作（Peer Collaboration）** | 少量平等身份的 Agent 通过多轮迭代互相提供反馈的拓扑结构 |
| **管理者模式（Orchestration）** | 一个中心化 Manager Agent 负责任务规划和调度，多个子 Agent 各负责特定子任务 |
| **去中心化模式（Decentralized / Choreography）** | 无运行时中心控制者，Agent 之间自主沟通、移交任务的拓扑结构 |
| **提议者-审核者（Proposer-Reviewer）** | Proposer 生成候选产物，Reviewer 读取独立证据验证并给出结构化改进建议的对等协作范式 |
| **Loop Engineering** | 将 Agent 工作组织为"发现→执行→验证→记录进度"的循环，由独立验证器判定是否可以停止，而非由模型自报"完成" |
| **移交包（Handoff Package）** | Agent 间传递的结构化信息包，包含任务描述、已确认事实与约束、产物引用（路径而非内容） |
| **Agent Card** | A2A 协议中描述 Agent 能力的元数据文档，声明能做什么、支持哪些模态、如何认证 |
| **虚拟文件系统（Virtual Filesystem）** | 将不同来源、生命周期与权限的存储统一挂载到同一目录树，Agent 通过统一接口访问 |
| **轨迹持久化（Trajectory Persistence）** | 将 Agent 的执行轨迹序列化为 JSONL 日志文件，使其他 Agent 可通过读取文件了解其执行全过程 |
| **乐观锁（Optimistic Locking）** | 每文件维护版本号，写入时校验版本号是否与读取时一致，防止并发写覆盖 |
| **了解债（Understanding Debt）** | 工程师使用 Agent 快速交付代码，但对系统实现的理解越来越落后，直至需要人工介入时已无法看懂自己的系统 |
| **认知投降（Cognitive Surrender）** | 工程师习惯用 Agent 代劳，逐渐放弃独立思考与审查 |
| **Graph Engineering** | 2026 年兴起的范式：显式设计执行图，节点为 Agent/程序/人工决策，边定义任务依赖、条件路由与失败后去向 |
| **生成式 Agent（Generative Agent）** | 具备记忆流、反思机制和规划能力的 Agent，能在开放社会环境中自主生活、社交和发展 |
| **生活奖励（Life Reward）** | 以马斯洛需求层次为先验，对社会地位、主观满足、经济收益三维度的综合评分 |
| **A2A 协议** | Google 提出的跨组织 Agent 互操作协议，含 Agent Card、任务生命周期管理和不透明协作三大要素 |
| **预算感知（Budget-Aware）** | Agent 根据剩余步骤预算动态调整策略——前期广泛探索，后期聚焦最有希望的方向 |
