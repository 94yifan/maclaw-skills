## B. 规避方案

**1. failureAlert配置（P0：第7次追踪，仍未执行）**

今天是第7次在dreaming中识别这个问题。isolated session无法update自身cron配置的机制性限制已经分析透彻。仍然需要逸凡在线的主session来操作。

**具体patch内容（可以直接复制）：**
```
cron update jobId=874aef37-02a2-4f34-a275-5d18157279b4 patch={
  "failureAlert": {
    "after": 3,
    "channel": "feishu",
    "to": "ou_c4249d713be906d36ef8607efab6506f",
    "mode": "announce",
    "cooldownMs": 86400000,
    "includeSkipped": false
  }
}
```

**2. 上下文污染防御**

如果在workdir存在/上次session崩溃留下的临时文件可能导致脚本污染，应该在cron启动时自动清理。这不是isolated session能做的。但SP的SOUL可以加一条防御：每次进入session的第一步是检查workdir是否有不属于当前session的临时文件。

**3. timeout从300s增加到600s**

07-12成功的两次（07-05和07-12）都用了291s，非常接近timeout极限。07-13/14/15虽然没有timeout（分别是124s/174s/216s的错误），但300s对SP的平均推理需求明显偏紧。增加到600s可以让SP在高峰期有更多buffer处理复杂context。
