## 三、Skill 正文（weibo-daily-report）

**路径**：`skills/weibo-daily-report/SKILL.md`

**description**：生成23个茶饮品牌微博每日监测日报。固定三段式结构，每条写清动作+品牌价值分析，营销活动带效果判断，行业洞察三条深入总结。

**适用范围**：每天爬取23个茶饮品牌微博数据后，生成结构化日报。调用此 skill 前确保原始数据已采集完成。

### 数据过滤铁律（2026-08-22 新增）

- **日报只写24小时窗口内（抓取时刻往前推24h）发布的内容**，超窗内容一律不写
- 过滤逻辑必须在抓取脚本内完成：解析每条微博 created_at 为时间戳（Date.parse），与 `Date.now()-24*3600*1000` 比较，只保留窗口内条目
- 不靠事后人工判断"这条算不算今天的"，抓取时就直接过滤
- 每个品牌同时返回 latest（最新一条微博发布时间），无动态品牌标注"今日无动态（最新微博日期）"，不写"本周无动态"等模糊表述

---

## 四、格式规范（固定三段式，不可改）

### 精确 Markdown 格式要求

- 品牌名用 `**品牌名**`（粗体，不是 Markdown `##` 标题，不用标题层级）
- 分类标签用 `### **【分类名】**`（H3标题+粗体）
- 内容一律用 `- ` 列表项，不用段落或编号
- 每条结尾写"对品牌而言，……"做品牌价值判断
- 品牌间空一行
- 无动态品牌直接写"今日无动态"，保持占位（末尾可合并一行）

### 三个分类

**【新品上市】**
- 产品名、核心卖点、技术标签（HPP/NFC/低温萃取等）、食材溯源信息
- 每条结尾加品牌价值判断

**【IP联名/艺人宣发】**
- 写清联名IP/艺人名称、联动形式（主题店/周边/短片等）、合作深度
- 每条结尾加品牌价值判断

**【营销活动】**
- 写清活动内容、时间范围、玩法机制
- **必须有对营销效果的判断分析**——为什么这么做、对品牌有什么用、能否形成差异化

### 汇总 + 行业洞察

- **今日概览汇总表**（品牌 | 新品 | IP联名 | 营销）— 注：正文要求"去掉概览表"，汇总数据仅在参考样例中出现
- **汇总数据**（总条数 | 覆盖品牌数 | 分类统计）
- **行业层面信号（3条左右）**：每条一个核心判断，摆数据/事实支撑，可跨品牌对比、找规律、预判趋势，**关键结论加粗**

## 五、内容写作原则

1. **新品要详细完善** — 产品卖点、技术工艺、食材溯源都写清楚，不让读者去猜"这产品到底好在哪"
2. **营销活动要有效果分析** — 不只写做了什么，要判断这个动作对品牌有什么用（如"618预售是上半年大促节点的大流量抢夺""高考送贺卡是低成本的线下门店引流"）
3. **品牌价值判断要精准** — 对品牌自身的价值，不发散到行业层面。"对品牌而言，这是XXX"一句说透
4. **不确定的信息不写** — 如上新时间未明确，不编造标注
5. **不发散行业意义** — 行业层面的洞察全部放到末尾的"行业层面信号"部分
6. **去掉概览汇总表** — 直接进入品牌内容
7. **去掉微博互动抽奖** — 转发抽奖/微博平台互动类内容不再写入

## 七、技术流程（抓取）

- **抓取方式（2026-08 起主流程）**：主代理直接用 browser 工具 evaluate 抓 m.weibo.cn API，分4批（6+6+6+5），每批间隔5秒
- API 字段是 `mblog`（不是 `m`），`containerid=107603{uid}` + `page_type=03` 稳定返回10条/页
- 星巴克 custom=starbucks 解析真实 UID 1741514817
- **CDP 9333**：用户浏览器 session 经常过期；备用 openclaw 沙箱浏览器（ws://127.0.0.1:18800）；node 直连 fetch 会被反爬，必须走浏览器同源 fetch（credentials:include）
- **逐品牌核验**：抓取后先列各品牌最新3条微博核对再写报告，特别是库迪/瑞幸等高频品牌

## 八、核心记忆要点

### 1. 24h 窗口铁律（2026-08-22 血泪教训）

- 日报只写24h窗口内内容，过滤逻辑（`Date.parse(created_at)` 与 `Date.now()-24h` 比较）写进 evaluate 脚本本身，不靠事后人工判断
- 无动态品牌标注"今日无动态（最新微博日期）"

### 2. 窗口口径纪律（2026-09-03 教训，8/22 铁律加强版）

- **header 窗口必须引用 raw crawlTime/爬虫日志的窗口**，不能用发稿时刻反推
- 写日报前凡 latest 距窗口起点 <60 分钟的帖子逐条核对 evaluate 判定
- 过滤只发生在 evaluate 内一次，报告阶段零人工过滤
- 根因案例：header 按发稿时刻 11:17 反推 vs 爬虫 11:00 过滤，产生 15-17 分钟缝隙，漏报古茗红颜石榴汁瓶装 + 喜茶周三小奖励

### 3. 交付链路失败模式（高频，2-3天1次）

- **现象**：报告文件完整落盘，但 run 标 error，`lastDeliveryStatus=not-delivered`，announce 投递被跳过，群里看不到日报
- **累计样本**：8/28、8/31、9/3、9/6、9/12、9/14、9/19
- **根因**：run 中途有一步工具调用失败（如引用不存在的目录 `social-crawler/scripts/`，或收尾解析 raw 的 node 脚本 exec 失败），整个 run 被判 error，交付被连带吞掉；与内容质量无关
- **判断铁律**：日报是否成功**只看 deliveryStatus（delivered），不看 job status**
- **补救**：手动补跑爬虫 → 与 11:00 版 raw 合并取并集 → 重写日报发群
- **修复方向**：考虑给 cron 加交付重试，或加一步"写文件后立即 message 发群"兜底
