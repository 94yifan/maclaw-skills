## B. 规避方案

1. **morning-crawl.sh 唯一路径**：主 session / 逸凡终端执行 `crontab -l | grep -v morning-crawl.sh | crontab -`
2. **pipeline config 清洗层**：brands 只收纯净标识名，任何人类可读备注一律进 brand_notes；可在 pipeline 入口加一道校验（品牌名含中文括号/逗号/空格时 WARN 并自动剥离备注）

5. **孤儿文件治理**：所有 debug / retry / 临时脚本统一放 workspace/tmp/，并把 `tmp/` 加进 .gitignore；执行完成即删。SC workspace 根的 140 个 .mjs 需一次性清理
6. **归档立即提交**：今日产出 + 09-09 遗留一并在本 dreaming 后提交，不等下次
7. **系统挂账送达方式修正**：不在报告交付消息里附带（会被业务内容淹没），改为逸凡每次主动交互时单独发一条、带一行可复制命令。今日损失一个在场窗口，明日首条消息补

## D. ★ 知识串联（核心环节）

### 缝合点1（主）：增量执行的正确性前提 = 被跳过步骤的副作用不得参与本次执行（今日坑位二 × 08-23 局部修改不得全局重建 × 08-10 输出目录隔离）

`--step 13` 把 from_step 默认成 1，于是 Step 0 全量清理被执行，删掉了本该复用的 charts PNG，docx 无图。串联 08-23 推理守卫十（局部修改不得触发全局重建）与 08-10 输出目录隔离修复：三者是同一个问题家族的不同剖面。08-23 是「改一处重写全篇」（重建脚本误用于增量场景），08-10 是「输出目录不隔离导致清理误伤」（修复动作本身成为破坏源），今天是「跳过步骤的初始化副作用被无差别执行」。整合结论：**任何支持局部重跑的系统，必须把「初始化/清理/重置」类副作用与「步骤执行」解耦——副作用只能在覆盖的步骤全部重新产生时触发；判断标准 = 本次执行是否重新生成了被清理的产物**。这是 pipeline 类系统（报告管线、数据管道、构建系统）的通用不变量，不限于本管线。

### 缝合点2（主）：配置清洗层缺失 = 标识符在人类形态与机器形态之间没有转换门（今日坑位一 × 08-15 config 纯名教训 × 08-23 文件名映射三处不一致）

08-15 逸凡踩过括号坑（品牌名带括号），当时固化「config 品牌名纯名」。今天踩的是变体：括号里的备注带逗号，目录名被逗号截断。说明「纯名」规则被理解成去掉括号，而不是去掉一切非标识字符。串联 08-23 docx_builder 文件名映射三处不一致（ch6_recommendations/ch6_strategy、industry_chain_map/ch2_chain_map、content_type_analysis/ch3_content_types）：同一实体的名字在不同环节被按不同规则处理。整合结论：**凡是同一个实体要在多个消费点（目录名 / 文件名 / dict key / 检索标签）出现，必须有一个清洗层把它归一到唯一机器形态；人类可读信息放在独立字段（brand_notes）而不是混进标识字段**。判断方法 = 拿配置里每个字符串问「它会变成路径名吗」，会的话就必须先过清洗。

### 缝合点3（主，元层）：孤儿文件的空间迁移 = 治理规则只盯地点不盯行为（今日 A3 × 05-03 教训5 × 08-10 归档检查）

05-03 教训 5 说 /tmp 下 60+ 脚本是失控证据，结论是「每创建一个调试文件都要问它明天还在是好事还是坏事」。今天实测：SC workspace 根 140 个 .mjs、repo 根新出 tmp/pay_def.py。治理规则盯的是地点（/tmp），行为（创建无主脚本）没被约束，于是行为迁移到了新地点——workspace 根看起来像正经工作区，debug 脚本放这里心理负担更低，而且它同时是 git repo，每次 git status 都多出十几个未跟踪文件。串联 08-10 归档检查从「新增文件」升级为「变更文件」全量扫描：归档噪音的根因之一就是这个。整合结论：**规则绑定行为不绑定地点——「临时产物必须可回收」才是规则，「不要放 /tmp」只是当时那个地点的一次性教训**；落地形态 = 统一的 tmp/ 目录 + .gitignore + 执行完即删三件套，任何新地点出现无主文件即视为规则失效信号。

### 缝合点4（主，机制轨）：无头环境的能力边界图 = 事前画边界比事后降级便宜（今日坑位三 × 09-04 isolated 边界图 × TOOLS.md image 工具记录）

今日视觉校验三层全断（无 LibreOffice + image 三家模型挂 + pdf 工具依赖前述）。09-04 花 7 天摸清 isolated 环境的三通道边界图，当时结论是「边界图未显式化导致每代分身重复验证我做不到」。今天同理：image 工具在本机失败已不是新事（TOOLS.md 早有一条），但每次交付仍要走一遍发现失败再降级。整合结论：**本机的验证能力边界应写成明文档 + 固定降级链，不等交付时才发现**。完整链：DOCX 结构验证（python-docx 可做，稳定）→ 视觉验证（image 工具，本机不可用）→ 降级 qlmanage 缩略图 → 人工目检。与 09-04 的差异是这次只花了几分钟而非几天，因为失败模式已被记录过——印证「边界图显式化的收益就是缩短下次撞墙时间」。

### 缝合点5（主，元层）：挂账送达的窗口条件——不是逸凡不在场，是在场时注意力已被业务占满（今日 A7 × 09-09 执行鸿沟周报 × 09-07 修复闭环路径距离）

09-07 结论是修复闭环速度取决于修复点与执行者自身路径的距离；09-09 周报把挂账归因部分落到逸凡连续静默。今天给出了反例：逸凡 13:24 在场、完成了一次框架确认、收到了一份报告——5 项挂账仍然 0 执行。这说明在场所需不是充分条件，还需要在场所属的注意力通道未被占用。业务交付日，逸凡的注意力通道是「春光报告」，系统挂账混在交付消息里等于没发。修正结论：**系统挂账的唯一有效送达 = 独立消息 + 逸凡主动交互的首条位置 + 一行可复制命令；报告交付消息里附带挂账 = 无效动作**（等价于 09-05 缝合 2 的降级观察，看着发了实际没被消费）。执行鸿沟家族判断再补一条：闭环速度 = 路径距离 × 注意力窗口可用性。
