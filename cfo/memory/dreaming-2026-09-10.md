## B. 规避方案（根因层，写入规则）

**B1 飞书多维表格熔断规则（针对 A1，硬规则）**
`feishu_bitable_*` 或飞书开放 API 连续 **2 次**返回 400 → 立即停止重试，**直接切本地脚本**（读 openclaw.json 的 appId/appSecret 换 tenant_access_token，走 `open.feishu.cn/open-apis/bitable`）。同时**禁止**在业务会话里翻插件 dist 源码、网关日志、plist 排查 —— 那是开发级任务，应挂给主 session 或写成一条清晰的问题报告，不占用业务处理轮次。业务会话的唯一目标是把逸凡交代的事做对。

**B2 参数护栏（针对 A1 根因）**
所有 feishu_bitable_* 调用手写完整 token，禁止任何形式的缩写/省略。中秋表固定值：app_token=`Kef2bE601agEKGsCxeGc8n0HnId`，table_id=`tblz46KG5vphhXVx`。已在本地脚本写死校验，此规则同时适用于工具调用与脚本两条路径。

**B3 临时文件纪律（针对 A2）**
调试/裁剪产物一律写 `workspace/tmp/`（已确认在 image 工具白名单内），不写 `/tmp/`；同一个用途只保留一份，命名带日期与用途，用完即删。shell 里含引号/特殊字符的密钥类文本改用环境变量或 python 读取配置，不用 heredoc 拼接。

**B4 金额类输入的最小记录模板（针对 A3）**
凡收到金额（截图/表格/口述），回执必须覆盖四项且缺项要问：**金额 + 用途/科目 + 归属项目或期间 + 对手方**。只有数字没有归属时，回执里明确写"这笔钱的用途我还没记到，方便的话补一句"，并落到当日 memory。

**B5 当日 open loops 清单（针对 A4）**
每日最后一个动作固定为写 memory 当日文件，文件末尾必须有「待逸凡确认」清单（本轮为：费老补录、哟哟/Yoyo 是否合并）。清单不跨天靠记忆传递。

**B6 边做边记（针对 A5）**
每次处理完一条业务动作即追加写 memory 当日文件（不是攒到晚上）；教训类内容收敛到文件末尾单一区块，正文严格按时间顺序只记事实与回执，不重复。

## Reflection

- **Goal**：8 轮指令全部完成并回执，目标达成；但达成方式有摩擦（工具链路反复失败、金额缺归属）。
- **Key Decision**：10:17 首次工具失败后选择"继续排查工具"而不是"立刻换脚本路径"。这个判断是错的，代价是后续三轮重复踩坑。正确判断依据应该是"逸凡要的是地址改对，不是我把工具修好"。
- **Main Mistake**：把业务会话当成了排障会话。64 处 400 记录里，真正必要的只有最后那几次成功的 API 调用。
- **Repeat Risk**：高。同类模式在蓝氏事故已出现过一次（导致 token 教训入库），今日再次发生 —— 属于系统性习惯问题，不是偶发。
- **Memory Update**：① feishu 调用 2 次失败即熔断切脚本，禁止业务会话内翻插件源码/日志；② 金额输入四项模板；③ 唯一有效投递通道是 MEMORY.md；④ 礼单工作线本轮 open loops：费老、哟哟/Yoyo。
- **Principle Update**：新增「业务会话优先级守卫」——业务会话中，任何技术故障的处置预算上限为 2 次尝试，超限即换路径或升级上报，绝不在业务会话内做技术根因分析。
