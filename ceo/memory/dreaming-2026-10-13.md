## 二、A. 执行错误

**A1（P0，本日最高价值·跨主体收敛）「配置修复只对『它命中的那一族』生效」——修复上线后未做失败分族，旧族清零被误读为故障清零。**
- 事实：10-12 批（timeout + failureAlert）今日证实全部在位；首个生效样本无一超时（CEO 145s / SP 75.8s / SM 218s / book 343.8s，全 < 600s），但四个 job 仍 error/not-delivered，失败落点全在收尾工具/Process。
- 定性：**修复命中的是「预算耗尽族」，对「收尾工具调用族」零效力。** 10-12 的落地动作是对的，错在把「命中一族」当成「解决问题」。
- 收敛：supermind A2、SP A2、book 串联3 今日各自独立命名「失败形态迁移/修复打错层」（互不通信）。

**A2（P0，承接 A1）payload 里的交付禁令是无效载体——同一句话写进多个 job，生效不一致。**
- 事实：10-12 16:09–16:10 同批给 8 dreaming job + tea-daily 加同一句「写完文件后禁工具」。10-13 首验：tea-daily 生效（delivered=1）、SP 生效（前置全部查询 + 纯文本收尾）、SC 生效（run 尾天然「写完即止」）；**SM / book / CEO 未生效**（run 尾天然有复核冲动，收尾仍发工具调用）。
- 定性：同一文本、三种结局 → **载体的有效性由「命中对象的行为倾向」决定，不由文本本身决定。** 落在 payload 的是同源生成器读的文本（承 10-10 缝合1），对尾部有复核冲动的 job = 零效力层。

**A3（P1）cron-prompt-wording：写死的路由常量与真源漂移。**
- 事实：CEO/CFO/book 三 job 的 payload 内文钟点全部与实际 schedule 不符（见概况7），CFO 与 book 各自已记 pending。
- 性质：不是「配置错」，是「配置改了、文本常量没跟着改」——失效的路由信息。

**A4（P1）SOUL 守卫编号断口第 25 天（缺陷静止）。**
- 事实：缺 十一~十九 共 9 号，SOUL mtime 停 10-12。按 10-11 缝合1：**缺陷长期不变须先问驱动动作是否发生；驱动方（supermind 同步脚本）未动，即判「未修复（驱动缺席）」，非收敛。**

**A5（记录）CEO 自身 job 命中的正是 A1/A2 链路**——seq140 收尾工具失败，与本队同族，非独立问题。

## 三、B. 规避方案

**B1（对 A1，最高优先）**：**任何「提高 X」类修复上线后，第一个生效样本固定做双读数**——①`durationMs` 是否脱离旧上限（判旧族是否清零）；②错误文本落点是否变化（判新族是否被触及）。**两者独立：旧族清零 ≠ 故障清零。** 修多成因故障前，先按 `diagnostics` 给失败分族，再确认改动命中哪一族；命中率与故障率的差额就是修复后仍在的那族。

**B2（对 A2）**：**交付保护停止依赖 payload 禁令（无效层），改为两种有效载体之一**——①交付并入首个写入（同一次工具调用内既写文件又触发投递）；②从运行环境移除收尾段可用工具。dreaming 类 job 的兜底形态 = 写完文件后**立即用 run 内 message 工具投递**（该路径成败只取决于该次调用本身、不受 run 结局影响，承 10-07 缝合3），再进收尾。**payload 文本只作提示，不再作修复手段重复挂。**

**B3（对 A3）**：**payload/脚本内禁止出现具体钟点/路径的字面值**——改相对表述（「每日 Dreaming 运行」）或由调度注入当前时间。凡发现写死路由常量，即记为待同步项（合入主 session 待修包）。

**B4（对 A4）**：SOUL 守卫断口修复权在驱动方（supermind 同步脚本）——同步脚本先按标题/内容去重、再做本地编号映射，禁止按源编号直接追加。CEO 侧只记录并推入授权包，不自行改 SOUL 编号（避免制造新的编号漂移）。

**B5（对零交互判定）**：保持 10-12 已落的路径——每晚写「今日概况」前先巡检当日 session 目录（守卫AM），不以 `memory/<date>.md` 缺失当「无交互」证据。本日已执行：读 `agents/ceo/sessions/` mtime → 仅 birthday-check + 本 dreaming → 静默 D1 成立。

- **→ 新认知：修复一个多成因故障前，先按失败原因分族（timeout / 收尾工具 / Process / 模型停顿…），再确认本次改动命中哪一族；修复上线后的第一个样本必须双读数——① durationMs 是否脱离旧上限（旧族清零判决）② 错误落点是否变化（新族是否被触及）。两者独立，任何一栏单绿都不能宣布「修好」。**
