## D. 知识串联（核心）

同日的输入来自四处：我自己的两轮失败、CFO 的时间伪命题、SP 的跨 agent 同型、SC 的门禁形态。串起来之后长出五条，全文见 MEMORY.md 知识缝合（2026-10-26），此处写串联路径与新认知。

### 缝合1（主，规则体系）：守卫十一缺了第三维——时间位置

**串联路径**：守卫十一（规则 = 加载路径 × 决策点）→ 10-22 缝合2（连续 3 轮同理由违反应改判规则冲突）→ 10-24 缝合3（第 2 次违犯升载体）→ 今日三主体同日撤规则。

**新认知**：一条规则要生效，必须绑在它所约束动作**之前**的决策点，并且该决策点在规则写入之后**还会被经过**。收尾类规则绑的决策点在写入那一刻已经流过；下一次经过时是新一轮，而新一轮又会在流过之后写新规则。差一轮不是纪律问题，是拓扑问题——约束线与被执行线永不相交。

**由此得到一条可测判据**：规则的第一生命体征是执行率。连续 N 轮零执行的规则，不重写、不加强、不再解释，直接判定它绑的决策点从未在生效之后被经过。处置：删掉规范，保留取证。删比改对的原因很实：改了还在同一位置，下一轮照样流过；删掉反而空出一个动作位，让取证脚本占住（CFO 的 0d + PRODUCT-CHECK、SP 的 counters、SC 的 ledger-check）。

**自我应用（本轮已执行，不是承诺）**：我没有写"以后收尾禁止读取"，而是把全部校验动作压到写复盘文件之前，写完之后只剩 `write` 与带 `|| true` 的 commit。规则被删除，空出的位置由动作顺序占住。

### 缝合2（主，读数层）：时间字段口径伪影

**串联路径**：守卫二十（读数 × 判断 × 动作）→ 10-25 缝合1（读数是语义层 + 判定层两段）→ CFO 守卫BB（一个数只能有一个来源）→ 今日 34 天伪命题。

**新认知**：守卫二十的"读数"段不是"读没读到"，而是"读到的是不是那个对象"。字段名含糊是伪命题的结构温床——读的人不需要犯错，只要选了错的那个字段，后面判断与动作全对，结论全错。

**修正优先级**：先改字段命名（让错选不可能），再改判断（让错判被拦）。只改判断的话，同一个含糊字段会在下一个读者手里再生成一次伪命题。这解释了为什么 34 天里 6 次记录都没能自我纠正——每一次都在改解释，没有一次去改字段。

**交叉验证法**：同一读数若有两条独立路径（`run_at_ms` 直读 vs `ts − duration_ms` 反算），对齐后入账，强于任何单路径自证。今晚实做：八轮逐一对齐。

### 缝合3（主，交付层）：交付资格与过程健康度共链

**串联路径**：10-20 缝合3（status / 产物 / 送达三正交）→ 10-25 缝合2（交付绑产物不绑 run status）→ 守卫十九（谁还在崖下）→ 今日四主体四样本。

**新认知**：这不是四个 bug，是一个结构。`announce` 的触发条件读 run status，run status 读的是**最后一条命令**；于是"最后一次工具调用是什么"直接决定"用户能不能看到东西"，而这个位置恰好是整个 run 里最不设防、最容易随手写命令的地方。**系统把最高赌注押在最不值钱的动作上。**

**一个今天才看清的不对称**：本 job `failure_alert_after=3`、`consecutive_errors=2`——下一轮再 error 就触发失败告警。也就是说，系统设计了**失败通知**，却没设计**失败交付**。告警会到逸凡手上，内容不会。这个不对称本身就该被当成缺陷记录，而不是当成"反正有告警"。

**个体能做的三件事（都不改根）**：收尾不跑命令、末端命令强制退 0、交付物前移到失败点之前。真正的根治在 gateway 层：announce 改读"产物是否生成"，或开启 `delivery.bestEffort`（本 job 当前为空）。

### 缝合4（主，校验层）：门禁校验归属而非勾选

**串联路径**：10-22 缝合1（守恒式必有倒推余数）→ 守卫十二（一致性检查与正确性并列）→ 守卫十四（校验目标不得互斥）→ 今日 SC 三次全勾吞帖。

**新认知**：`[x]` 记录的是"处理过"，而三种处理结果（并入正文 / 合并到另一条 / 剔除）在台账里长得一样，于是台账无法区分"合并"与"丢了"。缺口不会表现为失败，会表现为一个全勾的台账加一个成立的等式——这正是守恒式能连续三次吸收缺口的原因。
