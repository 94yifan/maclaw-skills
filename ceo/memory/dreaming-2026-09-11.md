## B. 规避方案

1. **【今日最强·系统层根本修正】待办的新增管理变量＝「执行权层级」。** 今日 SM 的实证把挂账的归因推进了一层：这类动作不是「没人做」，是**任何 agent 进程都做不了**（setuid + TCC 授权，只有人类终端会话能执行）。因此待办管理必须新增一个维度：
   - ①**agent 路径内**（改文件/跑脚本/写 MEMORY）→ 立即闭环；
   - ②**需人类终端授权**（crontab 写入 / launchd / TCC 保护目录）→ 唯一合法通道是**面对人的消息**，且必须显式标注「为什么 agent 做不了」；
   - ③**需人类决策**（visibility 放开 / 归档方案拍板）→ 必须写成问句（见下条）。
   - **可执行动作**：系统待办区块每条标注「执行权归属」；把长期挂账重新定性为「②类任务被投递到了只有 agent 会读的通道」。
2. **【今日最强·投递形态修正】系统待办必须从「通知式」改为「交互式」。** 逸凡今日全部响应都发生在「需要他下令/回答」的消息上（6 单审批、9 轮礼单、1 次确认），对任何「供他阅读的清单」零响应；CEO 通道连续 4 天零交互、09-10 摘要 delivered=true 而 5 项挂账 0 执行 = **送达 ≠ 阅读 ≠ 执行**。修复：每日摘要里的系统待办改写成「一个需要他回答的问题 + 默认方案」（例：「这 4 项在你的终端权限外，回 1 我把 4 条命令合并成一段给你粘贴」），不再是清单。

## D. 知识串联（核心）

### 串联1（系统层·CEO 视角·今日最强）：待办闭环第四变量「执行权层级」——挂账不是执行力问题，是任务授权层与投递层长期错配

**今日证据（SM 实证，跨 run 双复现）**：SM 生成目标 crontab 后执行 `crontab /tmp/ct.new` 挂起不返回，kill 后 `crontab -l` 原样无半改；反向证据 `crontab -l` 读正常。根因假设 `/usr/bin/crontab` 为 setuid root + macOS TCC 完整磁盘访问授权，非交互 agent 进程无授权且无法弹授权框。同族历史：09-04 SM crontab 写入路径挂起已实证、7/14 isolated session 无 update 权限（19 天被误判为意志力问题）、09-09 visibility=tree 阻断 sessions_send。

**串联已有知识**：09-10「跨代理待办闭环三变量（路径可达性 × 注意力窗口可用性 × 送达通道独立性）」→ 今日补第四变量；09-07「执行路径可达性三分类」；09-04「转达闭环瓶颈逐环后移」；7/14「不是意志力是权限设计」。

→ **新认知：跨代理待办闭环 = f(路径可达性 × 注意力窗口可用性 × 送达通道独立性 × 执行权层级)。** 第四变量＝**动作的物理执行权是否存在于任何 agent 进程内**。待办按执行权分三类：①agent 路径内（立即闭环）②需人类终端授权（crontab/launchd/TCC 保护目录——**任何 agent 都做不了**）③需人类决策（拍板）。②③类的唯一合法通道是面对人的消息，且必须显式标注「为什么 agent 做不了」，否则会被读成「没人做」——这正是 14 天挂账的真实形态：**把只有人能执行的动作，投递到了只有 agent 会读的通道里，两边的日志都显示「已完成投递」。**

→ **管理同构（给逸凡公司）**：组织里同样存在「只有某个层级能批的动作」（盖章、开户、签合同、改系统权限）。如果这类待办被放进下属能读的周报，等于没提——因为它需要的是「有权者的动作」，而周报只提供「阅读」。**管理层的第一动作不是催执行，是先判执行权归属：谁有权限做这件事，然后只投给他。** BD/内部应用：客户侧待办先分「我方内部可推进 / 需客户方拍板 / 需平台方操作」三类，各自走不同通道，不混在一封邮件里。
