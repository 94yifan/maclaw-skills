## B. 规避方案

1. **探针零副作用（对应 A1，本日新立）**：探未知接口/控件结构，一律走「非法或缺省值 → 读校验错误报文」路径枚举字段；**禁止用会真实创建/通知/付费的接口做探测**。副作用不可逆的接口，探测预算按 0 计。依据：合法探针成本 = 一次错误响应；错误探针成本 = 真建单 + 通知 + 撤回取证。
2. **外部文档的负面断言须实测取证（对应 A2）**：官方文档/平台说明里的「不支持/不可用/无此字段」类陈述，与自查负面结论同权——引用前实测一次（15 秒量级），落笔带实测时间。
3. **必填字段先入生成侧模板（对应 A3，承接 09-26 缝合4）**：SC 日报 header 三行（标题/窗口/覆盖）写进 payload 模板首行；字段不进入生成侧，任何校验都在跟未定义字段较劲。
4. **规则机械化（对应 A4）**：把系统状态复核前移到首个工具轮，使最终轮天然无工具可调，最终回复只输出正文——不再靠「记得不要调工具」。
5. **受阻项并入单点清单（对应 A5，承接 09-23 缝合5）**：timeout 300→600 + failureAlert 只挂不改，不再单点重复推送。
6. **系统状态一律以 cron sqlite 为准复核（对应 A6，沿用）**：任何系统状态类结论写入 MEMORY 前，以 `cron_jobs`/`cron_run_logs` 复核。
7. **当轮入账（对应 A7）**：本轮把跨分身未提交产出一次性提交，不留「下次一起补」。

## D. ★ 知识串联（核心）

### 缝合1（主，元层）：探针必须以「零副作用」为设计约束——错误信息是最便宜的枚举器。

- **链**：09-15 缝合4（校验目标不得互斥，诚实比造假代价高时系统必然造假）× 09-19 缝合3（复发缺陷正解＝删错误路径，不加规则）× 守卫九（临时修复须合并回源文件）× 09-26 缝合2（字段语义须用两条独立关系互推）。
- **今日证据**：探 account 子控件时用正式创建接口试格式，误建 9 条重复单须逐条撤回（A1）；而正解就在同一批记录里——用缺省字段提交时，接口自己回 `控件值不合法或者为空。控件= widgetXXX`，一次响应即枚举出一个子控件名，零副作用。
- **机制**：探针的成本不取决于探针本身，取决于**被探接口的副作用**。同一套「试→看反馈→修」循环，接在纯查询接口上是零成本，接在创建/支付/通知接口上每轮都产生不可逆外部动作。因此探测路径的选择先于探测技巧：**先问这个接口成功一次会留下什么**，会留下东西的一律不拿它当探针。
- **判据**：任何「未知结构 → 试错」的动作，第一步必须选定一个成功时不产生外部动作的接口作为探针；找不到就先用最小副作用的接口降级探测，不得直接打正式创建口。
- **客户用法**：对新平台/新工具的能力摸底，先在草稿或测试环境跑；确需在生产试，先选一个「失败无痕」的入口（查询/校验），不拿会对外发通知的按钮做小白鼠。

### 缝合2（主，机制轨）：外部文档的负面断言与自查负面结论同型——都不产生自然推翻机制。

- **链**：09-27 缝合1（负面结论不产生观测事件，默认寿命无限）× 守卫Z（负面结论须带有效期 + 下轮复测）× 09-18 缝合1（记忆第四态「已过时」）× 09-26 缝合2（字段语义未知）。
- **今日证据**：飞书官方标 account 控件「不支持」（A2），实测可写。这是一条由**外部权威**签发的负面断言，比自查结论更难被质疑，因此更可能被永久采信。
- **机制**：09-27 缝合1 只处理了「自己写的负面结论」；今日补出第二来源——**外部文档**。两者的风险结构完全相同：都断言「某事不行/不存在」，都不产生观测事件，都永久排除一条可行路径。区别在于外部文档自带权威光环，推翻它需要额外一次实测的勇气。守卫Z 的「带有效期 + 复测」必须同样套在文档引用上。
- **判据**：落笔任何「不支持/不可用/无此字段/接口限制」时，先分辨来源是自查还是文档；无论哪种，都必须紧跟一条本会话实测（或标注「引自文档，未实测」并降级为待验证）。
- **客户用法**：竞品资料、平台招商文档、行业报告里的「做不到/没有这个功能」，都要当作待验证命题；一次实测（打开后台点一下）比反复引用稳妥。

### 缝合3（次，机制轨）：必填字段集必须落在生成侧模板的首个输入——SC header 今日给出首个回退反证。

- **链**：09-26 缝合4（必填字段清单必须是生成侧的封闭集合，「有 header」不等于「header 字段集固定」）× 09-21 缝合1（被校验项必须先在生成侧被定义）× 守卫十一（规则必绑决策点）。
- **今日证据**：09-26 把「要有 header」写进规则后，9/26–9/28 靠模型发挥兜住标题+窗口两行，9/29 三行全丢（A3）。**规则写了，模板没改**，于是产出在「有标题+窗口」「三行全无」之间摆动——这正是「必填项没有落在生成侧」的直接证据。
- **机制**：必填规则有三种落点——①复盘/规则文档（最远）②校验脚本（中）③生成侧模板首行（最近）。落在①的规则只影响下一个愿意读它的人；落在③才影响每一次产出。SC header 规则此前落在①，所以它的效力完全等价于「当次模型的自觉」。
- **判据**：凡判定为「必填」的字段，先问它写进生成侧模板没有；答案是否，则这条必填尚未生效，其表现必然时有时无。
- **客户用法**：交付模板的必填项写进模板本体（带示例值），不写进项目 SOP 附注；附注会丢，模板不会。
