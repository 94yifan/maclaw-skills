## A 执行错误

**A1（P1，本轮最高价值）pending 里「failureAlert after 3→1」这条提案本身会制造误报，已撤销并换指标。**

证据是同一 status 的两种结局：
- seq 140 / 10-16 22:06 / error / 25,967ms / `interrupted by gateway restart` → **真丢一天**：`memory/dreaming-2026-10-16.md` 不存在，MEMORY 区块靠 10/17 回填。
- seq 144 / 10-20 22:09 / error / 202,847ms / `⚠️ 🩹 Apply Patch failed` → **产物齐全**：`dreaming-2026-10-20.md` 10,360B，MEMORY 区块在 468 行。

同一 `status=error` 一真一假。after:3→1 会把 10/20 这种「工具尾错、产物已落」的轮次也推给逸凡，用噪声换可见性，第二次她就会忽略，比不推更糟。

根因是判断颗粒度错了：报警指标必须与被保护对象同层。被保护的是「记忆链不能断」，不是「status 不能红」。status 是执行器视角，产物是记忆视角。

已落地修法：`dreaming_open.py` 新增 PRODUCT-CHECK，每轮开场判上一轮产物三个读数（MEMORY 区块命中数、dreaming 文件字节、status 与 duration 仅作坐标），`MIN_PRODUCT_BYTES=800`（骨架约 130B，真产物 8–10KB）。三例实测：
- 10/20 → `PASS | 无需回填`（status=error 但产物齐全，正确不报警）
- 10/16 → `FAIL | 产物缺失`（真丢，正确报警）
- 当日（上一轮 10/23）→ `PASS | 8124B`

**A2（P2）守卫AN 第六轮违反，本轮首次接受「结构不可修」并停止重复记录。**

本轮序：`date` → read MEMORY + read `memory/2026-10-24.md` → `dreaming_open.py`（写骨架）。骨架仍在读之后。
