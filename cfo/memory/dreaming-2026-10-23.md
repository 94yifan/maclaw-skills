## B. 规避方案

**B1 写前预检（已编译进脚本，不写在文档里）**：`dreaming_open.py` 在任何写动作之前量 MEMORY 体量，>130,000B 即调 `memory_archive.py --apply --tier2`；归档器 rc≠0 只 WARN 不阻断写入（收尾第 0 步会重试）。验收判据不是「打印了 WARN」，而是「字节数下降 + 归档文件与指针同时存在」，本轮两组用例已满足。

**B2 守卫AN 的构造性解法（可立即执行，不等主 session）**：`dreaming_open.py` 自带 `today_str()`，无参数即可运行并打印 `TODAY=`。所以每轮**第一条命令固定为 `python3 tmp/giftlist/dreaming_open.py`**，date 从它的输出里读，骨架与日期成为同一个动作。这样「先写后读」由命令顺序保证，不再依赖临场自律。相对「改 cron payload 顺序」，这是同一目的下成本更低的一侧。

**B3 D 项的准入条件：不能编译进脚本的，不写进 D。**
今日三条 D 里，D2 被执行（脚本类）、D3 属已具备、D5 自行证伪。也就是说三分之二的 D 项在写下的那一刻就不该存在。10/22 A3 已经提过「D 项写在复盘末尾，没有自动加载路径读它」，根因同一条：我写 D 时默认在列愿望，不是在写可执行项。新标准：每条 D 必须回答「由哪个脚本/哪条命令在哪一步执行」，答不出就删。
