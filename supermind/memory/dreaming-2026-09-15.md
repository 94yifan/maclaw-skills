## B. 规避方案（根因层，作为下次执行铁律）

1. **门禁校验升级（对应 A1，最高优先）**：`competitor_confirmed.txt` 必须写入「项目名 + 确认人 + 确认时间 + 确认内容摘要」，且 pipeline 校验三件事——文件里项目名 == 当前 config `project_name`、时间在 24h 内、内容非空。官方指引同步把 `touch` 改为写入确认记录。**通用判据：写任何门禁后自问「有没有一种不经过确认就能让它通过的方式」，答案是 touch / 复制旧文件 / 建空文件，就说明它只是仪式**
2. **无数据合法化（对应 A2）**：`charts.py` 无真实数据时**跳过并在 `_chart_report.json` 标 `data_unavailable` + 原因**，禁止静默写占位值；QA 的图表数量规则改为条件式（有可用数据才要求数量）；把「图表数值是否有可溯源来源」提为一级校验（优先于数量）。**通用判据：任何校验体系先问「把这项目标做得不真实，会不会更容易达标」**
3. **词表分级（对应 A3）**：污染词表分三级——全局硬禁词（跨行业必错）／项目白名单（本项目正常词）／软词（需上下文判断，命中只警告不失败）。软词命中不进入失败率统计
4. **隔离全集化（对应 A4）**：charts 与 gate 文件同 content 一样走 `_project_subdir`，文件名加项目前缀；交付后把通用目录的内容归位到项目目录，项目目录设为唯一真源。**判据：拿输出目录每个产物问两句——有没有项目前缀？会不会被下一次运行清理？**
5. **汇报绑里程碑不绑时间（对应 A5）**：把「每 10 分钟」改成事件触发——每次 subagent 收口（completion event 到达）、每次 yield 交回控制权前、每跑完一个 pipeline step 后，各发一条一行进度。写进 SOUL 原则 5 的可执行版本

9. **pipeline_error.md 口径升级（对应 Step 0 新检查项）**：QA 失败率 >0 时也在该文件落一行（区分 crash / qa_fail），使「无失败」结论可覆盖两类

## D. ★ 知识串联（7 条：4 主 3 次）

### 缝合点1（主，元层）：门禁的可验证性——存在性不是确认，校验"有没有"的门等于没锁的门

**来源**：`pipeline.py:343` 竞品门只判 `exists()`；官方指引就是 `touch`；今日实际开门用的是「确认时间 2026-09-10，确认内容春光四赛道」的陈旧文件，文件 mtime 被 touch 改成 09-15 14:38，内容一字未变。
**串联**：09-12 缝合1（规则效力三阶：编译进路径 > 自动加载文档 > dreaming 文件）＋09-13 缝合1（规则生效 = 加载路径 × 决策点绑定）＋09-14 缝合1（待办被非授权执行者认领）＋09-13 缝合4（一致性检查）。
**整合判断**：三阶阶梯今日补出第四刀——**编译进路径的检查本身分强弱**。检查分三档：①校验「存在」（touch 即可满足，最弱）②校验「内容与本次对象绑定」（项目名/对象 ID 对上）③校验「内容 + 时间 + 确认人」（最强）。今日的门在最低档，却承担着「不可逆动作前的人工授权」这一最高职责。执行鸿沟家族再补一态：此前是「识别后不执行」（少做）、「识别后被非授权执行者执行」（多做且做错），今日是**「门开着但没法证明是谁开的」**——授权动作发生了，但系统丢了授权证据。通用判据：写任何门禁后自问「有没有一种不经过确认就能让它通过的方式」；答案里出现 touch / 建空文件 / 复制上一份，这个门就只是仪式。客户用法：客户确认节点不能靠「有没有确认文件」，要留下确认对象 + 时间 + 确认人三件套，否则任何一次复用旧文件都会让「已确认」失去含义。

### 缝合点2（主，机制轨）：校验目标互斥时系统默认选择造假——造假能满足更多校验条目，诚实会失败

**来源**：`steps/charts.py:138-145` 无真实数据时写占位数值 `(len(brands)-i)*100+50`，subtext 仍写「数据来源: 电商平台」；Pipeline QA 规则 F-2 要求 docx 实际嵌入 ≥2 张图。今日正确动作（识别出假数据 → 删除 3 张假图）导致 F-2 判 FAIL（只剩 1 张真实图）。
**串联**：08-23 推理守卫十（局部修改不得全局重建）＋09-10 缝合1（初始化副作用与被跳过步骤解耦）＋09-12 缝合1（用代理指标验收 → 状态量替代行为证据）＋09-13 缝合4（一致性检查）＋09-11 缝合1（投递盲区：产出 ≠ 存在）。
**整合判断**：此前讨论的都是「规则失效」「信号错位」，今日是新的结构缺陷——**校验目标互斥**。「必须有 2 张图」与「数据必须真实」在缺数据时无法同时满足；系统在两条路里选了能通过更多条目的那条（造假），因为诚实会让校验失败率上升。于是**造假不是因为有人想造假，而是因为造假是当前校验结构下的局部最优**。这与 09-05 假成功家族、09-12 缝合1 归因错位同根：只要系统只看「有没有」，它就必然生产「有但假」的东西。修法不是加一条「禁止造假」的规则（那只是又一条常驻备注），而是**把「无数据」做成合法终态**（跳过 + 标 `data_unavailable`），并把「数据来源可溯源」提为一级校验，让诚实的代价低于造假的代价。通用判据：任何校验体系上线前先问一句「把这项目标做得不真实，会不会更容易达标」；答案是会，就先改校验，再加指标。客户用法：KPI/验收表设计同上——若「编一个数」比「承认没数据」更容易过表，团队就会编数。

### 缝合点3（主，机制轨）：隔离是输出目录的整体属性，不是逐产物选项——最不隔离的产物决定整套产物的生命周期

**来源**：同一 output 目录三种策略——content 走项目隔离（`_get_content_dir` 三级回退）、charts 明确不隔离且文件名项目无关（`chart_brand_comparison_1..4`，每个项目覆盖同一批文件名）、gate 文件单槽位不隔离（A1 成因）。后果链：主 session 手动 `cp -R` 项目内容到通用目录（双副本）→ `pipeline.py:229-255` 的 P0-1 会在下一个项目开跑时清空 `output/content/*.md` → 黄天鹅 docx 的源内容被删 → 推理守卫十（局部修改不得全局重建）失去可执行对象。
**串联**：08-23 推理守卫十（局部修改不得全局重建）＋09-10 缝合1（副作用只能在覆盖的步骤全重跑时触发）＋09-10 缝合2（同一实体在多个消费点必须归一到唯一机器形态：目录名/文件名/dict key）＋09-13 缝合2（数据表健康度：相对上次快照变了什么）。
**整合判断**：09-10 缝合2 讲的是「同一实体的名字要有唯一机器形态」，今日补出它的空间版本——**同一实体的产物要有唯一存放位置**。隔离若只覆盖 content，则不隔离的 charts 与 gate 会成为整个输出目录的公共槽位：它们既互相覆盖，也把被隔离产物的生命周期拉回「单项目槽位」。所以隔离必须作为输出目录的**全集属性**统一施加（子目录 + 项目前缀 + 清理范围与隔离范围一致）。今日更严重的一层：交付后源内容被镜像到公共槽位，等于**主动把自己降级为可被覆盖的对象**——这个动作是为了迁就 docx builder 读公共目录的旧约定，属于「用一个错的动作去适配一个错的默认值」。判据：拿输出目录每个产物问两句——有没有项目前缀？会不会被下一次运行清理？客户用法：项目交付物的归档不能靠「放在项目文件夹里」这一条，必须确认归档目录不被任何后续流程的清理规则覆盖，否则文档还在、源没了。

### 缝合点4（主，元层）：挂账闭环链第四因子——执行者带宽；业务日归零与逸凡在不在场无关

**来源**：今日主 session 13:18–15:08 全程在场，exec 55 次、spawn 12 次、消息可见输出 7 条，其中 100% 时间与带宽投放给黄天鹅交付；09-14 新立的两条规则（待办执行主体标注、告警通道分离）与四项老挂账（morning-crawl.sh、SC dreaming cron、飞书云文档存档、SP MEMORY 归档）全天 0 执行。
**串联**：09-07 缝合1（闭环速度 = 修复点与执行者的路径距离）＋09-10 缝合5（注意力窗口：在场不等于被消费）＋09-13 缝合3（第三因子决策带宽）＋09-12 缝合1（编译进路径才生效）＋09-13 缝合1（决策点绑定）。
**整合判断**：闭环链从三段扩到四段：**路径距离 × 注意力窗口 × 决策带宽 × 执行者带宽**。前三段都在讲「决策方」（逸凡），第四段讲**执行方**——系统债的执行者不只逸凡，主 session 也是（09-14 的 payload 硬化就是主 session 自己完成的）。业务任务对主 session 带宽的占用是 100%，所以「等有空再办」在业务日必然归零，与逸凡是否在场、消息是否置顶都无关。解法只有一个方向：把系统债从「待办事项」改写为「业务任务的固定尾动作」（像 SC「每天首条回复前先跑 audit.py」那样），让它挂在每天必到的决策点上，而不是挂在主 session 的空闲上。**判断方法：任何挂账项，答不出「它在哪次业务交付的尾步执行」，就一定会无限期挂下去。**

### 缝合点5（次，方法轨）：跨品类心智迁移是第四种任务形态，且加法标准与减法标准不可互换

**来源**：逸凡追加的两条指令——「增加蛋黄、溏心蛋即食这种品」「综合牛奶这个赛道去看，不是具体看某一个品牌」「看牛奶要看得更深，早于蒙牛伊利，思考它怎么建立一整个高端心智」。牛奶专项产出六机制（稀缺叙事/标准与认证/场景仪式/文化符号/渠道冷链/国家叙事）与核心结论「高端心智靠标准建立，不靠贵」，并落到黄天鹅可抄/不可抄清单。
**串联**：09-10 缝合6（燃创 pipeline 三种任务形态：单赛道深挖 / 多赛道并列 / 文化 IP 研究）＋09-12 缝合4（联名落地三阶）＋09-14 缝合6（原料叙事的双功能分离：信任资产 vs 传播资产）。
**整合判断**：燃创 pipeline 补出第四种任务形态——**跨品类心智迁移研究**（不研究同赛道对手，研究另一个品类历史上如何完成同一件事，把机制搬过来）。触发条件：品类无先例可抄（鸡蛋无品牌化先例），只能向已完成品牌化的邻近品类借路径。同时补出一条判断：**标准分加法与减法，二者不可互换**——牛奶的高端标准是加法（蛋白质 3.6g、专属牧场，可量化、可炫耀、可对比），鸡蛋的可生食标准是减法（把沙门氏菌降到零，是风险消除，消费者难以感知、难以对比）。减法标准更难卖溢价，只能靠信任建设（认证 + 溯源 + 场景绑定）而非参数炫耀。客户用法：给无先例品类做品牌化方案时，先判断它的标准是加法还是减法；减法品类不要照搬加法品类的参数式传播，要配信任资产与场景仪式。

### 缝合点6（次，机制轨）：校验器的噪声会吃掉校验器的价值——词表必须分级，软词命中不得计入失败率

**来源**：QA F-3 把饲料原料「玉米」判成跨项目污染词（3 次），成因是全局词表 + 纯关键词匹配、不看项目上下文。
**串联**：09-13 缝合4（一致性检查与正确性检查并列）＋09-14 缝合4（规则编译是持续维护，不是一次性工程）＋09-14 缝合5（决策成本由提出方预支付：告警方要先把噪声清掉）。
**整合判断**：校验器有两类错误——漏报（假阴性，掩盖缺陷）与误报（假阳性，制造噪声）。此前所有复盘的注意力都在漏报（「只查正确性查不出不一致」），今日暴露误报的代价：**误报不直接造成损失，但会把告警通道的可信度消耗掉**——当 F-3 天天报「玉米」，F-3 的真实命中就会被当噪声忽略。修法是词表分级（硬禁词 / 项目白名单 / 需上下文判断的软词），软词命中只警告不失败、不计入失败率。判据：任何告警上线后统计它的历史命中里有多少是误报；误报占比高就分级，不分级就会失信。客户用法：客户侧的监测/风控规则同理——先压误报，再谈灵敏度。

### 缝合点7（次，数据质量轨）：同一指标多口径 = 数字是选的，不是测的

**来源**：同一份交付的正文体量出现三个数字——交付消息「约 9.7 万字」、QA 读数 102,150 字、memory 记录 103,891 字。
**串联**：09-12 缝合7（数据资产质量第四支柱：完整性自动审计）＋09-14 缝合3（抽象规则描述意图，既有产物才是事实标准）＋守卫三（动手前必须三问，含数据来源）。
**整合判断**：多口径不是算错了，是**同一指标存在多个合法来源、且没有指定唯一权威源**，于是不同环节各取一个，数字从「测量结果」退化成「选择结果」。这与 09-14 缝合3 同构（规则文本 vs 既有样本，样本优先），推广为：**凡会有多人多次读取的指标，必须先指定唯一权威源，其余位置一律复制不重算**。今日落点：文档体量以 QA 读数为准，消息里的数字从 QA 报告复制。判据：同一个数字在整个交付链路里出现了几次？超过一次就要指定权威源。

## Reflection

- **Goal**：业务交付 + 系统复盘双重目标。业务侧达成（15:08 交付 167KB 完整排版 docx，正文 10.2 万字，阻断一/三未被触发）；复盘侧达成（识别出 5 个 P0/P1 系统缺陷 + 7 条缝合入库）
- **Key Decision**：把「删假图导致 QA 失败」定性为**校验目标互斥**（造假是当前校验结构的局部最优），而不是「pipeline 缺一个跳过逻辑」的工程问题。前者要求改校验结构（把无数据做成合法终态、把来源可溯源提为一级校验），后者只会再修一处代码——这个定性决定了下一次同类问题会不会换个产物再来一遍
- **Main Mistake**：今日最大系统缺陷是**阻断一被陈旧文件打开**。门禁设计成 `exists()` + 官方指引是 `touch`，等于不可逆动作前的人工授权在系统里没有证据；今天恰好逸凡实质确认了，所以没出事——这是运气，不是保护。个人层最大失误是 14:38 touch 后没读一眼文件内容，把「文件在」当成「确认过」
- **Repeat Risk**：高。① 挂账 0 执行连续第 3 个业务日，今日新增第四因子（执行者带宽），若不改成「业务尾动作」模式，第 N 天仍是 0；② pipeline 临时修复修在项目层、源文件未改（`charts.py` 占位分支原样保留），与推理守卫九同型，下次跑还是会造假；③ 节点汇报 29 分钟静默，SOUL 原则 5 至今是常驻备注；④ 归档欠账 63 项
